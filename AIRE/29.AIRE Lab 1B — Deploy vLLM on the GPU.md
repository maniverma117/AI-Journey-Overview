Now we move from:

```text
EC2 GPU
  ↓
NVIDIA Driver
  ↓
Container
  ↓
CUDA
  ↓
PyTorch
```

to the actual inference stack:

```text
Client
   ↓

   ↓
```

The objective is to get a **real OpenAI-compatible LLM endpoint running on your GPU**.

---

## 1. First decision: don't start with a 70B model

For this lab, use a small instruct model.

Why?

Because we're learning:

* vLLM startup
* model loading
* GPU memory
* API
* batching
* metrics
* latency
* throughput
* failure recovery

We don't want a 70B model's memory requirements to obscure the infrastructure concepts.

Later we'll deliberately deploy a large model and answer:

> "How many H100/H200 GPUs do I actually need?"

# 2. Understand the vLLM container

There are two broad approaches.

### Option A — Install vLLM yourself

```text
Ubuntu
 ↓
Python
 ↓
CUDA/PyTorch
 ↓
pip install vllm
 ↓
vLLM
```

### Option B — Use a vLLM container

```text
GPU node
 ├── NVIDIA driver
 └── Container runtime

vLLM container
 ├── vLLM
 ├── PyTorch
 ├── CUDA userspace
 ├── NCCL
 └── dependencies
```

For production, I strongly prefer the **containerized approach**.

It gives you a much more reproducible:

```text
Model + vLLM + PyTorch + CUDA userspace
```

environment.

The NVIDIA driver remains on the host.

# 4. What happens when vLLM starts?

This is extremely important.

You execute:

```bash
vllm serve <MODEL>
```

but internally a lot happens.

```text
                  vLLM startup
                       │
                       ▼
                Load configuration
                       │
                       ▼
                Load tokenizer
                       │
                       ▼
                Load model weights
                       │
                       ▼
                 Initialize CUDA
                       │
                       ▼
              Allocate GPU memory
                       │
                       ▼
               Allocate KV cache
                       │
                       ▼
              Initialize scheduler
                       │
                       ▼
             Initialize HTTP server
                       │
                       ▼
                    READY
```

That last step is important.

A process listening on port `8000` does **not necessarily mean the model is actually ready to serve useful inference**.

For production we eventually want readiness to represent something closer to:

```text
process alive
+
CUDA healthy
+
model loaded
+
KV cache initialized
+
server accepting requests
```

# 6. Kubernetes deployment

Now let's move vLLM into Kubernetes.

Create:

```bash
cat > vllm.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm
spec:
  replicas: 1

  selector:
    matchLabels:
      app: vllm

  template:
    metadata:
      labels:
        app: vllm

    spec:
      containers:
        - name: vllm

          image: vllm/vllm-openai:<PINNED_VERSION>

          args:
            - "--model"
            - "<MODEL>"
            - "--host"
            - "0.0.0.0"
            - "--port"
            - "8000"

          ports:
            - containerPort: 8000

          resources:
            requests:
              nvidia.com/gpu: 1

            limits:
              nvidia.com/gpu: 1
EOF
```

Apply:

```bash
kubectl apply -f vllm.yaml
```

Check:

```bash
kubectl get pods -o wide
```

Initially you may see:

```text
NAME                   READY   STATUS
vllm-xxxxx             0/1     ContainerCreating
```

Then:

```text
vllm-xxxxx             0/1     Running
```

And eventually:

```text
vllm-xxxxx             1/1     Running
```

# 7. Don't panic if startup takes time

A model-serving pod has several cold-start phases:

```text
Pod scheduled
     ↓
Image pull
     ↓
Container startup
     ↓
Model download
     ↓
Model loading
     ↓
GPU memory allocation
     ↓
KV cache initialization
     ↓
CUDA warmup
     ↓
READY
```

So:

```text
Pod = Running
```

doesn't necessarily mean:

```text
Inference = ready
```

This distinction becomes **very important later when we build Karpenter + KEDA autoscaling**.

# 9. What should happen to GPU memory?

Before vLLM:

```text
GPU memory:

used: very low
free: very high
```

During model loading:

```text
GPU memory:
████████████████
```

After model loading:

```text
weights
+
KV cache reservation
+
CUDA/runtime memory
+
workspace
```

You may see substantial memory already allocated even with **zero requests**.

That's normal.

This is one of the most important differences between:

```text
CPU web application
```

and:

```text
LLM inference server
```

A model server is effectively a **pre-warmed GPU memory resident application**.

# 14. Now enable streaming

This matters because most production LLM applications stream responses.

Try:

```bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<MODEL>",
    "messages": [
      {
        "role": "user",
        "content": "Explain Kubernetes networking."
      }
    ],
    "max_tokens": 200,
    "stream": true
  }'
```

Instead of waiting for the entire response:

```text
request
   ↓
......................
   ↓
token
token
token
token
token
...
```

you receive tokens progressively.

This is why **TTFT** becomes so important.

---

# 15. Measure TTFT

Suppose the request is:

```text
t0 = request sent
```

First generated token:

```text
t1 = first token received
```

Then:

```text
TTFT = t1 - t0
```

For the user:

```text
Click
  ↓
waiting...
  ↓
first token appears
  ↓
"Ah, it's responding."
```

That's TTFT.

---

# 16. Understand the latency components

A production request is approximately:

```text
                 Total latency
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
     Queue          Prefill        Decode
       │              │              │
       ▼              ▼              ▼
   scheduler       prompt         generated
    waiting        processing       tokens
```

More formally:

```text
TTFT ≈ queue time + prefill time + startup overhead
```

And:

```text
E2E latency ≈ TTFT + decode time
```

For streaming:

```text
User experience
      │
      ├── TTFT → responsiveness
      │
      └── TPOT/ITL → generation smoothness
```

# 20. This is the serving curve we're trying to discover

Conceptually:

```text
Latency
  │
  │                         /
  │                       /
  │                    __/
  │                 __/
  │              __/
  │___________ ______________
             Load →
```

Initially:

```text
load ↑
throughput ↑
latency relatively stable
```

Then we reach the **knee**.

After that:

```text
load ↑
queue ↑↑
TTFT ↑↑
latency ↑↑
```

That knee gives us a much more useful number than:

> "This H100 can run 500 users."

Instead we learn:

> "This vLLM configuration can sustainably serve X input tokens/sec and Y output tokens/sec at concurrency Z while meeting P95 TTFT and TPOT SLOs."

That is **capacity engineering**.

# 21. Now introduce `--gpu-memory-utilization`

vLLM exposes:

```bash
--gpu-memory-utilization
```

This controls the fraction of GPU memory vLLM is allowed to use for its execution/cache planning.

For example:

```bash
--gpu-memory-utilization 0.90
```

Don't immediately set:

```bash
1.0
```

because GPU memory isn't only:

```text
model weights
+
KV cache
```

There are also:

```text
CUDA runtime
workspace
CUDA graphs
PyTorch allocations
communication buffers
other runtime overhead
```

So the practical equation is:

```text
GPU memory
=
weights
+
KV cache
+
runtime
+
workspace
+
overhead
```

# 22. What if the model doesn't fit?

You'll encounter errors such as:

```text
CUDA out of memory
```

or model loading failures.

Do **not** immediately conclude:

> "I need a bigger GPU."

First ask:

```text
Why doesn't it fit?
```

Check:

```text
1. Model parameter count
2. Precision
3. Weight memory
4. KV cache requirement
5. Context length
6. Concurrency
7. GPU memory utilization
8. CUDA/runtime overhead
9. Tensor parallelism
10. Quantization
```

For example:

```text
70B BF16
≈ 140 GB weights
```

One 80 GB H100 cannot hold that model's weights in BF16.

That's a **fit problem**.

But:

```text
70B FP8
≈ 70 GB weights
```

may fit much more plausibly on an 80GB GPU, but that still doesn't mean you have enough memory for:

```text
KV cache + runtime + workspace
```

That's why "model size < GPU VRAM" is not a sufficient production sizing rule.
