# Part I — The Architecture Method

Before the case studies, establish one framework that you should use for **every AI architecture**.

---

# 1. Never Start With the GPU

A customer says:

> "We want to deploy a 70B model on AWS. How many H100s do we need?"

Do **not** answer immediately.

Your first response should be:

```text

```

Because:

```text

```

doesn't tell us:


# 18. First Architecture Decision — TP

Suppose benchmark:

| Configuration | RPS |  TTFT | TPOT |
| ------------- | --: | ----: | ---: |
| TP2           |  10 |  1.5s | 62ms |
| TP4           |  18 | 850ms | 46ms |
| TP8           |  30 | 700ms | 41ms |

SLO:

```text
TTFT <1s
TPOT <50ms
```

TP2:

```text
❌
```

TP4:

```text
✓
```

TP8:

```text
✓
```

Now compare economics and failure granularity.

---

# 19. Capacity

Peak:

```text
25 RPS
```

TP4 capacity:

```text
18 RPS
```

Required:

```text
25 / 18
= 1.39
```

So:

```text
2 replicas
```

With 25% headroom:

```text
2 × 1.25
= 2.5
```

Round:

```text
3 replicas
```

GPU:

```text
3 × 4
= 12 GPUs
```

---

# 20. N+1

If we need to survive one replica failure:

```text
3 + 1
= 4 replicas
```

Therefore:

```text
4 × TP4
= 16 GPUs
```

Now the architecture is:

```text
16 GPUs
```

not:

```text
25 users → 25 GPUs
```

---

# 21. AZ Distribution

Three AZs:

```text
AZ-A
 └── TP4

AZ-B
 └── TP4

AZ-C
 ├── TP4
 └── TP4
```

If AZ-A dies:

```text
3 replicas remain
```

which preserves our minimum production requirement.

---

# 22. Why Not Spread One TP4 Across AZs?

Because TP communication is latency-sensitive.

Bad:

```text
AZ-A
 GPU1 GPU2

AZ-B
 GPU3 GPU4
```

Now:

```text
GPU ↔ GPU
```

may traverse cross-AZ networking.

That introduces:

```text
latency
bandwidth constraints
AZ dependency
cost
```

Instead:

```text
TP4 group
=========
same tightly connected GPU topology
```

AZ is the failure domain around the replica.

---

# 23. EKS Architecture

```text
                         AWS
                          │
                         WAF
                          │
                    ALB / Gateway
                          │
                    AI Gateway
                          │
                   ┌──────┴──────┐
                   │             │
                 AZ-A          AZ-B/C
                   │             │
                 EKS           EKS
                   │             │
              GPU NodePool   GPU NodePool
                   │             │
                  TP4           TP4
```

And CPU workloads separately:

```text
CPU NodePool
 ├── AI Gateway
 ├── llm-d
 ├── RAG
 ├── embeddings
 └── orchestration
```

This is important.

Not everything belongs on GPU.

Current AWS EKS guidance explicitly notes that routing, retrieval, orchestration, guardrails and other AI pipeline components can often be CPU workloads, allowing GPU capacity to remain dedicated to inference. ([AWS Documentation][4])

---

# 24. Why Separate CPU and GPU Pools?

Because otherwise:

```text
GPU nodes
 ├── vLLM
 ├── API gateway
 ├── vector search
 ├── logging
 ├── random workloads
```

You create:

```text
CPU contention
memory contention
noisy neighbors
```

Instead:

```text
CPU pool
      │
      ├── gateway
      ├── router
      ├── RAG
      └── agents

GPU pool
      │
      └── vLLM
```

# Case Study 2 — 128K Context RAG Platform

Now make it harder.

Customer:

```text
70B model
128K context
10 RPS
P95 input = 50K
P99 = 100K
P95 output = 2K
```

This is a completely different workload.

---

# 34. Why This Is Hard

Long context creates:

```text
prefill cost ↑
KV ↑
TTFT ↑
GPU memory ↑
concurrency capacity ↓
```

For a hypothetical model architecture with:

```text
80 layers
8 KV heads
128 head dimension
BF16 KV
```

we previously calculated approximately:

```text
320 KB/token
```

Therefore:

```text
100K tokens
≈ 32 GB KV
```

per active sequence.

That's before considering the rest of the runtime.

So:

```text
10 concurrent 100K requests
```

could create enormous KV pressure.

---

# 35. Architecture Decision

Don't immediately choose:

```text
TP8
```

First ask:

```text
Can H200's larger HBM capacity materially improve concurrency?
```

H200 has 141 GB HBM3e and 4.8 TB/s bandwidth according to NVIDIA's current specification. ([NVIDIA][1])

Potential architecture:

```text
H200
  │
  └── larger KV capacity
```

versus:

```text
H100
  │
  └── TP / more replicas
```

Benchmark both.

---

# 36. P/D Becomes Interesting

Long context:

```text
50K–100K input
```

means prefill can interfere heavily with decode.

You could consider:

```text
Router
  │
  ├── Prefill fleet
  │
  └── Decode fleet
```

with KV transfer.

Current vLLM documentation describes disaggregated prefill as a way to independently tune TTFT and inter-token latency and control tail ITL; it explicitly notes that disaggregation does **not inherently improve throughput**. ([vLLM][6])

That distinction is critical.

---

# 37. P/D Architecture

```text
                 Router
                    │
             ┌──────┴──────┐
             ▼             ▼
         Prefill         Decode
           Pool            Pool
             │             │
             │    KV       │
             └──────┬──────┘
                    │
                  NIXL
                    │
                   EFA
```

Now we can scale:

```text
Prefill = 3 replicas
Decode = 2 replicas
```

if workload requires more prefill capacity.

---

# 38. But P/D Adds Failure Modes

Now we have:

```text
Prefill failure
Decode failure
KV transfer failure
NIXL failure
EFA failure
routing mismatch
KV incompatibility
```

So the architecture is more complex.

The question is:

> Does the workload justify that complexity?

For:

```text
500-token input
100-token output
2 RPS
```

probably not.

For:

```text
100K input
2K output
high concurrency
strict TTFT/TPOT
```

it becomes much more compelling.

# 65. The Customer Architecture Statement

After discovery, don't say:

> "I recommend eight H100s."

Say:

> "Based on the observed workload of 25 peak RPS, P95 input of 8K tokens, P95 output of 1K tokens, and the required TTFT/TPOT SLO, our benchmark shows TP4 as the smallest configuration meeting the SLO. We therefore need four TP4 replicas to maintain peak capacity plus failure headroom, resulting in 16 GPUs. We'll distribute replicas across three AZs, keep TP groups within a tightly connected GPU topology, and use inference-aware routing to preserve capacity and KV locality."

That's a **Solution Architect answer**.

# 66. Your Architecture Defense Framework

When someone challenges your design:

### "Why TP4?"

Answer:

```text
Because TP2 misses the latency SLO,
while TP8 provides additional performance
that isn't required by the workload.
TP4 gives the best SLO-constrained economics.
```

### "Why llm-d?"

```text
Because replica selection benefits from
queue/KV/prefix-aware routing rather than
simple round-robin.
```

### "Why Karpenter?"

```text
Because GPU capacity needs dynamic provisioning
and the workload isn't well represented by static
node groups.
```

### "Why H200?"

```text
Because the workload is constrained by memory/KV
rather than compute, and its larger HBM capacity
reduces the number of GPUs required.
```

### "Why P/D?"

```text
Because prefill and decode have materially different
resource and latency characteristics and coupled
serving cannot satisfy both SLOs efficiently.
```

# 84. One More Important Current Detail

The ecosystem is evolving quickly.

Current llm-d documentation describes version **0.9** as a hardened release with router HA, enhanced autoscaling, observability and broader hardware support. ([Llm-D][3])

The current vLLM production-stack documentation also describes a Kubernetes-native reference stack that adds routing, monitoring and KV-related capabilities around vLLM. ([vLLM][7])

So in your real-world implementation:

> **Treat exact CLI flags, APIs, Helm values and feature maturity as version-specific.**

The architecture principles are much more durable than individual flags.

For example, today's vLLM docs explicitly label some native disaggregated-prefill functionality experimental, while production-oriented stacks may provide additional connectors and deployment patterns. ([vLLM][8])

That distinction matters when you're advising a customer.
