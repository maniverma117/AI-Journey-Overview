# Lab 1G — Multi-Replica vLLM + Intelligent Routing

Now we reach a major architectural transition.

Until now:

```text
Client
  ↓
vLLM
  ↓
GPU
```

Then we added autoscaling:

```text
Client
  ↓
Service
  ↓
vLLM replicas
  ↓
KEDA/HPA
  ↓
Karpenter
```

Now we need to solve:

> **When there are multiple vLLM replicas, which replica should receive each request?**

This is where **llm-d** becomes important.

---

# 1. The problem with ordinary Kubernetes load balancing

Suppose we have:

```text
                  Kubernetes Service
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
          vLLM-1      vLLM-2      vLLM-3
             │           │           │
            GPU         GPU         GPU
```

A normal Service/load balancer primarily sees:

```text
Pod A
Pod B
Pod C
```

It doesn't inherently understand:

```text
KV cache utilization
prefix-cache locality
waiting requests
active sequences
prefill/decode state
token load
```

But LLM inference absolutely cares about these.

Current llm-d architecture specifically adds an inference-aware Router and Endpoint Picker (EPP) that can use model-server state such as KV-cache utilization, prefix-cache locality, queue depth and active requests. ([Llm-D][1])

---

# 2. Imagine three replicas

Suppose:

```text
vLLM-1
KV = 20%
queue = 2
running = 5

vLLM-2
KV = 95%
queue = 30
running = 40

vLLM-3
KV = 55%
queue = 8
running = 15
```

A simple round-robin router might do:

```text
request 1 → vLLM-1
request 2 → vLLM-2
request 3 → vLLM-3
request 4 → vLLM-1
...
```

It doesn't necessarily know that:

```text
vLLM-2
```

is already overloaded.

---

# 3. An inference-aware router thinks differently

It can reason:

```text
request
   │
   ├── Does vLLM-1 have capacity?
   ├── Does vLLM-2 have capacity?
   ├── Does vLLM-3 have capacity?
   │
   ├── Where is the prefix already cached?
   ├── Which endpoint has lower KV pressure?
   ├── Which endpoint has lower queue?
   └── Which endpoint satisfies the latency objective?
```

Then:

```text
                  Request
                     │
                     ▼
                   EPP
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       vLLM-1     vLLM-2     vLLM-3
       score 8    score 2    score 7
          │          │          │
          └──────────┼──────────┘
                     ▼
                  vLLM-1
```

That's the fundamental idea.

---

# 4. llm-d architecture

Current llm-d has three core concepts:

```text id="x8x6vf"
                    llm-d Router
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
            Proxy                  EPP
              │                     │
          network/data        routing intelligence
              │                     │
              └──────────┬──────────┘
                         ▼
                   InferencePool
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       vLLM-1         vLLM-2         vLLM-3
```

The current architecture describes:

* **Router** — intelligent entry point
* **InferencePool** — logical pool of model-server pods
* **Model Server** — vLLM/SGLang/etc.

([Llm-D][1])

---

# 5. What exactly is InferencePool?

Think of it as:

> **An LLM-aware Service abstraction.**

A normal Service says:

```text
select these pods
```

An InferencePool says conceptually:

```text
these are my inference endpoints
+
this is how inference-aware routing should discover them
+
this is the Endpoint Picker associated with them
```

Current `InferencePool` is:

```text
apiVersion:
inference.networking.k8s.io/v1
```

and includes things such as:

```text
selector
targetPorts
endpointPickerRef
```

([Llm-D][2])

---

# 6. The model-server layer remains vLLM

This is important.

llm-d does **not replace vLLM**.

Instead:

```text
llm-d
  =
routing / orchestration intelligence
```

while:

```text
vLLM
  =
actual inference engine
```

So:

```text
Client
  ↓
llm-d
  ↓
vLLM
  ↓
PyTorch
  ↓
CUDA
  ↓
GPU
```

Current llm-d supports vLLM, SGLang and TensorRT-LLM as model-server backends. ([Llm-D][3])

---

# 7. EPP = the brain

EPP means:

**Endpoint Picker**

Current llm-d documentation describes EPP as the routing "brains."

Its job is roughly:

```text
Request
   ↓
identify request
   ↓
find candidate endpoints
   ↓
filter bad candidates
   ↓
score candidates
   ↓
pick endpoint
```

The EPP communicates with the proxy through Envoy's External Processing (`ext-proc`) mechanism. ([Llm-D][4])

---

# 8. The request path

This is worth understanding carefully.

```text
                  HTTP Request
                       │
                       ▼
                     Proxy
                       │
                 "Where should
                  this go?"
                       │
                       ▼
                      EPP
                       │
              ┌────────┴─────────┐
              ▼                  ▼
          inspect state       apply policy
              │                  │
              └────────┬─────────┘
                       ▼
                select endpoint
                       │
                       ▼
                    Proxy
                       │
                       ▼
                   vLLM Pod
```

Current llm-d describes the proxy as effectively parking the request while the EPP makes its endpoint selection, then forwarding the request to the chosen model server. ([Llm-D][5])

---

# 9. EPP doesn't continuously poll every request blindly

The EPP has a **data layer**.

It gathers information such as:

```text
Kubernetes API
       +
model-server metrics
       +
prefix-cache information
       +
other inference signals
```

and maintains endpoint state.

Current llm-d documentation describes the Data Layer as collecting information such as queue depth, KV utilization and adapter state and exposing those attributes to scheduling plugins. ([Llm-D][6])

So conceptually:

```text
                 Data Layer
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
      Queue          KV        Prefix
        │            │            │
        └────────────┼────────────┘
                     ▼
                    EPP
                     │
                     ▼
                  Decision
```

---

# 10. Routing isn't just "least loaded"

This is one of the most important ideas.

Suppose:

```text
vLLM-1:
queue = 5
prefix hit = 0%

vLLM-2:
queue = 8
prefix hit potential = 90%
```

A naive least-queue router picks:

```text
vLLM-1
```

But an inference-aware router might choose:

```text
vLLM-2
```

because reusing the cached prefix saves substantial prefill work.

So:

> **The best endpoint isn't necessarily the least-loaded endpoint.**

It's the endpoint with the best **overall expected inference outcome**.

---

# 11. Prefix-cache locality

Let's make this concrete.

Suppose our application sends:

```text
SYSTEM PROMPT
+
COMPANY DOCUMENTATION
+
USER QUESTION
```

and:

```text
vLLM-1
```

already has the common prefix cached.

Then:

```text
request
   │
   ▼
vLLM-1
   │
cached prefix
   │
small new computation
```

Potentially much better than:

```text
request
   │
   ▼
vLLM-3
   │
prefix missing
   │
recompute everything
```

Therefore routing affects **compute efficiency**, not merely network distribution.

---

# 12. Queue-aware routing

Imagine:

```text
vLLM-1 queue = 3
vLLM-2 queue = 30
vLLM-3 queue = 5
```

Obviously:

```text
vLLM-2
```

should be penalized.

But now add:

```text
vLLM-2 has 95% prefix-cache match
```

The routing decision becomes a tradeoff.

This is why llm-d uses configurable filters/scorers rather than a single static algorithm.

---

# 13. Think of routing as a scoring function

Conceptually:

```text
Score(endpoint)
=
prefix benefit
+
capacity
+
latency headroom
+
queue health
+
KV health
+
priority
```

Not literally this exact equation—the actual implementation is plugin/config driven.

The important mental model is:

```text
Candidate endpoints
       ↓
filter
       ↓
score
       ↓
pick
```

Current llm-d's scheduling architecture uses filters and scorers to perform this process. ([Llm-D][4])

# 19. Deploying llm-d: two modes

Current llm-d router supports two broad deployment approaches:

### Standalone

```text
llm-d
 ├── Proxy
 └── EPP
```

The router provides its own proxy.

### Gateway mode

```text
Existing Gateway
       │
       ▼
   llm-d EPP
       │
       ▼
   InferencePool
```

Current llm-d publishes separate Helm charts for standalone and Gateway mode. ([Llm-D][9])

For **learning the architecture**, standalone mode is easier.

For an enterprise EKS platform, Gateway mode can make more sense when you already operate a standard Gateway/API ingress layer.

# 20. Our first InferencePool

Suppose our vLLM pods have:

```yaml
labels:
  app: vllm
  model: my-model
```

Then conceptually:

```yaml
apiVersion: inference.networking.k8s.io/v1
kind: InferencePool

metadata:
  name: vllm-pool

spec:
  selector:
    matchLabels:
      app: vllm
      model: my-model

  targetPorts:
    - number: 8000

  endpointPickerRef:
    name: epp
```

The key idea is:

```text
selector
```

means:

> "These pods belong to my inference pool."

The current API requires `selector` and `targetPorts`; the Endpoint Picker reference is supported for associating routing intelligence. ([Llm-D][2])

# 21. Why this is better than a normal Service

Normal Service:

```text
Service
  ↓
select Pods
  ↓
load balance
```

InferencePool:

```text
InferencePool
  ↓
discover model endpoints
  ↓
EPP
  ↓
inspect inference state
  ↓
intelligent endpoint selection
```

The distinction is:

```text
Service:
"Which pod?"

InferencePool:
"Which inference endpoint is the best destination
for THIS request right now?"
```

# 28. Failure scenario

Now kill:

```text
vLLM-2
```

What should happen?

```text
InferencePool
      ↓
endpoint disappears
      ↓
EPP state updates
      ↓
new requests
      ↓
avoid dead endpoint
```

Current llm-d's data layer watches Kubernetes and model-server state and updates endpoint information for scheduling. ([Llm-D][4])

This gives us another reliability benefit:

> **Routing state should adapt as inference endpoints change.**

---

# 29. Another failure scenario

Suppose:

```text
vLLM-1
KV = 95%
queue = 50

vLLM-2
KV = 30%
queue = 5
```

Traffic shouldn't blindly continue flowing evenly.

The routing layer should help prevent:

```text
already overloaded replica
        ↓
more requests
        ↓
queue grows
        ↓
TTFT explodes
```

This is **load-aware inference routing**.

---

# 30. One more concept: fairness

Imagine:

```text
Tenant A
large batch workload

Tenant B
interactive chat
```

If both share the same inference pool:

```text
Tenant A
████████████████████████

Tenant B
█
```

A naive system may let A consume the entire serving capacity.

Inference-aware scheduling can incorporate:

```text
priority
fairness
flow control
```

Current EPP architecture includes flow-control and fairness mechanisms in addition to endpoint selection. ([Llm-D][4])

This becomes very important for multi-tenant AI platforms.
