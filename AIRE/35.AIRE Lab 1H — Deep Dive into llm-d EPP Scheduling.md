# Lab 1H — Deep Dive into llm-d EPP Scheduling

Now we're going inside the **decision-making layer** of llm-d.

You've already learned:

```text
Client
  ↓
AI Gateway
  ↓
llm-d Router
  ↓
InferencePool
  ↓
vLLM
  ↓
GPU
```

Now we're going to answer:

> **How does llm-d decide which vLLM replica should receive a particular request?**

This is one of the most valuable concepts for advanced AI infrastructure interviews.

---

# 1. EPP is basically a scheduling engine

Think of EPP as:

```text
                  REQUEST
                     │
                     ▼
                  EPP
                     │
           ┌─────────┴─────────┐
           ▼                   ▼
        FILTER                SCORE
           │                   │
    remove bad nodes      rank candidates
           │                   │
           └─────────┬─────────┘
                     ▼
                    PICK
                     │
                     ▼
                  vLLM
```

Current llm-d describes the scheduling pipeline as **Filter → Score → Pick**, with pluggable filters and scorers.

That simple model is worth memorizing.

---

# 2. Step 1 — FILTER

Suppose our InferencePool contains:

```text
vLLM-1
vLLM-2
vLLM-3
vLLM-4
```

Before scoring anything, we remove endpoints that shouldn't receive the request.

For example:

```text
vLLM-1 → healthy
vLLM-2 → healthy
vLLM-3 → unhealthy
vLLM-4 → draining
```

After filtering:

```text
Candidates:

vLLM-1
vLLM-2
```

We shouldn't waste time calculating a score for endpoints that can't serve.

---

# 3. What can cause filtering?

Depending on configuration, llm-d supports filters around concepts such as:

```text
prefix-cache affinity
SLO headroom
label selectors
prefill
decode
```

The exact filters available depend on the deployed llm-d version/configuration.

For example:

```text
Request requires:
model = llama
```

and:

```text
vLLM-1 → llama ✓
vLLM-2 → llama ✓
vLLM-3 → mistral ✗
```

Then:

```text
vLLM-3
```

is eliminated before scoring.

---

# 4. Step 2 — SCORE

Now suppose:

```text
Candidates:

vLLM-1
vLLM-2
```

The EPP evaluates them.

Possible signals:

```text
queue
running requests
KV utilization
token load
prefix locality
latency
SLO headroom
LoRA affinity
session affinity
```

Current llm-d scheduling documentation lists scorers including KV utilization, latency, queue depth, running requests, token load, prefix affinity and session affinity.

---

# 5. Think of scoring as a decision matrix

Suppose:

| Signal           | vLLM-1 | vLLM-2 |
| ---------------- | -----: | -----: |
| Queue            |      3 |     15 |
| KV               |    40% |    80% |
| Prefix match     |    90% |     0% |
| Running requests |      5 |     25 |
| TTFT headroom    |   High |    Low |

An ordinary load balancer might just say:

```text
vLLM-1
```

because it has fewer requests.

But the interesting case is when signals conflict.

---

# 6. Scenario 1 — Lowest queue wins

```text
vLLM-1:
queue = 2
KV = 50%
prefix = 0%

vLLM-2:
queue = 20
KV = 70%
prefix = 0%
```

Easy:

```text
vLLM-1
```

should probably win.

Why?

```text
queue ↓
KV ↓
```

So the endpoint has more available capacity.

---

# 7. Scenario 2 — Prefix locality changes the answer

Now:

```text
vLLM-1:
queue = 2
KV = 40%
prefix = 0%

vLLM-2:
queue = 5
KV = 50%
prefix = 90%
```

Which is better?

Not necessarily vLLM-1.

Suppose the request has:

```text
50,000-token common prefix
```

If vLLM-2 already has the prefix cached:

```text
vLLM-2
   ↓
reuse cached computation
   ↓
less prefill
   ↓
potentially lower TTFT
```

Sending it to vLLM-1 means:

```text
vLLM-1
   ↓
prefix missing
   ↓
recompute 50K tokens
```

So:

> **A slightly busier endpoint can be faster because it has the right cached state.**

This is one of the key reasons ordinary load balancing isn't sufficient for LLM inference.

---

# 8. Scenario 3 — KV pressure

Now:

```text
vLLM-1:
KV = 95%
queue = 3

vLLM-2:
KV = 45%
queue = 10
```

A naive router may see:

```text
queue:
3 < 10
```

and select vLLM-1.

That's dangerous.

Because:

```text
KV = 95%
```

means this replica has little cache headroom.

A better inference-aware router may prefer:

```text
vLLM-2
```

because:

```text
KV headroom
```

is much healthier.

---

# 9. Scenario 4 — Long-context request

Suppose:

```text
Request:
input = 100K tokens
output = 1K
```

and:

```text
vLLM-1:
KV = 20%
queue = 5

vLLM-2:
KV = 80%
queue = 2
```

The lowest queue is vLLM-2.

But this request could significantly increase memory pressure.

Therefore a KV-aware policy may favor:

```text
vLLM-1
```

because it has much more cache headroom.

This is an important architectural insight:

> **The cost of a request isn't determined just by the number of requests.**

A 100K-token request and a 500-token request aren't equivalent.

---

# 10. Scenario 5 — Interactive vs batch

Imagine:

```text
Tenant A:
interactive chat

Tenant B:
offline summarization
```

Batch workload:

```text
large prompts
large outputs
long-running
```

Interactive:

```text
short request
strict TTFT
```

If both compete equally:

```text
batch workload
████████████████████████

chat
█
```

the chat user can suffer.

A production inference scheduler may need:

```text
priority
fairness
flow control
SLO objectives
```

rather than simply:

```text
least requests
```

---

# 11. SLO-aware routing

This is a very powerful concept.

Suppose:

```text
Request SLO:

TTFT < 500ms
```

Now:

```text
vLLM-1:
predicted TTFT = 300ms

vLLM-2:
predicted TTFT = 800ms
```

Even if:

```text
vLLM-2
```

has lower queue depth, it isn't a good candidate.

The routing decision should consider:

```text
Can this endpoint satisfy the request's objective?
```

Current llm-d supports SLO-related filtering/scoring concepts and exposes headers for objectives such as TTFT and TPOT.

For example, llm-d's HTTP headers include:

```text
x-llm-d-slo-ttft-ms
x-llm-d-slo-tpot-ms
```

---

# 12. Why request-specific SLOs are interesting

Imagine:

```text
Request A:
TTFT target = 300ms

Request B:
TTFT target = 2 seconds
```

They shouldn't necessarily be routed identically.

The EPP can potentially treat them differently.

Conceptually:

```text
                    Request
                       │
              ┌────────┴────────┐
              ▼                 ▼
          strict SLO        relaxed SLO
              │                 │
              ▼                 ▼
        fast endpoint       capacity endpoint
```

This opens the door to differentiated service tiers.

---

# 13. The scoring problem is really an optimization problem

Imagine each endpoint has:

```text
Queue
KV
Prefix
Latency
Token load
SLO headroom
```

You can think conceptually:

```text
                 Request
                    │
                    ▼
          ┌────────────────────┐
          │ Candidate endpoint │
          └─────────┬──────────┘
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
     Prefix         KV          Queue
       │            │            │
       └────────────┼────────────┘
                    │
                    ▼
                 Score
                    │
                    ▼
                  Pick
```

The actual llm-d implementation uses configurable plugins rather than one universal formula.

That's important.

---

# 14. Filter vs Score

This distinction is frequently misunderstood.

### Filter

Answers:

> **"Can this endpoint be considered?"**

Example:

```text
GPU incompatible
model incompatible
endpoint unhealthy
```

Remove it.

### Score

Answers:

> **"Among valid endpoints, which is better?"**

Example:

```text
queue
KV
prefix
latency
```

Rank them.

So:

```text
FILTER → eliminate
SCORE → rank
PICK → choose
```

Memorize this.

---

# 15. What happens when all endpoints are bad?

Suppose:

```text
vLLM-1 → KV 99%
vLLM-2 → unhealthy
vLLM-3 → queue 200
```

The router still needs a policy.

Possibilities include:

```text
reject
queue
choose least-bad
apply backpressure
retry
```

This is where **flow control** matters.

A system that blindly accepts infinite work creates:

```text
queue explosion
      ↓
TTFT explosion
      ↓
timeouts
      ↓
retries
      ↓
more load
      ↓
positive feedback loop
```

This can become a cascading failure.

---

# 16. Retry storms

Consider:

```text
vLLM overloaded
      ↓
request times out
      ↓
client retries
      ↓
2 requests
      ↓
more load
      ↓
more timeouts
      ↓
more retries
```

Eventually:

```text id="e7h5x2"
load ↑↑↑
```

This is a classic distributed-systems failure mode.

AI systems are particularly vulnerable because each request may be expensive.

A retry of:

```text
100K input tokens
+
4K output tokens
```

is not a cheap retry.

---

# 17. Flow control

A mature inference system needs to be able to say:

> "I cannot safely accept more work right now."

That's not failure.

That's **protective behavior**.

Possible mechanisms:

```text
rate limiting
queue limits
concurrency limits
priority
backpressure
load shedding
```

The goal:

```text
protect healthy service
```

rather than:

```text
accept everything
until everything dies
```

---

# 18. Prefix-cache indexing

Now let's connect this to what you learned earlier.

Suppose:

```text
vLLM-1
cached prefix A

vLLM-2
cached prefix B

vLLM-3
cached prefix C
```

The router needs to know:

```text
Which endpoint contains the prefix relevant to this request?
```

That's where a **KV Cache Indexer** becomes useful.

Current llm-d's KV Cache Indexer can receive cache block events from model servers and maintain mappings between cache blocks and endpoints.

Conceptually:

```text
                KV Cache Index
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Prefix A       Prefix B       Prefix C
        │              │              │
      vLLM-1          vLLM-2         vLLM-3
```

Now routing can exploit locality.

---

# 19. Why this can save GPU compute

Without prefix reuse:

```text
50K tokens
   ↓
prefill
   ↓
compute
```

With cached prefix:

```text
50K tokens
   ↓
cache hit
   ↓
only new suffix processed
```

So:

```text
prefix-aware routing
        ↓
less recomputation
        ↓
less GPU work
        ↓
lower TTFT
        ↓
higher effective capacity
```

This is a beautiful example of how **network routing can become a compute optimization**.

---

# 20. Now connect routing to autoscaling

This is subtle.

Suppose:

```text
vLLM-1
KV 95%
queue 50

vLLM-2
KV 30%
queue 5
```

Routing sends traffic toward vLLM-2.

But if all replicas become:

```text
KV > 90%
queue ↑
```

then:

```text
router
  ↓
cannot find healthy capacity
  ↓
queue increases
  ↓
KEDA observes queue
  ↓
HPA scales replicas
  ↓
Karpenter creates GPU node
```

So routing and autoscaling form a feedback loop:

```text
               ┌───────────────┐
               │     Traffic   │
               └───────┬───────┘
                       ▼
                     llm-d
                       │
                 route intelligently
                       │
                       ▼
                     vLLM
                       │
                 queue / KV / TTFT
                       │
                       ▼
                     KEDA
                       │
                       ▼
                      HPA
                       │
                       ▼
                   Karpenter
                       │
                       ▼
                   GPU capacity
                       │
                       └──────────→ llm-d
```

This is the beginning of a **closed-loop inference platform**.

---

# 21. Router and autoscaler must not fight each other

Imagine the router aggressively sends everything to:

```text
vLLM-1
```

because it has a prefix cache.

Then:

```text
vLLM-1 → overloaded
vLLM-2 → idle
vLLM-3 → idle
```

Autoscaling may see:

```text
average load = low
```

and refuse to scale.

But the user experience is bad.

This is why:

> **Load balancing, cache locality and autoscaling must be designed together.**

---

# 22. Another problem: cache locality vs load balancing

Imagine:

```text
vLLM-1 → prefix hit 90%
vLLM-2 → prefix hit 0%
```

If you always route to vLLM-1:

```text
cache locality ↑
but
vLLM-1 load ↑
```

If you always balance:

```text
load distribution ↑
but
cache hit ↓
```

So there is an optimization tradeoff:

```text
             Prefix locality
                    ▲
                    │
                    │
                    │
                    └──────────────► Load balance
```

The optimal point depends on workload.

This is why inference routing isn't trivial.

---

# 23. Session affinity

Some applications have:

```text
conversation
   ↓
many turns
```

For example:

```text
Turn 1 → endpoint A
Turn 2 → endpoint A
Turn 3 → endpoint A
Turn 4 → endpoint A
```

Why?

Potentially:

```text
session state
prefix cache
conversation context
LoRA adapter
```

can benefit from locality.

llm-d's scheduler architecture includes session-affinity concepts among its available scoring mechanisms.

---

# 24. LoRA affinity

Imagine one base model:

```text
Llama
```

with adapters:

```text
customer-A
customer-B
customer-C
```

Different replicas might have different adapters loaded or cached.

Then routing could consider:

```text
request requires adapter B
```

and prefer:

```text
replica with adapter B already resident
```

Again:

```text
routing
   ↓
cache/locality
   ↓
less loading
   ↓
better performance
```

This is another reason ordinary HTTP load balancing isn't enough.

---

# 25. EPP failure

Now consider:

```text
llm-d EPP
     X
```

What happens?

This is a critical production question.

The inference router itself becomes a dependency.

Your architecture needs:

```text
multiple router/EPP instances
+
health checks
+
appropriate failover
+
bounded decision latency
```

You don't want:

```text
100 GPUs
   ↓
one router
   ↓
router dies
   ↓
100 GPUs inaccessible
```

That would create a massive blast radius.

---

# 26. EPP decision latency matters

Imagine model inference takes:

```text
500ms
```

but routing decision takes:

```text
300ms
```

Then your intelligent router is hurting the system.

Therefore the routing layer itself has an SLO.

Conceptually:

```text
Router latency
+
queue
+
prefill
+
decode
=
user latency
```

So inference-aware routing must be:

```text
smart
+
fast
+
highly available
```
