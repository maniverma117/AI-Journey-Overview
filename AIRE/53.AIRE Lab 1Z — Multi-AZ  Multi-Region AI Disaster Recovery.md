# Lab 1Z — Multi-AZ / Multi-Region AI Disaster Recovery

Now we move from **securing and operating one AI platform** to designing an AI platform that can **survive infrastructure failure**.

The key mindset:

> **AI disaster recovery is not just "deploy another EKS cluster."**
>
> You must recover **compute, model artifacts, routing, RAG/data, identities, policies, capacity, and traffic** while preserving your AI SLOs.

---

# 1. Start With the Failure Domain

Before designing DR, define what can fail.

```text
                    AI PLATFORM
                        │
        ┌───────────────┼────────────────┐
        │               │                │
       Pod             GPU              Node
        │               │                │
        └───────────────┼────────────────┘
                        │
                       AZ
                        │
                      Region
                        │
                    Control Plane
```

But AI has additional failure domains:

```text
Model artifact
Tokenizer
Vector DB
RAG pipeline
Tool Gateway
IAM
DNS
Gateway
NCCL
EFA
KV transfer
External APIs
```

So your DR design must consider the **whole dependency graph**.

---

# 2. Availability vs Disaster Recovery

These are different.

### High availability

Protects against expected failures:

```text
GPU failure
Pod failure
Node failure
AZ failure
```

### Disaster recovery

Protects against major failures:

```text
EKS cluster loss
Region outage
Data corruption
Model artifact loss
Security incident
Configuration destruction
```

Think:

```text
HA
 │
 ├── Pod
 ├── GPU
 ├── Node
 └── AZ
       
DR
 │
 ├── Cluster
 ├── Region
 └── Data / control plane
```

---

# 3. RTO and RPO

Two terms you must know.

## RTO

**Recovery Time Objective**

> How long can the service be unavailable?

Example:

```text
RTO = 10 minutes
```

means:

```text
failure
  │
  ├──────────────┤
       10 min
  │
  ▼
service restored
```

---

## RPO

**Recovery Point Objective**

> How much data can we afford to lose?

Example:

```text
RPO = 5 minutes
```

means losing up to five minutes of recoverable state may be acceptable.

---

# 4. AI Has Multiple RPOs

This is interesting.

Not everything needs the same RPO.

| Component            | Typical concern       |
| -------------------- | --------------------- |
| Model artifact       | Usually zero/very low |
| Tokenizer            | Zero                  |
| Serving config       | Zero                  |
| Security policy      | Zero                  |
| IAM configuration    | Zero                  |
| Application code     | Zero/very low         |
| RAG documents        | Business dependent    |
| Vector DB            | Business dependent    |
| Conversation history | Business dependent    |
| KV cache             | Usually disposable    |
| Active generation    | Usually restart       |
| Metrics              | Some loss acceptable  |

This gives us an important principle:

> **Not all AI state deserves the same DR strategy.**

---

# 5. KV Cache Is Usually Disposable

This connects directly to our previous P/D lessons.

Suppose:

```text
Region A
   │
   └── GPU KV cache
```

Region A dies.

Should you replicate every KV cache entry to Region B?

Usually:

**No.**

KV cache is derived from:

```text
model weights
+
input tokens
```

You can recompute it.

Therefore:

```text
Region A
   │
   X
   │
KV lost
```

Region B:

```text
request
  │
  ▼
prefill
  │
  ▼
new KV
  │
  ▼
decode
```

This dramatically simplifies DR.

---

# 6. But Active Requests May Be Lost

Suppose:

```text
User
 │
 ▼
Region A
 │
 ▼
vLLM
 │
 ▼
decode
```

Region dies.

The active generation may disappear.

You generally don't attempt to magically continue the exact GPU execution in another region.

Instead:

```text
failure
   │
   ▼
request retry / reconnect
   │
   ▼
Region B
   │
   ▼
new inference
```

This is why API semantics matter.

Your application needs to distinguish:

```text
request failed
```

from:

```text
request successfully completed
```

Otherwise retrying can produce duplicate side effects.

# 7. Multi-AZ Architecture

Start with the simplest production HA design.

```text
                    Global / Regional Entry
                              │
                              ▼
                       AI Gateway
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
            AZ-A            AZ-B            AZ-C
              │               │               │
          EKS cluster      EKS cluster      EKS cluster
              │               │               │
          GPU pool         GPU pool         GPU pool
              │               │               │
            vLLM            vLLM            vLLM
```

Important:

> **Do not spread one TP group across AZs unless the architecture explicitly supports and justifies that network topology.**

For example:

```text
TP4
GPU1 GPU2 GPU3 GPU4
```

should generally remain within an appropriate tightly connected topology.

Instead:

```text
AZ-A
 ├── TP4 replica
 └── TP4 replica

AZ-B
 ├── TP4 replica
 └── TP4 replica
```

This gives you AZ-level failure tolerance.

---

# 8. Failure Unit Matters

Suppose you have:

```text
TP8
```

One replica consumes:

```text
8 GPUs
```

So:

```text
1 GPU failure
      ↓
TP group failure
      ↓
8-GPU replica unavailable
```

Your failure unit is effectively:

```text
TP8 replica
```

not one GPU.

Compare:

```text
4 × TP2
```

Now:

```text
1 GPU failure
     ↓
1 TP2 replica lost
     ↓
3 replicas remain
```

This is why **parallelism design and DR design are connected**.

---

# 9. N+1 Capacity

Suppose production requires:

```text
6 × TP4 replicas
```

That's:

```text
24 GPUs
```

If you require one-replica failure tolerance:

```text
6 + 1 = 7 replicas
```

Therefore:

```text
7 × TP4
=
28 GPUs
```

Your production capacity isn't merely:

```text
24 GPUs
```

It's:

```text
28 GPUs
```

if your SLO requires surviving one replica failure without capacity degradation.

---

# 10. AZ-Level N+1

Suppose:

```text
AZ-A → 3 replicas
AZ-B → 2 replicas
AZ-C → 2 replicas
```

Total:

```text
7 replicas
```

If AZ-A disappears:

```text
2 + 2 = 4 replicas
```

If normal demand requires six replicas:

```text
4 < 6
```

You survive the outage, but **not your SLO capacity**.

Therefore:

> HA availability does not necessarily mean HA capacity.

This is a very important Solution Architect distinction.

---

# 11. Multi-Region Architecture

Now go one level higher.

```text
                  Global Traffic
                        │
               ┌────────┴────────┐
               │                 │
          Region A          Region B
               │                 │
          AI Gateway        AI Gateway
               │                 │
             llm-d             llm-d
               │                 │
             vLLM              vLLM
               │                 │
              GPU               GPU
```

Possible strategies:

### Active-active

```text
Region A → 50%
Region B → 50%
```

Both serve traffic.

### Active-passive

```text
Region A → 100%

Region B → standby
```

Region B becomes active after failure.

---

# 12. Active-Active

Advantages:

* better resource utilization
* lower failover time
* regional traffic distribution
* easier capacity validation
* both regions continuously exercised

But:

```text
2 regions
×
GPU fleet
=
2× baseline GPU capacity
```

Potentially expensive.

And you now need:

```text
cross-region data strategy
routing
capacity management
model synchronization
RAG synchronization
security policy synchronization
```

---

# 13. Active-Passive

Architecture:

```text
              Global Router
                   │
             ┌─────┴─────┐
             ▼           ▼
         Region A     Region B
          ACTIVE       STANDBY
             │           │
           GPU         GPU
```

The difficult question is:

> What does "standby" mean?

There are several levels.

### Cold

```text
No GPU
No running vLLM
```

Cheapest.

But:

```text
RTO ↑↑
```

### Warm

```text
EKS ready
GPU capacity available
vLLM infrastructure ready
model partially/cached
```

Better RTO.

### Hot

```text
Full model fleet
Ready replicas
```

Fastest failover.

Most expensive.

---

# 14. Model Loading Is Part of RTO

Imagine:

```text
Region B
EKS ready
```

but model isn't loaded.

Then:

```text
download model
      ↓
load into CPU RAM
      ↓
load into GPU HBM
      ↓
initialize CUDA
      ↓
initialize KV cache
      ↓
warmup
      ↓
ready
```

If this takes 15 minutes:

```text
RTO ≈ 15+ minutes
```

Therefore:

> **GPU availability alone does not mean inference availability.**

Think of DR as:

```text
Level 0
Nothing

Level 1
Infrastructure

Level 2

Level 3
Serving stack

Level 4
```

> "Which level does the customer require for the stated RTO?"

# 16. Model Artifact DR

Never make Region B depend on:

```text
Region A's local disk
```

Instead:

```text
                Model Registry
                     │
             ┌───────┴───────┐
             ▼               ▼
         Region A         Region B
             │               │
         local cache      local cache
             │               │
             ▼               ▼
            GPU             GPU
```

Authoritative model artifacts should have:

* immutable version
* checksum/digest
* metadata
* tokenizer
* configuration
* compatibility information

---

# 17. S3 Strategy

Conceptually:

```text
                   S3
                    │
             model-v42/
                    │
         ┌──────────┴──────────┐
         ▼                     ▼
    Region A                Region B
      cache                   cache
```

You want Region B to be able to reconstruct the serving fleet without Region A.

This is a major DR principle:

> **A region should be operationally reconstructible from authoritative artifacts and configuration.**

# 18. GitOps DR

Your Git repository should contain desired infrastructure/configuration.

For example:

```text
git/
 ├── clusters/
 │    ├── region-a/
 │    └── region-b/
 │
 ├── models/
 │    └── gemma-70b/
 │
 ├── inference/
 │    ├── vllm/
 │    └── llm-d/
 │
 ├── networking/
 │
 ├── security/
 │
 └── policies/
```

Then:

```text
Region destroyed
      │
      ▼
Recreate infrastructure
      │
      ▼
GitOps reconciliation
      │
      ▼
model artifact
      │
      ▼
GPU fleet
      │
      ▼
serving
```

This is much safer than relying on manual reconstruction.

# 19. RAG DR

This is often harder than the LLM itself.

Architecture:

```text
                  RAG Data
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       Region A              Region B
       Vector DB             Vector DB
```

You need to decide:

```text
What is authoritative?
What replication model?
What consistency?
What RPO?
What indexing delay?
```

For example:

```text
Document DB
    │
    ▼
Embedding pipeline
    │
    ▼
Vector DB A
    │
    └──────── replication ───────► Vector DB B
```

If Region A dies:

```text
Region B
   │
   ▼
latest replicated knowledge
```

---

# 20. RAG Consistency vs Availability

Suppose a policy document changes at:

```text
10:00
```

Region B receives it at:

```text
10:05
```

Then failover at:

```text
10:02
```

Region B has stale knowledge.

That's an RPO/data consistency issue.

Therefore AI DR must include:

```text
data freshness SLO
```

not only:

```text
HTTP availability
```

---

# 21. Conversation State

If your agent stores conversations:

```text
User
 │
 ▼
Conversation DB
 │
 ▼
Agent
```

that database needs its own DR strategy.

But again:

```text
KV cache ≠ conversation state
```

Conversation state is business/application data.

KV cache is usually derived runtime state.

---

# 22. Tool State Is More Dangerous

Imagine an agent executes:

```text
create_refund()
```

Then Region A fails.

The client retries against Region B.

If the operation was actually successful before failure:

```text
Region A:
refund created ✓

client:
didn't receive response
```

Then retry:

```text
Region B:
refund created again
```

Now you have duplicate side effects.

Therefore critical tools need **idempotency**.

Example:

```text
idempotency_key:
request-8f72abc
```

The backend recognizes:

```text
already executed
```

and doesn't execute twice.

---

# 23. AI DR Must Understand Side Effects

For pure inference:

```text
retry → usually okay
```

For side-effecting tools:

```text
retry → potentially dangerous
```

Therefore classify operations:

| Operation       | Retry                        |
| --------------- | ---------------------------- |
| Generate text   | Usually                      |
| Search          | Usually                      |
| Read DB         | Usually                      |
| Read CloudWatch | Usually                      |
| Create ticket   | Idempotency required         |
| Send email      | Carefully                    |
| Refund          | Idempotency + policy         |
| Deploy          | Idempotency + change control |
| Delete resource | Strong protection            |

---

# 24. Regional Traffic Failover

A simplified architecture:

```text
                    Global DNS / Routing
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
          Region A                  Region B
           HEALTHY                    READY
              │                         │
            70%                       30%
```

If Region A fails:

```text
                    Global Routing
                           │
                           ▼
                       Region B
                         100%
```

But don't forget capacity.

If Region B normally handles:

```text
30%
```

it may not have enough GPU capacity for:

```text
100%
```

# 25. DR Capacity Trap

Normal:

```text
Region A = 70 RPS
Region B = 30 RPS
```

Total:

```text
100 RPS
```

Region A dies.

Region B suddenly needs:

```text
100 RPS
```

If B only has capacity for:

```text
40 RPS
```

then:

```text
FAILOVER SUCCESS
```

at the networking level but:

```text
SERVICE FAILURE
```

at the AI level.

This is why:

> **DR capacity must be designed from the failure scenario, not normal traffic.**

---

# 26. Multi-Region Capacity Formula

Suppose:

```text
Peak demand = 100 RPS

Region B sustainable capacity
= 120 RPS

Headroom = 25%
```

Required capacity:

```text
100 × 1.25
= 125 RPS
```

Region B:

```text
120 RPS
```

Therefore:

```text
NOT ENOUGH
```

even though normal Region B traffic might be only 30 RPS.

# 27. Model Router During Regional Failure

The router needs health information.

Not merely:

```text
HTTP 200
```

but:

```text
model ready?
GPU healthy?
queue?
KV capacity?
TTFT?
capacity?
```

Conceptually:

```text
Global Router
      │
      ├── Region A
      │     ├── health
      │     ├── capacity
      │     └── SLO
      │
      └── Region B
            ├── health
            ├── capacity
            └── SLO
```

This becomes **AI-aware global routing**.

# 28. Failover Should Be Layered

Don't depend on one giant failover switch.

Think:

```text
DNS / Global routing
        ↓
Gateway
        ↓
Regional AI Gateway
        ↓
llm-d
        ↓
InferencePool
        ↓
vLLM
        ↓
GPU
```

Each layer should have health/readiness semantics appropriate to its role.

# 29. Regional Health Check

A bad health check:

```text
GET /health
→ HTTP 200
```

The process may be alive while:

```text
model not loaded
GPU broken
KV exhausted
queue overloaded
```

Better readiness concept:

```text
Process
   +
CUDA
   +
Model loaded
   +
GPU healthy
   +
Serving functional
   +
Capacity available
```

But be careful:

> Don't make a temporary traffic spike cause the entire region to appear dead.

Separate:

```text
health
readiness
capacity
SLO
```

# 30. DR and llm-d

Suppose:

```text
Region A
 ├── Gateway
 ├── EPP
 ├── InferencePool
 └── vLLM
```

Region B has its own:

```text
 ├── Gateway
 ├── EPP
 ├── InferencePool
 └── vLLM
```

You generally don't want EPP in Region B routing requests to GPUs across the world.

Keep inference routing primarily local:

```text
Region A
 Gateway
    ↓
 llm-d
    ↓
 local vLLM
```

and:

```text
Region B
 Gateway
    ↓
 llm-d
    ↓
 local vLLM
```

Global routing happens **above** regional inference routing.

# 31. P/D and DR

Suppose Region A has:

```text
Prefill fleet
     │
     ▼
NIXL/EFA
     │
     ▼
Decode fleet
```

Don't design:

```text
Region A Prefill
       │
       ▼
Region B Decode
```

as the normal architecture.

Cross-region KV transfer would introduce:

```text
latency
network dependency
failure coupling
bandwidth cost
```

Instead:

```text
Region A
 Prefill → Decode

Region B
 Prefill → Decode
```

Then fail over the **whole regional serving system**.

---

# 32. Cross-Region KV?

Could you theoretically transfer KV across regions?

Technically, pieces can be transported.

Architecturally, ask:

```text
Why?
```

If the goal is DR:

> Recompute is often simpler and more reliable than making cross-region KV state a hard dependency.

Remember:

```text
KV = derived state
```

DR should minimize unnecessary state synchronization.

A mature design could look like:

```text
                       GLOBAL TRAFFIC
                             │
                    Global Routing / DNS
                             │
              ┌──────────────┴──────────────┐
              │                             │
              ▼                             ▼
         REGION A                       REGION B
              │                             │
           WAF/GW                        WAF/GW
              │                             │
         AI Gateway                    AI Gateway
              │                             │
            llm-d                         llm-d
              │                             │
        ┌─────┴─────┐                 ┌─────┴─────┐
        ▼           ▼                 ▼           ▼
     Prefill      Decode           Prefill      Decode
        │           │                 │           │
        └─────KV────┘                 └─────KV────┘
              │                             │
             GPU                           GPU
```

Shared/replicated dependencies:

```text
GitOps

Security policies

```

# 34. What Should NOT Be Cross-Region Synchronous?

Avoid making these hard synchronous dependencies unless absolutely necessary:

```text
GPU KV cache
vLLM scheduler state
NCCL state
EFA connections
active decode state
```

They are tightly coupled to the local compute environment.

Prefer:

```text
authoritative data
+
reconstructable infrastructure
+
recomputable runtime state
```

# 44. Customer Architecture Question

Customer says:

> "Our AI API must have 99.99% availability. We want multi-region DR with an RTO of 5 minutes. The model is a 70B FP8 model, TP4. Peak traffic is 80 RPS."

Do **not** immediately answer:

> "Deploy two EKS clusters."

Ask:

### Workload

```text
P50/P95/P99 input tokens?
P50/P95/P99 output tokens?
Peak concurrency?
Traffic burst?
TTFT?
TPOT?
```

### Failure

```text
Does 99.99% require surviving:
GPU?
node?
AZ?
region?
```

### Data

```text
RAG?
Conversation state?
Tool state?
Required RPO?
```

### Model

```text
Model artifact size?
Download time?
Load time?
Warmup time?
```

### Capacity

```text
How many RPS can one TP4 replica sustain
while meeting the SLO?
```

### Business

```text
Can active generations be lost?
Can requests be retried?
Which tools are side-effecting?
```

Only after these questions do you size DR.

# 45. Important Calculation

Suppose benchmark says:

```text
TP4 replica
=
20 sustainable RPS
```

Customer:

```text
80 RPS peak
```

Normal:

```text
80 / 20 = 4 replicas
```

With 25% headroom:

```text
4 × 1.25 = 5
```

So Region A:

```text
5 × TP4
= 20 GPUs
```

If Region B must survive Region A loss:

```text
Region B
≥ 5 TP4 replicas
```

Therefore:

```text
20 GPUs Region A
20 GPUs Region B
```

before additional failure headroom.

That's:

```text
40 GPUs
```

for regional DR.

Not:

```text
8 GPUs
```

simply because normal Region B traffic is low.

# 49. Interview Question

### "How would you design DR for a 70B LLM on EKS?"

Strong answer:

> I would first define the failure domains and business RTO/RPO rather than immediately choosing infrastructure. For intra-region HA I would distribute independent inference replicas across AZs while keeping tightly coupled TP groups within appropriate GPU topology. For regional DR I would maintain an independently deployable serving stack, replicated model artifacts and required application/RAG state. KV cache and active GPU execution would generally be treated as disposable runtime state rather than synchronously replicated. Regional traffic would fail over through a global routing layer, while each region would perform local inference-aware routing. I would size the secondary region against the required failure scenario and SLO, not normal traffic, and validate the actual RTO through regular game days.

That's a strong **AI Solution Architect/AIRE answer**.
