# 7. Stage 5 — Capacity

Now use benchmark data.

Suppose:

```text
TP4 = 20 RPS
TP8 = 34 RPS
```

and both meet SLO.

Customer needs:

```text
30 RPS peak
```

With 25% headroom:

```text
30 × 1.25
= 37.5 RPS
```

TP4:

```text
37.5 / 20
= 1.875
```

Therefore:

```text
2 replicas
```

But now check failure.

If one replica dies:

```text
2 × 20 = 40
```

After failure:

```text
20 RPS
```

Requirement:

```text
30 RPS
```

Not sufficient.

Therefore N+1:

```text
3 × TP4
```

Capacity:

```text
60 RPS
```

After one replica failure:

```text
40 RPS
```

Now we satisfy the requirement.

GPU count:

```text
3 × 4
= 12 GPUs
```

# 8. Stage 6 — Reliability

Now explain failure domains.

For TP4:

```text
Replica A
 ├── GPU1
 ├── GPU2
 ├── GPU3
 └── GPU4
```

The failure unit is approximately:

```text
TP4 replica
```

not an individual GPU.

Therefore:

```text
3 × TP4
```

gives three failure units.

Spread them:

```text
AZ-A → TP4
AZ-B → TP4
AZ-C → TP4
```

Now one AZ can potentially fail while the remaining replicas continue serving.

The exact architecture still needs sufficient surviving capacity.

---

# 9. Stage 7 — Trade-offs

This is where senior candidates separate themselves.

Don't say:

> "TP4 is better."

Say:

> "TP4 gives us smaller failure granularity and better horizontal scaling at this workload, while TP8 provides better per-replica latency and capacity. Given the customer's 30-RPS requirement and 99.99% availability target, three TP4 replicas provide a better capacity and failure-domain profile, assuming the benchmark remains valid for the production token distribution."

That is a defensible decision.

Interviewer:

> "Your P99 TTFT increases from 800 ms to 7 seconds. TPOT remains around 45 ms. What do you investigate?"

This is an extremely important question.

Your first observation:

```text

TPOT ≈ stable
```

This suggests the primary issue is probably **before or around first-token generation**, not decode performance.

Start:

```text

 ↓
```

```text

3. Prefill latency
4. Input token distribution
5. KV pressure
6. Routing

```


```text

↓

↓
```

# 15. Interview Answer

A strong answer:

> "Because TTFT increased while TPOT stayed stable, I'd split TTFT into queueing and prefill rather than immediately blaming the GPU. I'd check request queue time, prefill time, input-token distribution, KV utilization and preemptions, then correlate those with GPU memory/utilization and routing distribution. If queue time increased, I'd investigate capacity, routing imbalance or admission. If prefill time increased, I'd investigate long-context traffic or prefill saturation. If this is P/D, I'd additionally inspect KV-transfer latency."

Excellent.

# 17. TTFT vs TPOT Diagnostic Table

| Symptom                | First suspects           |
| ---------------------- | ------------------------ |
| TTFT ↑, TPOT normal    | Queue / prefill          |
| TTFT normal, TPOT ↑    | Decode                   |
| TTFT ↑, TPOT ↑         | General overload         |
| KV ↑                   | Context/concurrency      |
| Preemptions ↑          | KV pressure              |
| GPU memory ↑           | KV/model/runtime         |
| GPU compute ↑          | Prefill/compute          |
| GPU memory bandwidth ↑ | Decode                   |
| NCCL ↑                 | TP communication         |
| NIXL ↑                 | P/D transfer             |
| 429 ↑                  | Admission/quota/capacity |

This table should become automatic in your mind.

```text

```


Lower normal cost.


# 38. Interview Scenario #20 — "Why Not Scale Based on GPU?"

This is a common interviewer trap.

Answer:

> "GPU utilization is useful but insufficient. LLM inference has distinct prefill, decode and KV-cache constraints. A system can have moderate GPU utilization while being memory- or queue-bound, or high GPU utilization while already violating TTFT and TPOT SLOs. I'd prefer inference-aware signals such as queue depth, TTFT, token demand, active sequences and KV utilization, correlated with GPU metrics."

---

# 39. Interview Scenario #21 — "Why llm-d?"

Answer:

> "When inference is distributed across multiple model-serving replicas, ordinary load balancing doesn't understand inference state. llm-d can route using signals such as queue depth, KV utilization, prefix locality and other endpoint state, which is particularly valuable for long-context, prefix-cache-sensitive or disaggregated inference."

Current llm-d documentation describes endpoint selection through filtering and scoring, with inference-specific signals such as KV utilization, prefix locality and queue state.

---

# 40. Interview Scenario #22 — "Why P/D?"

Answer:

> "I'd consider prefill/decode disaggregation when prefill and decode have sufficiently different resource behavior or SLO requirements that independent scaling and isolation provide measurable benefit. I would not introduce it simply because it's an advanced architecture. I'd benchmark coupled serving against P/D under the actual workload."

That's the correct answer.

---

# 41. Interview Scenario #23 — "Why H200?"

Answer:

> "I'd choose H200 over H100 when its additional memory and bandwidth materially improve the workload—for example, allowing more KV capacity or reducing tensor parallelism for a memory-heavy long-context model. I'd validate the benefit with workload-specific benchmarks and compare total cost per useful capacity."

Current NVIDIA specifications list H200 with 141GB HBM3e and 4.8TB/s memory bandwidth, making it particularly relevant to memory-heavy inference workloads.

---

# 42. Interview Scenario #24 — "Why EKS?"

Answer:

> "I'd use EKS when the platform needs fleet orchestration, multiple replicas or models, autoscaling, GPU node provisioning, multi-tenancy, deployment automation, observability and HA. For a simple one-GPU POC, EC2 plus Docker and vLLM may be operationally simpler and more appropriate."

This answer shows architectural maturity.

---

# 43. Interview Scenario #25 — "Why Not EC2?"

Answer:

> "I wouldn't rule out EC2. The choice depends on operational complexity. For one or a few stable inference servers, EC2 can be simpler. As the platform grows to multiple models, replicas, tenants, AZs, autoscaling and GitOps, EKS becomes more valuable."

# 44. The Architecture Trade-Off Triangle

Almost every decision has:

```text
             Performance
                 ▲
                 │
                 │
                 │
                 └──────────────► Cost
                /
               /
              ▼

```

You cannot maximize everything.

For example:

```text

Failure granularity ↓

```

# 57. Final Interview Answer

A concise senior answer might be:

> "I'd first characterize the workload rather than size from 30 RPS alone. With a 70B FP8 model, 8K P95 inputs, 1K P95 outputs and a 1-second TTFT/50-ms TPOT SLO, I'd benchmark TP2/TP4/TP8 using the production token distribution. If TP4 sustains 20 RPS while meeting the SLO, three TP4 replicas provide 60 RPS normal capacity and 40 RPS after one replica failure, giving us a 12-GPU N+1 design. I'd distribute the TP groups across three AZs, use an AI Gateway for identity, quota and admission control, llm-d for inference-aware endpoint routing, vLLM for serving, KEDA/HPA for replica scaling and Karpenter for GPU node provisioning. I'd monitor TTFT, TPOT, queue, KV, preemption, GPU and network metrics, and use warm capacity or an appropriate DR strategy based on the RTO. Finally I'd validate the design against cost per successful request and useful tokens rather than GPU utilization alone."

That is the level you should aim for.

# 61. Senior vs Mid-Level Answer

### Mid-level

> "I'd deploy vLLM on EKS with H100 GPUs and use Karpenter for scaling."

### Senior

> "I'd first characterize the workload and SLO, benchmark candidate serving topologies, derive SLO-constrained sustainable capacity, then select the GPU and parallelism configuration. I'd size replicas against peak demand plus headroom and the required failure unit, and only then design EKS/Karpenter. Routing, observability, security and DR would be derived from the same requirements."

The difference is **reasoning order**.

---

# 62. Staff-Level Answer

A staff-level engineer goes further:

> "I would explicitly identify the assumptions that can invalidate the sizing—particularly input/output token distributions, burst factor, long-context usage and model-version changes. I'd define benchmark acceptance criteria and a capacity envelope, not just a point estimate. I'd also design operational feedback loops so that production telemetry can detect when the workload moves outside the benchmarked envelope."

That is where you should eventually reach.
