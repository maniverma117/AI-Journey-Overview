# Lab 1A — EKS GPU Validation & Kubernetes GPU Scheduling

The goal of this stage is **not vLLM yet**.

We first prove this entire chain:

```text
EC2 GPU
   ↓
NVIDIA Driver
   ↓
Container Runtime
   ↓
Kubernetes
   ↓
NVIDIA Device Plugin
   ↓
nvidia.com/gpu
   ↓
GPU Pod
   ↓
nvidia-smi
```

If this chain isn't healthy, debugging vLLM is a waste of time.

AWS currently supports both the NVIDIA Device Plugin and DRA for GPU management. For our learning lab, we'll use the **NVIDIA Device Plugin**, because it gives us the classic `nvidia.com/gpu` resource model that you need to understand before moving into DRA. ([AWS Documentation][1])

---

# 1. First: inspect your cluster

Run:

```bash
kubectl get nodes -o wide
```

Then:

```bash
kubectl get pods -A
```

Then:

```bash
kubectl get nodes \
  -o custom-columns='NAME:.metadata.name,INSTANCE:.metadata.labels.node\.kubernetes\.io/instance-type,GPU:.status.allocatable.nvidia\.com/gpu'
```

### What we want to discover

Something like:

```text
NAME                         INSTANCE       GPU
ip-10-0-1-20.ec2.internal   g5.xlarge      1
ip-10-0-2-30.ec2.internal   m5.xlarge      <none>
```

This immediately tells us:

* which nodes are GPU nodes
* which EC2 instance type is being used
* whether Kubernetes actually sees the GPU

---

# 2. Check the GPU node directly

If you have SSH access to the GPU node:

```bash
nvidia-smi
```

You should see something like:

```text
+-----------------------------------------------------------------------------+
| NVIDIA-SMI ...                                                             |
|-------------------------------+----------------------+----------------------+
| GPU  Name                     | Bus-Id               | Memory-Usage         |
|===============================+======================+======================|
| 0   NVIDIA H100 80GB          | ...                  | 0MiB / 81920MiB      |
+-------------------------------+----------------------+----------------------+
```

This proves:

```text
EC2
 ↓
PCIe
 ↓
GPU
 ↓
NVIDIA Driver
```

But **it does NOT yet prove Kubernetes can use the GPU.**

That's an important distinction.

---

# 3. Check the NVIDIA device plugin

Run:

```bash
kubectl get pods -A | grep -i nvidia
```

Depending on your installation, you may see something like:

```text
kube-system   nvidia-device-plugin-daemonset-xxxxx   1/1   Running
```

or:

```text
nvidia   nvdp-nvidia-device-plugin-xxxxx   1/1   Running
```

AWS's current documentation confirms that the NVIDIA device plugin exposes GPUs to Kubernetes as the extended resource:

```text
nvidia.com/gpu
```

and the plugin can be installed through its Helm chart. ([AWS Documentation][1])

# 4. Check what Kubernetes thinks the node has

This is one of the most important commands in the entire lab:

```bash
kubectl describe node <GPU_NODE>
```

Look for:

```text
Capacity:
  cpu: ...
  memory: ...
  nvidia.com/gpu: 1

Allocatable:
  cpu: ...
  memory: ...
  nvidia.com/gpu: 1
```

You can also directly query:

```bash
kubectl get node <GPU_NODE> \
  -o jsonpath='{.status.allocatable.nvidia\.com/gpu}{"\n"}'
```

Expected:

```text
1
```

For an 8-GPU node:

```text
8
```

---

# 5. Understand the critical Kubernetes abstraction

This is the point where you should stop thinking:

> "Kubernetes knows I have an H100."

Instead think:

```text
Kubernetes
     |
     | extended resource
     ↓
nvidia.com/gpu: 1
```

The Kubernetes scheduler doesn't fundamentally care that the physical device is an H100.

The device plugin tells Kubernetes:

> "This node has N NVIDIA GPU resources available."

For example:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

means:

> Schedule this container onto a node where one NVIDIA GPU is available.

---

# 6. Run our first GPU workload

Create:

```bash
cat > gpu-test.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: gpu-test
spec:
  restartPolicy: Never

  containers:
    - name: gpu-test
      image: nvidia/cuda:12.8.1-base-ubuntu24.04

      command:
        - nvidia-smi

      resources:
        limits:
          nvidia.com/gpu: 1
EOF
```

Then:

```bash
kubectl apply -f gpu-test.yaml
```

Check:

```bash
kubectl get pod gpu-test -o wide
```

Then:

```bash
kubectl logs gpu-test
```

You want:

```text
NVIDIA-SMI ...
GPU 0: NVIDIA ...
```

🎯 **This is our first major checkpoint.**

We have now proven:

```text
Kubernetes Pod
      ↓
Container
      ↓
NVIDIA Container Runtime
      ↓
NVIDIA Driver
      ↓
Physical GPU
```

AWS documents essentially this same pattern: request `nvidia.com/gpu` in the container resources and verify with `nvidia-smi`. ([AWS Documentation][1])

# 7. Now make the test more interesting

Instead of just:

```bash
nvidia-smi
```

keep the container alive:

```yaml
command:
  - /bin/bash
  - -c
  - |
    nvidia-smi
    sleep 3600
```

Apply:

```bash
kubectl delete pod gpu-test
kubectl apply -f gpu-test.yaml
```

Then:

```bash
kubectl exec -it gpu-test -- bash
```

Inside:

```bash
nvidia-smi
```

Now you have an interactive GPU container.

# 8. Prove Kubernetes actually assigned the GPU

Inside the container:

```bash
ls -l /dev/nvidia*
```

You should see devices such as:

```text
/dev/nvidia0
/dev/nvidiactl
/dev/nvidia-uvm
```

Now:

```bash
env | grep -i nvidia
```

Depending on the runtime/plugin version, you'll see NVIDIA-related environment configuration.

The important concept is:

```text
Pod requested:

nvidia.com/gpu: 1

        ↓

Scheduler selects GPU node

        ↓

Device plugin allocates physical GPU

        ↓

Container runtime exposes GPU devices

        ↓

Container sees /dev/nvidia0

        ↓

CUDA applications can access GPU
```

# 9. Now test PyTorch

This is our next layer.

We want:

```text
GPU
 ↓
Driver
 ↓
Container
 ↓
CUDA
 ↓
PyTorch
```

Create:

```bash
cat > pytorch-test.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: pytorch-gpu-test
spec:
  restartPolicy: Never

  containers:
    - name: pytorch
      image: pytorch/pytorch:2.7.1-cuda12.8-cudnn9-runtime

      command:
        - python
        - -c
        - |
          import torch

          print("PyTorch version:", torch.__version__)
          print("CUDA available:", torch.cuda.is_available())
          print("CUDA version:", torch.version.cuda)
          print("GPU count:", torch.cuda.device_count())

          if torch.cuda.is_available():
              print("GPU:", torch.cuda.get_device_name(0))

      resources:
        limits:
          nvidia.com/gpu: 1
EOF
```

Run:

```bash
kubectl apply -f pytorch-test.yaml
```

Then:

```bash
kubectl logs pytorch-gpu-test
```

Expected conceptually:

```text
PyTorch version: ...
CUDA available: True
CUDA version: 12.8
GPU count: 1
GPU: NVIDIA H100 80GB HBM3
```

# 11. Now introduce a GPU taint

In production, we normally don't want:

```text
frontend pod
redis pod
nginx pod
random cronjob
monitoring pod
```

landing on expensive H100 nodes.

We therefore commonly dedicate GPU nodes.

Example:

```bash
kubectl taint nodes <GPU_NODE> \
  nvidia.com/gpu=true:NoSchedule
```

Now ordinary workloads cannot schedule there unless they tolerate the taint.

Check:

```bash
kubectl describe node <GPU_NODE> | grep -i taint
```

You should see:

```text
Taints:
  nvidia.com/gpu=true:NoSchedule
```

---

# 12. Add the toleration to our GPU pod

Update:

```yaml
spec:
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
```

So:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-test
spec:
  restartPolicy: Never

  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule

  containers:
    - name: gpu-test
      image: nvidia/cuda:12.8.1-base-ubuntu24.04
      command:
        - nvidia-smi

      resources:
        limits:
          nvidia.com/gpu: 1
```

This gives us:

```text
Taint
  ↓
"Don't put ordinary workloads here"

Toleration
  ↓
"I'm allowed to run here"

GPU resource
  ↓
"I actually require a GPU"
```

### Very important interview point

A toleration **doesn't mean**:

> "Schedule me on the GPU node."

It only means:

> "The taint doesn't prevent me from scheduling there."

The actual GPU requirement comes from:

```yaml
nvidia.com/gpu: 1
```

# 13. Add GPU type selection

Suppose your cluster has:

```text
H100 nodes
H200 nodes
L40S nodes
CPU nodes
```

We don't want a workload blindly landing anywhere.

Inspect labels:

```bash
kubectl get node <GPU_NODE> --show-labels
```

Depending on your EKS/Karpenter configuration, you may have GPU-related labels.

For example:

```yaml
nodeSelector:
  karpenter.k8s.aws/instance-gpu-name: h100
```

AWS currently documents GPU-name based node selection with Karpenter as a way to target a particular GPU type. ([AWS Documentation][2])

So our eventual production pod could conceptually become:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1

tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule

nodeSelector:
  karpenter.k8s.aws/instance-gpu-name: h100
```

Now the intent is:

> "I need one NVIDIA GPU, and specifically an H100-class node."

# 14. One important 2026 update: DRA

Don't worry about implementing it yet.

But understand the evolution:

### Traditional Device Plugin

```text
GPU
 ↓
NVIDIA Device Plugin
 ↓
nvidia.com/gpu: 1
```

It's simple and extremely widely used.

### DRA

```text
GPU
 ↓
NVIDIA DRA Driver
 ↓
ResourceSlice
 ↓
DeviceClass
 ↓
ResourceClaim
 ↓
Pod
```

DRA gives Kubernetes richer information such as:

* GPU model
* GPU memory
* topology
* device attributes
* more expressive allocation
* topology-aware scheduling

AWS currently recommends DRA for **new deployments on Kubernetes 1.34+ when using static capacity provisioning**, while the NVIDIA device plugin remains appropriate for many existing setups and for dynamic Karpenter provisioning. ([AWS Documentation][1])

We will learn DRA later because **you need to understand the old/simple resource model first**.

# 15. Our first failure exercise

This is where the lab becomes useful.

Remove the GPU resource:

```yaml
resources:
  limits:
    cpu: "100m"
    memory: "128Mi"
```

Deploy it.

The pod may run on a CPU node.

Then try:

```bash
kubectl exec -it gpu-test -- nvidia-smi
```

You will likely get something equivalent to:

```text
NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver
```

Why?

Because:

```text
No GPU requested
       ↓
Scheduler doesn't need GPU node
       ↓
Pod lands on CPU node
       ↓
No NVIDIA device
       ↓
nvidia-smi fails
```

This is a very common Kubernetes GPU debugging scenario.

# 16. Second failure exercise — insufficient GPU

Now request:

```yaml
limits:
  nvidia.com/gpu: 2
```

on a node with only:

```text
nvidia.com/gpu: 1
```

Check:

```bash
kubectl get pod gpu-test
```

Then:

```bash
kubectl describe pod gpu-test
```

You should see a scheduling failure similar to:

```text
Insufficient nvidia.com/gpu
```

This teaches the important distinction:

```text
GPU physically exists
        ≠
GPU is schedulable
        ≠
GPU is available
```

# 17. Third failure — taint mismatch

Keep:

```text
nvidia.com/gpu=true:NoSchedule
```

but remove the toleration.

Then:

```bash
kubectl describe pod gpu-test
```

You may see:

```text
untolerated taint
```

Now you've reproduced one of the most common GPU scheduling failures.

# 18. Fourth failure — selector mismatch

Suppose you specify:

```yaml
nodeSelector:
  gpu-type: h200
```

but your cluster only has:

```text
gpu-type=h100
```

Then:

```bash
kubectl describe pod gpu-test
```

could show:

```text
node(s) didn't match Pod's node selector
```

This is exactly the type of failure you've encountered in your EKS work before.

# 19. Build your troubleshooting matrix

| Symptom                             | First command               | Likely layer       |
| ----------------------------------- | --------------------------- | ------------------ |
| `nvidia-smi` fails on EC2           | `nvidia-smi`                | Driver/GPU         |
| GPU works on host, not container    | `docker run --gpus all ...` | Container runtime  |
| GPU works in Docker, not Kubernetes | `kubectl describe node`     | Device plugin      |
| `nvidia.com/gpu` missing            | `kubectl get node ...`      | Device plugin      |
| Pod Pending                         | `kubectl describe pod`      | Scheduler          |
| `Insufficient nvidia.com/gpu`       | `kubectl describe pod`      | Capacity           |
| `untolerated taint`                 | `kubectl describe pod`      | Taints             |
| selector mismatch                   | `kubectl describe pod`      | Affinity/selector  |
| CUDA unavailable                    | PyTorch test                | CUDA/runtime       |
| vLLM fails                          | logs + PyTorch              | vLLM/model/runtime |
