> **AI reliability is not a one-time architecture decision. It's a feedback loop.**

# 2. What is an SLO?

You already know the term.

Let's make it operational.

Suppose your customer says:

> "The AI should feel responsive."

That's not an SLO.

We convert it into something measurable:

```text
Availability:
99.99%

TTFT:
P95 < 1 second

ITL:
P95 < 50 ms

Error rate:
< 0.1%
```

Now we can monitor it.

---

# 3. SLI vs SLO vs SLA

This is an interview favorite.

## SLI

**Service Level Indicator**

The actual measurement.

Example:

```text
P95 TTFT = 820 ms
```

---

## SLO

**Service Level Objective**

The target.

```text
P95 TTFT < 1 second
```

---

## SLA

**Service Level Agreement**

The contractual commitment to the customer.

Example:

```text
99.99% availability
```

with potentially financial consequences.

So:

```text
SLI
 ↓
measurement

SLO
 ↓
engineering target

SLA
 ↓
customer/business commitment
```

---

# 4. Don't confuse SLA and SLO

You may internally have:

```text
SLO:
99.95%
```

while customer contract says:

```text
SLA:
99.9%
```

Why?

Because you want engineering headroom.

```text
SLA
99.9%
     ↑
     │ safety margin
SLO
99.95%
     ↑
     │
internal target
99.99%
```

The exact values depend on business requirements.

# 7. Error budget

If:

```text
SLO = 99.99%
```

then allowed failure is:

```text
0.01%
```

For approximately 30 days:

```text
30 × 24 × 60
= 43,200 minutes
```

Allowed unavailable time:

```text
43,200 × 0.0001
= 4.32 minutes
```

So:

```text
99.99%
≈
4.32 minutes/month
```

This is your **error budget**.

---

# 8. Why error budgets matter

Without error budgets:

```text
Developer:
"Let's deploy the new vLLM version."
```

SRE:

```text
"No! Production is fragile."
```

Developer:

```text
"Yes!"
```

SRE:

```text
"No!"
```

😂

Error budgets turn this into an objective decision.

Suppose:

```text
Error budget remaining:
80%
```

You have room for controlled change.

But:

```text
Error budget remaining:
2%
```

You should be much more conservative.

---

# 9. Error budget isn't just downtime

For AI inference, you might consume error budget through:

```text
request failures
timeouts
TTFT SLO violations
ITL SLO violations
```

depending on how you've defined the SLO.

For example:

```text
1,000,000 requests

5,000 exceed TTFT SLO
```

If your latency SLO says:

```text
99.9% of requests must meet TTFT target
```

then:

```text
budget = 1,000 requests
actual = 5,000
```

You're burning budget rapidly.

# 10. Error budget burn rate

This is more useful than simply:

```text
SLO = 99.99%
```

Suppose your allowed monthly failure rate is:

```text
0.01%
```

but you're currently failing at:

```text
0.1%
```

You're consuming the budget:

```text
10× faster
```

than planned.

That's:

# **10× burn rate**

This should trigger serious investigation.

# 11. Why AI systems can burn budget suddenly

AI workloads are highly nonlinear.

Imagine:

```text
Traffic
   │
   │
   │
   │             /
   │           /
   │         /
   │       /
   │______/____________
             Capacity
```

Below saturation:

```text
latency stable
```

Near saturation:

```text
queue starts growing
```

Beyond saturation:

```text
latency explodes
```

This is classic queueing behavior.

---

# 12. This is why capacity planning matters

Suppose one vLLM replica can sustain:

```text
10,000 output tok/s
```

while meeting:

```text
TTFT P95 < 1s
TPOT P95 < 50ms
```

That is your **SLO-constrained capacity**.

Not:

```text
maximum theoretical throughput
```

This distinction is extremely important.

---

# 13. Sustainable capacity

Define:

```text
C_sustainable
```

as:

> Maximum workload a replica can sustain while satisfying SLOs.

Example:

```text
GPU:
H100

Model:
70B FP8

Replica:
TP4

Sustainable:
8,000 output tok/s
```

Then your capacity planning uses:

```text
8,000
```

not some benchmark peak:

```text
11,000
```

if 11,000 violates TTFT.

---

# 14. Capacity formula

Basic:

```text
Required replicas
=
Demand
───────────────
Sustainable capacity
```

Suppose:

```text
Demand = 50,000 tok/s

Capacity = 8,000 tok/s
```

Then:

```text
50,000 / 8,000
= 6.25
```

So:

```text
7 replicas
```

minimum.

But production shouldn't stop there.

---

# 15. Add headroom

Suppose you want:

```text
30% headroom
```

Then:

```text
Required capacity
=
Demand × 1.3
```

So:

```text
50,000 × 1.3
=
65,000 tok/s
```

Then:

```text
65,000 / 8,000
=
8.125
```

So:

```text
9 replicas
```

Now you have resilience to traffic variation.

---

# 16. HA changes the calculation

Suppose:

```text
9 replicas
```

across:

```text
3 AZs
```

Maybe you want enough capacity to survive losing one AZ.

Then:

```text
AZ A: 3
AZ B: 3
AZ C: 3
```

If AZ C disappears:

```text
6 replicas remain
```

Can six replicas handle demand?

If not, you don't actually have your desired HA posture.

This is:

# **Failure-domain capacity planning**

# 17. N+1

Classic infrastructure concept:

```text
N = required capacity
```

and:

```text
N+1 = required + one failure unit
```

For LLM inference, the failure unit could be:

```text
GPU
node
TP group
replica
AZ
```

This is where multi-GPU models become tricky.

# 18. TP changes the failure domain

Suppose:

```text
TP8
```

means:

```text
1 replica = 8 GPUs
```

If one GPU dies:

```text
Replica fails
```

So:

```text
8 GPUs
```

are one inference failure domain.

Compare:

```text
TP2 × 4 replicas
```

where:

```text
1 GPU failure
```

might affect only:

```text
1 replica
```

This is why:

> **Parallelism is also a reliability decision.**

Not just a performance decision.

# 20. Little's Law

You learned this earlier.

```text
L = λW
```

Where:

```text
L = average number of items in system
λ = arrival rate
W = average time in system
```

For inference:

```text
concurrent requests
≈
request arrival rate
×
average latency
```

Example:

```text
λ = 10 requests/sec

W = 2 sec
```

Then:

```text
L = 10 × 2
  = 20 concurrent requests
```

This is extremely useful for capacity planning.

---

# 21. Why concurrency alone is dangerous

Customer says:

> "We have 500 concurrent users."

You should ask:

```text
Are all 500 generating tokens simultaneously?
```

Because:

```text
500 connected
```

is not necessarily:

```text
500 active decode sequences
```

Maybe:

```text
500 users
↓
20 active requests
↓
480 idle
```

Completely different GPU requirement.

# 22. Token demand is more useful

Imagine:

```text
500 users
```

but:

```text
Input:
5M tokens/min

Output:
500K tokens/min
```

Compare with:

```text
500 users
```

but:

```text
Input:
50M tokens/min

Output:
10M tokens/min
```

Same users.

20× difference in input demand.

So:

> **User count is a business metric. Token rate is an infrastructure metric.**

🔥 Memorize that.

# 23. Arrival rate vs service rate

Suppose:

```text
Incoming:
100 requests/sec
```

and your system can sustainably process:

```text
120 requests/sec
```

Fine.

But if:

```text
Incoming:
150 requests/sec
```

then:

```text
arrival rate > service rate
```

Queue grows.

```text
λ > μ
```

where:

```text
λ = arrival
μ = service
```

This is the fundamental saturation condition.

Warm system.

### Step 4


# 27. The saturation curve

You want to discover:

```text
                 LATENCY
                    │
                    │                    /
                    │                  /
                    │               /
                    │            /
                    │         /
                    │_______/
                    └────────────────────► LOAD
                              ↑
                           SATURATION
```

Before the knee:

```text
throughput rises
latency acceptable
```

After the knee:

```text
queue explodes
latency explodes
```

The knee is more important than maximum throughput.

# 30. Autoscaling isn't capacity planning

This is another key distinction.

### Capacity planning

Answers:

> How much infrastructure do we need?

### Autoscaling

> When should we add/remove infrastructure?

Don't use:

```text

```

to hide a fundamentally incorrect capacity model.


```text

```

Karpenter provisions:

```text
10:00:45
```




# 33. Therefore warm capacity

For bursty inference:

```text
Desired:
10 GPUs

Warm:
4 GPUs

Cold:
6 GPUs
```

At spike:

```text
4 warm GPUs
+
6 provisioned
```

instead of:

```text

```

This reduces reaction time.

For dev/test:

```text

```

Fantastic cost savings.

But:

```text

 ↓

 ↓

 ↓
```


# 36. Error budget + autoscaling

Now combine them.

Suppose:

```text
TTFT SLO:
P95 < 1 sec
```

and:

```text
TTFT:
700ms → 1.5sec
```

