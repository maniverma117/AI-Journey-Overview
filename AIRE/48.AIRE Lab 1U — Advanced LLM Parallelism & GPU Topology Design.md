# Lab 1U — Advanced LLM Parallelism & GPU Topology Design

Now we move from **“how many GPUs?”** to the harder question:

> **“How should those GPUs be arranged?”**

This is where many AI infrastructure designs go wrong.

Having 8 H100s does **not** automatically mean:

```text
TP=8
```

The same 8 GPUs could be:

```text
TP8
```

or:

```text
2 × TP4
```

or:

```text
4 × TP2
```

or:

```text
8 × TP1
```

and these architectures can have **very different latency, throughput, availability, and cost characteristics**.

---

# 1. The four fundamental parallelism strategies

For LLM inference:

```text
                    MODEL
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
       TP             PP            DP
 Tensor Parallel   Pipeline       Data
                   Parallel      Parallel
        │             │             │
        └─────────────┼─────────────┘
                      ▼
                     EP
               Expert Parallel
```

And modern production systems can combine them:

```text
TP × PP × DP × EP
```

---

# 2. Tensor Parallelism — TP

Suppose one Transformer layer contains:

```text
W
```

Instead of one GPU calculating the entire operation:

```text
GPU0
 │
 └── entire matrix
```

we split the matrix:

```text
              Matrix
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
     GPU0     GPU1     GPU2
     part     part     part
```

For:

```text
TP=4
```

the computation is distributed across:

```text
GPU0
GPU1
GPU2
GPU3
```

---

# 3. Why TP exists

Two primary reasons:

### Reason 1 — Model doesn't fit

Example:

```text
70B BF16
≈ 140GB weights
```

One:

```text
H100 = 80GB
```

cannot hold it.

So:

```text
TP2
```

can distribute the weights.

Roughly:

```text
140GB / 2
=
70GB/GPU
```

before runtime/KV/overhead.

Now it can potentially fit.

---

# 4. Reason 2 — Increase compute capacity

Even if the model fits on one GPU, TP can distribute computation.

But this introduces:

```text
communication
```

So:

> **TP is not free performance.**

---

# 5. The TP communication problem

Imagine:

```text
GPU0 ─────┐
GPU1 ─────┤
GPU2 ─────┼── collective communication
GPU3 ─────┤
GPU4 ─────┤
GPU5 ─────┤
GPU6 ─────┤
GPU7 ─────┘
```

Each step may require:

```text
AllReduce
AllGather
ReduceScatter
```

depending on the implementation.

Therefore:

```text
more GPUs
```

doesn't necessarily mean:

```text
proportionally faster
```

---

# 6. TP scaling efficiency

Suppose:

```text
TP1 = 100 units
```

Ideal:

```text
TP2 = 200
TP4 = 400
TP8 = 800
```

Real:

```text
TP2 = 185
TP4 = 330
TP8 = 500
```

Why?

```text
computation
+
communication
+
synchronization
```

increase.

So we care about:

```text
Scaling efficiency
=
Actual speedup / Ideal speedup
```

For TP8:

```text
500 / 800
=
62.5%
```

Not great.

---

# 7. GPU topology now becomes critical

Consider:

```text
GPU0 ↔ GPU1
GPU1 ↔ GPU2
GPU2 ↔ GPU3
```

versus:

```text
GPU0 ─ NVLink ─ GPU1
GPU2 ─ NVLink ─ GPU3

GPU0 ─ PCIe ─ GPU2
```

The communication characteristics are different.

For TP:

> **Topology is part of the architecture.**

---

# 8. NVLink vs PCIe

Conceptually:

```text
NVLink
GPU ↔ GPU
high bandwidth
low latency
```

while:

```text
PCIe
GPU ↔ host/device
general-purpose interconnect
```

For communication-heavy TP:

```text
NVLink/NVSwitch
```

is highly valuable.

---

# 9. H100 SXM vs PCIe

This is one reason you cannot simply say:

> “It's an H100, so performance will be the same.”

H100 configurations differ.

An H100 SXM system can provide extremely high GPU-to-GPU connectivity through NVLink/NVSwitch-class systems, whereas PCIe-based systems have different communication characteristics.

For example, NVIDIA lists H100 SXM with **900 GB/s NVLink bandwidth**.

So when designing TP:

```text
GPU model
+
form factor
+
topology
```

matter.

---

# 10. TP2 vs TP4

Suppose your model fits:

```text
TP2
```

and:

```text
TP4
```

both work.

Don't automatically choose TP4.

Compare:

```text
                 TP2       TP4
--------------------------------
VRAM/GPU          ↑         ↓
communication     ↓         ↑
replica size      2 GPU     4 GPU
failure unit      2 GPU     4 GPU
latency           ?         ?
throughput        ?         ?
cost/request      ?         ?
```

Benchmark.

---

# 11. Failure granularity

This is extremely important for reliability.

Suppose:

```text
TP8
```

means:

```text
8 GPUs = 1 replica
```

If:

```text
GPU5 dies
```

then:

```text
entire TP8 replica
```

is unavailable.

So:

```text
8 GPUs
→ 1 failure unit
```

Compare:

```text
4 × TP2
```

Now:

```text
GPU5 dies
 ↓
one TP2 replica lost
 ↓
3 replicas remain
```

Much smaller blast radius.

---

# 12. TP8 versus multiple replicas

Suppose you have:

```text
8 H100 GPUs
```

Architecture A:

```text
TP8

8 GPUs
  ↓
1 replica
```

Architecture B:

```text
4 × TP2

GPU GPU
 │   │
TP2 replica

×4
```

Architecture B may provide:

```text
better availability
more routing flexibility
better request-level parallelism
smaller failure units
```

while Architecture A may provide:

```text
more model compute per replica
larger effective memory pool
potentially better single-request performance
```

depending on workload/model.

---

# 13. The architectural tradeoff

You are balancing:

```text
                    TP size
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   model fitting    latency        replica size
        │              │              │
        ▼              ▼              ▼
     memory        communication    failure
```

This is why GPU topology decisions are architecture decisions.

---

# 14. Data Parallelism — DP

DP is fundamentally different.

Instead of splitting one model across GPUs:

```text
TP:

GPU0 + GPU1 + GPU2 + GPU3
        ↓
   ONE model replica
```

DP does:

```text
DP:

GPU0 → model replica A
GPU1 → model replica B
GPU2 → model replica C
GPU3 → model replica D
```

Now incoming requests can be distributed.

---

# 15. DP is excellent for throughput

Suppose:

```text
TP1
```

can serve:

```text
100 requests/sec
```

Then:

```text
DP4
```

can potentially approach:

```text
400 requests/sec
```

assuming the workload scales well and routing/scheduling overhead doesn't dominate.

The model is replicated.

---

# 16. DP requires enough memory per GPU

If:

```text
70B FP8
```

fits on:

```text
1 × H100
```

then:

```text
DP8
```

is straightforward conceptually.

But if it requires:

```text
TP4
```

then:

```text
DP8 × TP4
```

means:

```text
32 GPUs
```

because:

```text
total GPUs = DP × TP
```

---

# 17. The formula

Memorize:

```text
Total GPUs
=
TP × PP × DP
```

For MoE:

```text
EP
```

also influences the actual placement/configuration.

Example:

```text
TP=4
PP=2
DP=4
```

means:

```text
4 × 2 × 4
=
32 GPUs
```

---

# 18. Pipeline Parallelism — PP

Now imagine a model has:

```text
80 Transformer layers
```

Instead of every GPU holding every layer:

```text
TP
```

we can split layers:

```text
GPU group A
layers 1–20

GPU group B
layers 21–40

GPU group C
layers 41–60

GPU group D
layers 61–80
```

That's pipeline parallelism.

---

# 19. PP architecture

```text
Request
   │
   ▼
Stage 1
Layers 1–20
   │
   ▼
Stage 2
Layers 21–40
   │
   ▼
Stage 3
Layers 41–60
   │
   ▼
Stage 4
Layers 61–80
   │
   ▼
Response
```

Each stage processes activations from the previous stage.

---

# 20. Pipeline bubble

The problem:

```text
Stage 1 → Stage 2 → Stage 3 → Stage 4
```

can't necessarily keep all stages busy for every single request.

You can get:

```text
Stage 1: █████
Stage 2:   █████
Stage 3:     █████
Stage 4:       █████
```

Those gaps are:

> **Pipeline bubbles.**

Microbatching reduces this inefficiency.

---

# 21. TP vs PP

A useful simplified comparison:

|                      | TP                      | PP                |
| -------------------- | ----------------------- | ----------------- |
| Splits               | tensor operations       | layers            |
| Communication        | frequent                | between stages    |
| Topology sensitivity | very high               | high              |
| Pipeline bubbles     | no                      | yes               |
| Main use             | model fitting / compute | very large models |
| Complexity           | high                    | high              |

---

# 22. Combining TP + PP

Suppose:

```text
80-layer model
```

You choose:

```text
TP4
PP2
```

Architecture:

```text
Stage 1
 ├── GPU0
 ├── GPU1
 ├── GPU2
 └── GPU3

Stage 2
 ├── GPU4
 ├── GPU5
 ├── GPU6
 └── GPU7
```

Total:

```text
TP × PP
=
4 × 2
=
8 GPUs
```

Now each stage internally uses TP4.

---

# 23. Then add DP

Suppose:

```text
TP4 × PP2 × DP4
```

Total:

```text
4 × 2 × 4
=
32 GPUs
```

Architecture:

```text
             DP
      ┌──────┼──────┐
      ▼      ▼      ▼
   replica replica replica ...
      │
     PP2
      │
   ┌──┴──┐
   ▼     ▼
stage1 stage2
   │     │
  TP4   TP4
```

This is getting into serious distributed inference.

---

# 24. Expert Parallelism — EP

Now consider a Mixture-of-Experts model.

Instead of every token passing through all experts:

```text
Token
 ↓
Expert 1
Expert 2
Expert 3
...
Expert N
```

the model selects a subset.

For example:

```text
Token
 ↓
router
 ├── Expert 3
 └── Expert 17
```

This creates another distribution problem.

---

# 25. Expert Parallelism architecture

```text
               Router
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    GPU0       GPU1       GPU2
   Expert     Expert     Expert
      │          │          │
      └──── communication ──┘
```

Tokens may need to move between GPUs.

This makes:

```text
AllToAll
```

particularly important.

---

# 26. EP networking

For MoE:

```text
token routing
 ↓
expert assignment
 ↓
GPU-to-GPU communication
```

can create huge communication traffic.

Therefore:

```text
NVLink
NVSwitch
PCIe
NIC
network
```

all become important.

For multi-node MoE:

```text
EFA/RDMA
```

can become a major performance factor.

---

# 27. Topology-aware architecture

Imagine:

```text
Node A
 ├── GPU0
 ├── GPU1
 ├── GPU2
 └── GPU3

Node B
 ├── GPU4
 ├── GPU5
 ├── GPU6
 └── GPU7
```

If your TP group is:

```text
GPU0–GPU7
```

some communication crosses:

```text
network
```

instead of:

```text
NVLink/NVSwitch
```

Potentially huge difference.

---

# 28. TP group placement rule

A strong production principle:

> **Keep tightly communicating GPUs inside the strongest available topology boundary whenever possible.**

For example:

```text
TP4
```

prefer:

```text
same tightly connected GPU domain
```

rather than randomly:

```text
GPU0
GPU7
GPU13
GPU21
```




# 35. KV cache implications

Remember Lab 1T.

If you use:

```text
DP4
```

you effectively have:

```text
4 independent replicas
```

and therefore:

```text
4 independent KV cache populations
```

Routing matters.

If a request returns to the same replica:

```text
prefix cache reuse
```

may improve.

Random routing can reduce locality.

# 37. TP and autoscaling

Suppose:

```text
TP4
```

one replica requires:

```text
4 GPUs
```

Scaling:

```text
1 replica = 4 GPUs
2 replicas = 8 GPUs

```

You cannot easily scale:

```text

```

because the replica unit is TP4.

Therefore:

> **Parallelism defines the granularity of autoscaling.**

# Lab 1U — Architecture Challenge

Customer gives you:

```text
Model: 70B
Precision: FP8
Context: 128K

Available:
16 × H100 80GB

SLO:
P95 TTFT < 1s
P95 TPOT < 50ms

Availability:
99.99%

```

```text

P95 TTFT = 750ms
P95 TPOT = 45ms
capacity = 25 RPS

P95 TTFT = 680ms
P95 TPOT = 40ms
```

Now reason carefully.

### Question 1

Which configurations meet the SLO?

### Question 2

How many GPUs per replica?

### Question 3

How many replicas are required for 30 RPS?

### Question 4

Can you satisfy N+1 with only 16 GPUs?

### Question 5

Would you choose TP4 or TP8?

### Question 6

What additional benchmark/topology information do you require?

### Question 7

If TP8 requires one 8-GPU tightly connected node, what happens if that node fails?

### Question 8

Would `2 × TP8` or `4 × TP4` be the better production architecture? **Defend it from performance, availability, scaling and cost perspectives.**
