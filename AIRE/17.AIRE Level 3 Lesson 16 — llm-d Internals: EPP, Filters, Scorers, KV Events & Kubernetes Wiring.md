# 1. First: What Exactly Is llm-d?

Let's remove some confusion.

llm-d is **not**:

```text
a replacement for vLLM
```

and not:

```text
another GPU runtime
```

and not:

```text
Kubernetes autoscaler
```

Instead:

```text
                    llm-d
                      │
          ┌───────────┴────────────┐
          │                        │
       Routing                 Scheduling
          │                        │
          └───────────┬────────────┘
                      ▼
                   vLLM
                      │
                      ▼
                    GPU
```

Current llm-d supports model servers including vLLM, SGLang and TensorRT-LLM. The model server remains the compute layer; llm-d provides inference-aware routing/orchestration around it. ([Llm-D][2])

# 2. The Most Important Architecture

Memorize this:

```text
                    ┌──────────────┐
                    │    Client    │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │   Gateway    │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ llm-d Proxy  │
                    └──────┬───────┘
                           │
                      ext-proc
                           │
                           ▼
                    ┌──────────────┐
                    │     EPP      │
                    │              │
                    │  Scheduler   │
                    └──────┬───────┘
                           │
                 ┌─────────┼─────────┐
                 │         │         │
                 ▼         ▼         ▼
               Queue       KV      Prefix
                 │         │         │
                 └─────────┼─────────┘
                           ▼
                    Filter → Score
                           │

                           │

                    │    vLLM      │

                    └──────┬───────┘

```

There are actually **two different data planes** involved:

### Request data

```text
Client
 ↓
Proxy
 ↓
vLLM
```

### Decision data

```text
vLLM / Kubernetes / KV events
          ↓
      EPP data layer
          ↓
       scheduler
```

That distinction is extremely important.

# 3. Why EPP Doesn't Directly Execute Inference

EPP doesn't generate tokens.

It doesn't run:

```text
CUDA
```

It doesn't execute:

```text
attention
```

It doesn't own:

```text
KV cache
```

Instead:

```text
EPP
 ↓
decision
 ↓
vLLM
 ↓
actual inference
```

So:

> **EPP is a control-plane-like decision component sitting directly in the inference request path.**

That makes its latency important.

If EPP takes:

```text
500 ms
```

to choose a backend, you've already destroyed a 1-second TTFT SLO.

# 4. The Request Lifecycle

Let's trace one request extremely carefully.

Suppose the client sends:

```json
{
  "model": "Qwen/Qwen3-32B",
  "messages": [
    {
      "role": "user",
      "content": "Explain Kubernetes."
    }
  ],
  "stream": true
}
```

The flow is:

```text
1. Client
      ↓
2. Gateway
      ↓
3. HTTPRoute
      ↓
4. InferencePool
      ↓
5. Proxy
      ↓
6. EPP
      ↓
7. Parse request
      ↓
8. Build candidate endpoints
      ↓
9. Filter
      ↓
10. Score
      ↓
11. Pick
      ↓
12. Return endpoint
      ↓
13. Proxy forwards request
      ↓
14. vLLM
      ↓
15. GPU
```

The important part:

```text
EPP does NOT simply look at:
"Which pod exists?"
```

It looks at:

```text
"Which pod is the best destination for THIS request?"
```

# 5. Kubernetes Discovery

How does EPP know which vLLM pods exist?

One source is Kubernetes.

Suppose:

```text
Pod 1
Pod 2
Pod 3
Pod 4
```

with:

```yaml
labels:
  app: qwen
```

The `InferencePool` selects them.

Current `InferencePool` is a `v1` API in the `inference.networking.k8s.io` group and uses a label selector plus target ports to define inference endpoints. ([Llm-D][3])

Conceptually:

```yaml
apiVersion: inference.networking.k8s.io/v1
kind: InferencePool
metadata:
  name: qwen-pool

spec:
  selector:
    matchLabels:
      app: qwen

  targetPorts:
    - number: 8000
```

Which means:

```text
InferencePool
     │
     │ selector
     ▼
Pods matching app=qwen
```

---

# 6. Why InferencePool Is Not Just a Service

This is subtle.

A normal Kubernetes Service says:

```text
I have these backend pods.
```

InferencePool says:

```text
I have these inference endpoints
AND
I want an Endpoint Picker to make intelligent inference decisions.
```

Current InferencePool semantics treat each selected `podIP:port` as an endpoint for EPP. A pod can expose multiple inference endpoints on different ports, which matters for data-parallel deployments. ([Llm-D][3])

So:

```text
Pod
 ├── port 8000 → endpoint A
 └── port 8001 → endpoint B
```

can conceptually become:

```text
InferencePool
 ├── A
 └── B
```

That's useful when one pod contains multiple logical model-server endpoints.

# 7. HTTPRoute

Now we need to connect the outside world.

Conceptually:

```text
Gateway
   ↓
HTTPRoute
   ↓
InferencePool
```

Example:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute

metadata:
  name: qwen-route

spec:
  parentRefs:
    - name: my-gateway

  rules:
    - backendRefs:
        - group: inference.networking.k8s.io
          kind: InferencePool
          name: qwen-pool
          port: 8000
```

Current llm-d documentation shows this pattern: traffic is matched by an `HTTPRoute`; when its backend is an `InferencePool`, the request is handed to the EPP for inference-aware selection. ([Llm-D][4])

So:

```text
HTTPRoute
    │
    ▼
InferencePool
    │
    ▼
EPP
    │
    ▼
vLLM endpoint
```

# 8. Where Envoy Comes In

This is another place people get confused.

The architecture can be:

```text
Client
 ↓
Envoy
 ↓
EPP
 ↓
vLLM
```

Envoy is responsible for proxying.

EPP is responsible for selecting.

Current llm-d uses Envoy's **External Processing (`ext-proc`) protocol** to integrate the proxy and EPP. ([Llm-D][1])

Conceptually:

```text
                Envoy
                  │
                  │
             "I have a request.
              Where should it go?"
                  │
                  ▼
                 EPP
                  │
                  │
             "Send to
              10.0.3.42:8000"
                  │
                  ▼
                Envoy
                  │
                  ▼
                vLLM
```

---

# 9. Why `ext-proc`?

Because Envoy already knows how to:

```text
receive HTTP
manage connections
stream traffic
forward requests
handle responses
```

EPP doesn't need to become a full proxy.

Instead:

```text
Envoy
=
traffic engine

EPP
=
decision engine
```

That's a very clean architecture.

# 10. The EPP Has Multiple Responsibilities

Current EPP architecture has several major pieces:

```text
EPP
│
├── Request Parser
│
├── Flow Control
│
├── Scheduler
│
├── Data Layer
│
└── Plugins
```

The current documentation explicitly describes request parsing, flow control, scheduling, and an asynchronous data layer that consumes Kubernetes/model-server/KV information. ([Llm-D][1])

Let's go through each.

# 11. Request Parser

The EPP needs to understand:

```text
What model?
What request type?
How many input tokens?
What SLO?
What objective?
What session?
```

For example:

```json
{
  "model": "qwen",
  "messages": [...]
}
```

becomes an internal:

```text
InferenceRequest
```

Conceptually:

```text
InferenceRequest
├── model
├── prompt
├── input tokens
├── output limit
├── streaming
├── objective
├── SLO
└── session information
```

Current EPP docs describe an `InferenceRequest` as the structured internal representation created by the parser. ([Llm-D][5])

---

# 12. Why Tokenization Matters

Suppose:

```text
Request A
input = 500 tokens

Request B
input = 50,000 tokens
```

Both are:

```text
1 HTTP request
```

But they are **not equivalent workloads**.

The router needs to understand that.

Because:

```text
50K tokens
```

may cause:

```text
huge prefill
large KV allocation
higher TTFT
```

while:

```text
500 tokens
```

is much cheaper.

This is why LLM-aware routing needs request semantics, not just HTTP metadata.

---

# 13. Flow Control

Now something new.

Imagine:

```text
Tenant A
  ↓
10,000 requests

Tenant B
  ↓
10 requests
```

If Tenant A can consume every inference slot:

```text
Tenant B
 ↓
starved
```

That's the classic:

> **noisy neighbor problem**

Current EPP includes flow-control mechanisms for prioritization and fairness across flows, including configurable fairness and ordering policies. ([Llm-D][1])

---

# 14. Fairness

Think:

```text
                     Inference Pool
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          Tenant A      Tenant B      Tenant C
           70%            20%            10%
```

You might define:

```text
priority
+
fairness
+
ordering
```

The exact policy depends on the application.

The important architecture is:

```text
Request
  ↓
Flow identification
  ↓
Priority
  ↓
Fairness
  ↓
Scheduling
```

This is becoming much closer to a distributed scheduler than a traditional load balancer.

---

# 15. Request Priorities

Imagine:

```text
Priority 1:
Emergency customer request

Priority 5:
Normal chatbot

Priority 10:
Batch summarization
```

You don't necessarily want:

```text
FIFO
```

to process everything equally.

Instead:

```text
priority
 ↓
admission
 ↓
scheduling
```

Current llm-d exposes `InferenceObjective` to define performance goals such as priority and latency for model workloads. ([Llm-D][6])

# 16. SLO-Aware Routing

This gets really interesting.

Suppose request A says:

```text
TTFT < 500ms
```

and request B says:

```text
TTFT < 2 seconds
```

They shouldn't necessarily receive identical treatment.

Current llm-d exposes request headers for TTFT and TPOT SLO targets, including:

```text
x-llm-d-slo-ttft-ms
x-llm-d-slo-tpot-ms
```

which can be used by admission/load-balancing plugins. ([Llm-D][7])

So the request can carry its performance objective.

---

# 17. This Changes Routing

Without SLO:

```text
Request
 ↓
choose best endpoint
```

With SLO:

```text
Request
 ↓
What SLO?
 ↓
Can endpoint satisfy it?
 ↓
If yes → candidate
If no → reject/defer/choose another
```

Now the router becomes:

> **SLO-aware inference scheduler.**

---

# 18. Scheduler: Filter → Score → Pick

This is the **single most important llm-d implementation concept**.

```text
                  Endpoints
                      │
                      ▼
                   FILTER
                      │
             remove bad candidates
                      │
                      ▼
                    SCORE
                      │
              rank remaining
                      │
                      ▼
                    PICK
                      │
                      ▼
                   Endpoint
```

Current llm-d's scheduler explicitly follows this lifecycle. ([Llm-D][5])

---

# 19. FILTER

Suppose you have:

```text
A
B
C
D
E
```

Filter might remove:

```text
B → unhealthy
D → wrong model
E → insufficient SLO headroom
```

Remaining:

```text
A
C
```

Filters answer:

> **Can this endpoint serve the request at all?**

---

# 20. SCORE

Now:

```text
A
C
```

are both valid.

Scoring answers:

> **Which valid endpoint is better?**

For example:

```text
A:
prefix match = 80%
queue = 5
KV = 60%

C:
prefix match = 10%
queue = 1
KV = 30%
```

Depending on weights, A might still win.

---

# 21. PICK

Finally:

```text
A = 0.83
C = 0.71
```

Picker:

```text
A
```

Current llm-d provides picker plugins such as max-score selection and weighted/random approaches. ([Llm-D][5])

---

# 22. Why Separate Filter and Score?

This is good software architecture.

You don't want:

```text
one giant function
```

like:

```python
choose_endpoint(request, endpoints):
    # 2000 lines
```

Instead:

```text
Filter:
"Is it eligible?"

Scorer:
"How good is it?"

Picker:
"Which one wins?"
```

That means you can swap policies independently.

```text
100 endpoints
```

# 24. Prefix Cache Affinity Filter

Current llm-d has a `prefix-cache-affinity-filter`. It identifies "sticky" endpoints with high prefix-cache affinity and includes a TTFT load gate so that cache stickiness can be broken if the preferred endpoint becomes significantly slower. ([Llm-D][5])

That last part is extremely important.

Remember our previous discussion:

```text
cache hit
```

is not everything.

Suppose:

```text
vLLM-A
prefix hit = 95%
queue = 100

vLLM-B
prefix hit = 0%
queue = 1
```

You probably shouldn't keep sending traffic to A just because it has the prefix.

The load gate protects against this.

---

# 25. SLO Headroom Filter

Another filter:

```text
slo-headroom-tier-filter
```

Conceptually:

```text
Request SLO:
TTFT < 1 sec
```

Endpoint:

```text
predicted TTFT = 400ms
```

Good.

Endpoint:

```text
predicted TTFT = 1.8 sec
```

Bad.

So:

```text
Endpoint
 ↓
Can it satisfy SLO?
```

This is much more intelligent than:

```text
GPU utilization < 80%
```

```text
prefill endpoints
```

and:


Current llm-d provides dedicated prefill/decode filters based on endpoint labels. ([Llm-D][5])

Conceptually:

```text
Request
 ↓
Need prefill?
 ↓
prefill filter

P endpoints
```

and:

```text
Decode request

 ↓
D endpoints
```

# 27. Scorers

Now the fun part.

Current llm-d includes scorers such as:

```text
KV cache utilization
latency
LoRA affinity
prefix cache
queue depth
running request count
token load
session affinity
```

among others. ([Llm-D][5])

This means an endpoint can be evaluated from multiple dimensions.

---

# 28. Queue Depth Scorer

Simple:

```text
Endpoint A
queue = 2

Endpoint B
queue = 20
```

A gets a better score.

But remember:

> Queue depth alone is not enough.

Because:

```text
A:
queue = 2
each request = 50K tokens

B:
queue = 8
each request = 500 tokens
```

B could actually have lower workload.

That's why token-load scoring exists too.

---

# 29. Token Load Scorer

Conceptually:

```text
total token load =
input tokens + expected output tokens
```

Example:

```text
Endpoint A:
5 requests × 10K tokens
= 50K

Endpoint B:
10 requests × 500 tokens
= 5K
```

Queue count says:

```text
A = 5
B = 10
```

Token load says:

```text
A = 50K
B = 5K
```

So B might be much healthier.

Current llm-d exposes a token-load scorer for this reason. ([Llm-D][5])

---

# 30. KV Cache Utilization Scorer

Suppose:

```text
A:
KV = 40%

B:
KV = 90%
```

A is generally more attractive.

Because:

```text
B
 ↓
less memory headroom
 ↓
greater preemption/OOM pressure
```

Current llm-d includes a KV-cache-utilization scorer that prefers endpoints with lower utilization. ([Llm-D][5])

---

# 31. Prefix Scorer

Now:

```text
Request prefix:
A B C D E F
```

Endpoint A has:

```text
A B C D E F
```

Endpoint B has:

```text
A B C
```

Endpoint C has:

```text
X Y Z
```

Prefix match:

```text
A = 6 tokens
B = 3
C = 0
```

So:

```text
A > B > C
```

This is the basic intuition behind prefix-cache scoring.

---

# 32. Precise Prefix Cache

Here's where we go deeper.

Approximate routing might say:

```text
"I previously sent similar requests to A."
```

But that's not necessarily the actual current cache state.

Cache could have been evicted.

Precise routing uses actual cache events.

Current llm-d's KV Cache Indexer receives KV events from model servers and maintains a mapping of cache block keys to pods. ([Llm-D][8])

---

# 33. KV Events

Model server changes its cache.

For example:

```text
BlockStored
```

means:

```text
this KV block now exists
```

Then:

```text
BlockRemoved
```

means:

```text
this block was evicted
```

And:

```text
AllBlocksCleared
```

means:

```text
cache reset
```

Current llm-d documentation describes these event types and says vLLM/SGLang publish them through ZMQ. ([Llm-D][8])

---

# 34. KV Event Architecture

This is worth memorizing:

```text
                 vLLM
                  │
             KV cache changes
                  │
                  ▼
              KV Events
                  │
                ZMQ
                  │
                  ▼
          ┌────────────────┐
          │ KV Indexer     │
          └───────┬────────┘
                  │
           block → pod map
                  │
                  ▼
                EPP
                  │
                  ▼
          prefix-cache scorer
                  │
                  ▼
               Router
```

This is a beautiful architecture.

The model server remains responsible for the cache.

The router maintains a **view** of the cache.

---

# 35. What Does the Index Actually Store?

Conceptually:

```text
Block Hash
      ↓
Which pods have it?
```

Example:

```text
hash-A → Pod 1, Pod 3
hash-B → Pod 2
hash-C → Pod 1
```

Then request:

```text
prefix hashes:
A → B → C
```

The index can calculate:

```text
Pod 1:
A + C

Pod 2:
B

Pod 3:
A
```

and determine which endpoint has the strongest prefix locality.

The current KV indexer uses a `block key → pods` mapping derived from KV events. ([Llm-D][8])

---

# 36. Why This Is Eventually Consistent

This is another advanced point.

The EPP isn't physically inside the vLLM process.

Therefore:

```text
vLLM cache changes
       ↓
KV event
       ↓
network
       ↓
indexer
       ↓
EPP
```

There is some delay.

So EPP's view is:

```text
near-real-time
```

not necessarily:

```text
perfectly synchronous
```

This is why routing systems need graceful behavior when the cache view is stale.

---

# 37. Cache Index Failure

Suppose:

```text
vLLM cache = healthy
```

but:

```text
KV Indexer = down
```

Does inference necessarily stop?

No.

Ideally:

```text
cache-aware optimization unavailable
```

rather than:

```text
entire inference platform unavailable
```

This illustrates a good production principle:

> **Optimization dependencies should degrade gracefully whenever possible.**

You don't want:

```text
KV index down
 ↓
all inference stops
```

if you can safely fall back to:

```text
queue/load routing
```

# 38. Weighted Scoring

Current EPP scheduling profiles allow multiple scorers with weights. ([Llm-D][5])

For example:

```yaml
schedulingProfiles:
- name: default

  plugins:

  - pluginRef: prefix-cache-scorer
    weight: 3.0

  - pluginRef: kv-cache-utilization-scorer
    weight: 2.0

  - pluginRef: queue-scorer
    weight: 2.0

  - pluginRef: max-score-picker
```

Current llm-d documentation gives this style of production-oriented configuration as an example. ([Llm-D][9])

---

# 39. Understand the Mathematics

Suppose:

```text
Prefix score = 0.9
weight = 3

KV score = 0.8
weight = 2

Queue score = 0.5
weight = 2
```

Then:

$$
Score =
(0.9 \times 3)
+
(0.8 \times 2)
+
(0.5 \times 2)
$$

$$
=2.7+1.6+1.0
$$

$$
=5.3
$$

Another endpoint:

```text
Prefix = 0.3
KV = 0.9
Queue = 0.9
```

gives:

$$
(0.3\times3)+(0.9\times2)+(0.9\times2)
$$

$$
=0.9+1.8+1.8
$$

$$
=4.5
$$

Therefore:

```text
Endpoint A = 5.3
Endpoint B = 4.5
```

A wins.

This is exactly why **weights matter**.

---

# 40. Weight Selection Is an Architecture Decision

Suppose:

```text
prefix weight = 10
queue weight = 1
```

You are telling the scheduler:

> Cache locality is overwhelmingly more important than load.

Potentially dangerous.

Instead:

```text
prefix = 3
KV = 2
queue = 2
```

says:

```text
cache matters
but don't overload cache-hot endpoints
```

This is not just YAML.

It encodes your **performance policy**.

# 41. Session Affinity

Suppose:

```text
Session 123
```

previously used:

```text
vLLM-3
```

You might want future requests from the same session to prefer:

```text
vLLM-3
```

because it may retain useful context/prefix state.

Current llm-d includes a session-affinity scorer. ([Llm-D][5])

Conceptually:

```text
Session
 ↓
previous endpoint
 ↓
affinity
 ↓
score boost
```

But again:

```text
affinity != absolute stickiness
```

because the endpoint may become overloaded.

---

# 42. LoRA Affinity

Suppose you're serving:

```text
Base model:
Qwen 32B
```

with adapters:

```text
customer-A
customer-B
customer-C
```

If a request needs:

```text
customer-B adapter
```

and endpoint 3 already has it loaded:

```text
Endpoint 3
 ↓
LoRA B loaded
```

sending the request there may be much cheaper.

Current llm-d includes a LoRA-affinity scorer. ([Llm-D][5])

This becomes important for:

```text
multi-tenant inference
```

# 43. Now Combine Everything

Suppose:

```text
Request:
model = Qwen
prefix = X
LoRA = customer-B
SLO TTFT = 1 sec
```

Endpoints:

```text
A:
prefix hit
LoRA loaded
queue = 20
KV = 80%

B:
no prefix
LoRA loaded
queue = 3
KV = 40%

C:
prefix hit
LoRA absent
queue = 2
KV = 30%
```

A naive load balancer:

```text
C
```

because queue = 2.

But intelligent routing evaluates:

```text
prefix
+
LoRA
+
queue
+
KV
+
SLO
```

Maybe:

```text
B
```

wins.

Or:

```text
A
```

if prefix reuse is extremely valuable and its latency still meets SLO.

That's what the EPP is solving.

# 44. The Data Layer

Where does all this information come from?

Current EPP documentation describes an asynchronous data layer consuming information from:

```text
Kubernetes API
```

# 45. Why Asynchronous?

You don't want EPP to make every routing decision by synchronously asking:

```text
Kubernetes:
"Is pod alive?"

vLLM:
"What's your queue?"

KV:
"What cache blocks do you have?"
```

for every request.

That would be:

```text
request
 ↓
3 network calls
 ↓
wait
 ↓
route
```

Terrible.

Instead:

```text
background watchers
        ↓
local state
        ↓
fast routing decision
```

This is a classic distributed-systems optimization.

---

# 46. Local State vs Source of Truth

Kubernetes remains source of truth for:

```text
Pod existence
labels
ports
readiness
```

vLLM is source of truth for:

```text
running requests
KV cache
model state
```

EPP maintains:

```text
routing-oriented view
```

This is a very important architecture pattern:

> **The router maintains derived state optimized for fast decisions.**

# 56. Failure Scenario: EPP Down

Suppose:

```text
vLLM healthy
```

```text

```

Potentially:

```text

```

even though the model servers themselves are healthy.

Therefore EPP becomes part of the critical request path.

Production architecture should therefore consider:

```text
multiple EPP instances
+
anti-affinity
+
PDB
+
readiness
+
resource limits
+
fast startup
```

The router/EPP isn't "just a controller."

It's part of your **inference availability path**.

This is not something I want you to blindly copy into every cluster.

The lesson is:

```text

what matters?

Weight:
how much does it matter?

who wins?
```

Current llm-d configuration documentation gives this pattern and notes that precise prefix-cache routing requires configuring the precise prefix producer; otherwise the scorer falls back to the approximate producer. ([Llm-D][9])

# 71. What I Want You to Remember From This Lesson

If someone asks:

> "Explain llm-d."

Your 30-second answer should be:

> **llm-d is an inference-aware orchestration and routing layer for Kubernetes-hosted model servers such as vLLM. Requests enter through a proxy/Gateway and are sent to an Endpoint Picker. The EPP maintains a near-real-time view of model-server state such as queue depth, active requests, KV-cache utilization and prefix locality. Its scheduler filters unsuitable endpoints, scores the remaining endpoints using configurable plugins, and picks the best destination. This enables cache-aware, load-aware and SLO-aware routing rather than traditional round-robin load balancing.**

That is a **strong AIRE answer**.
