# Lab 1V — Advanced Prefill/Decode Disaggregation + KV Architecture

This is where the pieces from the last several labs finally connect.

We've learned:

* GPU memory
* KV cache
* vLLM scheduling
* TP/DP
* NCCL
* EFA
* NIXL
* llm-d
* routing
* autoscaling
* SLOs
* capacity engineering

Now we're going to design **disaggregated LLM inference**.

---

# 1. The fundamental problem

A normal vLLM deployment looks like:

```text
                  Request
                     │
                     ▼
                  vLLM
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       Prefill                Decode
          │                     │
       compute                 KV
          │                     │
          └──────────┬──────────┘
                     ▼
                    GPU
```

The same GPU fleet performs:

```text
Prefill + Decode
```

This is called **coupled serving**.

---

# 2. Why can this become a problem?

Imagine:

```text
Request A
input = 100K tokens
```

and:

```text
Request B
input = 500 tokens
```

Request A requires substantial prefill computation.

While that happens, decode requests can experience interference.

You can get:

```text
Long prefill
     │
     ▼
GPU compute pressure
     │
     ▼
Decode delayed
     │
     ▼
ITL / TPOT increases
     │
     ▼
User sees slower streaming
```

This is especially painful when your SLO is:

```text
P95 TPOT < 50ms
```

---

# 3. The key observation

Prefill and decode have different characteristics.

### Prefill

```text
Large input
 ↓
many tokens processed together
 ↓
high compute intensity
 ↓
often compute-bound
```

### Decode

```text
one/few new tokens per iteration
 ↓
repeated KV access
 ↓
memory-bandwidth sensitive
 ↓
latency sensitive
```

So we have:

```text
                LLM inference
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       PREFILL                DECODE
       compute               memory/KV
       intensive              intensive
```

This creates an opportunity.

---

# 4. Disaggregation

Instead of:

```text
GPU
 ├── prefill
 └── decode
```

we create:

```text
Prefill GPUs
     │
     │ KV transfer
     ▼
Decode GPUs
```

Architecture:

```text
                    Request
                       │
                       ▼
                    Router
                       │
                       ▼
                Prefill Worker
                       │
                       │
                    KV Cache
                       │
                       ▼
                 NIXL / RDMA
                       │
                       ▼
                 Decode Worker
                       │
                       ▼
                   Response
```

This is **Prefill/Decode disaggregation**, commonly abbreviated **P/D**.

---

# 5. Why would we do this?

Because now we can independently scale:

```text
Prefill capacity
```

and:

```text
Decode capacity
```

Example:

```text
Prefill:
8 GPUs

Decode:
16 GPUs
```

instead of:

```text
24 GPUs
```

where every GPU does both jobs.

---

# 6. Think of it like a factory

Imagine:

```text
Raw material
     │
     ▼
Factory A
"prepare"
     │
     ▼
Intermediate product
     │
     ▼
Factory B
"finish"
     │
     ▼
Customer
```

Prefill:

> prepares the request and generates the KV state.

Decode:

> consumes that state and generates output tokens.

---

# 7. What exactly is transferred?

This is critical.

We are not normally transferring:

```text
model weights
```

The model weights already exist on both sides.

We transfer:

```text
KV cache
```

Conceptually:

```text
Prompt
 ↓
Prefill GPU
 ↓
Transformer layers
 ↓
K/V tensors
 ↓
KV cache
 ↓
network
 ↓
Decode GPU
 ↓
continue generation
```

---

# 8. Model weights remain local

You could have:

```text
Prefill GPU
 ├── model weights
 └── KV cache

Decode GPU
 ├── model weights
 └── KV cache
```

Both sides need the model because decode still has to execute Transformer layers.

P/D doesn't eliminate model memory.

---

# 9. Why NIXL?

We previously learned:

```text
NCCL
```

is excellent for:

```text
collective communication
```

such as:

```text
AllReduce
AllGather
ReduceScatter
```

But P/D needs something different.

We want:

```text
GPU memory
     ↓
KV data
     ↓
remote GPU memory
```

This is an inference-oriented data movement problem.

That's where:

> **NIXL — NVIDIA Inference Xfer Library**

comes in.

---

# 10. NCCL vs NIXL

Memorize this distinction:

```text
NCCL
=
collective GPU communication
```

while:

```text
NIXL
=
inference-oriented data transfer
```

Conceptually:

```text
NCCL:

GPU0 ─┐
GPU1 ─┼── AllReduce
GPU2 ─┤
GPU3 ─┘
```

versus:

```text
NIXL:

Prefill GPU
    │
    │ KV
    ▼
Decode GPU
```

---

# 11. Physical data path

The transfer might look like:

```text
Prefill GPU HBM
      │
      ▼
GPU / PCIe
      │
      ▼
NIC
      │
      ▼
EFA / RDMA
      │
      ▼
NIC
      │
      ▼
PCIe
      │
      ▼
Decode GPU HBM
```

The ideal goal is to minimize CPU involvement and unnecessary memory copies.

This is where **GPUDirect RDMA**, GPU/NIC topology, and EFA become important.

---

# 12. KV transfer time

At a high level:

```text
Transfer Time
≈
KV Size / Effective Bandwidth
```

Example:

```text
KV = 20 GB

effective bandwidth = 100 GB/s
```

Then idealized transfer:

```text
20 / 100
=
0.2 sec
=
200 ms
```

Already significant.

And that's before considering:

```text
synchronization
protocol overhead
memory registration
network contention
topology
software overhead
```

So don't say:

> "The network is 100 GB/s, therefore transfer is exactly 200 ms."

Real measurements matter.

---

# 13. Why long context makes this important

Suppose:

```text
input = 2K
```

KV might be relatively small.

But:

```text
input = 100K
```

KV can become enormous.

From our previous KV example:

```text
320 KB/token
```

for a particular hypothetical architecture.

Then:

```text
100K × 320 KB
≈ 32 GB
```

of KV.

Now imagine:

```text
32GB KV
```

moving between workers.

That's a serious networking event.

---

# 14. P/D doesn't magically make long context cheap

This is an important misconception.

P/D:

```text
doesn't eliminate
```

the computational work.

It changes **where** that work happens and can isolate workloads.

You still pay:

```text
prefill compute
+
KV memory
+
KV transfer
+
decode compute
```

---

# 15. When P/D can help

P/D becomes particularly attractive when:

```text
long prompts
+
high concurrency
+
strict decode latency
```

create strong interference.

Example:

```text
User A:
100K-token prompt

User B:
streaming response
```

Without P/D:

```text
A prefill
 ↓
B decode delayed
```

With P/D:

```text
A
 ↓
Prefill fleet

B
 ↓
Decode fleet
```

Now decode capacity can be protected.

---

# 16. The real goal

Don't think:

> "P/D makes inference faster."

Think:

> **P/D allows us to independently control and isolate different resource bottlenecks.**

That is much more accurate.

# 18. Router becomes more important

Without P/D:

```text
Request
 ↓
choose replica
```

With P/D:

```text
Request
 ↓
choose prefill worker
 ↓
choose decode worker
 ↓
transfer KV
```

Now routing has another dimension.

# 19. Routing problem

Suppose:

```text
P1:
queue = low

P2:
queue = high
```

You probably want:

```text
request → P1
```

But then:

```text
Decode:
D1 = 90% KV
D2 = 40% KV
D3 = 60% KV
```

Now you may prefer:

```text
P1 → D2
```

But prefix locality could say:

```text
P1 → D3
```

because D3 already has a relevant prefix.

Now the routing problem becomes:

```text
queue
+
KV
+
prefix locality
+
SLO
+
network cost
+
prefill state
+
decode state
```

This is exactly where llm-d becomes powerful.

---

# 20. P/D routing as an optimization problem

Conceptually:

```text
Best destination =
argmin(
    queue delay
    +
    KV transfer cost
    +
    decode load
    +
    SLO risk
)
```

The real implementation is more sophisticated, but this is the correct mental model.

# 21. KV compatibility

You cannot arbitrarily transfer KV between any two inference servers.

The receiving side needs to understand the KV representation.

Think:

```text
Model architecture
        +
layers
        +
KV heads
        +
head dimension
        +
dtype
        +
cache layout
        +
attention backend
        +
runtime compatibility
```

must be compatible.

---

# 22. Example incompatibility

Prefill:

```text
BF16 KV
```

Decode expects:

```text
FP8 KV
```

Potentially:

```text
incompatible
```

Similarly:

```text
different model revision
```

can make KV reuse unsafe.

Therefore:

> **Model rollout and P/D KV compatibility are tightly connected.**

# 23. Rolling deployment danger

Imagine:

```text
Prefill v1
Decode v1
```

Then rollout begins:

```text
Prefill v2
Decode v1
```

If the KV format/configuration changes:

```text
v2 KV
   ↓
v1 decode
   ↓
❌
```

Therefore P/D deployments may require coordinated compatibility rules.

This is one reason a release manifest should include:

```text
model
vLLM
KV configuration
attention backend
NIXL compatibility
```

Think of a P/D release as:

```text

          ┌──────────┴──────────┐
          ▼                     ▼
      Prefill                 Decode
          │                     │
       Model X                Model X
       vLLM X                 vLLM X
```

# 25. P/D scaling

This is one of the biggest benefits.

Suppose:

```text
Prefill:
capacity = 10K input tok/s/GPU
```

Demand:

```text
50K input tok/s
```

Need roughly:

```text
5 prefill GPU-equivalents
```

Now decode:

```text
capacity = 2K output tok/s/GPU
```

Demand:

```text
20K output tok/s
```

Need roughly:

```text
10 decode GPU-equivalents
```

So architecture can be approximately:

```text
5 prefill
+
10 decode
```

rather than one homogeneous pool.

Actual sizing still requires benchmark data and topology constraints.

Now our autoscaling architecture becomes:

```text
                  llm-d
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
     Prefill Pool         Decode Pool
          │                   │
       KEDA-P              KEDA-D
          │                   │
      Karpenter           Karpenter
          │                   │
        GPUs                GPUs
```

Prefill scaling signals:

```text

```

```text

```

# 27. P/D introduces another queue

Without P/D:

```text
Request
 ↓
vLLM scheduler
```

With P/D:

```text
Request
 ↓
prefill queue
 ↓
prefill
 ↓
KV transfer queue
 ↓
decode queue
 ↓
decode
```

Therefore end-to-end latency becomes:

```text
E2E
=
request queue
+
prefill queue
+
prefill compute
+
KV transfer
+
decode queue
+
decode
```

This decomposition is extremely valuable for troubleshooting.

---

# 28. TTFT in P/D

TTFT roughly becomes:

```text
TTFT
=
gateway
+
routing
+
prefill queue
+
prefill compute
+
KV transfer
+
decode startup
```

So if:

```text
P95 TTFT = 2 sec
```

don't immediately blame prefill compute.

Could be:

```text
KV transfer = 700ms
```

or:

```text
prefill queue = 1 sec
```

---

# 29. TPOT in P/D

TPOT is mostly influenced by decode:

```text
TPOT
≈
decode scheduling
+
KV access
+
decode compute
+
communication
```

Therefore:

```text
P95 TTFT bad
P95 TPOT good
```

could indicate:

```text
prefill problem
```

while:

```text
P95 TTFT good
P95 TPOT bad
```

could indicate:

```text
decode capacity problem
```

This separation is extremely useful.

---

# 30. P/D troubleshooting matrix

| Symptom                  | Likely area                   |
| ------------------------ | ----------------------------- |
| TTFT high, TPOT normal   | Prefill/queue/transfer        |
| TTFT normal, TPOT high   | Decode                        |
| Both high                | overall saturation            |
| KV transfer latency high | NIXL/EFA/network              |
| KV transfer failures     | compatibility/connectivity    |
| Prefill queue high       | insufficient prefill capacity |
| Decode queue high        | insufficient decode capacity  |
| KV >90%                  | decode memory pressure        |
| NCCL high                | TP communication              |
| EFA bandwidth low        | network/topology              |
| prefix hit rate low      | routing/locality              |

# 31. Failure: prefill worker dies

Suppose:

```text
P1
```

dies after computing:

```text
80% of prefill
```

Possible behavior:

```text
KV unavailable
 ↓
request retry/recompute
```

This is why KV should not automatically be treated as durable state.

Depending on the architecture:

```text
recompute
```

may be preferable to:

```text
complex durable KV recovery
```

---

# 32. Failure: decode worker dies

Suppose:

```text
D2
```

is serving 100 active streams.

Failure:

```text
D2 dies
```

Those requests may need:

```text
retry
recompute
KV reconstruction
```

depending on system support.

Streaming requests make this particularly important.

# 33. P/D failure philosophy

A useful principle:

> **KV is generally derived state.**

The authoritative state is usually:

```text
model
+
request/prompt
```

KV is a performance optimization/state representation generated from them.

Therefore:

```text
KV loss
```

may be recoverable through recomputation.

This is useful for DR and failure design.

# 34. Network failure

Suppose:

```text
Prefill
   │
   X
NIXL/EFA
   │
Decode
```

Transfer fails.

Options:

### Fail request

```text
fast failure
```

### Retry transfer

```text
may recover
```

### Recompute

```text
prefill again
```

### fallback to coupled serving

Potentially possible depending on platform architecture.

Your policy depends on:

```text
SLO
cost
latency
failure frequency
request type
```

# 35. P/D doesn't always win

This is extremely important.

If workload is:

```text
short prompts
low concurrency
low traffic
```

then P/D introduces:

```text
network hop
routing complexity
KV transfer
extra fleet management
```

and may actually make the system worse.

So:

> **P/D is an optimization for a particular workload shape, not a default architecture.**

---

# 36. P/D economics

Coupled:

```text
GPU fleet
=
N
```

P/D:

```text
Prefill fleet
+
Decode fleet
+
possibly additional networking
```

You may need more total GPUs.

So why use it?

Because the objective isn't:

```text
minimum GPU count
```

It's:

```text
minimum cost while meeting SLO
```

You may spend more GPUs but obtain:

```text
better TTFT
better TPOT
higher predictable throughput
better isolation
```

# 37. P/D and long-context workloads

This is where P/D becomes especially interesting.

Imagine:

```text
Customer A:
80K-token prompt
```

and:

```text
Customer B:

```

A huge prefill can consume substantial compute.

P/D allows:

```text

```

```text

```

This can make latency behavior much more predictable.

P/D creates a new resource:

# 55. When should you recommend P/D?

Use this checklist.

P/D becomes attractive when:

```text
☑ long prompts
☑ high concurrency
☑ strong prefill/decode interference
☑ strict TTFT/TPOT SLOs
☑ independent scaling is valuable
☑ high-speed networking exists
☑ workload justifies complexity
☑ sufficient observability
```

Avoid it initially when:

```text
☑ short prompts
☑ low traffic
☑ relaxed latency
☑ simple deployment preferred
☑ network is weak
```
