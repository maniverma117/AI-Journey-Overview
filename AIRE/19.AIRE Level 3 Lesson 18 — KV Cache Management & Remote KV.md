# 🧠 Lesson 18 — KV Cache Management & Remote KV

## 1. First, remember the fundamental problem

Our inference stack currently looks like:

```text
                         REQUEST
                            │
                            ▼
                    ┌───────────────┐
                    │     vLLM      │
                    │   Scheduler   │
                    └───────┬───────┘
                            │
                 ┌──────────┴──────────┐
                 │                     │
              Prefill                Decode
                 │                     │
                 ▼                     ▼
             Compute QKV          Reuse KV
                 │                     │
                 └──────────┬──────────┘
                            ▼
                       GPU HBM
                     ┌───────────┐
                     │ Weights   │
                     │ KV Cache  │
                     │ Workspace │
                     └───────────┘
```

The problem is:

**GPU HBM is extremely fast but limited.**

For example:

```text
H100
 └── 80 GB HBM

H200
 └── 141 GB HBM
```

And that memory has to accommodate:

```text
GPU HBM
│
├── Model weights
├── KV cache
├── CUDA workspace
├── CUDA graphs
├── activations
├── runtime allocations
└── other overhead
```

AWS itself now explicitly recommends monitoring **KV cache utilization** alongside TTFT, TPOT, throughput and GPU utilization for inference workloads. ([AWS Documentation][1])

# 2. The key insight

Here's the important mental model:

```text
GPU HBM
   │
   │ fastest
   ▼
CPU DRAM
   │
   │ slower
   ▼
Local NVMe / SSD
   │
   │ slower
   ▼
Remote distributed storage
   │
   │ potentially much slower
   ▼
Object storage
```

Think of this as a **memory hierarchy for KV cache**.

```text
              SPEED
                ▲
                │
       GPU HBM  │  $$$$$$$
                │
       CPU RAM  │  $$$
                │
       NVMe     │  $$
                │
 Remote Memory  │  $
                │
                └──────────────────► CAPACITY
```

The closer to the GPU:

* faster
* more expensive
* smaller

The farther away:

* slower
* cheaper
* larger

# 3. Why does KV cache need to survive?

Consider an agent.

The user sends:

```text
System:
You are an expert financial assistant...

User:
Analyze this 40-page document...
```

The model computes:

```text
40,000 tokens
       │
       ▼
    PREFILL
       │
       ▼
KV cache
```

Then the user asks:

```text
"Now summarize section 7."
```

If the relevant prefix remains cached:

```text
Existing KV
    │
    ├── system prompt
    ├── document
    └── conversation
          │
          ▼
       reuse
          │
          ▼
       decode
```

Excellent.

But suppose GPU HBM became full.

The cache might be evicted:

```text
GPU HBM
┌──────────────────────┐
│ KV A                 │
│ KV B                 │
│ KV C                 │
│ KV D                 │
│ KV E                 │
│                      │
│       FULL           │
└──────────────────────┘

KV A → evicted
```

Now the follow-up request arrives.

Without another tier:

```text
Request
   │
   ▼
KV not found
   │
   ▼
RECOMPUTE PREFILL
   │
   ▼
GPU work
   │
   ▼
latency + cost
```

This is wasted computation.

---

# 4. KV offloading changes the story

Instead of:

```text
GPU KV
   │
   └── eviction → DELETE
```

we can do:

```text
GPU KV
   │
   │ evict
   ▼
CPU RAM
```

Now:

```text
GPU HBM
┌─────────────────┐
│ hot KV          │
│ hot KV          │
│ hot KV          │
└───────┬─────────┘
        │
        │ eviction
        ▼
CPU RAM
┌──────────────────────────┐
│ KV A                     │
│ KV B                     │
│ KV C                     │
│ KV D                     │
│ KV E                     │
└──────────────────────────┘
```

Then:

```text
follow-up request
        │
        ▼
KV lookup
        │
        ▼
CPU cache HIT
        │
        ▼
GPU HBM
        │
        ▼
continue inference
```

That's the fundamental idea behind **KV offloading**.

llm-d describes this as extending effective KV capacity beyond GPU HBM using lower-cost tiers such as CPU DRAM and shared storage. ([Llm-D][2])

```text

```

with `native` and `lmcache` supported backends in the current CLI. ([vLLM][3])

The architecture is essentially:

```text
                vLLM

           │             │
           ▼             ▼
       GPU HBM        CPU RAM
       hot KV         cold KV
```

# 6. Why CPU memory?

Because CPU RAM is much larger.

Imagine:

```text
GPU:
80 GB HBM

Node:
512 GB RAM
```

You don't want to replace:

```text
80 GB GPU
```

with:

```text
another 80 GB GPU
```

just because you need more **cold KV capacity**.

Instead:

```text
80 GB HBM
+
hundreds of GB CPU RAM
```

can create a much larger effective cache.

But there is an important tradeoff.

# 7. GPU HBM vs CPU RAM

Think about the latency hierarchy:

```text
GPU HBM
    │
    │ very fast
    ▼
GPU compute

CPU RAM
    │
    │ transfer required
    ▼
GPU

NVMe
    │
    │ I/O
    ▼
CPU RAM
    │
    ▼
GPU

Remote storage
    │
    │ network + storage
    ▼
CPU
    │
    ▼
GPU
```

Therefore:

> **Offloading does not make CPU RAM equivalent to GPU HBM.**

This is critical.

You are trading:

```text
GPU memory pressure
```

for:

```text
transfer latency + bandwidth
```

# 8. DMA — an important concept

How do we move data between GPU and CPU efficiently?

One mechanism is **DMA — Direct Memory Access**.

Instead of:

```text
GPU
 │
 ▼
CPU cores
 │
 ▼
memory
```

we want hardware-assisted movement:

```text
GPU
 │
 │ DMA
 ▼
Pinned CPU memory
```

vLLM's native offloading path uses pinned CPU memory and asynchronous GPU DMA transfers. ([vLLM][4])

This matters because we don't want the CPU doing:

```text
copy
copy
copy
copy
copy
```

for every KV block.

We want:

```text
GPU DMA engine
       │
       ▼
Pinned host memory
```

while GPU computation continues where possible.

# 9. The next tier: NVMe

CPU RAM isn't infinite either.

So we can build:

```text
GPU HBM
   │
   ▼
CPU DRAM
   │
   ▼
NVMe
```

Example:

```text
              KV CACHE HIERARCHY

        ┌─────────────────────┐
        │      GPU HBM        │
        │      HOT KV         │
        └─────────┬───────────┘
                  │
                  ▼
        ┌─────────────────────┐
        │      CPU RAM        │
        │     WARM KV         │
        └─────────┬───────────┘
                  │
                  ▼
        ┌─────────────────────┐
        │      NVMe SSD       │
        │     COLD KV         │
        └─────────────────────┘
```

This is **tiered KV caching**.

llm-d's current architecture explicitly describes GPU HBM → CPU RAM → filesystem/storage as a tiered approach, while noting that hierarchical native tiering is evolving. ([Llm-D][2])

# 10. Why would we ever use NVMe?

Suppose:

```text

80 GB

512 GB

7 TB
```

You could keep:

```text

512 GB warm
7 TB cold
```

instead of:


* long conversations

* document Q&A
* multi-turn sessions
* coding agents
* enterprise copilots

Because these workloads often reuse prefixes.

# 16. GPUDirect RDMA

This is an important AIRE concept.

Without optimized GPU networking:

```text
GPU
 │
 ▼

 ▼
NIC
 │
 ▼
network
 │
 ▼

 │
 ▼

 │
 ▼
```

That's expensive.

With GPUDirect RDMA:


# 20. P2P KV sharing — this is the really advanced part

Suppose:

```text
Pod A
GPU
CPU KV
```

has:

```text
Prefix = "Company confidential document..."
```

Then Pod A gets restarted.

Pod B receives the next request.

Normally:

```text
Pod B
  │
  ▼
KV miss
  │
  ▼
recompute
```

But with P2P sharing:

```text
                   ┌─────────────┐
                   │ KV Index    │
                   └──────┬──────┘
                          │
                   Prefix → Pod A
                          │
                          ▼
Request ──► Pod B ─────► Pod A
                   KV pull
                          │
                          ▼
                     Pod B CPU
                          │
                          ▼
                     Pod B GPU
```

The key insight:

> **Pod B can retrieve cached KV from Pod A without asking Pod A's GPU to recompute the prefix.**

llm-d describes this as P2P prefix-cache sharing, where the source pod's GPU does not need to perform prefill for the pull. ([Llm-D][6])

---

# 21. This creates a fleet-wide cache

Previously:

```text
Pod A
 └── cache A

Pod B
 └── cache B

Pod C
 └── cache C
```

Cache is fragmented.

Now:

```text
              ┌────────────────────┐
              │  KV Index          │
              └─────────┬──────────┘
                        │
         ┌──────────────┼──────────────┐
         │              │              │
         ▼              ▼              ▼
       Pod A           Pod B          Pod C
        KV              KV             KV
         │              │              │
       CPU             CPU            CPU
```

The fleet behaves more like:

```text
             DISTRIBUTED KV CACHE
```

rather than independent vLLM caches.

🔥 This is a major architectural shift.

```text

```



```text

```

```text

cache lookup
```

# 34. One very important distinction: model weights vs KV cache

Never mix these.

### Model weights

```text
70B model
       │
       ▼
S3 / ECR / model registry
       │
       ▼
GPU HBM
```

Weights are relatively static.

### KV cache

```text
requests
   │
   ▼
GPU HBM
   │
   ├── dynamic
   ├── request-specific
   ├── evicted
   ├── transferred
   └── reused
```

KV is dynamic.

Therefore:

```text
Model storage architecture
```

and

```text
KV storage architecture
```

are separate design problems.

# 36. Architecture decision framework

When should you use what?

| Situation                         | Architecture            |
| --------------------------------- | ----------------------- |
| Short context, low concurrency    | GPU-only KV             |
| Moderate context, memory pressure | GPU + CPU KV            |
| Very large working set            | GPU + CPU + storage     |
| Repeated prefixes across replicas | Prefix-aware routing    |
| Cache reuse across nodes          | Remote/P2P KV           |
| Separate prefill/decode           | NIXL KV transfer        |
| Huge agentic workloads            | Tiered + distributed KV |
| Extreme latency requirements      | Keep hot KV on GPU      |
| Cost-sensitive workloads          | Offload cold KV         |

# 38. Production failure scenarios

## Failure 1 — CPU KV full

```text
GPU
 ↓
CPU KV
 ↓
FULL
```

Need:

```text
eviction policy
```

Possible response:

```text
CPU KV evicts old blocks
```

then future request:

```text
cache miss
```

and recompute.

---

## Failure 2 — Remote KV unavailable

```text
vLLM B
   │
   ▼
remote KV
   X
```

What should happen?

**Never make cache availability equivalent to request availability.**

The ideal degradation is:

```text
KV unavailable
      │
      ▼
cache miss
      │
      ▼
recompute locally
      │
      ▼
request succeeds
```

This is a fantastic reliability principle:

> **Cache should accelerate inference, not become a hard dependency for correctness.**

llm-d's P2P cache-sharing design explicitly treats failed lookup as a miss and allows local recomputation rather than failing the request. ([Llm-D][8])

🔥 That's exactly how an AIRE thinks.

---

# 39. Failure 3 — NIXL broken

For P/D:

```text
Prefill
  │
  │ KV
  X
Decode
```

Now the request can't continue normally.

Unlike optional cache sharing, P/D KV transfer is often part of the request's execution path.

Therefore:

```text
P/D disaggregation
```

has a much stronger dependency on:

```text
NIXL
RDMA
network
compatibility
```

This is why P/D operations are more complex than ordinary vLLM replicas. llm-d's current documentation explicitly calls out KV transfer as critical to high-performance disaggregated serving. ([Llm-D][5])

---

# 40. Failure 4 — wrong KV compatibility

Suppose:

```text
Prefill:
vLLM X
FP8 KV

Decode:
vLLM Y
BF16 KV
```

Potentially:

```text
KV transfer
      │
      ▼
INCOMPATIBLE
```

This should be caught by compatibility validation rather than silently corrupting inference.

That's why version/configuration consistency becomes part of your deployment contract. ([vLLM][7])

# 🎯 AIRE Interview Questions

You should be able to answer these without notes.

### Q1

**Why can't we simply keep all KV cache in GPU memory?**

Expected:

> GPU HBM is limited and shared with weights/runtime/workspace. Long contexts and high concurrency make KV a major dynamic memory consumer.

---

### Q2

**What is KV offloading?**

> Moving less-active KV blocks from accelerator HBM to lower-cost memory/storage tiers such as CPU DRAM or filesystem and restoring them when needed.

---

### Q3

**Does CPU offloading increase GPU memory?**

No.

It increases:

> **effective cache capacity**

not physical GPU HBM.

---

### Q4

**What's the difference between KV offloading and KV transfer?**

```text
Offloading:
GPU → CPU/NVMe

Transfer:
GPU A → GPU B
```

---

### Q5

**Why is NIXL important?**

> It provides an efficient abstraction for moving inference memory/KV data between instances, enabling high-performance KV transfer for disaggregated inference and P2P scenarios.

---

### Q6

**Why is GPUDirect RDMA useful?**

> It can allow network transfers involving GPU memory without unnecessary CPU copies, reducing CPU involvement and improving transfer efficiency.

---

### Q7

**What happens if remote KV fails?**

For optional P2P cache:

```text
remote miss
   ↓
local recompute
```

not:

```text
HTTP 500
```

---

### Q8

**What is the danger of KV offloading?**

You trade:

```text
HBM capacity pressure
```

for:

```text
data movement latency + bandwidth pressure
```

---

### Q9

**What determines whether offloading helps?**

Think:

```text
working-set size
cache hit rate
reuse distance
KV size
transfer bandwidth
transfer latency
GPU compute cost
CPU memory bandwidth
storage latency
```
