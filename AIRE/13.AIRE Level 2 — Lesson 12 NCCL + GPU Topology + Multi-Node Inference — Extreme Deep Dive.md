# 2. Why communication exists at all

Imagine:

```text
Y = XW
```

where `W` is enormous.

With one GPU:

```text
X ──► GPU
       │
       ▼
      XW
```

With TP=4:

```text
              W
       ┌──────┼──────┬──────┐
       ▼      ▼      ▼      ▼
      W0     W1     W2     W3
       │      │      │      │
      GPU0   GPU1   GPU2   GPU3
       │      │      │      │
       └──────┴──────┴──────┘
                  │
                  ▼
               combine
```

Each GPU computes only part of the result.

Eventually those partial results have to be combined or redistributed.

That communication is where:

```text
NCCL
```

comes in.

NCCL is specifically designed for topology-aware multi-GPU collective communication and supports intra-node and inter-node communication over technologies including PCIe, NVLink, InfiniBand and IP sockets. ([NVIDIA Docs][1])

# 3. The hierarchy of communication

Think of GPU communication as a hierarchy:

```text
FASTEST / CLOSEST
        │
        ▼
GPU memory
        │
        ▼
NVLink
        │
        ▼
PCIe
        │
        ▼
NIC / RDMA
        │
        ▼
EFA / InfiniBand
        │
        ▼
ordinary network path
        │
        ▼
SLOWEST / FURTHEST
```

But don't memorize this as an absolute speed ranking.

The real question is:

> **What physical topology connects these particular GPUs?**

# 4. GPU topology

Imagine an 8-GPU server:

```text
             CPU / NUMA
              /      \
             /        \
         PCIe          PCIe
          │              │
      ┌───┴───┐      ┌───┴───┐
      │       │      │       │
     GPU0    GPU1    GPU2    GPU3
      │       │      │       │
      └──────NVLink───────┘
```

The actual topology is hardware-specific.

That's why this command matters:

```bash
nvidia-smi topo -m
```

It shows the relationship between GPUs, CPUs and network interfaces.

NVIDIA's NCCL troubleshooting documentation specifically recommends topology inspection because NCCL relies on the PCI topology exposed through `/sys` to discover GPUs and network cards. ([NVIDIA Docs][2])

> **Not every GPU pair is equally close.**

# 6. NVLink

NVLink is a high-bandwidth GPU interconnect.

Conceptually:

```text
GPU0 ═════ GPU1
 │          │
 ║          ║
GPU2 ═════ GPU3
```

Instead of:

```text
GPU
 │
PCIe
 │
CPU
 │
PCIe
 │
GPU
```

you can have a much more direct GPU-to-GPU communication path.

This is extremely valuable for:

```text
TP
collectives
KV-related operations
distributed inference
MoE communication
```

# 7. Why TP loves fast interconnects

Suppose TP=4 requires:

```text
compute
↓
NCCL
↓
compute
↓
NCCL
↓
compute
```

If communication is cheap:

```text
compute ███████████
NCCL    ██
compute ███████████
NCCL    ██
```

Good.

If communication is expensive:

```text
compute ███████████
NCCL    █████████████
compute ███████████
NCCL    █████████████
```

Your GPUs may spend substantial time waiting for each other.

So:

> **TP scaling depends on both GPU compute and communication efficiency.**

---

# 8. Communication/computation overlap

Advanced systems try to overlap:

```text
GPU computation
```

with:

```text
communication
```

Instead of:

```text
compute
   ↓
wait
   ↓
communication
   ↓
wait
   ↓
compute
```

you want something closer to:

```text
GPU compute:     ███████████████████
communication:      █████████████
```

So communication happens while useful computation continues where possible.

This is one reason optimized CUDA/NCCL systems can achieve much better scaling than naive implementations.

NCCL understands:


# 10. NCCL collectives in inference

You've already seen:

```text
AllReduce
AllGather
ReduceScatter
AllToAll
```

Let's connect them to inference.

---

## AllReduce

Concept:

```text
GPU0 ─┐
GPU1 ─┤
GPU2 ─┼──► reduce ──► everyone
GPU3 ─┘
```

Useful when distributed computation produces partial results that must be combined.

---

## AllGather

```text
GPU0 → A
GPU1 → B
GPU2 → C
GPU3 → D

Everyone gets:

[A B C D]
```

---

## ReduceScatter

```text
all partial results
       ↓
    reduce
       ↓
split result among GPUs
```

---

## AllToAll

This one becomes especially important for MoE.

```text
GPU0 ─────┐
GPU1 ─────┤
GPU2 ─────┼──► everybody exchanges with everybody
GPU3 ─────┘
```

NCCL provides all of these collective primitives. ([NVIDIA Docs][1])

# 11. Multi-node changes the game

One node:

```text
Node A
┌───────────────────────────┐
│ GPU0 GPU1 GPU2 GPU3       │
│                           │
│ GPU4 GPU5 GPU6 GPU7       │
└───────────────────────────┘
```

Communication can leverage local GPU interconnects.

Now:

```text
Node A                  Node B
┌──────────────┐        ┌──────────────┐
│ GPU0...GPU7  │        │ GPU0...GPU7  │
└───────┬──────┘        └───────┬──────┘
        │                       │
        └────── NETWORK ────────┘
```

Now communication crosses:

```text
NIC
↓
network
↓
NIC
↓
remote GPU
```

This is much more complicated.

# 12. EFA — AWS's answer for high-performance networking

On AWS, for supported accelerated instances, you can use:

```text
EFA
```

Elastic Fabric Adapter.

AWS describes EFA as a network interface optimized for HPC and ML workloads, integrating with Libfabric and supporting NCCL. EFA can provide OS-bypass capabilities and RDMA functionality to reduce networking overhead. ([AWS Documentation][3])

So conceptually:

```text
GPU
 │
NCCL
 │
AWS OFI NCCL plugin
 │
Libfabric
 │
EFA
 │
AWS network
 │
EFA
 │
Libfabric
 │
NCCL
 │
GPU
```

This is very different from ordinary:

```text
TCP/IP
```

traffic.

# 13. EFA versus ENA

This distinction is important in AWS.

### ENA

Normal high-performance AWS network interface.

Used for:

```text
HTTP
API
SSH
DNS
ordinary VPC traffic
```

### EFA

Specialized for:

```text
HPC
distributed ML
NCCL
RDMA-style communication
```

AWS explains that traditional ENA networking uses the OS networking path, while EFA can provide direct user-space communication through Libfabric, reducing overhead. ([AWS Documentation][3])

So:

```text
Application
    │
    ├── ordinary traffic → ENA
    │
    └── distributed GPU communication → EFA
```

Conceptually.

# 14. GPU Direct

Now another major concept.

Without efficient GPU Direct:

```text
GPU
 ↓
CPU memory
 ↓
NIC
 ↓
network
```

That involves additional data movement.

With GPU Direct/RDMA-oriented paths:

```text
GPU
 │
 ▼
NIC
 │
 ▼
network
 │
 ▼
NIC
 │
 ▼
GPU
```

The goal is to reduce unnecessary CPU involvement and memory copies.

NCCL heavily relies on GPU Direct for inter-GPU communication and can use peer-to-peer GPU access over NVLink or PCIe when supported. ([NVIDIA Docs][2])

# 15. Why NIC-to-GPU affinity matters

Imagine:

```text
GPU0 ─── NIC0
GPU1 ─── NIC0
GPU2 ─── NIC1
GPU3 ─── NIC1
```

Now your distributed communication may benefit if GPU workers use the NICs that are physically closest to them.

You therefore care about:

```text
GPU ↔ NIC affinity
```

not just:

```text
GPU count
```

This becomes important on large GPU servers with multiple network cards.

# 16. AWS multi-node inference architecture

For a large inference deployment:

```text
                 Router
                    │
                    ▼
             vLLM distributed
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Node 0              Node 1
    ┌───────────┐        ┌───────────┐
    │ H100 × 8  │        │ H100 × 8  │
    └─────┬─────┘        └─────┬─────┘
          │                     │
       NVLink                NVLink
          │                     │
          └────── EFA ─────────┘
```

Inside node:

```text
GPU ↔ GPU
```

uses local topology.

Across nodes:

```text
GPU ↔ NIC ↔ EFA ↔ NIC ↔ GPU
```

---

# 17. This explains TP8 vs TP16

Suppose:

```text
Node 0 = 8 GPUs
Node 1 = 8 GPUs
```

### Option A

```text
TP=8
PP=2
```

Communication-heavy TP remains within each node.

Cross-node communication occurs between pipeline stages.

### Option B

```text
TP=16
```

The tensor-parallel group spans nodes.

Now frequent TP collectives may cross EFA.

Potentially:

```text
TP communication
+
network latency
+
network bandwidth constraints
+
NCCL synchronization
```

This can make TP16 slower.



# 21. Strong scaling

This is a classic distributed-computing concept.

You keep the workload fixed:

```text
same model
same request
same total work
```

and add GPUs:

```text
1 → 2 → 4 → 8 → 16
```

Ideal:

```text
latency ↓ proportionally
```

Reality:

```text
latency ↓
     ↓
communication ↑
     ↓
efficiency ↓
```

Eventually:

```text
adding GPUs
```

doesn't help much.

---

# 22. Weak scaling

Different concept.

As GPUs increase:

```text
workload also increases
```

Example:

```text
1 GPU → 100 requests
2 GPU → 200 requests
4 GPU → 400 requests
8 GPU → 800 requests
```

You're asking:

> Can the system maintain similar performance as workload grows with resources?

This matters for large-scale serving.

# 36. The dangerous NCCL problem: hangs

One of the most painful distributed inference failures:

```text
rank 0 waiting
rank 1 waiting
rank 2 waiting
...
```

Application appears:

```text
STUCK
```

Maybe no obvious exception.

Why?

Collectives require participants to coordinate.

If one rank:

```text
crashes
```

or:

```text
takes a different execution path
```

or:

```text
loses communication
```

other ranks may wait.

This is why distributed systems debugging is much harder than single-GPU debugging.

---

```text

```

```text

```


# 38. Why distributed inference is a reliability problem

Single GPU:

```text
1 GPU failure
    ↓
1 replica failure
```

TP8:

```text
1 GPU failure
    ↓
1 distributed replica failure
```

TP16:

```text
1 GPU failure
    ↓
1 distributed replica failure
```

but the blast radius is larger.

Therefore:

> **Parallelism configuration is also a failure-domain decision.**
