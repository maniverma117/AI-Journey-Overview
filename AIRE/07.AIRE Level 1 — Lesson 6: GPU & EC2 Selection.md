# AIRE Level 1 — Lesson 6: GPU & EC2 Selection

Now we get into one of the most important **Solution Architect skills**:

> **Given a model + workload + SLO + budget, how do I choose the GPU and AWS instance?**

The wrong approach is:

```text
70B model
   ↓
H100
```

The right approach is:

```text
Customer workload
       ↓
Memory requirement
       ↓
Performance requirement
       ↓
Concurrency
       ↓
SLO
       ↓
Benchmark
       ↓
GPU selection
       ↓
Capacity planning
       ↓
Cost/token
```

AWS maintains the current accelerated-computing instance catalog, including P5/P5e/P5en and newer GPU families. [AWS Accelerated Computing Instances](https://docs.aws.amazon.com/ec2/latest/instancetypes/ac.html?utm_source=chatgpt.com)

---

# 1. First rule: Never choose a GPU from model size alone

Suppose:

```text
Model = 70B
Precision = FP16/BF16
```

Approximate weights:

```text
70B × 2 bytes
≈ 140 GB
```

You might think:

```text
2 × 80 GB H100
= 160 GB
```

Therefore:

> "It fits."

But that is not enough.

You still need:

```text
weights
+ KV cache
+ activations
+ runtime
+ CUDA workspace
+ communication buffers
+ fragmentation
+ headroom
```

So:

```text
160 GB theoretical
```

doesn't mean:

```text
160 GB available for model weights
```

---

# 2. GPU sizing has two independent problems

This is extremely important.

You have:

## Problem A — Can the model fit?

```text
Memory capacity problem
```

and:

## Problem B — Can the GPU serve it fast enough?

```text
Performance/capacity problem
```

These are different.

Example:

```text
GPU A:
192 GB VRAM
lower compute

GPU B:
80 GB VRAM
much higher compute/bandwidth
```

A may fit the model more comfortably.

B may serve it faster.

# 5. Dimension 1 — VRAM capacity

First question:

> Can the model fit?

Approximation:

```text
Weight memory =
parameters × bytes/parameter
```

Examples:

```text
70B BF16
≈ 140 GB

70B FP8
≈ 70 GB

70B INT4
≈ 35 GB
```

But serving memory is:

```text
Model
+
KV
+
Runtime
+
Workspace
+
Overhead
```

So don't size to 100%.

---

# 6. Dimension 2 — HBM bandwidth

Once the model fits, ask:

> How quickly can the GPU move data?

This matters especially for decode-heavy workloads.

Conceptually:

```text
More HBM bandwidth
        ↓
faster weight/KV movement
        ↓
potentially higher token throughput
```

This is why a GPU with more VRAM isn't necessarily the better inference GPU.

---

# 7. Dimension 3 — Tensor Core compute

Now ask:

> How much matrix computation can the GPU perform?

Transformers are dominated by matrix operations:

```text
Linear layers
Attention
MLP
Projections
```

Therefore Tensor Core capability matters significantly.

But again:

```text
Peak TFLOPS
≠
real vLLM tokens/sec
```

Why?

Because real inference includes:

```text
memory bandwidth
batching
KV cache
kernel efficiency
communication
scheduler
CPU
```

---

# 8. Dimension 4 — Interconnect

This becomes critical for multi-GPU inference.

Suppose:

```text
70B model
requires 4 GPUs
```

You might configure:

```text
TP=4
```

Now:

```text
GPU0 ↔ GPU1
GPU0 ↔ GPU2
GPU0 ↔ GPU3
...
```

Communication matters.

So evaluate:

```text
NVLink
NVSwitch
PCIe
network
NCCL
```

For tightly coupled tensor-parallel inference, high-bandwidth GPU-to-GPU communication can be extremely important.

# 10. H100 as a reference point

The H100 is based on NVIDIA's Hopper architecture.

For the H100 SXM, NVIDIA specifies:

```text
80 GB HBM
3.35 TB/s memory bandwidth
900 GB/s NVLink
```

along with substantial Tensor Core performance.

This makes it a strong reference point for learning inference sizing.

But don't turn:

> H100 = best GPU

into a permanent rule.

GPU generations and AWS availability change.

Your skill should be:

> **How to evaluate a GPU**, not memorizing one GPU.

---

# 11. H100 vs H200 — the architectural difference

A simplified way to think about it:

```text
H100
→ excellent compute
→ 80 GB HBM
→ high bandwidth

H200
→ Hopper generation
→ substantially more HBM
→ higher memory bandwidth
```

NVIDIA's H200 specification lists **141 GB HBM3e** and **4.8 TB/s** memory bandwidth.

What does that mean for inference?

Potentially:

```text
larger model
larger KV cache
longer context
more concurrent sequences
less tensor parallelism
```

The last point is especially interesting.

---

# 12. More VRAM can reduce GPU count

Imagine a model requires:

```text
110 GB
```

and your effective per-GPU memory budget is around:

```text
70 GB
```

With an 80 GB-class GPU:

```text
2 GPUs
```

might be necessary.

But if another GPU provides enough usable memory:

```text
1 GPU
```

might become possible.

That can change:

```text
TP
latency
communication
complexity
cost
```

So sometimes:

> **More VRAM isn't just a memory benefit; it changes the architecture.**

# 13. TP vs replicas

This is one of the biggest concepts in GPU infrastructure.

Suppose you have:

```text
8 GPUs
```

You could have:

### Option A

```text
1 replica
TP=8
```

### Option B

```text
2 replicas
TP=4
```

### Option C

```text
4 replicas
TP=2
```

### Option D

```text
8 replicas
TP=1
```

Which is best?

**You cannot answer without benchmarking.**

---

# 14. What TP solves

Tensor parallelism solves:

> **How do I distribute one model across multiple GPUs?**

Example:

```text
70B
 ↓
TP=4

GPU0 → part
GPU1 → part
GPU2 → part
GPU3 → part
```

Useful when:

```text
model doesn't fit on one GPU
```

or:

```text
single-GPU performance is insufficient
```

But TP introduces communication.

---

# 15. What data parallelism solves

Data parallelism is conceptually:

```text
same model
     ↓
multiple independent replicas
```

Example:

```text
Replica 1 → GPU
Replica 2 → GPU
Replica 3 → GPU
Replica 4 → GPU
```

Traffic is distributed between replicas.

This is often attractive for inference because replicas can scale horizontally.

---

# 16. TP and DP together

Real systems can combine them.

Example:

```text
8 GPUs

Replica A
 ├── GPU0
 └── GPU1

Replica B
 ├── GPU2
 └── GPU3

Replica C
 ├── GPU4
 └── GPU5

Replica D
 ├── GPU6
 └── GPU7
```

That's:

```text
TP = 2
DP = 4
```

This is a very important pattern.

---

# 17. Why this can beat TP=8

Compare:

```text
TP=8
```

versus:

```text
4 × TP=2
```

TP=8:

```text
one request
 ↓
8 GPUs
 ↓
lots of communication
```

TP=2:

```text
request
 ↓
2 GPUs

request
 ↓
2 GPUs

request
 ↓
2 GPUs

request
 ↓
2 GPUs
```

The second architecture can have:

```text
more independent requests
less synchronization
more horizontal scalability
```

But again:

> If the model requires TP=8 to fit, this option doesn't exist.

# 18. Sizing starts with memory

Let's do a simplified example.

Customer:

```text
Model = 70B
Precision = FP8
```

Weights:

```text
70B × 1 byte
≈ 70 GB
```

Suppose GPU:

```text
80 GB
```

You have:

```text
80 - 70
= 10 GB
```

remaining.

Can you put:

```text
KV cache
runtime
workspace
```

into 10 GB?

Maybe not enough.

Therefore:

```text
70 GB model
+
80 GB GPU
```

is **not sufficient information**.

# 19. Now quantization changes the architecture

Suppose:

```text
70B BF16
≈ 140 GB
```

You might require:

```text
TP=2+
```

But with FP8:

```text
≈ 70 GB
```

potentially:

```text
TP=1
```

could become possible on an 80 GB GPU, depending on runtime/KV requirements.

That means precision can change:

```text
GPU count
+
TP
+
latency
+
cost
```

This is why AI infrastructure engineers need to understand ML fundamentals.

---

# 20. Context length changes everything

Consider:

```text
Model = 70B
FP8
```

Request A:

```text
Input = 2K
Output = 500
```

Request B:

```text
Input = 100K
Output = 2K
```

Same model.

Completely different infrastructure requirements.

Request B creates:

```text
massive prefill
+
large KV cache
+
higher memory pressure
+
higher latency
```

Therefore:

```text
model size alone
```

is a terrible sizing methodology.

---

# 21. Concurrency matters

Suppose:

```text
1 user
```

versus:

```text
500 concurrent users
```

The GPU doesn't experience these workloads the same way.

Higher concurrency can improve:

```text
GPU utilization
batching
aggregate throughput
```

until you reach saturation.

Then:

```text
queue
 ↓
TTFT increases
 ↓
SLO violation
```

This is why capacity planning needs actual traffic.

---

# 22. RPS is not enough

Suppose someone says:

> “We have 10 requests/sec.”

You still don't know enough.

Because:

```text
10 requests/sec
× 1K input
```

is completely different from:

```text
10 requests/sec
× 100K input
```

And:

```text
10 requests/sec
× 500 output
```

is different from:

```text
10 requests/sec
× 10K output
```

Therefore AI capacity planning should often think in:

```text
input tokens/sec
output tokens/sec
total tokens/sec
```

not only requests/sec.

---

# 23. A useful traffic model

You can estimate:

```text
Input token rate
=
RPS × average input tokens
```

and:

```text
Output token rate
=
RPS × average output tokens
```

Example:

```text
RPS = 5

input = 4K
output = 1K
```

Then:

```text
input:
5 × 4,000
= 20,000 tokens/sec

output:
5 × 1,000
= 5,000 tokens/sec
```

That is much more meaningful for inference capacity planning.

---

# 24. Peak vs average

Never size production solely from average traffic.

Customer:

```text
Average = 5 RPS
Peak = 20 RPS
```

If you provision only for:

```text
5 RPS
```

then peak traffic causes:

```text
queue
latency
SLO violations
```

You need a capacity strategy:

```text
baseline
+
headroom
+
autoscaling
```

---

# 25. Availability changes GPU count

Suppose your calculated requirement is:

```text
2 GPUs
```

for performance.

Does that mean deploy:

```text
2 GPUs
```

?

Not necessarily.

If one GPU/node failure takes down service, your availability architecture may require:

```text
N+1
```

or multiple replicas.

For example:

```text
Required serving capacity = 2 GPUs

Production:
3 GPUs
```

or:

```text
2 independent replicas
```

depending on topology and model requirements.

For:

# 31. Cost per token

Now we reach the **architect level**.

Suppose:

```text
GPU cost = $X/hour
```

and:

```text
sustainable output = Y tokens/sec
```

Then approximate:

```text
tokens/hour
=
Y × 3600
```

And:

```text
$/token
=
GPU $/hour
----------------
tokens/hour
```

Or:

```text
$/1M output tokens
=
GPU $/hour × 1,000,000
-----------------------
sustainable output tokens/hour
```

This is a much more useful business metric than:

> “H100 costs $X/hour.”

---

# 32. Example

Suppose:

```text
GPU cost = $5/hour

output throughput = 1,000 tok/sec
```

Then:

```text
tokens/hour
=
1,000 × 3,600
=
3.6M tokens
```

Therefore:

```text
$/1M tokens
=
$5 / 3.6
≈ $1.39
```

This is simplified because production workloads also include:

```text
input processing
idle capacity
HA
network
storage
orchestration
monitoring
```

But it introduces the right mindset.

---

# 33. Utilization isn't the same as efficiency

Suppose:

```text
GPU A:
95% utilization
1,000 tok/s

GPU B:
75% utilization
1,400 tok/s
```

Which is better?

Potentially B.

Why?

Because:

```text
tokens/sec
```

is the business output.

GPU utilization is only an operational signal.

Your actual goal is:

```text
SLO-compliant tokens
per dollar
```

# 34. The AIRE GPU scorecard

When evaluating a GPU:

| Category     | Question                                     |
| ------------ | -------------------------------------------- |
| VRAM         | Does the model + KV fit?                     |
| HBM          | Is bandwidth sufficient?                     |
| Tensor       | Is compute sufficient?                       |
| Precision    | Does GPU support desired format efficiently? |
| Interconnect | Can TP communicate efficiently?              |
| CPU          | Enough host resources?                       |
| Network      | Enough ingress/egress?                       |
| Availability | Can we obtain enough GPUs?                   |
| Scaling      | Can capacity scale?                          |
| Reliability  | What happens on GPU/node failure?            |
| Cost         | What is $/1M tokens?                         |
| Benchmark    | What does real workload achieve?             |

# 35. Customer conversation framework

Customer:

> “We need GPUs for our 70B model.”

Don't respond:

> “Use H100.”

Instead:

> “Before selecting the GPU, I need the model precision, average/P95 input and output token counts, concurrency, peak request rate, TTFT and TPOT SLOs, availability requirement, and expected traffic growth. I'll use those to determine memory requirements, KV-cache capacity, throughput requirements and parallelism, then benchmark candidate GPU configurations and compare cost per token.”

That is a **Solution Architect answer**.
