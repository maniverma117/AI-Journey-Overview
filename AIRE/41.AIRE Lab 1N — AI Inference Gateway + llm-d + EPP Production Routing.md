# Lab 1N — Production AI Inference Gateway + llm-d EPP Routing

This is a **very important AIRE/Solution Architect lab** because now we move from:

> “Can I run vLLM?”

to:

> **“How do I safely expose, control, route, prioritize, and protect an entire LLM inference platform?”**

At production scale, **vLLM is not your API gateway** and **llm-d EPP is not your authentication/tenant gateway**.

---

# 1. The production architecture

The architecture we are building is:

```text
                         INTERNET
                            │
                            ▼
                     ┌─────────────┐
                     │     WAF     │
                     └──────┬──────┘
                            │
                            ▼
                  ┌───────────────────┐
                  │ ALB / API Gateway │
                  └─────────┬─────────┘
                            │
                            ▼
                  ┌─────────────────────┐
                  │    AI Gateway       │
                  │                     │
                  │ AuthN / AuthZ       │
                  │ Tenant isolation    │
                  │ Rate limits         │
                  │ Token quotas        │
                  │ Cost attribution    │
                  │ Request policy      │
                  │ Priority            │
                  └──────────┬──────────┘
                             │
                             ▼
                 ┌──────────────────────┐
                 │ Kubernetes Gateway   │
                 │      + HTTPRoute     │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │      llm-d EPP       │
                 │                      │
                 │ Filter               │
                 │ Score                │
                 │ Pick                 │
                 │                      │
                 │ KV-aware             │
                 │ Prefix-aware         │
                 │ Queue-aware          │
                 │ SLO-aware            │
                 │ P/D-aware            │
                 │ Fairness             │
                 └──────────┬───────────┘
                            │
               ┌────────────┴─────────────┐
               │                          │
               ▼                          ▼
       ┌────────────────┐        ┌────────────────┐
       │ Prefill Pool   │        │ Decode Pool    │
       │                │        │                │
       │ vLLM           │───────►│ vLLM           │
       │ H100/H200      │ NIXL   │ H100/H200      │
       └────────────────┘ EFA    └────────────────┘
```

The key idea:

### External gateway decides:

**“Is this request allowed?”**

### llm-d decides:

**“Where should this request run?”**

That distinction is fundamental.

# 2. AI Gateway vs llm-d EPP

This is one of the most important interview questions.

| Responsibility               | AI Gateway |            llm-d EPP |
| ---------------------------- | ---------: | -------------------: |
| Authentication               |          ✅ |                    ❌ |
| Authorization                |          ✅ |                    ❌ |
| Tenant identity              |          ✅ |              Limited |
| API keys                     |          ✅ |                    ❌ |
| Rate limiting                |          ✅ | Flow-control related |
| Billing                      |          ✅ |                    ❌ |
| Token quotas                 |          ✅ |              Partial |
| Request policy               |          ✅ |              Partial |
| WAF integration              |          ✅ |                    ❌ |
| Model routing                |  ❌/limited |                    ✅ |
| GPU-aware routing            |          ❌ |                    ✅ |
| KV-aware routing             |          ❌ |                    ✅ |
| Prefix-aware routing         |          ❌ |                    ✅ |
| Queue-aware routing          |          ❌ |                    ✅ |
| P/D routing                  |          ❌ |                    ✅ |
| SLO-aware endpoint selection |          ❌ |                    ✅ |
| Model-server selection       |          ❌ |                    ✅ |

llm-d's EPP performs a **Filter → Score → Pick** scheduling pipeline and can use queue depth, KV utilization, prefix locality, latency, token load, session affinity and other signals. ([Llm-D][1])

So think:

```text
AI Gateway
    │
    │ "Should this request be allowed?"
    ▼
llm-d
    │
    │ "Which GPU/model-server should receive it?"
    ▼
vLLM
    │
    │ "How should tokens be scheduled?"
    ▼
GPU
```

There are actually **three major scheduling layers**:

```text
AI Gateway
    │
    │ admission / tenant / quota
    ▼
llm-d
    │
    │ endpoint selection
    ▼
vLLM
    │
    │ token scheduling / batching
    ▼
GPU
```

# 3. Why a normal Kubernetes Service is not enough

Suppose you have:

```text
vLLM-1
vLLM-2
vLLM-3
vLLM-4
```

A traditional Kubernetes Service might distribute requests approximately:

```text
request 1 → vLLM-1
request 2 → vLLM-2
request 3 → vLLM-3
request 4 → vLLM-4
```

But it doesn't understand:

```text
vLLM-1:
  KV = 30%
  queue = 2
  prefix hit = 80%

vLLM-2:
  KV = 92%
  queue = 40
  prefix hit = 10%

vLLM-3:
  KV = 50%
  queue = 5
  prefix hit = 70%

vLLM-4:
  KV = 40%
  queue = 1
  prefix hit = 0%
```

For an LLM, these are **very different destinations**.

A simple load balancer might send traffic to vLLM-2.

An inference-aware router should probably avoid it.

# 4. EPP decision pipeline

The mental model is:

```text
Request
   │
   ▼
Parse request
   │
   ▼
Flow control
   │
   ▼
Candidate endpoints
   │
   ▼
FILTER
   │
   ├── healthy?
   ├── correct model?
   ├── correct role?
   ├── SLO headroom?
   └── P/D role?
   │
   ▼
SCORE
   │
   ├── KV utilization
   ├── queue depth
   ├── prefix match
   ├── predicted latency
   ├── token load
   ├── session affinity
   └── LoRA affinity
   │
   ▼
PICK
   │
   ▼
vLLM endpoint
```

This is the core of llm-d.

The current llm-d scheduler supports filters such as prefix-cache affinity, SLO-headroom and prefill/decode endpoint filters, and scorers including KV utilization, latency, prefix, queue depth, token load and session affinity. ([Llm-D][1])

# 5. First major production problem: Authentication

Imagine:

```text
Customer A
Customer B
Customer C
```

All call:

```http
POST /v1/chat/completions
```

You need to establish:

```text
Who are you?
        │
        ▼
Are you allowed?
        │
        ▼
Which tenant?
        │
        ▼
Which models?
        │
        ▼
What quota?
        │
        ▼
What priority?
```

For example:

```text
tenant-a:
  models:
    - llama-70b
  max_concurrency: 20
  tokens_per_minute: 2M
  priority: premium

tenant-b:
  models:
    - llama-8b
  max_concurrency: 5
  tokens_per_minute: 500K
  priority: standard

tenant-c:
  models:
    - llama-8b
  max_concurrency: 2
  tokens_per_minute: 100K
  priority: batch
```

The **AI Gateway** should establish the trusted tenant identity.

Don't trust:

```http
X-Tenant-ID: premium-customer
```

from an arbitrary client.

Instead:

```text
Client
  │
  │ API key / OAuth / JWT
  ▼
Gateway
  │
  │ validates identity
  ▼
trusted internal metadata
```

# 6. Tenant identity should become infrastructure metadata

Conceptually:

```text
JWT
 │
 ├── subject
 ├── tenant_id
 ├── scopes
 ├── plan
 └── allowed_models
```

Gateway converts that into internal request metadata:

```text
tenant = customer-a
plan = premium
priority = high
model = gemma-31b
```

Then routing can use that information.

For example:

```text
premium
   ↓
high priority inference objective

standard
   ↓
normal priority

batch
   ↓
low priority
```

# 7. Rate limiting is not enough

This is a classic mistake.

Normal API:

```text
100 requests/minute
```

LLM:

```text
100 requests/minute
```

doesn't tell you much.

These are radically different:

```text
100 × 100 input tokens
```

versus:

```text
100 × 100,000 input tokens
```

The second workload can destroy your inference capacity.

So AI platforms need **token-aware controls**.

---

# 8. Token quotas

Instead of only:

```text
requests/minute
```

use:

```text
requests/minute
+
input tokens/minute
+
output tokens/minute
+
concurrent requests
```

Example:

```text
Tenant A

RPM             = 100
Input TPM       = 2,000,000
Output TPM      = 500,000
Concurrency     = 20
```

This is much closer to actual GPU consumption.

---

# 9. Why concurrency limits matter

Suppose tenant A sends:

```text
1,000 requests
```

with:

```text
max_tokens = 10,000
```

Even if your RPM limit allows it, you could suddenly create:

```text
huge KV demand
+
huge decode demand
+
queue explosion
+
TTFT degradation
```

Therefore:

```text
Admission control
        │
        ├── RPM
        ├── TPM
        ├── concurrency
        ├── max input tokens
        └── max output tokens
```

# 10. Request admission control

This is extremely important for AI reliability.

Without admission control:

```text
Traffic
   │
   ▼
GPU
   │
   ▼
queue
   │
   ▼
queue
   │
   ▼
queue
   │
   ▼
timeouts
```

With admission control:

```text
Traffic
   │
   ▼
Admission
   │
   ├── ACCEPT ──────► GPU
   │
   └── REJECT/DEFER
```

Instead of allowing the entire platform to collapse, you deliberately reject or defer excess work.

This is:

> **Graceful degradation.**

---

# 11. Load shedding

Suppose:

```text
GPU capacity = 100 concurrent sequences
```

Current:

```text
95 running
20 waiting
```

New request arrives.

If you blindly accept:

```text
95
+
20
+
new
```

the queue continues growing.

Eventually:

```text
TTFT ↑
TPOT ↑
timeouts ↑
retries ↑
traffic ↑
```

Now you're in a feedback loop.

A production system may instead say:

```text
capacity unavailable

→ reject low-priority request
→ preserve premium traffic
```

This is much healthier.

---

# 12. Priority

Imagine:

```text
Premium customer:
  "urgent production request"

Batch customer:
  "generate 10 million summaries"
```

You don't want:

```text
batch workload
     ↓
fills all GPUs
     ↓
premium request waits
```

Instead:

```text
Priority

P0 ─ production critical
P1 ─ premium interactive
P2 ─ standard interactive
P3 ─ batch
```

Then scheduling becomes:

```text
priority
   ↓
fairness
   ↓
endpoint selection
```

llm-d EPP currently has flow-control concepts for prioritization and fairness, including fairness IDs and inference objectives. ([Llm-D][2])

---

# 13. Fairness

Suppose:

```text
Tenant A → 90% traffic
Tenant B → 5%
Tenant C → 5%
```

Without fairness:

```text
Tenant A
   │
   ▼
consumes GPU
   │
   ▼
B/C wait
```

This is the classic:

> **Noisy neighbor problem.**

A production AI platform needs isolation.

Conceptually:

```text
                    GPU Pool
                       │
          ┌────────────┼────────────┐
          │            │            │
       Tenant A     Tenant B     Tenant C
          │            │            │
        quota        quota        quota
        queue        queue        queue
```

The current llm-d EPP flow-control architecture explicitly addresses noisy-neighbor protection and fairness across flows. ([Llm-D][3])

---

# 14. Fairness ID

llm-d has:

```http
x-llm-d-inference-fairness-id
```

This identifies a group/flow for fairness handling.

For example:

```http
x-llm-d-inference-fairness-id: tenant-a
```

All requests from tenant A can therefore participate in the same fairness grouping.

If omitted, llm-d uses its default flow behavior. ([Llm-D][2])

This is useful because:

```text
tenant
   ↓
fairness ID
   ↓
flow control
   ↓
fair resource allocation
```

# 15. SLO-aware routing

Now we reach the really interesting part.

Suppose request A says:

```text
TTFT SLO = 500 ms
TPOT SLO = 40 ms
```

Request B says:

```text
TTFT SLO = 5 seconds
TPOT SLO = 100 ms
```

They shouldn't necessarily be routed identically.

llm-d supports:

```http
x-llm-d-slo-ttft-ms
x-llm-d-slo-tpot-ms
```

These allow routing/admission components to reason about the request's latency objective. ([Llm-D][2])

---

# 16. Example

Suppose:

```text
Endpoint A predicted TTFT = 300ms
Endpoint B predicted TTFT = 700ms
Endpoint C predicted TTFT = 1.5s
```

Request:

```text
TTFT SLO = 500ms
```

Then:

```text
A → likely acceptable
B → likely unacceptable
C → unacceptable
```

So:

```text
Request
   │
   ▼
SLO
   │
   ▼
candidate filtering/scoring
   │
   ▼
Endpoint A
```

This is fundamentally different from:

```text
round robin
```

---

# 17. Predicted latency

This is where AI infrastructure becomes very sophisticated.

Instead of:

```text
GPU utilization = 65%
```

you can ask:

> “If I send this request here, what will its TTFT probably be?”

The llm-d ecosystem has predicted-latency scheduling components that use live workload characteristics and predict TTFT/TPOT for scheduling. ([Llm-D][4])

Conceptually:

```text
Request
   │
   ├── input tokens = 40K
   ├── max output = 2K
   ├── SLO TTFT = 800ms
   └── SLO TPOT = 40ms
             │
             ▼
       Latency Predictor
             │
       ┌─────┼─────┐
       ▼     ▼     ▼
      GPU1  GPU2  GPU3
       │     │     │
     450ms 900ms 600ms
       │     │     │
       └─────┼─────┘
             ▼
           GPU1
```

Now routing is effectively a **capacity prediction problem**.

---

# 18. Prefix-aware routing

Consider:

```text
System prompt:
"You are an enterprise financial assistant..."

User request:
"Analyze Q3 revenue..."
```

Many requests may share:

```text
same system prompt
+
same company policy
+
same RAG instructions
```

Suppose:

```text
GPU1 prefix cache:
80% match

GPU2:
0%

GPU3:
10%
```

Sending to GPU1 may dramatically reduce repeated prefill work.

So:

```text
prefix locality
       ↓
routing decision
```

llm-d supports prefix-cache affinity/scoring and can combine this with a TTFT load gate so cache locality does not blindly force traffic onto an overloaded endpoint. ([Llm-D][1])

That's an important architectural principle:

> **Cache affinity should not override SLOs indefinitely.**

---

# 19. KV-aware routing

Suppose:

```text
GPU1 KV = 35%
GPU2 KV = 55%
GPU3 KV = 94%
```

For a large-context request:

```text
prefer GPU1/GPU2
avoid GPU3
```

Because the request may require substantial additional KV capacity.

llm-d has a KV-cache-utilization scorer specifically for this type of routing decision. ([Llm-D][1])

---

# 20. Queue-aware routing

Example:

```text
GPU1 queue = 2
GPU2 queue = 30
GPU3 queue = 5
```

Simple routing:

```text
round robin
```

might select GPU2.

Inference-aware routing:

```text
GPU1
```

The queue-depth scorer is one of the available llm-d scheduling signals. ([Llm-D][1])

---

# 21. Combining signals

Real routing becomes:

```text
Endpoint score =
    prefix affinity
  + KV health
  + queue health
  + predicted latency
  + token load
  + session affinity
  + SLO headroom
```

Conceptually:

```text
                Request
                   │
          ┌────────┴────────┐
          │                 │
       Filters           Scorers
          │                 │
     ┌────┴────┐       ┌────┴──────┐
     │          │       │           │
   healthy    model    prefix      KV
                       queue       latency
                         │
                         ▼
                       score
                         │
                         ▼
                       PICK
```

llm-d's scheduler implements this as configurable filters, weighted scorers and a picker. ([Llm-D][1])

# 22. P/D routing makes it even harder

From our previous lab:

```text
                    Request
                       │
                       ▼
                 llm-d EPP
                  /       \
                 /         \
                ▼           ▼
          PREFILL          DECODE
             │                │
             │     KV         │
             └──────►─────────┘
                   NIXL
```

Now EPP must select:

```text
Prefill endpoint
+
Decode endpoint
```

not just one endpoint.

The current llm-d scheduler has a `disagg-profile-handler` specifically for this pattern: it schedules prefill and decode separately, with the decode endpoint becoming the primary destination and the prefill endpoint passed through specialized request metadata. ([Llm-D][1])

---

# 23. The routing problem becomes a graph

Without P/D:

```text
Request → GPU
```

With P/D:

```text
             ┌── Prefill GPU
Request ─────┤
             └── Decode GPU
```

But the optimal pair isn't necessarily:

```text
P1 → D1
```

You may have:

```text
P1 → D1
P1 → D2
P2 → D1
P2 → D2
```

And each pair has different:

```text
KV transfer bandwidth
queue
KV capacity
latency
network congestion
prefix locality
```

So routing becomes a **pair-selection optimization problem**.

---

# 24. Timeout budgeting

This is another common production mistake.

Suppose:

```text
Client timeout = 30 sec
```

But internal components each have:

```text
Gateway = 30s
Router = 30s
Prefill = 30s
Decode = 30s
```

That is dangerous.

You want a **deadline budget**.

Example:

```text
Client deadline = 30s

Gateway         29s
Router          28s
Prefill         25s
KV transfer     23s
Decode          22s
```

Not:

```text
30 + 30 + 30 + 30
```

Otherwise a request can survive internally long after the client has disappeared.

# 25. Client cancellation

Streaming makes this particularly important.

User:

```text
curl /v1/chat/completions
```

vLLM starts generating:

```text
token 1
token 2
token 3
token 4
...
```

Client disconnects.

If cancellation isn't propagated:

```text
Client gone
   │
   X
   │
Gateway
   │
   ▼
llm-d
   │
   ▼
vLLM
   │
   ▼
GPU still generating
```

That's wasted GPU capacity.

Correct behavior:

```text
client disconnect
      ↓
gateway cancellation
      ↓
router cancellation
      ↓
vLLM cancellation
      ↓
sequence released
      ↓
KV/resources released
```

This is an **AI FinOps + reliability** issue, not just API correctness.

# 26. Retries are dangerous for LLMs

Imagine:

```text
Request
   │
   ▼
vLLM
   │
timeout
   │
   ▼
retry
   │
   ▼
vLLM
```

But maybe the original request wasn't actually dead.

Now:

```text
1 request
→ 2 requests
```

If 1,000 requests timeout:

```text
1,000
→ 2,000
```

Now the extra traffic creates more load.

More load:

```text
→ longer queues
→ more timeout
→ more retries
→ more load
```

This is a:

# Retry Storm

---

# 27. The AI retry rule

For inference:

> **Retry only when you understand whether the request is safe to retry.**

Especially for:

```text
streaming
long-running generation
tool calls
agent workflows
non-idempotent external actions
```

LLM inference itself is usually computationally repeatable, but an **agent request may not be**.

For example:

```text
LLM
 │
 └── tool call
       │
       └── charge credit card
```

You absolutely don't want:

```text
timeout
↓
retry
↓
charge again
```

Therefore:

```text
LLM retry policy
+
tool/action idempotency
```

must be designed together.

# 28. Backpressure

Think of backpressure as:

> “Stop accepting work faster than the system can safely process it.”

Architecture:

```text
                    Arrival
                       │
                       ▼
                 Admission
                       │
              ┌────────┴────────┐
              │                 │
          capacity            saturated
              │                 │
              ▼                 ▼
           ACCEPT          WAIT/REJECT
                                │
                                ▼
                         graceful degradation
```

Without backpressure:

```text
traffic → queue → queue → queue → OOM → outage
```

With backpressure:

```text
traffic → controlled queue → GPU
                    │
                    └── reject excess
```

# 29. Multi-tenant architecture

For a serious platform I'd structure traffic approximately as:

```text
                    AI Gateway
                         │
             ┌───────────┼───────────┐
             │           │           │
          Tenant A    Tenant B    Tenant C
             │           │           │
           quota       quota       quota
           policy      policy      policy
             │           │           │
             └───────────┼───────────┘
                         │
                      llm-d
                         │
                 inference pools
```

Then potentially:

```text
                   Model A
                     │
              ┌──────┼──────┐
              ▼      ▼      ▼
            H100    H100    H100

                   Model B
                     │
              ┌──────┼──────┐
              ▼      ▼      ▼
            H200    H200    H200
```

You can isolate tenants logically without necessarily dedicating GPUs per tenant.

# 30. When should you dedicate GPUs?

Three approaches:

### Shared pool

```text
Tenant A ─┐
Tenant B ─┼──► shared GPU pool
Tenant C ─┘
```

Cheapest.

But requires strong quotas/fairness.

---

### Dedicated pool

```text
Enterprise A
     │
     ▼
dedicated H100 pool
```

Better isolation.

Higher cost.

---

### Hybrid

Usually more realistic:

```text
Premium tenants
       │
       ▼
dedicated/warm capacity

Standard tenants
       │
       ▼
shared pool

Batch
       │
       ▼
low-priority/Spot pool
```

This is exactly the sort of tradeoff a Solution Architect should be able to defend.

# 31. Kubernetes Gateway API

At the Kubernetes networking layer, Gateway API gives us:

```text
Gateway
   │
   ▼
HTTPRoute
   │
   ▼
backend
```

`HTTPRoute` is a GA Gateway API resource for routing HTTP requests from a Gateway to backend objects. ([Gateway API][5])

llm-d's current Gateway Mode integrates with Kubernetes Gateway infrastructure and uses `InferencePool` for inference endpoints. ([Llm-D][6])

# 32. InferencePool

Current llm-d `InferencePool` is:

```yaml
apiVersion: inference.networking.k8s.io/v1
kind: InferencePool
```

It defines:

```text
which Pods belong to the pool
+
which ports are endpoints
+
which EPP should perform endpoint selection
```

The current API uses a label selector and target ports, and references an Endpoint Picker extension. ([Llm-D][7])

Conceptually:

```yaml
apiVersion: inference.networking.k8s.io/v1
kind: InferencePool
metadata:
  name: gemma-pool
spec:
  selector:
    matchLabels:
      app: gemma
  targetPorts:
    - number: 8000
  endpointPickerRef:
    name: gemma-epp
```

**Important:** treat this as a conceptual manifest for understanding the objects; exact Gateway/GAIE/llm-d installation manifests should be generated from the versioned llm-d chart/docs you deploy.

# 33. HTTPRoute

Conceptually:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: llm-route
spec:
  parentRefs:
    - name: inference-gateway

  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /v1/

      backendRefs:
        - name: inference-pool
```

The exact backend integration depends on the Gateway API Inference Extension implementation/controller.

Don't blindly copy a random blog's YAML here.

That's an important production habit:

> **CRDs are APIs. Always match manifests to the installed CRD/controller version.**


This is the direction I'd study for production Kubernetes platforms. llm-d's current Gateway documentation describes Gateway Mode as the production-oriented integration with Kubernetes Gateway infrastructure. ([Llm-D][6])

# 35. One very important EPP HA detail

Don't assume:

```text
EPP replicas = throughput
```

Current llm-d Router operations documentation says the default multi-replica EPP deployment uses active-passive leader election, where one replica actively handles routing decisions and the others are warm standbys. Simply increasing replicas therefore doesn't necessarily increase routing throughput. ([Llm-D][8])

This is a **great interview trap**.

Question:

> “I need 10× routing throughput. I'll scale EPP from 2 to 20.”

Bad answer.

You first ask:

```text
Which HA mode?
Active-active?
Active-passive?
What is the actual EPP bottleneck?
Prefix matching?
Latency predictor?
Request rate?
CPU?
Memory?
```

# 39. The feedback loop you must understand

This is one of the most important diagrams in the entire curriculum:

```text
                    Traffic
                       │
                       ▼
                 AI Gateway
                       │
                       ▼
                 Admission
                       │
                       ▼
                    llm-d
                       │
              ┌────────┴────────┐
              ▼                 ▼
           Routing           Scaling
              │                 │
              ▼                 ▼
            vLLM              KEDA
              │                 │
              ▼                 ▼
             GPU             Karpenter
              │                 │
              └────────┬────────┘
                       │
                       ▼
                   Metrics
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
         TTFT         KV           GPU
          │            │            │
          └────────────┼────────────┘
                       │
                       ▼
                    Routing
```

These control loops can interact badly.

For example:

```text
GPU busy
 ↓
KEDA scales
 ↓
new pod
 ↓
Karpenter launches GPU
 ↓
model downloads
 ↓
pod not ready
 ↓
existing GPUs become overloaded
 ↓
EPP queues increase
 ↓
TTFT increases
 ↓
KEDA scales again
```

You can accidentally create an **autoscaling storm**.

Therefore:

> Routing, admission control, autoscaling and capacity planning must be designed as one system.
