# 🚀 Lesson 14 — GPU Autoscaling for LLM Inference

Absolutely. Now we move into one of the **most important AIRE topics**:

> **How do you automatically add/remove expensive GPUs while keeping LLM latency within SLO?**

This is where Kubernetes autoscaling knowledge meets **LLM-specific behavior**.

And there is one key idea I want you to remember throughout this lesson:

> **For LLM inference, scaling the application and scaling the GPU infrastructure are two different problems.**

AWS's current EKS guidance explicitly describes inference autoscaling as two stages: HPA/KEDA scales the model replicas, while Karpenter provisions the GPU nodes needed to run those replicas. ([AWS Documentation][1])

# 3. HPA vs KEDA vs Karpenter

This distinction will come up constantly in interviews.

| Component            | Controls        | Question                                           |
| -------------------- | --------------- | -------------------------------------------------- |
| HPA                  | Pod replicas    | How many pods?                                     |
| KEDA                 | Pod replicas    | Should replicas respond to external/event metrics? |
| Kubernetes Scheduler | Pod placement   | Which node?                                        |
| Karpenter            | Nodes           | How many EC2 nodes?                                |
| vLLM scheduler       | Requests/tokens | Which request runs when?                           |

### HPA

HPA can say:

```text
1 replica → 2 replicas → 4 replicas
```

based on a metric.

### KEDA

KEDA extends Kubernetes autoscaling to external/event-driven metrics. Its current scaler catalog includes Prometheus, SQS, Kafka, CloudWatch, etc. ([KEDA][2])

For AI inference, Prometheus is particularly useful:

```text
vLLM / router metrics
       ↓
Prometheus
       ↓
KEDA
       ↓
HPA
       ↓
Deployment replicas
```

### Karpenter

Karpenter does **not** decide:

> "I need 4 vLLM replicas."

Instead, it sees something like:

```text
Pod A → Pending
Pod B → Pending
```

because there isn't enough GPU capacity.

Then:

```text
Karpenter
    ↓
find compatible EC2 instance
    ↓
launch node
    ↓
node joins EKS
    ↓
GPU discovered
    ↓
scheduler places pod
```

AWS currently recommends Karpenter for changing/spiky capacity and emphasizes that it provisions nodes based on pending workload requirements rather than relying on traditional fixed node groups. ([AWS Documentation][3])

# 4. Why GPU Utilization Is a Bad Primary Autoscaling Signal

This is one of the most important lessons.

Suppose:

```text
GPU utilization = 98%
```

You might think:

> "Scale!"

Not necessarily.

A vLLM GPU could sit around high utilization while still serving requests within your SLO.

Conversely:

```text
GPU utilization = 70%
TTFT P95 = 4 seconds
queue = 50 requests
```

You absolutely have a problem.

AWS explicitly recommends **leading inference metrics rather than GPU utilization alone**, particularly queue depth, TTFT/request latency and KV-cache utilization. ([AWS Documentation][1])

For CPU applications:

```text

     ↓

     ↓

     ↓
```

For an LLM:

```text

 ↓

NVIDIA driver
 ↓

 ↓
```

# 9. The Critical Concept: Scale Before the User Feels It

Suppose:

```text
Current capacity = 100 req/s
Traffic = 95 req/s
```

Looks okay.

Then:

```text
traffic = 120 req/s
```

You are already overloaded.

If GPU startup takes 2 minutes:

```text
T+0       overload starts
T+10 sec  HPA detects
T+15 sec  Karpenter starts
T+60 sec  EC2 ready
T+90 sec  model loading
T+120 sec replica ready
```

Your users suffered for two minutes.

Therefore you need:

```text
                    Traffic forecast
                          │
                          ▼
                   ┌─────────────┐
                   │ Warm GPU    │
                   │ capacity    │
                   └──────┬──────┘
                          │
                    traffic spike
                          │
                          ▼
                     serve fast
```

This introduces:

# Warm Capacity

Instead of:

```text
0 GPUs → spike → create GPUs
```

you might maintain:

```text
2 warm GPUs
```

and dynamically add:

```text
2 → 4 → 8
```

This costs more but dramatically reduces cold-start risk.

# 11. Autoscaling Is Actually a Queueing Problem

This is where your AIRE thinking becomes much stronger.

A useful queueing relationship is:

$$
L = \lambda W
$$

where:

* `L` = number of requests in system
* `λ` = arrival rate
* `W` = average time in system

This is **Little's Law**.

Example:

```text
arrival rate = 10 requests/sec

average request latency = 2 sec
```

Then:

$$
L = 10 \times 2 = 20
$$

Approximately:

```text
20 requests
```

are in the system.

If latency increases:

```text
W = 5 sec
```

then:

$$
L = 10 \times 5 = 50
$$

Now your system has:

```text
50 active/in-flight requests
```

That explains why latency and queue depth are deeply connected.

# 13. Token-Based Capacity Planning

This is another major AIRE concept.

Suppose benchmarking tells us one replica sustainably handles:

```text
30,000 input tokens/sec
+
10,000 output tokens/sec
```

under your SLO.

Your production demand is:

```text
90,000 input tok/s
+
30,000 output tok/s
```

Then approximately:

```text
required replicas
=
90k / 30k
=
3
```

and:

```text
30k / 10k
=
3
```

So:

```text
3 replicas
```

before headroom.

With 30% headroom:

$$
3 \times 1.3 = 3.9
$$

Therefore:

```text
4 replicas
```

is the practical target.

This is much better than:

```text
GPU utilization > 70% → scale
```

---

# 14. But Sustainable Capacity Matters

Don't benchmark:

> maximum throughput.

Benchmark:

> **maximum throughput while meeting the SLO.**

Example:

```text
Replica capacity

Load       Output tok/s     P95 TTFT
---------------------------------------
Low             8k             400ms
Medium         12k             500ms
High           16k             800ms
Very high      20k            2.5s
```

If your SLO is:

```text
P95 TTFT < 1 sec
```

then:

```text
20k tok/s
```

is **not** your capacity.

Your sustainable capacity might be:

```text
16k tok/s
```

Therefore:

$$
Capacity_{replica}=16k
$$

not:

$$
20k
$$

This is one of the most important distinctions in capacity engineering.

---

# 15. LLM Autoscaling Formula

A useful conceptual model:

$$
Replicas =
\left\lceil
\frac{Demand}
{SustainableCapacityPerReplica}
\right\rceil
$$

Then:

$$
Replicas_{final}
=
\left\lceil
\frac{Demand}
{Capacity}
\times
Headroom
\right\rceil
$$

Example:

```text
Demand = 70k output tok/s

Sustainable replica capacity = 20k

Headroom = 1.25
```

Then:

$$
\frac{70}{20}\times1.25=4.375
$$

Therefore:

```text
5 replicas
```

# 19. Don't Make Autoscaling Too Sensitive

This creates:

# Autoscaling Thrashing

Example:

```text
2 replicas
 ↓
queue 6
 ↓
3 replicas
 ↓
queue 2
 ↓
2 replicas
 ↓
queue 7
 ↓
3 replicas
```

You now have:

```text
2 → 3 → 2 → 3 → 2 → 3
```

This is terrible for GPU infrastructure.

Why?

Because every scale operation may cause:

```text
GPU allocation
model loading
cache loss
routing changes
node provisioning
node termination
```

---

# 20. Hysteresis

You want:

```text
Scale UP quickly
Scale DOWN slowly
```

For example:

```text
Scale UP:
queue > 5

Scale DOWN:
queue < 1
for 5 minutes
```

So small fluctuations don't cause GPU churn.

Kubernetes HPA supports configurable scale-up/down policies and stabilization windows specifically to control this kind of flapping. ([Kubernetes][6])

---

# 21. Production HPA Behavior

Conceptually:

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0

  scaleDown:
    stabilizationWindowSeconds: 300
```

Meaning:

```text
UP:
don't wait too long

DOWN:
wait 5 minutes
```

For LLMs this is often much safer than symmetric behavior.

# 22. Why Scale Down Is Dangerous for LLMs

Suppose:

```text
GPU node
  ↓
vLLM
  ↓
KV cache
  ↓
active requests
```

Karpenter decides:

> "This node is underutilized."

It might attempt consolidation.

But moving that workload means:

```text
terminate old vLLM
        ↓
KV cache lost
        ↓
model reload / warmup
        ↓
new pod
        ↓
latency spike
```

Therefore:

> **GPU consolidation is not equivalent to CPU consolidation.**

You must account for:

* model load time
* KV cache
* active requests
* warm state
* prefix cache
* replica startup
* SLO
* disruption budget

AWS currently recommends disruption controls such as PDBs and Karpenter disruption controls for GPU inference workloads. ([AWS Documentation][1])

# 23. Karpenter Consolidation

Current Karpenter supports policies such as:

```text
WhenEmpty
WhenEmptyOrUnderutilized
Balanced
```

and controls such as:

```text
consolidateAfter
disruption budgets
```

The current documentation describes consolidation as actively reducing cost by removing empty/underutilized nodes or replacing them when cheaper capacity can satisfy workloads. ([Karpenter][7])

For LLMs, I'd be conservative.

For example:

```yaml
disruption:
  consolidationPolicy: WhenEmpty
```

can be a safer starting point for a latency-critical model than aggressively consolidating active GPU nodes.

# 33. Karpenter + GPU Capacity Diversification

Scale down should look like:

```text

      ↓

      ↓

      ↓

      ↓

      ↓

      ↓
GPU freed
      ↓

```

Not:

```text

 ↓
kill pod
 ↓
active users get errors
```

# 47. Interview Question

### Question

> Why shouldn't you autoscale an LLM inference service purely on GPU utilization?

### Weak answer

> Because GPU utilization isn't accurate.

### Strong AIRE answer

> GPU utilization measures whether the GPU is busy, but not how much inference capacity remains under the application's latency SLO. LLM workloads can maintain high GPU utilization while still meeting latency requirements, or have moderate GPU utilization while experiencing queueing, KV-cache pressure, CPU/tokenization bottlenecks, or communication bottlenecks. Therefore I would use inference-level leading indicators such as request queue depth and TTFT/latency, with KV-cache utilization as a memory-capacity safeguard, while using GPU metrics primarily for diagnosis and capacity analysis.

That is the answer I want you to be able to give.

AWS's current guidance makes essentially this same distinction. ([AWS Documentation][1])

# 48. Interview Question

### HPA vs Karpenter?

Your answer:

> HPA/KEDA controls workload replicas, while Karpenter provisions the underlying nodes needed to satisfy those replicas. In GPU inference, HPA can increase vLLM replicas based on queue depth or latency, which can leave pods Pending when GPU capacity is exhausted. Karpenter observes those unschedulable pods and provisions compatible GPU nodes. Kubernetes scheduling then places the replicas on the new nodes.

Excellent.
