# 🚀 Lab 1T — AI Capacity Engineering & Production Benchmarking

This is probably the **most important lab for your Solution Architect goal**.

Until now we've said:

> "Benchmark the model."

Now we're going to learn **exactly how to turn customer traffic into GPU capacity**.

---

## 1. The mistake we must eliminate

Customer says:

> "We have 500 users. How many H100s do we need?"

Bad answer:

```text
500 users
→ 8 H100
```

We don't know enough.

Instead:

```text
500 users
       ↓
concurrent requests
       ↓
RPS
       ↓
input token distribution
       ↓
output token distribution
       ↓
TTFT/TPOT SLO
       ↓
KV requirement
       ↓
benchmark
       ↓
sustainable GPU capacity
       ↓
replicas
       ↓
N+1
       ↓
GPU count
```

That's the AIRE/Solution Architect approach.

---

# 2. User count ≠ workload

Suppose:

```text
500 registered users
```

Doesn't mean:

```text
500 simultaneous inference requests
```

Could actually be:

```text
500 users
 ↓
50 active
 ↓
20 concurrent requests
```

or:

```text
500 users
 ↓
300 active
 ↓
150 concurrent requests
```

Completely different GPU requirement.

---

### Performance


### Availability


### Architecture

```text
single GPU?

```

### Economics

```text

```

# 4. Example customer

Let's use:

```text
Model: 70B
Precision: FP8
Context: 128K
Users: 500
Peak concurrency: 100
Peak RPS: 20
```

Token workload:

```text
P50 input = 2K
P95 input = 16K
P99 input = 64K

P50 output = 300
P95 output = 2K
P99 output = 4K
```

SLO:

```text
P95 TTFT < 1 sec
P95 TPOT < 50ms
```

Availability:

```text
99.99%
```

Now we can start engineering.

---

# 5. First calculation — token demand

Suppose peak:

```text
20 requests/sec
```

and average:

```text
2K input tokens
```

Then:

```text
Input token rate
=
20 × 2,000

= 40,000 input tokens/sec
```

Output:

```text
20 × 300

= 6,000 output tokens/sec
```

Total:

```text
46,000 tokens/sec
```

But **do not immediately size GPUs from 46K tok/s**.

Why?

Because input and output behave differently.

---

# 6. Prefill vs decode

Input:

```text
2K tokens
```

mostly creates:

```text
PREFILL
```

Output:

```text
300 tokens
```

creates:

```text
DECODE
```

So we really have:

```text
40K input tok/s
+
6K output tok/s
```

with different compute/memory characteristics.

---

# 7. P95 matters more than average

Suppose:

```text
average input = 2K
P95 = 16K
P99 = 64K
```

If you size using:

```text
2K
```

you may get:

```text
average traffic = healthy
P95 traffic = terrible
```

Therefore benchmark distributions.

---

# 8. Capacity isn't one-dimensional

This is critical.

Your GPU has multiple limits:

```text
                GPU
                 │
     ┌───────────┼───────────┐
     ▼           ▼           ▼
   Compute      HBM         KV
     │           │           │
     ▼           ▼           ▼
  Prefill      Weights    Concurrency
                 │
                 ▼
             Bandwidth
```

And:

```text
Network
CPU
NCCL
PCIe
NVLink
Scheduler
```

can become additional bottlenecks.

---

# 9. Sustainable capacity

Suppose benchmark gives:

```text
1 H100 / replica

At:
P95 TTFT < 1s
P95 TPOT < 50ms

sustainable capacity:
4,500 output tok/s
```

We could calculate:

```text
Required replicas
=
Demand / sustainable capacity
```

For output:

```text
6,000 / 4,500
=
1.33
```

So:

```text
2 replicas
```

But we're not finished.

---

# 10. Failure headroom

99.99% availability means we need redundancy.

If:

```text
2 replicas
```

and one dies:

```text
1 replica
```

remaining.

Can one handle the workload?

Maybe not.

Therefore:

```text
N
+
failure capacity
```

is required.

For example:

```text
3 replicas
```

may be needed so that:

```text
3 healthy
 ↓
1 failure
 ↓
2 healthy
 ↓
still meet SLO
```

That's **N+1 capacity**.

---

# 11. But what if TP4?

Suppose benchmark shows:

```text
TP4
=
4 GPUs / replica
```

Then:

```text
3 replicas
×
4 GPUs

=
12 GPUs
```

Now your answer isn't:

> "3 GPUs."

It is:

> **12 H100 GPUs arranged as three TP4 inference replicas.**

Much more precise.

---

# 12. Benchmarking is mandatory

Before production sizing:

```text
candidate architecture
       ↓
benchmark
       ↓
find saturation point
       ↓
find SLO-constrained capacity
```

Example:

```text
Load          P95 TTFT
-----------------------
10 RPS         350ms
20 RPS         520ms
30 RPS         700ms
40 RPS         930ms
50 RPS       1,800ms
```

SLO:

```text
< 1 second
```

Therefore:

```text
~40 RPS
```

is around the sustainable boundary.

But production shouldn't necessarily operate exactly at that boundary.

---

# 13. Add headroom

Suppose:

```text
sustainable = 40 RPS
```

Peak demand:

```text
30 RPS
```

You might want:

```text
20–30% headroom
```

So:

```text
30 × 1.25
=
37.5 RPS
```

One replica with:

```text
40 RPS
```

could technically work.

But then:

```text
failure
```

could immediately violate the SLO.

Hence:

```text
2 replicas
```

may be the correct production architecture.

---

# 14. The important equation

Memorize this:

```text
Required Capacity
=
Peak Demand
×
Headroom
×
Failure Factor
÷
SLO-constrained Sustainable Capacity
```

Then:

```text
GPU Count
=
Required Replicas
×
GPUs per Replica
```

---

# 15. But there's another trap

Suppose benchmark says:

```text
1 H100
=
4,500 output tok/s
```

Your customer says:

```text
"Great, 6,000 / 4,500 = 2 GPUs."
```

Not necessarily.

Because benchmark conditions may have been:

```text
2K input
300 output
```

while production P95 is:

```text
16K input
2K output
```

That can drastically change:

```text
prefill pressure
KV memory
batching
TTFT
decode behavior
```

Therefore:

> **Capacity numbers are only meaningful together with workload shape.**

# 17. Capacity curve

You should visualize:

```text
Latency
  │
  │                       /
  │                     /
  │                  /
  │               /
  │           ___/
  │       ___/
  │_____/
  └──────────────────────── Load
```

The important point is:

```text
        saturation
            ↓
           /
          /
---------/---------- SLO
        ↑
 sustainable capacity
```

Once you enter the nonlinear region:

```text
queue
 ↓
TTFT
 ↓
SLO violation
```

can explode quickly.

---

# 18. This explains autoscaling

Your KEDA/HPA system from Lab 1Q should ideally scale **before** this point.

For example:

```text
Healthy
   │
   ▼
70% capacity
   │
   ▼
scale out
   │
   ▼
new GPU replica
   │
   ▼
capacity restored
```

Not:

```text
GPU = 100%
   ↓
wait
   ↓
queue explodes
   ↓
start GPU
```

because GPU startup isn't instantaneous.

---

# 19. Startup time belongs in capacity planning

Suppose:

```text
Karpenter node startup = 90 sec
Model loading = 120 sec
Warmup = 30 sec
```

Total:

```text
~240 seconds
```

If traffic doubles in:

```text
30 seconds
```

reactive autoscaling cannot save you.

You need:

```text
warm capacity
+
predictive scaling
+
queueing
+
load shedding
```

# 20. The Solution Architect answer

When a customer asks:

> "How many GPUs?"

Don't answer immediately.

Say:

> "I need your peak arrival rate, concurrency, input/output token distributions, latency SLOs, availability requirement, model architecture and precision. I'll then benchmark the candidate GPU/runtime configuration using production-shaped traffic and derive sustainable SLO-constrained capacity. From that we'll calculate replicas, failure headroom and the final GPU fleet."

That is the answer I want you to internalize.
