# Lab 1M — P/D Hands-On on EKS: llm-d + vLLM + NIXL + EFA

Now we turn the P/D architecture into an **actual Kubernetes deployment design**.

One important current-version correction before we start: vLLM's current P/D implementation is still marked **experimental**, while llm-d provides orchestration around P/D and its latest docs describe the routing sidecar, `prefill`/`decode` profiles, and NIXL-based KV transfer. ([vLLM][1])

So for this lab, the objective is **not** "copy this YAML into production." The objective is:

> Build the complete mental and operational model, validate each layer independently, then assemble the system.

---

# 1. Final architecture

We're building:

```text
                         CLIENT
                           │
                           ▼
                      AI Gateway
                           │
                           ▼
                       llm-d EPP
                           │
                 ┌─────────┴─────────┐
                 │                   │
                 ▼                   ▼
             PREFILL              DECODE
             PROFILE              PROFILE
                 │                   │
        ┌────────┴──────┐     ┌──────┴────────┐
        │               │     │               │
       P1              P2    D1              D2
        │               │     │               │
       vLLM            vLLM  vLLM            vLLM
        │               │     │               │
       GPU             GPU   GPU             GPU
        │               │     │               │
        └─────── NIXL / EFA / RDMA ─────────┘
                         │
                       KV Cache
```

The critical path is:

```text
Request
   ↓
llm-d
   ↓
Prefill P1
   ↓
KV generated
   ↓
NIXL
   ↓
EFA/RDMA
   ↓
Decode D1
   ↓
Streaming response
```

Current llm-d documentation describes this P/D flow as a combination of **request-flow orchestration + efficient KV transfer**, with RDMA recommended for production-quality transfer. ([Llm-D][2])

# 7. Layer 4 — vLLM NIXL

Current vLLM uses:

```text
--kv-transfer-config
```

for the NIXL connector.

A simplified producer configuration is:

```bash
vllm serve <MODEL> \
  --port 8100 \
  --enforce-eager \
  --kv-transfer-config '{
    "kv_connector": "NixlConnector",
    "kv_role": "kv_producer",
    "kv_connector_extra_config": {
      "backends": ["LIBFABRIC"]
    }
  }'
```

And the decoder:

```bash
vllm serve <MODEL> \
  --port 8200 \
  --enforce-eager \
  --kv-transfer-config '{
    "kv_connector": "NixlConnector",
    "kv_role": "kv_consumer",
    "kv_connector_extra_config": {
      "backends": ["LIBFABRIC"]
    }
  }'
```

Current vLLM documentation shows `NixlConnector` with `kv_producer` and `kv_consumer` roles and supports `LIBFABRIC` as a NIXL backend. ([vLLM][5])

**Do not blindly copy these flags into your exact vLLM version.** The P/D interfaces are evolving quickly.

# 8. Understand producer vs consumer

This terminology is important.

### Prefill

```text
P
│
├── processes prompt
├── generates KV
└── produces KV
```

Therefore:

```text
kv_role = kv_producer
```

### Decode

```text
D
│
├── receives KV
└── continues generation
```

Therefore:

```text
kv_role = kv_consumer
```

Conceptually:

```text
P
 │
 │ PUT / SEND KV
 ▼
NIXL
 │
 │ RECEIVE KV
 ▼
D
```

---

# 9. What NIXL is actually moving

It's not:

```text
whole model
```

It's:

```text
KV cache
```

The model itself exists on both sides.

Think:

```text
P node:

Model weights
+
Input
   ↓
KV

D node:

Model weights
+
KV
   ↓
Output
```

So:

```text
Model
```

must already be loaded on both sides.

NIXL doesn't magically move your 70B model.

It moves inference state.

---

# 10. Very important: both P and D need the model

You might ask:

> "If P computes the prompt, why does D need the model?"

Because D needs the model to continue autoregressive generation.

So:

```text
Prefill:

Model + prompt
      ↓
KV
```

and:

```text
Decode:

Model + KV + last token
      ↓
next token
```

Therefore:

```text
P model ✓
D model ✓
```

This is why P/D does not eliminate model-memory cost.

# 17. The request flow without llm-d

Start simple.

```text
Client
  │
  ▼
P Proxy
  │
  ▼
Prefill
  │
  │ KV metadata
  ▼
Decode
  │
  ▼
Client
```

The proxy needs to:

1. choose a prefiller
2. send the request
3. obtain KV-transfer metadata
4. forward the appropriate metadata to decoder
5. stream decoder output

Current vLLM provides example proxy implementations for this type of P/D flow. ([vLLM][5])

---

# 18. Then llm-d takes over

Instead of writing:

```text
custom P/D proxy
```

we use:

```text
llm-d
```

Now:

```text
Client
  │
  ▼
llm-d
  │
  ├── choose P
  │
  └── choose D
```

The current llm-d architecture uses a routing proxy sidecar with decode pods for this multi-step P/D request flow. ([Llm-D][2])

---

# 19. Why the decode sidecar exists

This is subtle.

The request isn't simply:

```text
request → D
```

The sidecar can transform the request into:

```text
request
   ↓
P
   ↓
KV metadata
   ↓
D
```

For vLLM's current protocol, llm-d describes a two-phase flow in which the sidecar sends the prefill request with KV-transfer metadata, captures the resulting transfer parameters, then injects those into the decode request. ([Llm-D][2])

So:

```text
Client
   │
   ▼
Decode sidecar
   │
   ├──── P
   │      │
   │      └── KV
   │
   └──── D
```

The sidecar is effectively an orchestration adapter.

# 24. P/D pair selection

Imagine:

```text
P1:
queue = 5

P2:
queue = 20
```

and:

```text
D1:
active = 80

D2:
active = 20
```

A sensible decision might be:

```text
P2? ❌
D1? ❌

P1 + D2 ✓
```

So the request becomes:

```text
Request
  ↓
P1
  ↓
KV
  ↓
D2
```

That is a **pair-selection problem**, not merely endpoint selection.

---

# 25. Why pair selection matters

Suppose:

```text
P1
```

has an excellent prefix cache.

But:

```text
D1
```

is overloaded.

You have a tradeoff:

```text
P1 + D1
```

versus:

```text
P2 + D2
```

where P2 has no prefix cache.

The scheduler has to balance:

```text
prefill cost
+
KV reuse
+
decode load
+
transfer cost
+
SLO
```

This is where intelligent inference routing becomes genuinely interesting.

The request lifecycle now becomes:

```text
T0:

T1:

T2:
P starts prefill

T3:
KV becomes available

T4:
NIXL transfers KV

T5:
D receives KV

T6:

stream continues
```

Therefore:

```text

=
routing
+
prefill queue
+
prefill compute
+
KV transfer
+
decode startup
```

This is your observability model.

# 28. Failure policy

Now one of the most important production questions:

> What happens if KV transfer fails?

Current llm-d operational documentation explicitly describes vLLM P/D fault-tolerance policies including `fail` versus `recompute`. ([Llm-D][6])

Conceptually:

### Fail

```text
P ✓
KV transfer ❌
D
 ↓
request fails
```

### Recompute

```text
P ✓
KV transfer ❌
      ↓
D recomputes required state
      ↓
higher latency
      ↓
request succeeds
```

Tradeoff:

```text
fail
=
lower resource waste
+
higher error rate

recompute
=
higher latency/compute
+
better availability
```

This is classic reliability engineering.

---

# 29. What should production use?

Don't blindly choose.

Define:

```text
P(error)
KV transfer failure rate
recompute cost
SLO
```

Then decide.

For a strict availability service:

```text
recompute
```

may be attractive.

For an extremely latency-sensitive service:

```text
fail
```

might be preferable in some circumstances.

Or you can implement:

```text
primary transfer
      ↓
retry
      ↓
recompute
```

depending on supported behavior and application requirements.

# 31. Don't let the control loops fight

Imagine:

```text
Prefill queue ↑
```

KEDA adds P nodes.

But:

```text
Decode capacity ↓
```

So KV piles up.

Now:

```text
D queue ↑
```

KEDA adds D nodes.

But now:

```text
P overprovisioned
```

You need balanced control.

A useful mental model:

```text
P capacity
   ↓
KV production rate
   ↓
D capacity
```

The two pools are coupled through:

```text
KV flow
```

Therefore:

> **P/D autoscaling is a coupled control system.**

---

# 32. Backpressure

Suppose:

```text
P capacity = 100 requests/sec
D capacity = 40 requests/sec
```

Then:

```text
P
100/s
 ↓
KV
100/s
 ↓
D
40/s
```

You create a backlog.

So you need:

```text
backpressure
```

The router should avoid accepting unlimited work simply because prefill capacity exists.

This is another reason:

```text
queue
+
capacity
+
SLO
```

must be considered jointly.

# 40. Current implementation caution

This is especially important for your career.

Current vLLM documentation explicitly labels disaggregated prefilling as **experimental** and says it **does not improve throughput inherently**; its main value is separately tuning TTFT/ITL and controlling tail ITL. ([vLLM][1])

So if a customer says:

> "Can P/D double our throughput?"

Your answer should be:

> "Not inherently. P/D primarily separates prefill and decode resource contention and lets us independently tune them. Throughput gains, if any, depend on workload characteristics and resource efficiency. We need to benchmark the integrated and disaggregated architectures under the target SLO."

That is exactly the kind of distinction a senior AI architect needs to make.
