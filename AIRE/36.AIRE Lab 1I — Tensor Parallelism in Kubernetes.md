# 1. The problem TP solves

Suppose we have:

```text
70B parameter model
```

Even with FP8:

```text
70B × 1 byte
≈ 70 GB weights
```

And that is **before**:

* KV cache
* CUDA workspace
* runtime overhead
* activations
* batching
* allocator fragmentation
* safety margin

So a single:

```text
H100 80GB
```

may not be enough for a useful serving configuration.

Instead:

```text
                70B Model
                    │
          ┌─────────┼─────────┐
          │         │         │
        GPU 0     GPU 1     GPU 2 ... GPU 3
          │         │         │
          └─────────┼─────────┘
                    │
                  NCCL
                    │
               NVLink/PCIe
```

We split the model across GPUs.

This is **Tensor Parallelism (TP)**.

vLLM officially recommends single-node tensor parallelism when the model is too large for one GPU but fits within the GPUs of a single node. ([vLLM][1])

---

# 2. TP = splitting the computation

The important thing:

> TP does **not** simply mean "copy the model onto four GPUs."

That's Data Parallelism.

Instead:

```text
TP = split model computation/parameters
DP = replicate model
```

For example:

```text
                 Transformer Layer
                       │
              ┌────────┴────────┐
              │                 │
          GPU 0 shard        GPU 1 shard
              │                 │
              └────────┬────────┘
                       │
                    NCCL
```

Each GPU owns only part of the tensors.

---

# 3. Simple matrix example

Imagine:

```text
Y = X × W
```

Suppose:

```text
X = [batch × 8]

W = [8 × 16]
```

With TP=2:

```text
W
┌───────────────┐
│       │       │
│ GPU 0 │ GPU 1 │
│ 8×8   │ 8×8   │
│       │       │
└───────────────┘
```

Each GPU computes:

```text
GPU0:
X × W0

GPU1:
X × W1
```

Then the partial results have to be combined.

That communication is where:

> **NCCL becomes extremely important.**

---

# 4. Why NVLink matters

Imagine:

```text
GPU0 ───── GPU1
 │           │
 │ NVLink   │
 │           │
GPU2 ───── GPU3
```

TP requires communication between GPUs.

Therefore:

```text
TP performance
        ↓
GPU compute
        +
GPU memory bandwidth
        +
GPU interconnect
        +
NCCL efficiency
```

This is why:

> **4 GPUs in one tightly connected node can sometimes outperform 8 GPUs spread across multiple nodes.**

The raw GPU count is not enough.

# 5. TP=1 vs TP=2 vs TP=4 vs TP=8

Think of a model:

```text
70B
```

Possible deployments:

### TP=1

```text
1 replica

GPU0
└── complete model
```

Requires enough VRAM.

---

### TP=2

```text
GPU0 ── GPU1
  │       │
 model   model
 shard   shard
```

Two GPUs cooperate.

---

### TP=4

```text
GPU0 ─┐
GPU1 ─┼── model replica
GPU2 ─┤
GPU3 ─┘
```

---

### TP=8

```text
GPU0 ─┐
GPU1 ─┤
GPU2 ─┤
GPU3 ─┤
GPU4 ─┼── one model replica
GPU5 ─┤
GPU6 ─┤
GPU7 ─┘
```

Now one model replica consumes:

```text
8 GPUs
```

This has major architectural consequences.

---

# 6. Critical concept: TP does NOT automatically make inference faster

This is one of the most important interview questions.

You might think:

```text
1 GPU → 100 tok/s

4 GPUs → 400 tok/s
```

Not necessarily.

Realistically:

```text
1 GPU
100 tok/s

2 GPU
180 tok/s

4 GPU
300 tok/s

8 GPU
350 tok/s
```

Why?

Because:

```text
more GPUs
   ↓
more parallel computation
   ↓
more communication
   ↓
NCCL overhead
   ↓
synchronization
```

Eventually:

```text
communication overhead
>
additional compute benefit
```

So:

> **TP has diminishing returns.**

# 7. The famous TP=8 mistake

Suppose someone tells you:

> "We have 8 H100s. Let's use TP=8 because that's fastest."

🚨 **Wrong architecture decision.**

You should benchmark:

```text
TP=1
TP=2
TP=4
TP=8
```

if the model fits.

Then compare:

```text
                    TP1 TP2 TP4 TP8
TTFT
TPOT
throughput
GPU memory
GPU utilization
NCCL overhead
$/1M tokens
```

Your final decision might actually be:

```text
TP=4
+
2 replicas
```

instead of:

```text
TP=8
+
1 replica
```

# 8. This is a HUGE production distinction

Consider:

### Architecture A

```text
8 GPUs

       vLLM
        │
   ┌────┼────┐
   │    │    │
 GPU0 ...   GPU7

       TP=8
```

One replica.

---

### Architecture B

```text
8 GPUs

 Replica 1          Replica 2
 ┌───────┐          ┌───────┐
 │ GPU0  │          │ GPU4  │
 │ GPU1  │          │ GPU5  │
 │ GPU2  │          │ GPU6  │
 │ GPU3  │          │ GPU7  │
 └───────┘          └───────┘

   TP=4                TP=4
```

Two independent replicas.

Now:

```text
Total GPUs = 8
```

but:

```text
TP=8 → 1 serving unit

TP=4 → 2 serving units
```

This dramatically changes:

* concurrency
* availability
* scaling
* failure domain
* routing
* capacity
* cost
* maintenance

# 9. Why TP=4 × 2 replicas can be better

Suppose each TP4 replica can handle:

```text
100 requests/sec
```

Then:

```text
Replica 1 → 100 RPS
Replica 2 → 100 RPS

Total → 200 RPS
```

With TP8:

```text
Replica 1 → maybe 140 RPS
```

Even though both consume:

```text
8 GPUs
```

TP4×2 may win.

But there's another enormous advantage.

# 10. Failure domain

### TP=8

```text
GPU0
GPU1
GPU2
GPU3
GPU4
GPU5
GPU6
GPU7
 │
 └── one replica
```

If:

```text
GPU3 fails
```

the entire replica fails.

So:

```text
1 GPU failure
      ↓
8-GPU replica unavailable
      ↓
traffic affected
```

---

### TP4 × 2

```text
Replica A       Replica B

GPU0            GPU4
GPU1            GPU5
GPU2            GPU6
GPU3            GPU7
```

GPU2 fails:

```text
Replica A ❌

Replica B ✅
```

You still have:

```text
50% capacity
```

instead of:

```text
0% capacity
```

This is why:

> **parallelism strategy is also an availability decision.**

# 11. Kubernetes changes everything

Now let's bring Kubernetes into the picture.

A normal GPU pod:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

means:

```text
give this pod one GPU
```

For TP=4:

```yaml
resources:
  limits:
    nvidia.com/gpu: 4
```

Conceptually:

```text
Pod
 │
 ├── GPU0
 ├── GPU1
 ├── GPU2
 └── GPU3
```

The important point:

> **The four GPUs belong to one pod.**

You don't normally create:

```text
Pod 1 → GPU0
Pod 2 → GPU1
Pod 3 → GPU2
Pod 4 → GPU3
```

for a conventional TP deployment.

You create:

```text
one vLLM pod
        │
        ├── GPU0
        ├── GPU1
        ├── GPU2
        └── GPU3
```

# 12. Basic TP4 Kubernetes deployment

For a lab, something conceptually like:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm-tp4
spec:
  replicas: 1
  selector:
    matchLabels:
      app: vllm-tp4
  template:
    metadata:
      labels:
        app: vllm-tp4
    spec:
      nodeSelector:
        gpu-type: h100

      tolerations:
      - key: nvidia.com/gpu
        operator: Exists
        effect: NoSchedule

      containers:
      - name: vllm
        image: vllm/vllm-openai:latest

        args:
        - "--model"
        - "YOUR_MODEL"
        - "--tensor-parallel-size"
        - "4"

        resources:
          requests:
            nvidia.com/gpu: 4
          limits:
            nvidia.com/gpu: 4
```

The important relationship is:

```text
Kubernetes:

nvidia.com/gpu = 4

        ↓

vLLM:

--tensor-parallel-size 4
```

These should agree.

---

# 13. What happens if they don't?

Imagine:

```yaml
nvidia.com/gpu: 4
```

but:

```text
--tensor-parallel-size 8
```

You are asking vLLM for:

```text
8 GPUs
```

while Kubernetes gave:

```text
4 GPUs
```

That deployment cannot work correctly.

Conversely:

```yaml
nvidia.com/gpu: 8
```

and:

```text
--tensor-parallel-size 4
```

could leave resources underutilized depending on deployment architecture.

Always think:

```text
Kubernetes resource allocation
             ↕
vLLM parallelism configuration
```

# 14. One very important Kubernetes detail

The scheduler sees:

```text
nvidia.com/gpu: 4
```

as a resource request.

But historically, device plugins expose GPUs largely as integer resources.

That means Kubernetes doesn't inherently understand:

```text
GPU0 and GPU1 have NVLink
GPU2 and GPU3 are across PCIe
GPU4 is attached to another NUMA domain
```

The topology problem is deeper than simply:

```text
4 GPUs available
```

Kubernetes Topology Manager can coordinate device allocation using topology information supplied by device plugins. ([Kubernetes][2])

And modern EKS has moved further toward **DRA**, which can expose richer GPU attributes and topology-aware allocation. AWS recommends NVIDIA DRA for new EKS 1.34+ deployments using static capacity, while the NVIDIA device plugin remains broadly supported and is recommended in several dynamic-capacity scenarios. ([AWS Documentation][3])

# 15. Why topology matters

Imagine:

```text
        PCIe Switch
        /         \
     GPU0         GPU1
       \           /
        NVLink

        PCIe Switch
        /         \
     GPU2         GPU3
       \           /
        NVLink
```

This may be excellent:

```text
GPU0 ↔ GPU1
GPU2 ↔ GPU3
```

But perhaps:

```text
GPU0 ↔ GPU7
```

requires a much slower path.

So two different TP4 placements can have different performance.

That's why you should always inspect:

```bash
nvidia-smi topo -m
```

# 17. TP and KV cache

Here's an important nuance.

TP doesn't simply mean:

> "KV cache gets divided perfectly across GPUs forever."

The KV cache is also affected by the attention architecture and the parallelism strategy.

For ordinary tensor parallelism, KV heads are sharded across GPUs where supported.

But as TP becomes very large relative to the number of KV heads, duplication/inefficiencies can arise. Current vLLM documentation explicitly discusses this and introduces decode-context parallelism for further KV-cache sharding in such cases. ([vLLM][4])

This becomes especially interesting with:

```text
long context
+
many concurrent requests
+
large TP
```

because KV cache can become the actual bottleneck.

# 18. TP and memory

Suppose:

```text
Model weights = 140 GB
```

With TP=4, approximately:

```text
140 / 4
≈ 35 GB per GPU
```

That leaves room for:

```text
KV cache
+
runtime
+
CUDA workspace
```

But **don't** interpret this as:

```text
140 / 4 = exact GPU requirement
```

Real memory usage includes additional components.

That's why vLLM reports the resulting KV-cache capacity after initialization. ([vLLM][1])

# 19. TP and batching

This is where production optimization becomes interesting.

Suppose:

```text
TP=4
```

and one request arrives.

All four GPUs participate.

Now:

```text
100 concurrent requests
```

The same four GPUs can work together on batches.

Therefore TP doesn't mean:

```text
GPU0 handles request 1
GPU1 handles request 2
```

Instead, think:

```text
                 Request batch
                      │
              ┌───────┴───────┐
              │ Transformer   │
              │ computation   │
              └───────┬───────┘
                      │
           ┌──────────┼──────────┐
           ▼          ▼          ▼
         GPU0       GPU1       GPU2 ... GPU3
           │          │          │
           └──────────┼──────────┘
                    NCCL
```

Each request still flows through the complete model computation.

The tensors are distributed.

---

# 20. TP vs DP — memorize this

|                 | Tensor Parallel        | Data Parallel          |
| --------------- | ---------------------- | ---------------------- |
| Model           | Split                  | Replicated             |
| Purpose         | Fit / accelerate model | Increase throughput    |
| GPUs cooperate? | Yes                    | Mostly independently   |
| KV cache        | Per TP shard           | Separate per replica   |
| Communication   | High                   | Lower for dense models |
| Failure domain  | TP group               | Individual replica     |
| Scaling         | Model size/performance | Request throughput     |
| Typical use     | Large model            | Multiple replicas      |

vLLM describes DP as replicating model weights across independent GPU sets for independent request batches. ([vLLM][5])

# 22. The Solution Architect question

Customer says:

> "We have 8 H100 GPUs. Which TP should we use?"

Your answer should **not** be:

> "TP=8."

Instead:

> "First we determine whether the model fits on one GPU. If not, we identify the minimum TP required to fit it while preserving enough memory for KV cache and runtime overhead. Then we benchmark TP2/4/8 under the customer's actual input/output distribution and SLO. We also compare that with multiple smaller TP replicas because replica granularity affects throughput, availability, autoscaling and failure domains."

🔥 **That is an AIRE/Solution Architect answer.**

# 26. Multi-node TP

Now we reach the dangerous territory.

Suppose:

```text
Node A
8 GPUs

Node B
8 GPUs
```

Total:

```text
16 GPUs
```

You could theoretically do:

```text
TP=16
```

But now the TP communication crosses:

```text
Node A
   ↓
NIC
   ↓
EFA/RDMA
   ↓
NIC
   ↓
Node B
```

instead of staying inside:

```text
GPU
 ↓
NVLink
 ↓
GPU
```

Huge architectural difference.

vLLM supports multi-node distributed inference, including combinations such as TP across GPUs per node and PP across nodes. ([vLLM][1])

---

# 27. Preferred multi-node pattern

For:

```text
2 nodes
8 GPUs/node
```

a common layout is:

```text
TP=8
PP=2
```

Meaning:

```text
Node A
GPU0-7
   │
   │ TP
   ▼
Pipeline stage 0

        ↓ network

Node B
GPU0-7
   │
   │ TP
   ▼
Pipeline stage 1
```

Total:

```text
8 × 2 = 16 GPUs
```

vLLM documents this pattern as a common approach for multi-node deployments. ([vLLM][1])

---

# 28. Why not TP16?

Because then the tensor-parallel communication domain spans:

```text
Node A + Node B
```

and communication can become much more expensive.

You need:

```text
NCCL
+
EFA
+
RDMA
+
GPUDirect RDMA
+
correct topology
```

This is why our previous:

> **Lab 1J — Multi-node vLLM + NCCL + EFA**

will be significantly harder.

# 29. Kubernetes architecture for TP

Production:

```text
                    AI Gateway
                         │
                    llm-d Router
                         │
                 ┌───────┴───────┐
                 │               │
             TP4 Replica A   TP4 Replica B
                 │               │
          ┌──────┼──────┐  ┌─────┼──────┐
          ▼      ▼      ▼  ▼     ▼      ▼
        GPU0   GPU1   GPU2 GPU4  GPU5  GPU6
                 │               │
              NCCL            NCCL
                 │               │
              GPU3            GPU7
```

Now:

```text
llm-d
```

chooses the replica.

Inside each replica:

```text
vLLM
```

handles token scheduling.

Inside vLLM:

```text
NCCL
```

handles GPU communication.

Inside Kubernetes:

```text
scheduler
```

handles pod placement.

And:

```text
Karpenter
```

handles physical node provisioning.

This is the **four-layer scheduling system** we're building toward:

```text
AI Gateway / llm-d
        ↓
request routing

vLLM
        ↓
token scheduling

Kubernetes
        ↓
pod/GPU placement

Karpenter
        ↓
EC2 capacity
```

# 35. Interview questions

You should now be able to answer these without memorizing definitions:

### Q1

**Why can TP4 outperform TP8?**

Expected:

> Because TP increases parallel computation but also increases synchronization and communication overhead. If communication and synchronization dominate, adding GPUs reduces scaling efficiency.

---

### Q2

**Why might TP4×2 be better than TP8×1?**

Expected:

> Two independent replicas provide greater request-level parallelism, better failure granularity, more flexible autoscaling and potentially better throughput, provided the model fits and each TP4 replica meets the latency SLO.

---

### Q3

**What happens if one GPU in a TP8 group fails?**

Expected:

> The TP group generally becomes unavailable because all ranks participating in the model replica are required. Therefore the failure domain is the entire TP8 replica.

---

### Q4

**Why does GPU topology matter?**

Expected:

> TP requires frequent inter-GPU communication. NVLink/NVSwitch, PCIe topology, NUMA locality and, for multi-node deployments, EFA/RDMA can materially affect NCCL communication performance.

---

### Q5

**How does TP affect Kubernetes autoscaling?**

Expected:

> The scaling unit becomes the complete TP replica. A TP4 deployment needs four GPUs per additional replica, so scaling is less granular than TP1 and may require provisioning an entire suitable GPU node.

---

### Q6

**Would you choose TP8 just because the node has 8 GPUs?**

Correct answer:

> No. I would benchmark the minimum TP that satisfies model-memory and SLO requirements, then compare throughput, latency, KV capacity, communication overhead, availability and cost across TP configurations.
