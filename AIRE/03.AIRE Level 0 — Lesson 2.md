# 1. First: what is a Transformer?

Modern LLMs such as GPT-style models are based on the **Transformer architecture** introduced in the famous 2017 paper *Attention Is All You Need*. [Attention Is All You Need — arXiv](https://arxiv.org/abs/1706.03762?utm_source=chatgpt.com)

The high-level structure is:

```text
Text
 ↓
Tokenizer
 ↓
Token IDs
 ↓
Embeddings
 ↓
Transformer
 ↓
Logits
 ↓
Token
```

But the Transformer itself contains many repeated blocks.

```text
                    Transformer

Input embeddings
       │
       ▼
┌──────────────────────┐
│ Transformer Layer 1  │
└──────────┬───────────┘
           │
┌──────────▼───────────┐
│ Transformer Layer 2  │
└──────────┬───────────┘
           │
           ⋮
           │
┌──────────▼───────────┐
│ Transformer Layer N  │
└──────────┬───────────┘
           │
           ▼
        Logits
```

A 70B model might have dozens of such layers.

# 2. What is an embedding?

Previously we saw:

```text
"Kubernetes"
      ↓
Token ID
```

The model needs a richer representation than:

```text
42381
```

So it maps the token ID to a vector.

For example:

```text
Token ID
  42381
     │
     ▼
Embedding
     │
     ▼
[0.21, -0.17, 0.92, ...]
```

Maybe:

```text
Embedding dimension = 4096
```

Then every token becomes a vector with 4096 numbers.

Conceptually:

```text
Token 1 → vector
Token 2 → vector
Token 3 → vector
Token 4 → vector
```

Together:

```text
       sequence

        ↓

┌─────────────────┐
│ token vector 1  │
│ token vector 2  │
│ token vector 3  │
│ token vector 4  │
│ ...             │
└─────────────────┘
```

This is the input to the Transformer.

# 3. Why does position matter?

Consider:

```text
Dog bites man
```

versus:

```text
Man bites dog
```

Same words.

Different meaning.

The model therefore needs information about **position/order**.

Historically, Transformers used positional encodings.

Modern LLMs often use techniques such as **RoPE — Rotary Positional Embeddings**.

You don't need to derive RoPE mathematically yet.

For AIRE purposes:

```text
Token
 +
Position information
       ↓
Transformer input
```

RoPE is particularly important later when discussing:

```text
long context
context extension
KV cache
attention
performance
```

A useful reference is the original RoFormer paper. [RoFormer: Enhanced Transformer with Rotary Position Embedding — arXiv](https://arxiv.org/abs/2104.09864?utm_source=chatgpt.com)

# 4. Now the famous Q, K, V

This is the most important part of today's lesson.

Attention uses:

```text
Q = Query
K = Key
V = Value
```

Imagine a sentence:

```text
"The server crashed because it ran out of memory."
```

When processing:

```text
"it"
```

the model needs to determine what "it" refers to.

Attention lets the current token determine which other tokens are relevant.

Conceptually:

```text
                 "it"
                  │
                  ▼
               Query
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
     server     crashed     memory
       │          │           │
       K          K           K
       │          │           │
       └──────────┼───────────┘
                  │
              similarity
                  │
                  ▼
             attention
                  │
                  ▼
               Values
```

This is simplified, but the intuition is important.

---

# 5. What does Q actually mean?

Think:

> **"What information am I looking for?"**

The current token produces a Query.

```text
Current token
      ↓
     Q
```

---

# 6. What does K mean?

Think:

> **"What information do I represent, and how relevant am I to this query?"**

Each token has a Key.

```text
Token 1 → K1
Token 2 → K2
Token 3 → K3
...
```

---

# 7. What does V mean?

Think:

> **"If you decide I'm relevant, what information should I provide?"**

Each token has a Value.

```text
Token 1 → V1
Token 2 → V2
Token 3 → V3
```

Therefore:

```text
Q
+
K
+
V
```

are the fundamental building blocks of attention.

---

# 8. The attention calculation

The classic Transformer attention equation is:

```text
Attention(Q,K,V)
=
softmax(QKᵀ / √dₖ)V
```

Don't panic. 😄

For an AIRE, understand the pipeline:

```text
Q
 │
 ├─────── compare ───────┐
 │                       │
 ▼                       ▼
K                     similarity
                         │
                         ▼
                    attention scores
                         │
                         ▼
                       softmax
                         │
                         ▼
                  weighted Values
                         │
                         ▼
                       output
```

That's what matters operationally.

---

# 9. Why is QKᵀ important?

It calculates how strongly a Query matches Keys.

Imagine:

```text
Query = "it"

Keys:

server     → 0.80
crashed    → 0.10
memory     → 0.60
because    → 0.20
```

After softmax, these become attention weights.

Something conceptually like:

```text
server     █████████
crashed    █
memory     ██████
because    ██
```

Then the model combines the corresponding Values.

This lets the model construct contextual information.

# 10. Multi-head attention

One attention operation isn't enough.

So Transformers use multiple **attention heads**.

Imagine:

```text
                 Input
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
      Head 1     Head 2     Head 3
        │          │          │
        ▼          ▼          ▼
     pattern     syntax     meaning
        │          │          │
        └──────────┼──────────┘
                   ▼
                Combine
```

Different heads can learn different relationships.

Real models have many heads.

For example:

```text
32 heads
64 heads
80 heads
```

depending on architecture.

---

# 11. Why should an AIRE care about heads?

Because later you'll encounter:

```text
MHA
GQA
MQA
```

These aren't random acronyms.

They determine how much KV-cache memory is required.

This is directly relevant to:

```text
GPU VRAM
concurrency
long context
throughput
```

# 12. Multi-Head Attention — MHA

Traditional Multi-Head Attention:

```text
Queries
 ├── Q1
 ├── Q2
 ├── Q3
 └── ...

Keys
 ├── K1
 ├── K2
 ├── K3
 └── ...

Values
 ├── V1
 ├── V2
 ├── V3
 └── ...
```

Every attention head has its own K and V.

That creates a substantial KV-cache footprint.

---

# 13. Why KV cache can become huge

Suppose:

```text
Context = 128K tokens
```

And:

```text
many layers
×
many KV heads
×
large head dimension
```

Then:

```text
KV cache
```

can consume many GB of GPU memory.

This is one reason long-context inference is difficult.

---

# 14. GQA

Modern models frequently use **Grouped Query Attention (GQA)**.

The basic idea:

```text
Many Query heads

       ↓

Fewer KV heads
```

For example:

```text
Query heads:

Q Q Q Q Q Q Q Q
│ │ │ │ │ │ │ │

KV groups:

K V     K V
│ │     │ │
└─┴─────┴─┴─
```

Instead of every query head having independent K/V heads, multiple query heads share K/V heads.

Result:

```text
KV cache ↓
GPU memory ↓
```

while retaining much of the modeling capability of MHA.

The GQA paper provides the underlying architecture and memory motivation. [GQA — arXiv](https://arxiv.org/abs/2305.13245?utm_source=chatgpt.com)

---

# 15. MQA

Another approach is **Multi-Query Attention**.

Instead of:

```text
Q1 → K1 V1
Q2 → K2 V2
Q3 → K3 V3
Q4 → K4 V4
```

you can have:

```text
Q1 ─┐
Q2 ─┤
Q3 ─┼──► K V
Q4 ─┘
```

So all Query heads share one K/V pair.

That dramatically reduces KV memory.

Tradeoff:

```text
KV memory ↓↓↓

but

potential quality/modeling tradeoffs
```

---

# 16. The architecture evolution

Think:

```text
MHA
 │
 ├── lots of KV heads
 │
 └── high KV memory
       ↓
GQA
 │
 ├── fewer KV heads
 │
 └── lower KV memory
       ↓
MQA
 │
 ├── very few KV heads
 │
 └── very low KV memory
```

This is one of the reasons you must know **model architecture**, not just parameter count.

Two models can both be:

```text
70B
```

but have different inference characteristics.

---

# 17. This is an interview question

### Interviewer:

> Two 70B models have the same parameter count. Will they require exactly the same GPU resources?

### Strong AIRE answer:

> No. Parameter count primarily determines weight memory, but inference memory and performance also depend on architecture, precision, KV-cache configuration, context length, number of layers, attention/KV heads, head dimension, concurrency, batching, and runtime overhead. Models using GQA/MQA can have substantially different KV-cache requirements from traditional MHA models.

That's the type of answer we're targeting.

# 19. What is an MLP?

MLP = Multi-Layer Perceptron.

It's basically a feed-forward neural network component.

Conceptually:

```text
Input
  │
  ▼
Linear
  │
  ▼
Activation
  │
  ▼
Linear
  │
  ▼
Output
```

Modern LLMs may use variants such as:

```text
GELU
SwiGLU
other gated architectures
```

We'll discuss those only when they become operationally relevant.

---

# 20. Why is MLP important for GPUs?

Because MLP layers involve large matrix multiplications.

Something like:

```text
Input matrix
     ×
Weight matrix
     ↓
Large matrix
```

This is exactly the kind of operation GPUs and Tensor Cores are very good at.

Therefore:

```text
Transformer
    ↓
Matrix operations
    ↓
GPU
    ↓
Tensor Cores
```

# 21. Attention vs MLP

A useful operational distinction:

```text
Transformer Layer

┌───────────────────────┐
│ Attention             │
│                       │
│ Q/K/V                 │
│ KV cache              │
│ sequence interaction  │
└──────────┬────────────┘
           │
           ▼
┌───────────────────────┐
│ MLP                   │
│                       │
│ large matrix multipl. │
│ compute-heavy         │
└───────────────────────┘
```

Attention has strong sequence/context dependencies.

MLP performs huge matrix operations.

This difference matters when reasoning about performance.

# 22. Residual connections

You may see:

```text
x → attention → y
```

but Transformer architectures commonly use residual connections:

```text
              ┌──────────────┐
              │              │
              │              ▼
Input ───────► Attention ───► +
  │                           │
  └───────────────────────────┘
```

Conceptually:

```text
output = input + transformation(input)
```

This helps deep networks train effectively.

You don't need to become a research expert on this for AIRE.

# 25. What are logits?

After the final Transformer layer:

```text
Hidden representation
       ↓
Output projection
       ↓
Logits
```

Suppose the vocabulary contains:

```text
100,000 possible tokens
```

The model produces a score for every possible next token.

Conceptually:

```text
"Kubernetes"
      0.8

"automatically"
      4.2

"banana"
      -2.1

"cloud"
      1.7

...
```

These are **logits**.

Higher score means the model considers that token more likely before sampling/normalization.

---

# 26. Softmax

Logits are converted into probabilities.

Conceptually:

```text
logits

 ↓ softmax

probabilities
```

Example:

```text
Kubernetes      0.05
automatically   0.60
cloud           0.20
banana          0.01
...
```

Then the sampling strategy chooses the next token.

---

# 27. Temperature

You will see:

```text
temperature
```

everywhere in LLM APIs.

Very roughly:

```text
temperature low
     ↓
more deterministic
```

while:

```text
temperature high
     ↓
more randomness
```

Conceptually:

```text
Low temperature

A = 0.90
B = 0.08
C = 0.02
```

versus:

```text
Higher temperature

A = 0.50
B = 0.30
C = 0.20
```

The exact probability transformation is more nuanced, but this is the correct intuition.

---

# 28. Top-p

Another common parameter:

```text
top_p
```

Instead of considering every possible token, the sampler can restrict choices to a probability mass.

For example:

```text
top_p = 0.9
```

means approximately:

> Consider the smallest group of highest-probability tokens whose cumulative probability reaches 90%.

Then sample from that set.

For infrastructure:

```text
temperature
top_p
```

are generally **application/model behavior controls**, not primary GPU scaling controls.

That's an important distinction.

# 34. Interview scenario #1

### Interviewer:

> Our model has a 128K context window. Does that mean every request uses 128K tokens?

Answer:

> No. 128K is the maximum supported context length, not the actual request length. Actual KV-cache consumption depends on the number of tokens in the request and generated sequence. A workload with mostly 5K-token contexts behaves very differently from one using 100K-token contexts.

---

# 35. Interview scenario #2

### Interviewer:

> Why does increasing max context length affect GPU capacity even when most requests are short?

Good answer:

> The configured maximum context can influence how the inference engine plans and allocates KV-cache capacity, depending on the runtime and configuration. More importantly, allowing long sequences means the system must be capable of accommodating larger KV-cache requirements, which can reduce the number of concurrent sequences that fit in GPU memory.

Don't say:

> "128K context means 128K KV cache is permanently allocated for every request."

That's generally incorrect.

---

# 36. Interview scenario #3

### Interviewer:

> GPU utilization is 98%, but TTFT is getting worse. Is the system healthy?

Strong answer:

> Not necessarily. GPU utilization alone isn't a sufficient inference SLI. I'd inspect queue depth, running/waiting requests, TTFT percentiles, inter-token latency, KV-cache utilization, request token lengths and throughput. If TTFT is violating the SLO, the system may be saturated even though GPU utilization looks healthy.

Excellent AIRE answer.

---

# 37. Interview scenario #4

### Interviewer:

> Why can increasing concurrency improve throughput?

Answer:

> LLM inference engines can use continuous/in-flight batching to execute work from multiple requests together. Higher concurrency can provide more work for the GPU and improve utilization and aggregate tokens/sec. However, after saturation, queueing increases and TTFT/latency can deteriorate. Therefore the objective is maximum throughput while maintaining the latency SLO.

That's an **AIRE answer**, not simply a vLLM answer.

---

# 38. Interview scenario #5

### Interviewer:

> Why does GQA help long-context inference?

Answer:

> GQA uses fewer KV heads than Query heads, so the KV cache requires less memory than traditional MHA. This can increase the number of concurrent sequences that fit into GPU memory, which is particularly valuable for long-context workloads.

---

# 39. Interview scenario #6

### Interviewer:

> Two models are both 32B. Can we assume the same GPU sizing?

Answer:

> No. Parameter count is only the first approximation for weight memory. Architecture, precision, number of layers, hidden size, attention heads, KV heads, context length, KV-cache datatype, quantization, batching behavior and runtime overhead can all change the actual GPU requirement and performance.

Excellent.

```text
vLLM configuration

```

This is deliberately ambiguous.

There isn't enough information to size it correctly.
