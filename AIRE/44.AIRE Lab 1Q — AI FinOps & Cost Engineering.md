# Lab 1Q — AI FinOps & GPU Cost Engineering

Now we answer the question every customer eventually asks:

> **“How much will this AI platform cost, and what architecture gives me the lowest cost while still meeting my SLO?”**

This is where **AIRE + Solution Architect** thinking becomes much stronger.

A bad answer is:

> “H100 costs $X/hour.”

A production answer is:

> “Given your token workload, SLO, model, precision, batching behavior, failure domain and sustainable throughput per replica, we need X GPU capacity, costing approximately Y, with Z% headroom. Here are the cheaper alternatives and their SLO trade-offs.”

---

But AI has a special characteristic:

> **GPU cost is strongly coupled to token generation and memory capacity.**

# 5. The most important AI FinOps metric

I want you to remember:

# $ / 1M output tokens

Suppose:

```text
GPU cost = $10/hour

Sustainable output =
20,000 tokens/sec
```

Hourly tokens:

```text
20,000 × 3,600
=
72,000,000 tokens/hour
```

Cost:

```text
$10 / 72M tokens
```

Therefore:

```text
$0.139 / 1M output tokens
```

That is far more useful than simply saying:

> “This GPU costs $10/hour.”

# 13. GPU utilization isn't cost efficiency

Suppose:

```text
GPU A:
95% utilization
$10/hour

GPU B:
70% utilization
$5/hour
```

GPU A isn't necessarily better.

What matters:

```text
useful tokens/sec
÷
GPU cost
```

Example:

```text
GPU A:
20K tok/s
$10/h

GPU B:
15K tok/s
$5/h
```

Efficiency:

```text
A = 2K tok/s per $/hour
B = 3K tok/s per $/hour
```

GPU B is economically better.

# 14. SLO-constrained cost

Now add latency.

Suppose:

```text
GPU A:
20K tok/s
P95 TTFT = 700ms
$10/h

GPU B:
15K tok/s
P95 TTFT = 2.5s
$5/h
```

Customer requirement:

```text
P95 TTFT < 1s
```

GPU B may be cheaper but **doesn't satisfy the requirement**.

So the correct metric is:

> **Cost per useful capacity while satisfying the SLO.**

# 15. The Pareto frontier

Imagine benchmark results:

```text
Configuration      Cost      TTFT      Throughput
--------------------------------------------------
TP2                 $       900ms       10K
TP4                 $$      600ms       18K
TP8                 $$$     550ms       20K
```

If requirement:

```text
TTFT < 1s
```

all three qualify.

But if:

```text
TTFT < 500ms
```

none may qualify.

The cheapest **qualifying** architecture wins.

That's the Solution Architect approach.

# 17. Example

Suppose:

```text
TP4:
18K tok/s
4 GPUs

TP8:
22K tok/s
8 GPUs
```

Assume:

```text
$5/GPU-hour
```

TP4:

```text
4 × $5 = $20/hour

18K × 3600
= 64.8M tok/hour

$20 / 64.8M
≈ $0.309/M tokens
```

TP8:

```text
8 × $5 = $40/hour

22K × 3600
= 79.2M tok/hour

$40 / 79.2M
≈ $0.505/M tokens
```

TP8 is faster.

But:

> **TP4 is substantially cheaper per token.**

This is why:

# Faster ≠ cheaper.


# 24. Spot instances

AWS Spot can provide substantial discounts versus On-Demand, with AWS stating that Spot can offer up to 90% savings, but Spot capacity can be interrupted.

This creates an architecture question:

```text
Can this workload tolerate interruption?
```

Good Spot candidates:

```text
batch inference
offline embedding
evaluation
benchmarking
non-critical workloads
```

Riskier:

```text
premium interactive inference
strict 99.99% SLO
long-lived TP8 groups
```

---

A 70% discount doesn't automatically mean 70% lower effective production cost.

# 42. Cost optimization decision tree

When customer says:

> “This is too expensive.”

Don't immediately reduce GPU count.

Ask:

```text
Can we reduce token usage?
        │
        ├── prompt compression?
        ├── RAG optimization?
        └── output limits?

Can we use a smaller model?
        │
        ├── routing?
        └── fallback?

Can we quantize?
        │
        ├── FP8?
        └── INT4?

Can we improve batching?
        │
        ├── continuous batching
        └── scheduling

Can we improve cache locality?
        │
        └── prefix-aware routing

Can we improve topology?
        │
        └── TP reduction

Can we reduce idle capacity?
        │
        ├── Karpenter
        └── warm/cold balance

Can we use Spot?
        │
        └── non-critical workloads
```

That's the FinOps toolbox.

# 43. The optimization hierarchy

I'd optimize in this order:

```text
1. Reduce unnecessary tokens
        ↓
2. Right-size model
        ↓
3. Improve batching
        ↓
4. Improve cache reuse
        ↓
5. Quantization
        ↓
6. Optimize TP/parallelism
        ↓
7. Optimize GPU type
        ↓
8. Optimize autoscaling
        ↓
9. Spot where safe
        ↓
10. Micro-optimize infrastructure
```

Why?

Because a 30% reduction in token demand can be much more valuable than spending days tuning a 5% GPU kernel improvement.
