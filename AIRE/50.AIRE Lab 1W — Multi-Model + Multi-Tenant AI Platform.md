# Lab 1W — Multi-Model + Multi-Tenant AI Platform

This is a major step toward **AI Platform Solution Architect**.

So far we've mostly designed:

```text
One model
   ↓
vLLM
   ↓
GPU fleet
```

Real enterprise platforms rarely stay that simple.

You may have:

```text
Tenant A → Model A
Tenant B → Model A
Tenant C → Model B
Tenant D → Model C
Internal → Model D
```

while all competing for:

```text
GPU
KV cache
network
CPU
memory
model storage
```

The challenge becomes:

> **How do we provide isolation, fairness, reliability and cost control while keeping expensive GPUs efficiently utilized?**

---

# 1. Target architecture

Our target platform:

```text id="1z6j2k"
                         INTERNET
                            │
                            ▼
                           WAF
                            │
                            ▼
                      AI Gateway
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
       Tenant A          Tenant B          Tenant C
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ▼
                    Auth / Quota / Policy
                            │
                            ▼
                     Model Router
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
           Model A       Model B       Model C
              │             │             │
            llm-d         llm-d         llm-d
              │             │             │
            vLLM          vLLM          vLLM
              │             │             │
          GPU Pool A    GPU Pool B    GPU Pool C
```

But we want to avoid unnecessarily dedicating an entire GPU fleet to every model.

That's the optimization challenge.

---

# 2. Why multi-model is difficult

Imagine:

```text id="1ozf2j"
Model A = 70B
Model B = 8B
Model C = 3B
Model D = embedding model
```

Their requirements are completely different.

| Model     | Typical concern    |
| --------- | ------------------ |
| 70B       | huge VRAM / TP     |
| 8B        | throughput         |
| 3B        | cost efficiency    |
| Embedding | CPU/GPU throughput |

If you create:

```text id="1j5v8e"
dedicated GPU fleet
```

for every model, you may get massive idle capacity.

---

# 3. GPU fragmentation

Suppose you have:

```text id="w8g3n1"
16 H100 GPUs
```

Model A needs:

```text id="e4h8r2"
8 GPUs
```

Model B needs:

```text id="g7k5v9"
2 GPUs
```

Model C needs:

```text id="x9p2m6"
2 GPUs
```

You might end up with:

```text id="b5k1q7"
8 → Model A

2 → Model B

2 → Model C

4 → idle
```

Those 4 GPUs may be impossible to use efficiently depending on topology/model requirements.

This is:

> **GPU fragmentation.**

For example:

```text id="x4q7n2"

     ↓
```

Don't let the model decide:


# 17. Token-based quotas

Request count alone isn't enough.

Compare:

```text id="0r7q3m"
Request A:
100 tokens

Request B:
100,000 tokens
```

Both count as:

```text id="v8n4p1"
1 request
```

but their GPU cost is radically different.

Therefore AI platforms should often use:

```text id="k5m9x2"
token budgets
```

as well as request quotas.

---

# 18. Example quota

Tenant:

```text id="s3w7q1"

+
2 billion output tokens
```

At request time:

```text id="h6p2n8"

```

is tracked.

This gives you:

```text id="m9v4x7"

+
billing
+
FinOps
```

from the same telemetry.

# 23. Queue isolation

One giant queue:

```text id="c4m8x1"
Tenant A ─┐
Tenant B ─┼── Global queue
Tenant C ─┘
```

can allow one workload to dominate.

Better:

```text id="j7q2v9"
Tenant queues
   │
   ▼
Fair scheduler
   │
   ▼
Inference workers
```

The implementation can vary, but the architectural principle is:

> **Don't let unbounded work from one tenant become everyone else's latency problem.**

# 28. Model loading problem

Suppose:

```text id="a9v2k7"

```




# 57. AIRE interview question

> **Why is multi-tenant LLM serving harder than multi-tenant web applications?**

Strong answer:

> "LLM requests have highly variable computational and memory cost because input and output token counts vary dramatically. A single request can consume significant KV cache and GPU time. Therefore request count alone is insufficient for capacity and fairness. We need token-aware quotas, concurrency control, inference-aware routing, KV-aware scheduling, priority, admission control and careful isolation to prevent noisy neighbors."

Excellent.

---

# 58. Another interview question

> **Why not put all models on the same GPUs?**

Answer:

> "GPU sharing can improve utilization, but it introduces memory fragmentation, model loading overhead, interference and unpredictable latency. Large models with strict SLOs generally benefit from dedicated GPU capacity, while smaller or batch workloads may be candidates for controlled sharing. I'd benchmark the tradeoff rather than applying one policy universally."
