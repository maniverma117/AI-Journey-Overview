# Lab 2D — AI Solution Architect: Customer Discovery, Workload Characterization & GPU Sizing

This is one of the **most important lessons in the entire AIRE journey**.

Up to now, we learned how every component works:

* GPU
* CUDA
* vLLM
* KV cache
* TP/PP/DP/EP
* EKS
* Karpenter
* KEDA
* llm-d
* P/D
* NIXL/EFA
* observability
* security
* DR
* FinOps

Now we combine all of them into the skill a **Solution Architect / AI Infrastructure Architect** actually needs:

> **A customer gives you business requirements. You convert them into workload numbers, workload numbers into benchmark requirements, benchmarks into GPU architecture, and GPU architecture into a reliable/costed production platform.**

The most important rule:

> **Never start a customer conversation with “Which GPU do you want?”**

Start with:

```text
Business requirement
       ↓
Workload characterization
       ↓
Model characteristics
       ↓
SLO / SLA
       ↓
Benchmark
       ↓
Sustainable capacity
       ↓
GPU architecture
       ↓
Replica / HA sizing
       ↓
EKS architecture
       ↓
Cost
       ↓
Production architecture
```

---

# 1. What a Solution Architect Actually Does

Suppose a customer says:

> "We need an AI chatbot for 500 concurrent users. Can you give us 8 H100s?"

A junior engineer might say:

> "Yes, 8 H100s should be enough."

An experienced AI architect says:

> "I can't size the platform from 500 concurrent users alone. I first need request rate, input/output token distributions, model, context length, latency SLO, availability requirement, traffic burst characteristics, and whether the workload is interactive, RAG, or agentic. Then we'll benchmark the actual model and derive GPU capacity."

That difference is enormous.

# 4. User Count Is NOT Capacity

This is probably the most important concept in this lesson.

Suppose:

```text
500 users
```

This tells you almost nothing.

These two systems are completely different:

### System A

```text
500 users
1 request/user/hour
1K input
200 output
```

versus:

### System B

```text
500 users
20 requests/user/minute
50K input
4K output
agentic workflow
```

The second workload could be orders of magnitude larger.

Therefore:

> **Users are a business metric. Tokens and request arrival rate are infrastructure metrics.**

# 6. Why P95/P99 Matter

Imagine:

```text
Input tokens

P50 = 2K
P95 = 12K
P99 = 60K
```

If you size infrastructure around:

```text
2K input
```

you'll probably fail during long requests.

But if you size everything around:

```text
60K
```

you may massively overpay.

Therefore:

> **Use distributions, not a single average.**

---

# 7. Request Arrival Rate

Suppose:

```text
10,000 users
2 requests/hour/user
```

Average RPS:

```text
10,000 × 2
----------------
3600

= 5.56 RPS
```

But suppose peak traffic is 5× average:

```text
5.56 × 5
= 27.8 RPS
```

Now your platform should potentially be designed around:

```text
~28 peak RPS
```

not:

```text
5.56 RPS
```

---

# 8. Burst Factor

You should explicitly ask:

> "What is your peak-to-average ratio?"

For example:

```text
Average = 10 RPS
Peak = 40 RPS
```

Then:

```text
Burst factor = 40 / 10 = 4×
```

This matters tremendously for GPU systems.

---

# 9. Concurrency vs RPS

These are different.

Suppose:

```text
10 RPS
average request duration = 5 seconds
```

Using Little's Law:

```text
L = λW
```

where:

```text
L = concurrent requests
λ = arrival rate
W = average time in system
```

Therefore:

```text
L = 10 × 5
  = 50
```

Approximately:

```text
50 concurrent requests
```

This is why:

> **Concurrency is not the same thing as RPS.**

---

# 10. Token Demand

Now we move to AI-specific capacity.

Suppose:

```text
Peak RPS = 30

P95 input = 8,000 tokens
P95 output = 1,000 tokens
```

Approximate P95 token demand:

### Input

```text
30 × 8,000
= 240,000 input tokens/sec
```

### Output

```text
30 × 1,000
= 30,000 output tokens/sec
```

This is much more meaningful than saying:

> "30 requests/sec."

Because inference hardware is fundamentally processing tokens.

---

# 11. But Don't Blindly Multiply P95 × P95

This is an important architect-level nuance.

Suppose:

```text
P95 input = 8K
P95 output = 1K
```

It does **not necessarily mean** that 95% of requests simultaneously have:

```text
8K input + 1K output
```

Percentiles can be correlated or uncorrelated.

So for serious capacity planning, use an actual workload distribution:

```text
Request 1: 1K → 300
Request 2: 5K → 900
Request 3: 20K → 2K
...
```

Then replay that distribution.

This is one reason production-shaped benchmarking is so important.

---

# 12. Prefill vs Decode Demand

Remember:

```text
Input tokens
     ↓
   PREFILL
     ↓
   KV cache
     ↓
   DECODE
     ↓
Output tokens
```

Therefore:

```text
Input token rate → prefill workload

Output token rate → decode workload
```

And their bottlenecks can be different.

---

# 13. Example: Workload Decomposition

Customer:

```text
Peak = 30 RPS

Input = 8K
Output = 1K
```

Then:

```text
Prefill demand:

30 × 8K
= 240K input tok/s
```

Decode:

```text
30 × 1K
= 30K output tok/s
```

If decode becomes the bottleneck:

```text
TPOT ↑
```

If prefill becomes the bottleneck:

```text
TTFT ↑
```

This gives you a powerful diagnostic model.

# 14. RAG Changes the Workload

Suppose user asks:

> "What is our refund policy?"

The application might do:

```text

     ↓

     ↓
Vector DB
     ↓
Retrieve 10 documents
     ↓
Prompt assembly
     ↓

```

Now the LLM input may become:

```text

+ user query
+ retrieved documents
+ conversation history
```

So:

```text

```

This distinction is critical.

A user makes one request:

> "Investigate why EC2 instance i-123 is unhealthy and fix it."

```text

   ↓

   ↓

   ↓

   ↓

   ↓

   ↓
```

One user request could generate:


Therefore:

> **Agent concurrency can amplify LLM traffic.**

```text

Maximum iterations?
Average model calls?
Maximum model calls?
```

# 17. Model Memory Calculation

Basic weight memory:

```text
Model parameters × bytes/parameter
```

Example:

```text
70B × 1 byte
≈ 70GB
```

for approximately FP8 storage.

But production memory is:

```text
Weights
+
KV cache
+
CUDA graphs
+
workspace
+
activations
+
runtime overhead
+
fragmentation/headroom
```

Therefore:

```text
70GB weights
```

does NOT mean:

> "70GB GPU is enough."

# 18. Context Length Is a Capacity Multiplier

Suppose:

```text
Context = 2K
```

versus:

```text
Context = 128K
```

The second workload can consume dramatically more:

```text

```

And concurrency becomes harder.

Therefore ask:

```text

P95?
P99?
maximum?
```

Do not size only from:

```text

```

unless customers actually use it.

# 19. Latency SLO Discovery

Don't accept:

> "We need low latency."

Ask for numbers.

For example:

```text
P95 TTFT < 1 sec
P99 TTFT < 2 sec

P95 TPOT < 50 ms
P99 TPOT < 80 ms

P95 E2E < 8 sec
```

Now we have engineering requirements.

---

# 20. Explain TTFT Correctly

For streaming inference:

```text
Request
   ↓
Queue
   ↓
Prefill
   ↓
First token
```

So:

```text
TTFT =
queue
+
prefill
+
other overhead
```

Therefore high TTFT does not automatically mean:

> "GPU is slow."

It could be:

```text
queueing
KV pressure
long prompt
scheduler contention
network
routing
prefill saturation
```

---

# 21. TPOT / ITL

After the first token:

```text
token
 ↓
token
 ↓
token
 ↓
token
```

Time between tokens matters.

If:

```text
TPOT = 45ms
```

then approximately:

```text
1000 / 45
≈ 22 tokens/sec
```

per sequence.

But aggregate throughput depends on batching and concurrency.

---

# 22. Customer SLO Example

Suppose:

```text
P95 TTFT < 1 second
P95 TPOT < 50ms
99.99% availability
```

Now benchmark results might look like:

| Configuration | RPS | P95 TTFT | P95 TPOT |
| ------------- | --: | -------: | -------: |
| TP2           |  12 |     1.5s |     62ms |
| TP4           |  20 |    850ms |     46ms |
| TP8           |  34 |    700ms |     41ms |

Which configurations meet SLO?

### TP2

```text
TTFT = 1.5s ❌
TPOT = 62ms ❌
```

Doesn't meet.

### TP4

```text
850ms < 1s ✅
46ms < 50ms ✅
```

Meets.

### TP8

```text
700ms < 1s
41ms < 50ms
```

Also meets.

Now comes the architecture decision.

---

# 23. Don't Automatically Choose TP8

This is where Solution Architect thinking begins.

TP8:

```text
34 RPS
700ms TTFT
41ms TPOT
8 GPUs
```

TP4:

```text
20 RPS
850ms TTFT
46ms TPOT
4 GPUs
```

Suppose customer needs:

```text
30 RPS peak
```

TP4 needs:

```text
30 / 20
= 1.5
```

Therefore:

```text
2 × TP4 replicas
```

Capacity:

```text
2 × 20
= 40 RPS
```

GPU:

```text
2 × 4
= 8 GPUs
```

TP8:

```text
1 × TP8
= 34 RPS
```

GPU:

```text
8
```

Same GPU count.

But failure behavior is different.

---

# 24. Failure Granularity

### Architecture A

```text
TP8
```

One replica:

```text
GPU1
GPU2
GPU3
GPU4
GPU5
GPU6
GPU7
GPU8
```

If one GPU fails:

```text
entire TP group affected
```

### Architecture B

```text
TP4 + TP4
```

```text
Replica A
GPU1 GPU2 GPU3 GPU4

Replica B
GPU5 GPU6 GPU7 GPU8
```

One GPU failure:

```text
one replica lost
```

The other can potentially continue.

Therefore:

> **Same GPU count does not mean same reliability.**

---

# 25. N+1 Capacity

Suppose:

```text
Each TP4 replica = 20 RPS
Peak demand = 30 RPS
```

Without failure:

```text
2 replicas = 40 RPS
```

But if one replica fails:

```text
1 replica = 20 RPS
```

which is below:

```text
30 RPS
```

So:

```text
2 replicas
```

is NOT N+1 capacity for a 30 RPS requirement.

Need:

```text
3 × TP4
```

Then:

```text
Normal = 60 RPS

After one replica failure:
40 RPS
```

Still above 30 RPS.

GPU count:

```text
3 × 4
= 12 GPUs
```

This is why HA can dramatically change GPU requirements.

---

# 26. Failure Factor

A useful capacity equation:

```text
Required Capacity =
Peak Demand
× Headroom
× Failure Factor
÷
SLO-Constrained Capacity
```

Suppose:

```text
Peak = 30 RPS
Headroom = 1.25
Failure factor = 1.5
Per replica = 20 RPS
```

Then:

```text
30 × 1.25 × 1.5
-----------------
20

= 2.8125
```

Round up:

```text
3 replicas
```

This is a **planning model**, not a replacement for benchmark validation.

---

# 27. Headroom

Why not run at exactly 100%?

Because:

```text
traffic changes
token lengths change
GPU performance varies
dependencies slow down
deployments happen
nodes fail
AZ failures happen
```

If your capacity is:

```text
30 RPS
```

and traffic is:

```text
30 RPS
```

you're already at the edge.

Instead:

```text
capacity = 40 RPS
demand   = 30 RPS
```

gives:

```text
25% headroom
```

---

# 28. Sustainable Capacity

Never say:

> "This H100 can generate 100K tokens/sec."

Ask:

> "At what workload can this configuration sustain the customer's SLO?"

Example:

```text
TP4

At 15 RPS:
TTFT = 600ms
TPOT = 40ms

At 20 RPS:
TTFT = 850ms
TPOT = 46ms

At 25 RPS:
TTFT = 1.8s
TPOT = 75ms
```

The sustainable capacity might be:

```text
20 RPS
```

even though the system can technically process:

```text
25 RPS
```

The latter violates the SLO.

Therefore:

> **Sustainable capacity = maximum workload while meeting the SLO.**

---

# 29. The Saturation Curve

This is one of the most important graphs you should learn to interpret.

```text
Latency
  │
  │                         /
  │                       /
  │                    __/
  │                 __/
  │              __/
  │___________ _/
  │
  └────────────────────────────
              Load
```

At low load:

```text
latency relatively stable
```

Near saturation:

```text
queue grows
TTFT grows rapidly
TPOT may degrade
KV fills
preemption increases
```

Therefore:

> **Don't operate at the knee unless you have a very good reason.**

# 37. H100 vs H200

Current AWS EC2 documentation lists:

```text
p5.4xlarge
1 × H100
80 GiB

p5.48xlarge
8 × H100
80 GiB each

p5e.48xlarge
8 × H200
141 GiB each

p5en.48xlarge
8 × H200

```

The H200 configurations therefore provide substantially more per-GPU memory than H100. ([AWS Documentation][2])

This matters enormously for:

```text
long context
large models
high concurrency
KV-heavy inference
```

But:

> **More VRAM doesn't automatically mean lower latency.**

You still benchmark.

# 43. Karpenter's Role

Karpenter doesn't understand your model quality.

It primarily reacts to Kubernetes scheduling requirements and provisions nodes matching pod requirements. AWS describes it as provisioning/removing nodes based on unschedulable pods and their scheduling constraints. ([AWS Documentation][3])

Conceptually:

```text
Traffic
  ↓
AI Gateway
  ↓
KEDA/HPA
  ↓
More vLLM pods
  ↓
Pending pods
  ↓
Kubernetes scheduler
  ↓
Karpenter
  ↓
GPU node
```

Important:

> Karpenter provisions infrastructure. It does not decide which request should use which GPU.

That's llm-d/router territory.

---

# 44. The Four Decision Makers

Production architecture can have:

```text
AI Gateway
     ↓
llm-d Router/EPP
     ↓
Kubernetes Scheduler
     ↓
Karpenter
```

And inside the model server:

```text
vLLM scheduler
```

So there are multiple scheduling layers.

### AI Gateway

```text
Who is allowed?
How much?
Which model?
What priority?
```

### llm-d EPP

```text
Which model server?
Which replica?
Which endpoint?
KV locality?
Queue?
SLO?
```

### Kubernetes

```text
Which node?
```

### Karpenter

```text
Should we create a node?
Which EC2 instance?
```

### vLLM

```text
Which token/request executes next?
How much batching?
KV allocation?
```

Current llm-d documentation explicitly describes the EPP as the routing brain, using signals such as KV-cache utilization, prefix locality, queue depth and active requests. ([Llm-D][4])

# 57. DR Is Not Always 2×

Lower cost but higher failover time.

Cheaper, slower.

# 98. Interview Question

### Interviewer:

> "A customer asks for 500 concurrent users on a 70B model. How many H100s do you recommend?"

### Weak answer:

> "Maybe 8 H100s."

### Strong answer:

> "I wouldn't size from concurrency alone. I'd first characterize peak RPS, request concurrency, input/output token distributions, context length, streaming behavior, RAG or agentic amplification, model precision, and TTFT/TPOT SLOs. Then I'd benchmark the exact model on candidate TP configurations using production-shaped traffic. From the SLO-constrained sustainable capacity per replica, I'd calculate replica count with traffic headroom and the required failure unit, then map that to GPU count and multi-AZ topology."

That's the answer you want to give.

# 100. Interview Question — Why Isn't GPU Utilization Enough?

Answer:

> "GPU utilization doesn't tell me whether the workload is meeting its user SLO. A GPU can be highly utilized while queue depth, TTFT and TPOT are unacceptable, or lightly utilized while the workload is latency-sensitive and fully meeting its SLO. I correlate GPU utilization with token throughput, KV utilization, queueing, TTFT, TPOT, memory bandwidth and NCCL/network behavior."

---

# 101. Interview Question — Why Does RPS Alone Not Work?

Answer:

> "Because inference cost is highly dependent on token volume and sequence length. Ten requests containing 1K tokens each are completely different from ten requests containing 100K tokens each. I therefore model input/output token distributions and prefill/decode demand, not just request count."

---

# 102. Interview Question — Why Does 99.99% Change GPU Sizing?

Answer:

> "Because the failure unit matters. If I deploy TP8, one GPU failure can affect an entire eight-GPU serving replica. I need enough independent replicas to survive the required failure scenario while retaining sufficient SLO-constrained capacity. Therefore availability requirements can change TP topology and total GPU count."

---

# 103. Interview Question — Why Benchmark TP4 and TP8?

Answer:

> "Because parallelism has a tradeoff. Larger TP can improve single-replica latency and capacity but increases communication and failure granularity. Multiple smaller replicas can improve horizontal scalability and availability. I choose based on measured SLO-constrained capacity, topology, failure requirements and cost."

---

# 104. Interview Question — What Does "Production Capacity" Mean?

Best answer:

> "The maximum sustainable workload at which the system continues to meet defined latency, error and availability objectives under the production workload distribution."

Not:

> "Maximum tokens/sec."

# 108. The Final Architecture Defense Framework

When presenting to a customer, use:

### Requirement

> "You need 30 peak RPS with P95 TTFT below one second."

### Evidence

> "We benchmarked the target model using your production-shaped token distribution."

### Finding

> "TP4 sustains 20 RPS while meeting the latency SLO."

### Decision

> "We selected three TP4 replicas."

### Reliability

> "One replica can fail while retaining 40 RPS capacity."

### Infrastructure

> "That requires 12 GPUs distributed across three AZs."

### Scaling

> "KEDA/HPA scales serving replicas and Karpenter provisions GPU nodes."

### Routing

> "llm-d selects endpoints using inference-aware signals."

### Security

> "AI Gateway handles tenant authentication, quota and policy; model output is not treated as authorization."

### Observability

> "TTFT, TPOT, queue, KV, GPU and routing metrics form the primary SLO signals."

### Cost

> "We'll calculate cost per successful request and tokens against the measured sustainable capacity."

That is a **production AI architecture defense**.
