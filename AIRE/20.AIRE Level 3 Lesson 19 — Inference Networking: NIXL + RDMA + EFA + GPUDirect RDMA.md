# 3. First distinction: NVLink vs RDMA

This is one of the most important things to understand.

## NVLink

Primarily:

```text
GPU ↔ GPU
```

within a tightly coupled GPU system.

Example:

```text
GPU 0
 │
 │ NVLink
 ▼
GPU 1
```

Very high bandwidth and low latency.

---

## RDMA

RDMA means:

> **Remote Direct Memory Access**

It is about accessing memory across a network without requiring the CPU to handle every byte.

Conceptually:

```text
GPU A
  │
  ▼
NIC A
  │
  │ RDMA
  ▼
NIC B
  │
  ▼
GPU B
```

NVIDIA's GPUDirect RDMA technology provides a direct data path between GPU memory and a peer device such as a network interface over PCIe. ([NVIDIA Docs][1])

---

# 4. Why CPU involvement matters

Consider a naive network transfer:

```text
GPU A
  │
  ▼
CPU A memory
  │
  ▼
NIC A
  │
  │ network
  ▼
NIC B
  │
  ▼
CPU B memory
  │
  ▼
GPU B
```

You have:

```text
GPU → CPU
CPU → NIC
NIC → CPU
CPU → GPU
```

That's a lot of movement.

Now consider GPUDirect RDMA:

```text
GPU A
  │
  ▼
NIC A
  │
  │ RDMA
  ▼
NIC B
  │
  ▼
GPU B
```

The CPU doesn't need to be the data-copy middleman.

That's the fundamental idea.

---

# 5. GPUDirect RDMA

NVIDIA defines GPUDirect RDMA as enabling direct exchange between GPU memory and a third-party peer device using PCI Express, including network interfaces and storage adapters. ([NVIDIA Docs][1])

Think:

```text
                 CPU
                  │
             control path
                  │
                  │
GPU ──────────────┼──────────── NIC
     data path
```

Instead of:

```text
GPU → CPU → NIC
```

we want:

```text
GPU ───────────────► NIC
```

This matters enormously for:

* distributed inference
* distributed training
* KV transfer
* NCCL
* P/D disaggregation
* GPU-to-GPU communication

---

# 6. But GPUDirect RDMA isn't magic

There are hardware/topology requirements.

For example, NVIDIA documents PCIe topology constraints; the GPU and peer device need an appropriate PCIe relationship. ([NVIDIA Docs][1])

That's why we previously learned:

```bash
nvidia-smi topo -m
```

This isn't just a troubleshooting command.

It tells you:

> **How are my GPUs and NICs physically connected?**

# 11. Now: NCCL vs NIXL

This is extremely important.

You already know NCCL.

### NCCL

Primarily:

> **Collective GPU communication**

Examples:

```text
AllReduce
AllGather
ReduceScatter
AllToAll
Broadcast
```

Typical use:

```text
Tensor Parallelism
Data Parallelism
Expert Parallelism
```

---

### NIXL

Primarily:

> **Point-to-point inference memory transfer**

Especially:

```text
KV cache
Prefill → Decode
P2P KV
Disaggregated inference
```

So:

```text
NCCL
   =
collective communication
```

while:

```text
NIXL
   =
inference-oriented memory transfer
```

That's a very useful mental model.

---

# 12. Why can't NCCL just do everything?

Because the communication patterns are different.

NCCL might do:

```text
GPU0 ─┐
GPU1 ─┤
GPU2 ─┼── AllReduce
GPU3 ─┤
GPU4 ─┘
```

Every rank participates.

But P/D KV transfer might look like:

```text
Prefill GPU
     │
     │ 50 GB KV
     ▼
Decode GPU
```

That's fundamentally a different pattern.

NIXL is designed around this kind of point-to-point inference transfer. llm-d currently focuses on NIXL for P/D KV movement. ([llm-d.ai][3])

---

# 13. NIXL's role

NIXL gives inference frameworks a common interface:

```text
                  NIXL
                   │
        ┌──────────┼──────────┐
        │          │          │
       UCX       UCCL      libfabric
        │          │          │
       ┌┴──┐      ┌┴─┐       └───┐
       │   │      │  │           │
      IB RoCE    EFA ...        EFA
```

llm-d's current documentation describes NIXL as a standardized API for transferring memory between remote instances, with backends such as UCX, UCCL and libfabric supporting transports including NVLink, RoCE, InfiniBand and EFA. ([llm-d.ai][3])

So NIXL is an abstraction layer.

# 14. Why abstraction matters

Imagine your application says:

```text

    source_gpu_memory,
    destination_gpu_memory
)
```

You don't want application logic to contain:

```text
if AWS:
    EFA

elif InfiniBand:
    IB

elif RoCE:
    RoCE
```

Instead:

```text
Application
     │
     ▼
    NIXL
     │
     ▼
appropriate backend/transport
```

That's the same reason we like:

```text
Kubernetes
```

rather than writing:

```text
if AWS:
    EC2 API

if GCP:
    Compute API
```

Abstraction allows the upper layer to reason about intent.

# 15. The critical path in P/D disaggregation

Now we reach the most important lesson of today.

Consider:

```text
Client
  │
  ▼
Prefill
  │
  │ compute
  ▼
KV cache
  │
  │ TRANSFER
  ▼
Decode
  │
  ▼
First token
```

TTFT is:

```text
TTFT =
queue
+
prefill
+
KV transfer
+
decode startup
```

Therefore:

> **KV transfer is directly on the critical path to the first token.**

The current llm-d networking guidance explicitly calls this out: P/D disaggregation introduces a hard network dependency because KV must be transferred before decode can generate the first token. ([llm-d.ai][4])

---

# 16. AIRE equation

This is a useful conceptual model:

```text
TTFT
=
Tqueue
+
Tprefill
+
TKV-transfer
+
Tdecode-start
```

Suppose:

```text
queue       = 100 ms
prefill     = 300 ms
KV transfer = 450 ms
decode start= 50 ms
```

Then:

```text
TTFT = 900 ms
```

Now you optimize GPU compute:

```text
prefill:
300 ms → 200 ms
```

Great.

But:

```text
KV transfer = 450 ms
```

still dominates.

You only improved:

```text
900 → 800 ms
```

But if networking can improve:

```text
450 → 100 ms
```

you get:

```text
900 → 550 ms
```

🔥 That's why **networking becomes part of inference performance engineering.**

# 17. Calculate transfer time

Let's make this concrete.

Suppose KV:

```text
50 GB
```

and effective transfer bandwidth:

```text
500 GB/s
```

Idealized transfer time:

```text
T = data / bandwidth

T = 50 / 500

T = 0.1 seconds
```

So:

```text
100 ms
```

But real systems have:

* protocol overhead
* synchronization
* memory registration
* PCIe limitations
* topology effects
* congestion
* software overhead
* serialization
* contention

Therefore actual performance won't simply equal:

```text
50 / 500
```

Still, this equation is extremely useful for architecture reasoning.

---

# 18. Another example

Suppose:

```text
KV = 100 GB
```

and effective network throughput:

```text
100 GB/s
```

Then:

```text
T ≈ 1 second
```

If your requirement is:

```text
P95 TTFT < 1 sec
```

you already have a problem.

Because the **network transfer alone** can consume your entire SLO budget.

This is why an AIRE must ask:

> "How large is the KV transfer?"

before saying:

> "P/D disaggregation will improve performance."

# 19. And here's the subtle part

P/D disaggregation is **not automatically faster**.

Current vLLM documentation explicitly states that disaggregated prefilling does not inherently improve throughput. Its major benefit is better control/isolation of latency characteristics, especially tail ITL/TTFT behavior. ([vLLM][5])

Think:

```text
Combined:
┌───────────────────────┐
│ Prefill + Decode GPU  │
└───────────────────────┘
```

A long prefill can interfere with decode.

P/D:

```text
┌──────────────┐       ┌──────────────┐
│ Prefill GPU  │──────►│ Decode GPU   │
│ compute      │  KV   │ latency      │
└──────────────┘       └──────────────┘
```

Now you can scale:

```text
P capacity
```

independently from:

```text
D capacity
```

---

# 20. Example scaling problem

Suppose workload has:

```text
very long prompts
short outputs
```

Then:

```text
Prefill demand = HIGH
Decode demand = LOW
```

A combined architecture might require:

```text
10 GPUs
```

but decode GPUs are underutilized.

P/D can potentially create:

```text
6 Prefill GPUs
4 Decode GPUs
```

or another optimized ratio based on benchmarked demand.

Now imagine a different workload:

```text
short prompts
very long outputs
```

Then:

```text
Prefill demand = LOW
Decode demand = HIGH
```

You may want:

```text
2 Prefill
8 Decode
```

That's the architectural advantage.

# 27. TCP fallback — dangerous for production P/D

Current llm-d documentation is very explicit:

> P/D disaggregation requires high-performance RDMA interconnects for efficient KV transfer.

Without RDMA, NIXL can fall back to TCP, but llm-d recommends TCP only for testing/development because it is not efficient enough for this use case. ([llm-d.ai][3])

So:

```text
Production:
NIXL → RDMA/EFA
```

not:

```text
Production:
NIXL → TCP
```

unless you have a very deliberate reason and benchmarked it.

# 33. Pull vs Push KV

Current vLLM NIXL support has both conceptual transfer modes.

### Pull

```text
Decode
   │
   │ READ
   ▼
Prefill KV
```

Decode pulls KV from prefill.

### Push

```text
Prefill
   │
   │ WRITE
   ▼
Decode
```

Prefill pushes KV to decode.

Current vLLM documentation explicitly documents both pull-mode and push-mode NIXL disaggregated serving. ([vLLM][7])

---

# 34. Pull model

Imagine:

```text
P:
KV blocks:
A B C D E

D:
needs:
A B C D E
```

Decode says:

```text
READ(A,B,C,D,E)
```

and NIXL performs the transfer.

Conceptually:

```text
D ───────── READ ─────────► P
D ◄──────── KV ─────────── P
```

---

# 35. Push model

Decode first allocates destination memory:

```text
D:
"I have space for A B C D E."
```

Then:

```text
P
 │
 │ WRITE
 ▼
D
```

Current vLLM's push-mode example describes D registering its local blocks with P through a NIXL notification, after which P writes the KV to D. ([vLLM][7])

# 37. KV transfer failure

```text
Prefill complete
      │

      X
```

```text

```

---

# 38. Fail vs recompute

### Fail

```text
KV transfer failed
      ↓
request fails
```

Advantages:

* lower wasted compute
* explicit failure
* potentially lower latency if retry path exists

Disadvantages:

* availability impact

---

### Recompute

```text
KV transfer failed
      ↓
decode recomputes
      ↓
request continues
```

Advantages:

* better resilience
* cache/network failure doesn't necessarily become user-visible

Disadvantages:

* expensive
* adds latency
* consumes GPU compute

# 41. A very important AIRE formula

For P/D:

```text
TTFT ≈

queue
+
prefill
+
KV transfer
+
decode initialization
```

For KV transfer:

```text
Transfer time ≈

KV bytes
──────────────
effective bandwidth
```

Therefore:

```text
TTFT pressure ∝ KV size / network bandwidth
```

This is simplified, but architecturally extremely useful.

# 44. Same-node vs cross-node

This is an important design choice.

### Same node

```text
GPU P
 │
 │ NVLink/PCIe
 ▼
GPU D
```

Potentially excellent latency.

### Cross node

```text
GPU P
 │
NIC
 │
EFA/RDMA
 │
NIC
 │
GPU D
```

More flexible scaling, but networking becomes critical.

Therefore:

> **Disaggregation increases scheduling flexibility at the cost of communication complexity.**

Imagine customer reports:


```text

```

Network:

```text
EFA utilization = 20%
```

Your first thought should **not** be:

> "Network is only 20%, so network is fine."

You investigate:

```text
1. KV size
2. KV transfer latency
3. effective bandwidth
4. NIXL backend
5. RDMA vs TCP
6. GPUDirect RDMA
7. GPU/NIC topology
8. connection setup
9. synchronization
10. P/D scheduling
```

Maybe the network has plenty of aggregate bandwidth but:

```text
KV transfer is serialized
```

or:

```text
connection setup adds latency
```

or:

```text
GPUDirect RDMA isn't active
```

or:

```text
KV is much larger than expected
```

---

# 50. One of the best AIRE debugging principles

Remember:

> **Aggregate utilization is not equivalent to per-request latency.**

You can have:

```text
Network utilization = 20%
```

and still have:

```text
P95 KV transfer latency = 500 ms
```

because of:

* serialization
* queueing
* synchronization
* topology
* small-message inefficiency
* connection setup
* software overhead

This is exactly like Kubernetes:

```text
CPU 30%
```

doesn't prove:

```text
application latency is healthy
```
