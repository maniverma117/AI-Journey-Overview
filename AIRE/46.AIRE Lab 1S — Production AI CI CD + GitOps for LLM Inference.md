# Lab 1S — Production AI CI/CD + GitOps for LLM Inference

Now we're moving from **running and operating** the AI platform to **safely changing it**.

This is a major distinction.

A traditional application deployment is roughly:

```text
Code
 ↓
Build
 ↓
Test
 ↓
Deploy
```

An AI inference deployment is:

```text
Application code
      +
Model
      +
Tokenizer
      +
vLLM
      +
PyTorch
      +
CUDA
      +
NCCL
      +
GPU architecture
      +
Serving configuration
      +
Prompt / policy
      +
RAG configuration
      +
Security policy
      +
Performance characteristics
```

So an AI deployment pipeline needs to validate **both correctness and operational behavior**.

---

# 1. The AI release unit

Don't think:

> "We're deploying a new Docker image."

Think:

```text id="6dr3g7"
              AI RELEASE
                  │
      ┌───────────┼───────────┐
      ▼           ▼           ▼
 Application    Model       Runtime
    code       artifact      stack
      │           │           │
      ▼           ▼           ▼
  Gateway       weights      vLLM
  Router        tokenizer    PyTorch
  RAG           config       CUDA
                             NCCL
```

Then:

```text id="0z13xv"
Configuration
Security policy
Inference parameters
Autoscaling
Routing
Observability
```

are also part of the release.

# 2. Why model changes are infrastructure changes

Suppose you replace:

```text id="8t9fpl"
Model v1
```

with:

```text id="8x8d1j"
Model v2
```

You might unexpectedly get:

```text id="bl82v5"
VRAM ↑
KV usage ↑
TTFT ↑
TPOT ↑
throughput ↓
startup time ↑
GPU count ↑
cost ↑
```

Therefore:

> **A model release is a capacity event.**

This is one of the most important concepts in AI platform engineering.

For example:

  revision: "..."

  revision: "..."

  max_num_seqs: 64

# 4. Immutable artifacts

Avoid:

```text id="zqgd9u"
model: latest
image: latest
chart: latest
```

Because six months later you won't know what actually ran.

Prefer:

```text id="v7i4w3"
image digest
model revision/digest
Git commit
Helm chart version
config commit
policy version
```

Then:

```text id="6a0x3d"
Release 001
    ↓
immutable

Release 002
    ↓
immutable
```

Rollback becomes:

```text id="l6f4ds"
002 → 001
```

instead of trying to reconstruct 001.

---

# 5. Separate model artifact from container

This is a very useful design.

Don't build:

```text id="1pl9e3"
Docker image
 └── 140GB model
```

Prefer:

```text id="3k4p1f"
Container image
 ├── vLLM
 ├── PyTorch
 ├── CUDA userspace
 └── dependencies

Model artifact
 ├── weights
 ├── tokenizer
 └── config
```

Stored separately:

```text id="ny0i4x"
Private S3 / model registry
```

Benefits:

```text id="e0k8g6"
smaller image
faster CI
independent model lifecycle
better rollback
better artifact governance
```

# 23. Canary by tenant

For enterprise platforms, you might prefer:

```text id="s5g8y2"

tenant-a → v2
tenant-b → v1
```

instead of random 5%.

This allows:

```text id="8d3p6q"

```

But tenant-specific traffic can have very different workloads.

So:

> **Canary selection must represent the production workload you care about.**

# 24. Shadow traffic

Another technique:

```text id="3w6x1p"
                  Request
                     │
             ┌───────┴───────┐
             ▼               ▼
           v1                v2
        real response      shadow
             │               │
             ▼               ▼
           user            discard
```

v2 sees real traffic patterns but doesn't serve the user.

Useful for:

```text id="8j0r6v"
performance
quality
compatibility
```

But there is a security concern:

> **Shadow traffic can duplicate sensitive customer data.**

Therefore PII/data governance must be considered.

# 25. Blue-green deployment

```text id="m0v3n8"
               Gateway
                  │
          ┌───────┴───────┐
          ▼               ▼
       BLUE v1         GREEN v2
```

Switch:

```text id="e4q1w6"
100% BLUE
       ↓
100% GREEN
```

Rollback:

```text id="5k8d0s"
GREEN
 ↓
BLUE
```

Excellent rollback characteristics.

But GPU cost can be enormous because:

```text id="u2x7h5"
v1 GPUs
+
v2 GPUs
```

may need to be running simultaneously.

That's where FinOps returns.

---

# 26. Canary vs blue-green

| Strategy   |   Cost |  Rollback | Exposure         |
| ---------- | -----: | --------: | ---------------- |
| Rolling    |    Low |  Moderate | gradual          |
| Canary     | Medium |      Fast | small            |
| Blue-green |   High | Very fast | controlled       |
| Shadow     |   High |       N/A | no user response |
| Big bang   |    Low | Dangerous | 100%             |

For expensive GPU inference:

> **Canary is often an attractive default**, assuming your routing and capacity model support it.

# 47. Deployment strategy for TP groups

This is particularly important.

Suppose:

```text id="v1k6m9"
TP4 replica
```

Rolling deployment:

```text id="n4p8q2"
old replica
+
new replica
```

temporarily requires:

```text id="d5r1x7"
8 GPUs
```

for only two replicas.

If:

```text id="q7m3w8"

```

the rollout can stall.

Therefore:

> **Deployment strategy itself consumes GPU capacity.**

You need to account for:

```text id="s8n2k5"

```

and actual GPU group size.

# 58. AIRE interview challenge

Customer asks:

> “We upgraded our 70B model and the benchmark says accuracy improved by 2%. Why can't we just deploy it?”

Your answer:

> “Because model quality is only one production dimension. I need to compare the new model's memory footprint, KV requirements, TTFT, TPOT, sustainable throughput, GPU utilization, startup time, cost per token, security evaluation and workload-specific SLOs against the current release. If the model requires additional GPU capacity or violates latency SLOs, we need to change the serving architecture or reject the release.”

Excellent answer.

---

# 59. Another interview question

> “Why does changing vLLM require performance testing if the model hasn't changed?”

Answer:

> “Because the serving runtime controls scheduling, batching, KV management, attention backends, CUDA graph behavior, memory allocation and distributed communication. A runtime change can therefore alter throughput, latency, memory consumption and GPU efficiency even with identical model weights.”

---

# 60. Another

> “Why isn't Kubernetes rollout success enough?”

Answer:

> “Kubernetes only tells me the workload reached its infrastructure availability criteria. For inference I also need to validate model readiness, TTFT, TPOT, queue depth, KV utilization, throughput, errors and application-specific quality. A pod can be Running and Ready while the model is operationally worse.”

That's an **AIRE-level answer**.
