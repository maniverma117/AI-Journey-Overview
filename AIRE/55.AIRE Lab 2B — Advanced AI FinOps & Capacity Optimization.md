# Lab 2B — Advanced AI FinOps & Capacity Optimization

Now we go deeper than simply asking:

> **"How much does one H100 cost?"**

A production AI architect must answer:

> **"What is the cheapest architecture that can reliably serve this workload while meeting the customer's latency, availability, security, and throughput SLOs?"**

That is a much harder problem.

---

# 1. The AI FinOps Mental Model

Traditional cloud FinOps:

```text
EC2 hours
EBS
Network
S3
RDS
```

AI FinOps adds:

```text
GPU hours
        ↓
tokens generated
        ↓
requests served
        ↓
successful requests
        ↓
business value
```

So your cost chain becomes:

```text
$ GPU-hour
     ↓
$ / GPU-second
     ↓
tokens / GPU-second
     ↓
$ / 1M tokens
     ↓
$ / request
     ↓
$ / successful request
```

The final metric is often the most useful.

---

# 2. GPU Cost Is Not the Same as AI Cost

Suppose:

```text
GPU = $5/hour
```

and:

```text
GPU utilization = 90%
```

That doesn't tell us whether the platform is efficient.

Compare:

### System A

```text
90% GPU utilization
10K output tok/s
```

### System B

```text
70% GPU utilization
15K output tok/s
```

System B may be significantly better.

Therefore:

> **Optimize useful token throughput, not utilization alone.**

---

# 3. Cost Per GPU-Second

Suppose a GPU costs:

```text
$4/hour
```

Then:

```text
$4 / 3600
≈ $0.00111/sec
```

If it generates:

```text
1000 output tokens/sec
```

then:

```text
cost/token
≈ $0.00111 / 1000
≈ $0.00000111
```

or approximately:

```text
$1.11 / 1M output tokens
```

This is simplified because real inference also has:

* input processing
* idle time
* batching effects
* memory overhead
* orchestration
* networking
* storage
* HA capacity

But it gives us a useful first-order model.

---

# 4. The Most Important Cost Formula

For a serving fleet:

```text
GPU cost / useful output tokens
```

approximately:

```text
Cost per 1M tokens
=
GPU fleet cost
/
useful tokens produced
× 1M
```

Where:

```text
useful tokens
```

means tokens produced while meeting the required SLO.

This distinction matters enormously.

---

# 5. SLO-Constrained Cost

Suppose:

```text
Configuration A
= $2 / 1M tokens
```

but:

```text
P95 TTFT = 3s
```

Customer requires:

```text
P95 TTFT < 1s
```

Configuration B:

```text
$2.50 / 1M tokens
P95 TTFT = 700ms
```

Configuration B is actually the cheaper production solution.

Why?

Because A doesn't provide usable capacity under the contract.

Therefore:

> **The cheapest architecture is the cheapest architecture that satisfies the SLO.**

# 8. Batching Is a FinOps Lever

Suppose one request uses:

```text
20% GPU capacity
```

Five requests separately:

```text
20%
20%
20%
20%
20%
```

might waste execution efficiency.

Continuous batching can combine work:

```text
request A
request B
request C
request D
request E
       ↓

```

This can improve:

```text
GPU utilization
tokens/sec
cost/token
```

But excessive batching can increase:

```text
queueing
TTFT
ITL
```

Therefore:

> **Batching is an optimization under latency constraints, not "more is always better."**

# 11. Long Context Is Expensive


For many workloads:


# 13. Model Routing

One of the strongest FinOps strategies is:

> **Don't use the most expensive model for every request.**

Example:

```text
User request
      │
      ▼
Model Router
      │
 ┌────┼────┐
 ▼    ▼    ▼
3B   8B   70B
```

Simple questions:

```text
→ 3B
```

Normal business:

```text
→ 8B
```

Complex reasoning:

```text
→ 70B
```

This can drastically reduce cost.

---

# 14. Quality-Aware Routing

Don't route purely by model size.

Consider:

```text
quality
latency
cost
availability
context length
tenant policy
```

For example:

```text
if task_complexity < threshold:
    use 8B
else:
    use 70B
```

But quality must be measured.

Otherwise:

```text
cheap model
→ poor answer
→ retry
→ human correction
→ business cost
```

You saved GPU cost but increased total cost.

# 21. Spot GPUs

Spot can dramatically reduce cost for interruptible workloads.

Good candidates:


```text

```

# 29. P/D Economics

Prefill/decode disaggregation:

```text
Prefill fleet
     +
Decode fleet
```

allows independent scaling.

Suppose workload:

```text
long prompts
short outputs
```

Prefill becomes expensive.

You may need:

```text
3 prefill
2 decode
```

rather than:

```text
3 coupled replicas
```

Potential efficiency improvement.

But P/D introduces:

```text
NIXL
EFA
KV transfer
additional pods
additional networking
additional operational complexity
```

Therefore P/D should be justified by workload shape.

---

# 30. When P/D Is Economically Bad

```text

```

```text

```

The complexity and infrastructure overhead may outweigh any benefit.

Use coupled serving.

This is a critical architecture principle:

> **Don't deploy advanced distributed infrastructure just because it exists.**

# 43. Interview Question

### "How would you reduce the cost of a 70B LLM platform?"

Strong answer:

> I would first characterize the workload and identify whether the cost is driven by unnecessary tokens, model selection, poor batching, KV pressure, inefficient parallelism, idle GPU capacity, or insufficient utilization. I would then benchmark alternative model sizes, quantization levels, TP configurations and GPU types under the actual TTFT/TPOT SLO. After that I'd optimize autoscaling, warm capacity, routing and potentially Spot for appropriate workloads. I would compare architectures using cost per successful request or SLO-constrained tokens rather than GPU utilization alone.

---

# 44. Interview Question

### "Why isn't the cheapest GPU necessarily the cheapest solution?"

Answer:

> Because hourly GPU price isn't the economic unit of inference. A more expensive GPU may provide significantly higher memory capacity, bandwidth or throughput, reducing the number of GPUs and replicas required. I would compare total fleet cost and cost per successful request while meeting latency and availability SLOs.

Excellent Solution Architect answer.

---

# 45. Interview Question

### "How do you decide H100 vs H200?"

Don't say:

> H200 is faster.

Instead:

> I first determine whether the workload is constrained by model fit, KV capacity, memory bandwidth or compute. For long-context and high-concurrency workloads, additional HBM capacity and bandwidth can be more valuable than raw compute. I'd benchmark both GPUs using the production token distribution and compare sustainable SLO-constrained throughput, replica count, failure tolerance and total cost.
