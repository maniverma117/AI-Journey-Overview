# 🚀 Lesson 15 — LLM-Aware Routing, KV-Cache-Aware Routing, llm-d & Prefill/Decode Disaggregation

Yes — **this is the lesson where all the previous pieces start connecting together.**

You've already learned:

```text
GPU
 ↓
CUDA
 ↓
NCCL
 ↓
vLLM
 ↓
KV Cache
 ↓
Continuous Batching
 ↓
TP / PP / DP / EP
 ↓
EKS GPU Scheduling
 ↓
KEDA / HPA
 ↓

```

Now we add the missing intelligence layer:

```text
                    USER
                      │
                      ▼
                ┌───────────┐
                │   Router  │
                └─────┬─────┘
                      │
          ┌───────────┼───────────┐
          │           │           │
          ▼           ▼           ▼
       vLLM A       vLLM B      vLLM C
          │           │           │
       KV A          KV B        KV C
```

A normal load balancer asks:

> **"Which backend should receive this request?"**

An LLM-aware router asks:

> **"Which backend can serve this particular request most efficiently, considering its queue, KV cache, prefix locality, latency, model variant, and current inference state?"**

That is a **massive architectural difference**.

And this is exactly the problem space that **llm-d** is designed for.

Current llm-d architecture is built around a **Router + InferencePool + Model Server**, with the Router's Endpoint Picker (EPP) making LLM-aware endpoint decisions. ([GitHub][1])

# 1. First: Why Normal Load Balancing Starts Breaking

Imagine:

```text
                  Load Balancer
                       │
           ┌───────────┼───────────┐
           ▼           ▼           ▼
        vLLM-1      vLLM-2      vLLM-3
```

Traditional load balancing:

```text
request 1 → vLLM-1
request 2 → vLLM-2
request 3 → vLLM-3
request 4 → vLLM-1
request 5 → vLLM-2
```

Maybe:

```text
round robin
```

Looks reasonable.

But LLM inference has **state**.

Specifically:

```text
KV cache
```

# 2. The Problem With Random Routing

Suppose the user repeatedly sends:

```text
System prompt:
"You are an enterprise banking assistant..."

User:
"What is my balance?"
```

Then:

```text
User:
"What transactions happened yesterday?"
```

Then:

```text
User:
"Why was this transaction declined?"
```

A large portion of the prompt may be identical.

For example:

```text
┌──────────────────────────────────────────┐
│ System prompt                            │
│ Enterprise policy                        │
│ Security instructions                    │
│ Tool definitions                         │
│ Conversation history                     │
├──────────────────────────────────────────┤
│ New user question                        │
└──────────────────────────────────────────┘
```

The first request causes:

```text
prefill
 ↓
KV cache created
```

If request #2 goes to the same replica:

```text
existing prefix
       ↓
KV cache hit
       ↓
less prefill computation
```

Excellent.

But if request #2 goes somewhere else:

```text
request #2
    ↓
vLLM-2
    ↓
prefix not present
    ↓
recompute prefill
```

You just lost the benefit.

This is why llm-d explicitly supports **prefix-cache-aware routing**. Its Router/EPP can select replicas that already contain relevant KV cache for a prompt prefix. ([Llm-D][2])

# 3. Important Distinction: KV Cache vs Prefix Cache

You already learned this in Lesson 9, but now we need to use it architecturally.

### KV cache

The runtime state for active sequences:

```text
tokens
 ↓
K/V tensors
 ↓
GPU memory
```

Used during decode.

### Prefix cache

Previously computed KV blocks that can be reused by another request with the same prefix.

Conceptually:

```text
Request A
───────────────┐
               │
Common prefix  │
               ▼
           KV blocks
               │
               ├──────── Request A
               │
               └──────── Request B
```

So:

> **Prefix caching turns previous computation into reusable inference state.**

That creates a new routing problem:

> Where is the useful cache?

This is fundamentally different.

# 10. Filter → Score → Pick

Suppose you have:

```text
vLLM-1
vLLM-2
vLLM-3
vLLM-4
```

First:

## FILTER

Remove endpoints that cannot handle the request.

For example:

```text
wrong model
wrong variant
prefill-only
decode-only
unhealthy
capacity unavailable
```

Now:

```text
vLLM-1
vLLM-3
vLLM-4
```

remain.

Then:

## SCORE

Calculate:

```text
prefix affinity
+
queue
+
KV availability
+
load
+
latency
+
policy
```

Example:

```text
vLLM-1 = 92
vLLM-3 = 74
vLLM-4 = 51
```

Then:

## PICK

```text
vLLM-1
```

That's the request's destination.

# 15. The Big Problem: Cache Locality

Let's build a real example.

We have:

```text
vLLM-1 → prefix A
vLLM-2 → prefix B
vLLM-3 → prefix C
```

Request:

```text
prefix A + question X
```

Ideal:

```text
Router
  ↓
vLLM-1
  ↓
prefix cache hit
```

Random routing:

```text
Router
  ↓
vLLM-3
  ↓
cache miss
  ↓
prefill again
```

Therefore:

```text
cache-aware routing
```

can reduce:

```text
prefill computation
TTFT
GPU work
```

and increase effective throughput.

llm-d explicitly describes prefix-cache-aware routing as a technique to reduce tail latency and increase throughput. ([Llm-D][2])

# 16. Approximate vs Precise Prefix Routing

This is a fascinating implementation detail.

llm-d currently supports different approaches to prefix-cache awareness, including approximate and precise implementations. ([Llm-D][2])

### Approximate

Router estimates:

```text
"This replica probably has this prefix."
```

This can be lightweight.

### Precise

Router tracks actual KV cache events.

Current llm-d documentation describes a KV Cache Indexer that consumes `KVEvents` from model servers to maintain a near-real-time view of cache state. ([Llm-D][8])

Conceptually:

```text
vLLM
 │
 │ KV events
 ▼
KV Cache Indexer
 │
 ▼
Prefix index
 │
 ▼
EPP
 │
 ▼
routing decision
```

Now the router has much better information.

# 24. Now Let's Split Prefill and Decode

This is the second half of the lesson.

You've learned:

```text
Prompt
  ↓
Prefill
  ↓
KV cache
  ↓
Decode
  ↓

```

The important discovery is:

> **Prefill and decode stress GPUs differently.**

---

# 25. Prefill

During prefill:

```text
Input:
10,000 tokens
```

The model processes the prompt.

This tends to be:

```text
compute-heavy
```

Think:

```text
large matrix operations
high FLOPs
high parallelism
```

---

# 26. Decode

During decode:

```text
Generate:
token 1
token 2
token 3
...
```

Each step generally generates one/few new tokens per sequence while reading KV state.

This tends to be more:

```text
memory-bandwidth-sensitive
```

because the system repeatedly moves model/KV data through the memory hierarchy.

llm-d's current disaggregation documentation describes prefill as FLOPs-bound and decode as memory-bandwidth-bound. ([Llm-D][10])

---

# 27. The Interference Problem

Suppose:

```text
Request A
10K-token prompt
```

arrives while:

```text
Request B
already decoding
```

Without disaggregation:

```text
                 vLLM
                  │
        ┌─────────┴─────────┐
        │                   │
     Prefill              Decode
        │                   │
        └─────────┬─────────┘
                  │
                 GPU
```

Large prefill work can interfere with decode scheduling.

Result:

```text
TPOT / ITL
     ↑
tail latency
     ↑
```

This is particularly painful when:

```text
one request has huge context
```

while:

```text
100 users
are streaming tokens
```

# 34. This Is Why Disaggregation Is Powerful

Without:

```text
P/D disaggregation
```

you have:

```text
same hardware configuration
same replica
same scheduling
```

for:

```text
prefill + decode
```

With disaggregation:

```text
P capacity
+
D capacity
```

can be independently optimized.

For example:

```text
Traffic pattern:

long prompts

```

might require:

```text
more P capacity
```

```text

```

might require:

```text
more D capacity
```

# 35. This Creates Independent Autoscaling

This is a huge architectural advantage.

Instead of:

```text
replicas
 ↓
same P+D capacity
```

you can have:

```text
Prefill autoscaler
       │
       ├── P1
       ├── P2
       └── P3

Decode autoscaler
       │
       ├── D1
       ├── D2
       ├── D3
       └── D4
```

Now:

```text
P replicas != D replicas
```

This is much more efficient when workload characteristics vary.

Current vLLM documentation also describes disaggregated prefill as a mechanism to independently tune TTFT and inter-token latency. ([vLLM][11])

---

# 36. Important Warning

Do not think:

> "Disaggregated prefill always gives more throughput."

Current vLLM documentation explicitly states that disaggregated prefilling **does not inherently improve throughput**. Its major benefits are independent tuning of TTFT/ITL and control of tail ITL by avoiding prefill interference with decoding. ([vLLM][11])

This is a very important interview point.

---

# 37. Disaggregation Does NOT Magically Remove Work

You still have:

```text
Prefill compute
+
KV generation
+
KV transfer
+
Decode
```

You have added:

```text
network transfer
orchestration
failure modes
```

So:

```text
performance benefit
```

must exceed:

```text
transfer + orchestration overhead
```

# 64. Interview Questions — Lesson 15

### Q1. Why isn't round-robin ideal for LLM inference?

Because LLM replicas have stateful inference characteristics such as KV/prefix cache locality, queue depth and varying workloads. Round-robin ignores this state and can cause cache misses, unnecessary prefill computation and poor tail latency.

---

### Q2. What is an InferencePool?

An `InferencePool` is a Kubernetes inference-specific abstraction representing a group of model-server pods and enabling an Endpoint Picker to intelligently select among them. The current API is v1/GA. ([K8s Gateway API Extension][4])

---

### Q3. What is EPP?

> Endpoint Picker.

It is the routing/scheduling engine that evaluates candidate inference endpoints and selects the best one, typically using filtering and scoring plugins.

---

### Q4. What is the difference between Service and InferencePool?

A normal Service primarily provides:

```text
stable endpoint
+
pod selection
+
load distribution
```

InferencePool adds inference-specific semantics:

```text
LLM endpoint discovery
+
EPP
+
KV awareness
+
queue awareness
+
inference-specific routing
```

The Gateway API Inference Extension explicitly positions InferencePool as an inference-focused backend rather than merely a replacement mask for Service. ([K8s Gateway API Extension][4])

---

### Q5. Why does prefix-cache-aware routing matter?

Because a request sent to a replica containing the required prefix KV cache can avoid recomputing the corresponding prefill work, improving latency and reducing accelerator work. ([Llm-D][2])

---

### Q6. Does cache-aware routing always mean "send to the replica with cache"?

**No.**

Because that replica could be overloaded.

You need:

```text
cache affinity
+
load
+
latency
+
capacity
+
policy
```

---

### Q7. Why separate prefill and decode?

Because they have different resource characteristics and interfere with each other. Disaggregation allows independent optimization/scaling of the two phases and can improve tail ITL/TTFT behavior. ([Llm-D][10])

---

### Q8. Does P/D disaggregation automatically increase throughput?

**No.**

Current vLLM documentation explicitly says disaggregated prefilling does not inherently improve throughput. Its primary benefits include independent TTFT/ITL tuning and reducing prefill interference with decode. ([vLLM][11])

---

### Q9. Why do we need RDMA/EFA?

Because KV cache can be very large and must be transferred efficiently between prefill and decode workers. Production disaggregation needs high-performance interconnects; llm-d specifically calls out RDMA for efficient KV transfer. ([Llm-D][10])

---

### Q10. What is NIXL?

At the architecture level:

> A high-performance abstraction used for point-to-point movement of inference data, including KV cache, across accelerator/server boundaries.

Don't memorize the acronym first.

Understand:

```text
GPU
 ↓
KV
 ↓
NIXL
 ↓
RDMA/EFA
 ↓
GPU
```

That's what matters.
