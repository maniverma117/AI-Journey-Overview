# 3. Why don't we just use Transformers?

You can technically do:

```python
model.generate(...)
```

But production serving is more complicated.

Imagine:

```text
User A → request
User B → request
User C → request
User D → request
```

A naive server might process:

```text
A
 ↓
B
 ↓
C
 ↓
D
```

That wastes GPU capacity.

vLLM instead tries to efficiently schedule many requests onto the GPU.

Conceptually:

```text
A ─┐
B ─┤
C ─┼──→ Scheduler → GPU
D ─┤
E ─┘
```

That's where inference engineering starts.

# 6. Step 2 — Scheduler

This is one of vLLM's most important components.

Imagine:

```text
Request A
input = 2K
output = 1K

Request B
input = 10K
output = 500

Request C
input = 500
output = 5K
```

The scheduler decides how GPU execution should be organized.

You can think of it as:

```text
                   Requests
                      │
                      ▼
                 vLLM Scheduler
                      │
           ┌──────────┼──────────┐
           ▼          ▼          ▼
        Prefill     Decode     Waiting
           │          │
           └─────┬────┘
                 ▼

```

This is one reason vLLM can achieve much better utilization than simplistic one-request-at-a-time serving.

# 7. Prefill

For a prompt:

```text
You are an AI infrastructure engineer...
```

vLLM processes the input tokens.

This is:

```text
PREFILL
```

It processes the existing context and generates the internal state required for decoding.

The first token latency is heavily influenced by this stage.

Therefore:

```text
TTFT
```

is strongly connected to prefill behavior.

---

# 8. Decode

After prefill:

```text
Token 1
 ↓
Token 2
 ↓
Token 3
 ↓
Token 4
```

Each generated token depends on previous tokens.

That's:

```text
DECODE
```

And this is where:

```text
TPOT / ITL
```

becomes important.

---

# 9. Why TTFT and TPOT are different

Suppose:

```text
TTFT = 500 ms
TPOT = 30 ms
```

User experiences:

```text
wait 500ms
 ↓
first token
 ↓
next token every ~30ms
```

If:

```text
TTFT = 3 seconds
TPOT = 20ms
```

the generation itself may be fast.

The problem is the initial wait.

Conversely:

```text
TTFT = 300ms
TPOT = 100ms
```

starts quickly but generates slowly.

You need both metrics.

# 10. vLLM and continuous batching

This is one of the most important Level 2 concepts.

Traditional batching:

```text
Batch starts
 ↓
A
B
C
 ↓
all finish
 ↓
next batch
```

Problem:

```text
A finishes early
```

but may leave GPU capacity unused while B/C continue.

Continuous batching dynamically schedules requests as they progress.

Conceptually:

```text
Time →

A A A A A
B B B B
C C C
D D D D D
E E
```

Requests enter and leave the batch dynamically.

This dramatically improves serving efficiency for variable-length workloads.

---

# 11. Why this matters for your customer

Suppose:

```text
100 concurrent users
```

with:

```text
different prompt lengths
different output lengths
```

A traditional fixed batch can be inefficient.

Continuous batching lets the inference engine keep feeding useful work to the GPU.

Therefore:

```text
GPU utilization
        ↓
better scheduling
        ↓
higher aggregate throughput
```

But remember:

> Higher throughput can come at the expense of individual latency if the scheduler becomes overloaded.

That's why we always measure SLOs.

# 12. PagedAttention

Now we reach one of vLLM's foundational ideas.

Remember KV cache?

For every active request, you need:

```text
K
V
```

for previous tokens.

Naively allocating large contiguous KV-cache memory can create:

```text
fragmentation
wasted memory
allocation complexity
```

PagedAttention addresses this by managing KV cache in blocks/pages rather than requiring each sequence to own one giant contiguous allocation.

Conceptually:

```text
Request A
KV → [Block 1][Block 7][Block 12]

Request B
KV → [Block 2][Block 4][Block 9]

Request C
KV → [Block 3][Block 5][Block 6]
```

instead of:

```text
A → giant contiguous area
B → giant contiguous area
C → giant contiguous area
```

This is one of the key innovations behind vLLM.

---

# 13. Why PagedAttention matters to AIRE

You don't need to implement it.

You need to understand the infrastructure consequence:

```text
better KV memory management
        ↓
less fragmentation
        ↓
more effective KV capacity
        ↓
potentially more concurrent requests
```

Therefore:

```text
vLLM
```

is not simply:

```text
PyTorch + HTTP
```

It is an inference runtime optimized around serving behavior.

---

# 14. KV cache becomes your capacity currency

This is a very useful mental model.

Suppose:

```text
GPU VRAM = 80GB
```

and:

```text
weights = 60GB
```

Then only roughly:

```text
20GB
```

remains for:

```text

```

The amount of KV cache determines how many active tokens you can keep resident.

So:

```text

   ↓

   ↓

```

This is why Lesson 3 matters so much now.

# 15. `gpu-memory-utilization`

vLLM provides configuration around GPU memory allocation.

For example:

```bash
--gpu-memory-utilization 0.90
```

Conceptually:

```text
80GB GPU
 ×
0.90
=
72GB target allocation
```

But don't interpret this as:

> “vLLM gets exactly 72GB and nothing else exists.”

There are runtime allocations and implementation details.

The current vLLM CLI documentation describes `--gpu-memory-utilization` as the fraction of GPU memory allocated for the model executor, with a current default of 0.92.

---

# 16. Why you shouldn't blindly use 0.99

A beginner may think:

```text
80GB
×
99%
=
79.2GB
```

Great!

More memory!

Not necessarily.

Production needs headroom.

You can encounter:

```text

```

during runtime because of:

```text

workspace allocations
fragmentation
CUDA graphs
model behavior
```

So:

```text
maximum memory
```

doesn't necessarily equal:

```text
maximum safe production memory
```

Benchmark it.

# 23. The saturation curve

This is one of the most important graphs you'll eventually create.

Conceptually:

```text
Throughput
   │
   │             ┌────────────
   │          ┌──┘
   │       ┌──┘
   │    ┌──┘
   │ ┌──┘
   └────────────────────────────
             Concurrency
```

Initially:

```text

      ↓
more throughput
```

Eventually:

```text
GPU saturation
      ↓
queue grows
      ↓
TTFT increases
```

So:

```text
throughput ↑
latency    ↑↑
```

after saturation.

That point is your **serving capacity boundary**.

# 🔥 Interview Questions

### 1. What problem does vLLM solve?

Don't say:

> "It runs LLMs."

Better:

> "vLLM is an optimized LLM inference engine that manages model execution, request scheduling, continuous batching, KV cache, parallelism and serving APIs to improve inference efficiency and throughput."

---

### 2. What is continuous batching?

> Dynamically scheduling active requests into GPU execution rather than waiting for a fixed batch to completely finish before admitting new work.

---

### 3. What is PagedAttention?

> A KV-cache memory-management approach that manages KV cache in blocks/pages, reducing fragmentation and enabling more efficient memory utilization across concurrent sequences.

---

### 4. Why isn't GPU utilization a sufficient autoscaling metric?

Because high GPU utilization can occur while latency and queue depth are still healthy or unhealthy. Inference autoscaling should correlate GPU signals with queue depth, TTFT, TPOT and request/token rates.

---

### 5. What is the difference between TTFT and TPOT?

```text
TTFT
Time to first token

TPOT
Time per output token
```

TTFT is strongly influenced by request admission and prefill; TPOT primarily reflects token-generation/decode performance.

---

### 6. Why does concurrency initially improve throughput?

Because additional requests provide more parallel work for batching and GPU execution.

Eventually:

```text
GPU saturation
 ↓
queue
 ↓
latency increases
```

---

### 7. What is the first thing you do when optimizing vLLM?

> Establish a reproducible baseline using the real model and representative workload, measure TTFT/TPOT/throughput/KV/GPU/CPU, identify the bottleneck, then change one variable at a time and benchmark again.

**That's an excellent production answer.**
