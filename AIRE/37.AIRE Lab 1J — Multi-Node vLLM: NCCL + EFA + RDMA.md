# Lab 1J — Multi-Node vLLM: NCCL + EFA + RDMA

We now cross the boundary from:

```text
ONE EC2 GPU node
        ↓
multi-GPU inference
```

to:

```text
        EC2 Node A                         EC2 Node B
   ┌─────────────────┐              ┌─────────────────┐
   │ GPU0 ... GPU7   │              │ GPU0 ... GPU7   │
   │      H100       │              │      H100       │
   └────────┬────────┘              └────────┬────────┘
            │                                │
          NIC/EFA                          NIC/EFA
            │                                │
            └──────────── RDMA ─────────────┘
                         │
                       NCCL
```

This is one of the most important topics for an **AI Infrastructure / AI Reliability Engineer**, because once communication crosses the EC2 node boundary, **networking becomes part of your GPU performance**.

AWS documents EFA as integrating with Libfabric and supporting both NCCL and NIXL for AI/ML workloads. ([AWS Documentation][1])

---

# 1. First: why do we need multiple nodes?

Imagine:

```text
Model = 200B parameters
```

and suppose:

```text
1 GPU = 80 GB
8 GPUs = 640 GB
```

Maybe one 8-GPU node isn't enough.

You could have:

```text
Node A
8 × H100
= 640 GB

Node B
8 × H100
= 640 GB
```

Total:

```text
16 GPUs
1.28 TB GPU memory
```

Now we can potentially distribute the model across both nodes.

For example:

```text
TP = 8
PP = 2
```

or:

```text
TP = 16
PP = 1
```

These are **very different architectures**.

---

# 2. The fundamental difference

Inside one node:

```text
GPU
 ↓
NVLink/NVSwitch
 ↓
GPU
```

Across nodes:

```text
GPU
 ↓
PCIe
 ↓
NIC
 ↓
EFA
 ↓
AWS network
 ↓
EFA
 ↓
NIC
 ↓
PCIe
 ↓
GPU
```

That additional path matters enormously.

Think of it as:

```text
                    SPEED
                      │
          ┌───────────┴───────────┐
          │                       │
      Same node              Cross node
          │                       │
       NVLink                    EFA
          │                       │
       extremely              network
        tightly                latency
       connected             + bandwidth
```

So:

> **Multi-node inference is not simply "add more GPUs."**

# 3. NCCL is the communication engine

We already learned NCCL.

Now put it into the actual architecture:

```text
                  vLLM
                    │
                 PyTorch
                    │
                  NCCL
              ┌─────┴─────┐
              │            │
         same-node     cross-node
              │            │
          NVLink/PCIe     EFA
                           │
                       Libfabric
```

NCCL provides collective communication primitives across GPUs, including GPUs located on different nodes. AWS explicitly documents NCCL + EFA for multi-node ML workloads. ([AWS Documentation][2])

# 4. What exactly is being communicated?

Suppose we have:

```text
TP=16
```

and:

```text
Node A → GPUs 0-7
Node B → GPUs 8-15
```

A Transformer operation may require GPUs to exchange:

```text
activations
partial results
gradients   ← training
tensor shards
routing information
```

For inference, the important pieces are primarily:

```text
weights/shards
activations
collective results
```

The communication pattern depends on the model architecture and parallelism.

# 5. AllReduce example

Suppose four GPUs calculate:

```text
GPU0 → [1,2]
GPU1 → [3,4]
GPU2 → [5,6]
GPU3 → [7,8]
```

An AllReduce sum produces:

```text
[16,20]
```

and every participant gets:

```text
GPU0 → [16,20]
GPU1 → [16,20]
GPU2 → [16,20]
GPU3 → [16,20]
```

Now imagine GPU0-3 are on Node A and GPU4-7 are on Node B.

The communication now has to cross the network.

---

# 6. Why the network can become the bottleneck

Imagine:

```text
GPU compute
   ↓
100 units
```

but communication can only sustain:

```text
60 units
```

Then adding GPUs doesn't give linear performance.

You get:

```text
1 node  → 100
2 nodes → 140
```

instead of:

```text
2 × 100 = 200
```

This is **scaling efficiency**.

```text
Scaling efficiency =
actual speedup / ideal speedup
```

For example:

```text
1 node = 100 tok/s

2 nodes = 170 tok/s

ideal = 200

efficiency = 170 / 200
           = 85%
```

That's pretty good.

If:

```text
2 nodes = 110 tok/s
```

then:

```text
efficiency = 55%
```

Something is probably wrong—or the workload simply doesn't scale well.

# 7. EFA

Now introduce AWS EFA.

EFA is AWS's high-performance networking interface for HPC and AI/ML workloads.

The stack looks roughly like:

```text
Application
    │
PyTorch
    │
NCCL
    │
AWS OFI NCCL plugin
    │
Libfabric
    │
EFA
    │
AWS network
```

EFA integrates with Libfabric and supports NCCL and NIXL. ([AWS Documentation][1])

---

# 8. EFA vs ENA

This is an interview question.

### ENA

General-purpose AWS networking:

```text
application
    ↓
TCP/IP
    ↓
ENA
```

Used for:

* normal APIs
* microservices
* databases
* web traffic

---

### EFA

Specialized high-performance networking:

```text
AI/HPC
  ↓
Libfabric
  ↓
EFA
```

Used for:

* distributed training
* distributed inference
* NCCL
* MPI
* NIXL
* RDMA-style communication

So:

> **Don't think of EFA as simply "a faster ENA."**

It is a specialized communication path designed for high-performance workloads.

---

# 9. RDMA

Now the next concept.

**RDMA = Remote Direct Memory Access.**

Conceptually:

```text
Normal path:

GPU
 ↓
CPU
 ↓
kernel/network stack
 ↓
NIC
 ↓
network
```

Potentially:

```text
GPU
 ↓
NIC
 ↓
network
 ↓
NIC
 ↓
GPU
```

with GPUDirect RDMA enabling direct exchange between GPU memory and peer devices such as network interfaces, avoiding a CPU-memory bounce path. ([NVIDIA Docs][3])

This reduces:

```text
CPU involvement
memory copies
latency
CPU overhead
```

---

# 10. GPUDirect RDMA

This is particularly important.

Think:

```text
         Traditional

GPU
 │
 ▼
CPU memory
 │
 ▼
NIC
 │
 ▼
Network
 │
 ▼
NIC
 │
 ▼
CPU memory
 │
 ▼
GPU
```

versus:

```text
          GPUDirect RDMA

GPU
 │
 │ direct
 ▼
NIC
 │
 ▼
Network
 │
 ▼
NIC
 │
 │ direct
 ▼
GPU
```

NVIDIA documents GPUDirect RDMA as enabling direct GPU ↔ peer-device data exchange over PCIe. ([NVIDIA Docs][3])

NCCL can automatically use GPU Direct RDMA when the topology permits it; its current documentation exposes controls such as `NCCL_NET_GDR_LEVEL` for GPU/NIC topology distance. ([NVIDIA Docs][4])

This can affect GPUDirect RDMA.

# 13. TP8 × 2 nodes vs TP16

This is an important architecture decision.

Suppose:

```text
Node A = 8 GPUs
Node B = 8 GPUs
```

### Architecture A

```text
TP=16
```

One giant tensor-parallel group:

```text
GPU0 ─┐
GPU1  │
...   ├── Node A
GPU7 ─┘

       EFA

GPU8 ─┐
GPU9  │
...   ├── Node B
GPU15 ─┘
```

Every GPU participates.

---

### Architecture B

```text
TP=8
PP=2
```

```text
Node A
GPU0-7
   │
   │ TP
   ▼
Pipeline Stage 0
   │
   │ network
   ▼
Node B
GPU0-7
   │
   │ TP
   ▼
Pipeline Stage 1
```

This can keep tensor-parallel communication local to each node while pipeline-stage communication crosses nodes.

Whether this is better depends on the model and workload.

---

# 14. The key design principle

When possible:

> **Keep the most communication-intensive parallelism inside the strongest interconnect domain.**

For example:

```text
Node
 ├── GPU0
 ├── GPU1
 ├── GPU2
 ...
 └── GPU7

NVLink/NVSwitch
```

Use that domain for:

```text
TP=8
```

Then potentially use:

```text
PP
```

between nodes.

This isn't a universal rule, but it is an excellent architecture starting point.

Distributed AI stacks are particularly sensitive to combinations of:

```text
NVIDIA driver
CUDA
PyTorch
NCCL
EFA software
OFI NCCL plugin

```

Imagine:

```text

```

and:

```text

   ↓
```


# 35. Failure domains become enormous

Suppose:

```text
TP=16
```

across:

```text
2 nodes
```

If Node B fails:

```text
Node B ❌
```

your entire distributed replica probably fails.

Therefore:

```text
TP16
```

has a massive failure domain.

Compare:

```text
TP4 × 4 replicas
```

Now:

```text
Node A → Replica 1
Node B → Replica 2
Node C → Replica 3
Node D → Replica 4
```

One node failure:

```text
1 replica lost
3 replicas remain
```

This is why:

> **Parallelism architecture and reliability architecture cannot be designed independently.**

---

# 36. Capacity planning changes

With TP16:

```text
1 replica = 16 GPUs
```

Suppose your demand requires:

```text
1.2 replicas
```

You can't provision:

```text
1.2 × 16
```

You need another full distributed group.

So your effective capacity granularity becomes:

```text
16 GPUs
```

This can create substantial idle capacity.

With:

```text
TP4 × 4
```

your unit is:

```text
4 GPUs
```

Much more granular.

```text
    ↓
PCIe
    ↓
NIC
    ↓
EFA/RDMA
    ↓
EC2 network
```

Every step introduces a different performance and failure characteristic.

That is what makes **AI infrastructure different from ordinary Kubernetes infrastructure**.

## Interview checkpoint

If an interviewer asks:

> **"Why is multi-node tensor parallelism difficult?"**

A strong answer is:

> "Because the model's execution becomes dependent on distributed GPU communication. Within a node, tensor-parallel communication can use NVLink/NVSwitch, but across nodes it depends on the PCIe-to-NIC path, EFA/RDMA, NCCL, Libfabric and the GPU/NIC topology. Communication latency and bandwidth can reduce scaling efficiency, while node or network failures can take down the entire distributed replica. Therefore I validate the EFA/NCCL stack independently, benchmark communication bandwidth, use topology-aware placement, keep software versions consistent, and choose TP/PP based on SLO, memory, scaling efficiency and failure-domain requirements."

That is the level we're targeting.
