# Level 2 — Lesson 10 vLLM Performance Engineering — Extreme Deep Dive

The goal of this lesson is not:

> “Which vLLM flag gives me more tokens/sec?”

The real goal is:

> **Given a workload, GPU, model, latency SLO, and cost target, how do I determine what is limiting performance and systematically improve it?**

That is an **AI Reliability Engineer** skill.

---

# 1. First: Forget GPU utilization as your primary KPI

Suppose you have:

```text
H100
GPU utilization = 97%
```

A junior engineer says:

> Great. GPU is almost fully utilized.

An AIRE asks:

```text
TTFT P50      = ?
TTFT P95      = ?
TTFT P99      = ?

TPOT P50      = ?
TPOT P95      = ?
TPOT P99      = ?

Input tok/s   = ?
Output tok/s  = ?

Queue depth   = ?
KV usage      = ?
Preemptions   = ?

HBM bandwidth = ?
Tensor activity = ?
DRAM activity = ?

CPU utilization = ?
NCCL utilization = ?

Error rate    = ?
```

Because:

**97% GPU utilization can mean either:**

```text
A. Excellent utilization
```

or

```text
B. The GPU is overloaded and users are waiting
```

Those are completely different situations.

---

# 2. The fundamental performance model

Think of vLLM as four layers:

```text
                    REQUESTS
                       │
                       ▼
              ┌─────────────────┐
              │   HTTP/API      │
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │    SCHEDULER    │
              │                 │
              │ admission       │
              │ batching        │
              │ priorities      │
              └────────┬────────┘
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        PREFILL               DECODE
        compute-heavy         memory-heavy
             │                   │
             └─────────┬─────────┘
                       ▼
              ┌─────────────────┐
              │ GPU EXECUTION   │
              │                 │
              │ CUDA            │
              │ Tensor Cores    │
              │ HBM             │
              │ NCCL            │
              └─────────────────┘
```

Performance problems generally fall into one of five buckets:

```text
1. Compute-bound
2. Memory-bandwidth-bound
3. KV-cache / memory-capacity-bound
4. Scheduler / queue-bound
5. Communication-bound
```

Your first job is to identify **which one**.

---

# 3. Prefill and decode behave differently

This is one of the most important concepts in LLM infrastructure.

Imagine:

```text
Input:
"Explain Kubernetes networking in extreme detail..."
       ↓
20,000 input tokens

Output:
2,000 tokens
```

The request has two major phases.

## Phase 1 — Prefill

Process:

```text
20,000 input tokens
```

This involves huge matrix operations.

Conceptually:

```text
20K tokens
   │
   ▼
Transformer layers
   │
   ▼
large matrix operations
   │
   ▼
Tensor Cores
```

Prefill tends to be relatively **compute intensive**.

---

## Phase 2 — Decode

Now the model generates:

```text
token 1
token 2
token 3
...
token 2000
```

Each decode step typically produces the next token while consulting the accumulated KV cache.

The workload becomes much more sensitive to:

```text
HBM bandwidth
KV cache access
memory movement
kernel launch overhead
batching
```

So:

```text
PREFILL
   ↓
compute-heavy

DECODE
   ↓
memory-bandwidth-sensitive
```

This distinction is fundamental when diagnosing performance.

---

# 4. Why batching changes everything

Suppose you have:

```text
1 request
```

GPU:

```text
┌─────────────────────────────┐
│                             │
│       GPU mostly idle       │
│                             │
└─────────────────────────────┘
```

Now:

```text
100 concurrent requests
```

You can combine work:

```text
Request 1 ─┐
Request 2 ─┤
Request 3 ─┤
Request 4 ─┤
...         ├──► GPU
Request 100 ┘
```

This gives the GPU more work per scheduling iteration.

Therefore:

```text
Concurrency ↑
      ↓
Batch size ↑
      ↓
GPU utilization ↑
      ↓
Throughput ↑
```

But only until saturation.

Eventually:

```text
Concurrency ↑
      ↓
KV usage ↑
      ↓
queue ↑
      ↓
TTFT ↑
      ↓
P99 ↑
```

This is why:

> **Maximum throughput is not necessarily your production operating point.**

---

# 5. The throughput/latency curve

Imagine we run:

```text
Concurrency = 1
2
4
8
16
32
64
128
256
```

We might see:

```text
Output tok/s

 ^
 |                         ─────────
 |                    ─────
 |                ────
 |            ───
 |        ───
 |    ───
 |___───────────────────────────────> concurrency
```

Throughput eventually plateaus.

But latency might look like:

```text
P99 TTFT

 ^
 |                              /
 |                            /
 |                         __/
 |                     ___/
 |                ____/
 |___________─────
 +──────────────────────────────► concurrency
```

The dangerous region is:

```text
             saturation
                 │
                 ▼
───────────────┐
               │
               │ latency explodes
               │
               ▼
```

You generally want to operate **before** the steep latency knee.

---

# 6. This gives us a production concept: saturation point

Suppose:

```text
Concurrency  Output tok/s  P95 TTFT
-------------------------------------
1             80           120ms
4             300          150ms
8             550          190ms
16            900          280ms
32            1,250        450ms
64            1,300        1.2s
128           1,280        4.8s
```

Where is the useful operating region?

Probably around:

```text
32–64
```

Not:

```text
128
```

Even though GPU utilization might be excellent at 128.

Because your SLO might be:

```text
P95 TTFT < 1 second
```

Then 128 concurrency is unacceptable.

---

# 7. vLLM's two important scheduling knobs

Two parameters you should understand deeply:

```text
max_num_seqs
max_num_batched_tokens
```

They control different dimensions.

---

# 8. `max_num_seqs`

Conceptually:

> Maximum number of sequences processed in one iteration.

For example:

```text
max_num_seqs = 32
```

means the scheduler won't process an arbitrary number of sequences in the iteration.

Think:

```text
                Scheduler
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
      seq          seq          seq
       ...
       └──────── up to limit ────┘
```

This interacts strongly with:

```text
KV cache
batching
CUDA graphs
scheduler overhead
memory
latency
```

Increasing it can increase concurrency/throughput, but can also increase KV pressure.

Current vLLM documentation explicitly recommends considering reducing `max_num_seqs` or `max_num_batched_tokens` when preemptions occur because reducing the batch reduces KV-cache pressure. ([vLLM][1])

---

# 9. `max_num_batched_tokens`

This is even more interesting.

Think of it as:

> How many tokens can the scheduler process in an iteration.

Suppose:

```text
max_num_batched_tokens = 8192
```

You might have:

```text
Request A = 2000 tokens
Request B = 3000
Request C = 1000
Request D = 2000

Total = 8000
```

Fits.

But:

```text
Request A = 6000
Request B = 5000
```

Total:

```text
11,000
```

doesn't fit into:

```text
8,192
```

So scheduling has to manage that work.

This is especially important for **chunked prefill**.

---

# 10. Chunked prefill — one of the most important concepts

Suppose:

```text
Request A
input = 50,000 tokens
```

Without chunking, you could think of it as:

```text
AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
             50K tokens
                    ↓
                  GPU
```

This huge prefill can monopolize GPU compute.

Meanwhile:

```text
Request B → decoding
Request C → decoding
Request D → decoding
```

are waiting.

That can cause:

```text
TPOT ↑
ITL ↑
```

for already-running generations.

---

# 11. Chunked prefill

Instead:

```text
50K prefill
```

becomes:

```text
chunk 1 = 8K
chunk 2 = 8K
chunk 3 = 8K
...
```

The scheduler can interleave work.

Conceptually:

```text
iteration 1:

Prefill A chunk
Decode B
Decode C
Decode D


iteration 2:

Prefill A chunk
Decode B
Decode C
Decode D


iteration 3:

Prefill A chunk
Decode B
Decode C
Decode D
```

Now the GPU is doing:

```text
compute-heavy prefill
+
memory-sensitive decode
```

in a more balanced way.

Current vLLM V1 enables chunked prefill whenever possible and prioritizes pending decode work before scheduling available prefill tokens. ([vLLM][1])

---

# 12. The `max_num_batched_tokens` tradeoff

This parameter creates a fascinating triangle.

### Smaller value

Example:

```text
2048
```

You limit prefill work per iteration.

Potential result:

```text
decode gets more protection
       ↓
ITL improves
```

But:

```text
prefill takes longer
       ↓
TTFT can increase
```

---

### Larger value

Example:

```text
16384
```

More prefill can happen per iteration.

Potential result:

```text
prefill completes faster
       ↓
TTFT improves
```

But:

```text
decode may wait longer
       ↓
ITL/TPOT may worsen
```

And there is a throughput tradeoff.

vLLM's current optimization guidance specifically describes this relationship: smaller values can favor ITL, while larger values can favor TTFT; it notes values above 8192 can be useful for throughput in some smaller-model/large-GPU workloads. ([vLLM][1])

**Important:** treat those as tuning guidance, not universal magic numbers.

---

# 13. This is how an AIRE tunes it

Don't say:

> "Let's set it to 8192 because the docs say so."

Instead:

```text
baseline
   │
   ├── 2048
   ├── 4096
   ├── 8192
   ├── 16384
   └── 32768
```

Measure:

```text
P50 TTFT
P95 TTFT
P99 TTFT

P50 TPOT
P95 TPOT
P99 TPOT

output tok/s
total tok/s

GPU memory
KV utilization
preemption

GPU DRAM activity
Tensor activity
```

Then select the configuration that satisfies the **SLO**, not the configuration with the highest raw throughput.

---

# 14. Preemption — a signal you should learn to love

Imagine:

```text
KV cache
████████████████████████████ 96%
```

Incoming requests need more KV blocks.

vLLM may need to preempt requests.

Conceptually:

```text
running request
      ↓
preempt
      ↓
free resources
      ↓
other request executes
      ↓
previous request recomputed
```

That can hurt latency.

Current vLLM documentation states that preemption/recomputation can adversely affect end-to-end latency and recommends actions such as increasing GPU memory utilization, decreasing `max_num_seqs`/`max_num_batched_tokens`, or increasing parallelism when appropriate. ([vLLM][1])

So:

```text
preemption_count > 0
```

is not merely an informational metric.

It is a **performance warning**.

---

# 15. Why increasing GPU memory utilization can help

Suppose:

```text
H100 = 80GB
```

and vLLM has:

```text
gpu_memory_utilization = 0.90
```

Approximately:

```text
72GB
```

is available to the relevant allocation budget.

Increasing it may allow:

```text
more KV blocks
      ↓
more active sequences
      ↓
fewer preemptions
```

But:

> **Never blindly set this to 1.0.**

You need headroom for:

```text
CUDA allocations
kernels
workspace
graphs
runtime overhead
model memory
```

The right value is workload and version dependent.

---

# 16. CUDA Graphs

Now we go one level deeper into GPU execution.

Normally, launching GPU work involves host-side dispatch.

Conceptually:

```text
CPU
 │
 ├── launch kernel
 ├── launch kernel
 ├── launch kernel
 ├── launch kernel
 └── ...
       ↓
     GPU
```

There is overhead associated with repeatedly launching operations.

CUDA Graphs allow a sequence of GPU operations to be captured and replayed.

Conceptually:

```text
normal:

CPU → kernel → CPU → kernel → CPU → kernel


CUDA Graph:

CPU ───────► GRAPH
              │
              ├── kernel
              ├── kernel
              ├── kernel
              └── kernel
```

This can reduce launch/dispatch overhead.

vLLM uses CUDA graphs in performance-critical paths and has different capture configurations for decode and other execution patterns. ([vLLM][2])

---

# 17. Why CUDA Graphs are particularly interesting for decode

Decode often operates with:

```text
query length ≈ 1
```

per sequence per step.

That means individual operations can be relatively small.

If:

```text
GPU computation = 100 μs
CPU launch overhead = 20 μs
```

then overhead is significant.

But if:

```text
GPU computation = 5 ms
CPU launch overhead = 20 μs
```

it is less significant.

So reducing dispatch overhead can be particularly useful for latency-sensitive small operations.

---

# 18. CUDA Graphs aren't free

Here's the AIRE-level insight.

CUDA graphs can consume additional GPU memory.

Therefore:

```text
CUDA graphs
     ↓
performance ↑
but
     ↓
GPU memory usage ↑
```

That memory could otherwise be:

```text
KV cache
```

So you have:

```text
CUDA graph memory
        vs
KV cache capacity
```

Current vLLM documentation explicitly notes that CUDA graphs consume extra GPU memory and provides controls for reducing captured graph sizes or disabling graph capture with `enforce_eager`. ([vLLM][3])

This is exactly the kind of tradeoff a production AI infrastructure engineer needs to understand.

---

# 19. A classic production failure

Suppose:

```text
Before optimization:

KV cache = 88%
Preemption = 0
P95 TTFT = 600ms
```

Engineer enables more CUDA graphs.

Now:

```text
GPU memory
█████████████████████████████

KV cache = 94%
preemption = 12/min
P95 TTFT = 1.8s
```

They might say:

> CUDA graphs made vLLM slower.

Not exactly.

The actual chain might be:

```text
more CUDA graph memory
       ↓
less KV capacity
       ↓
more preemption
       ↓
recomputation
       ↓
higher latency
```

This is why isolated metrics are dangerous.

---

# 20. Performance debugging is causal analysis

This should become your mindset.

Don't say:

> TTFT increased.

Ask:

```text
Why?
```

Possibilities:

```text
arrival rate ↑
      ↓
queue ↑
      ↓
TTFT ↑
```

or:

```text
input tokens ↑
      ↓
prefill work ↑
      ↓
TTFT ↑
```

or:

```text
KV capacity ↓
      ↓
preemption ↑
      ↓
recompute ↑
      ↓
TTFT ↑
```

or:

```text
NCCL communication ↑
      ↓
GPU synchronization ↑
      ↓
TP latency ↑
```

or:

```text
CPU saturation
      ↓
request processing delay
      ↓
GPU starvation
      ↓
throughput ↓
```

That's the difference between **monitoring** and **reliability engineering**.

# 21. Prefix caching

Let's revisit prefix caching from a performance perspective.

Imagine an agent sends:

```text
SYSTEM PROMPT
+
TOOL DEFINITIONS
+
POLICY
+
USER MESSAGE
```

Every request has:

```text
same system prompt
same tool definitions
same policy
```

Only:

```text
user message
```

changes.

Without prefix caching:

```text
Request 1 → compute 10K tokens
Request 2 → compute same 10K tokens again
Request 3 → compute same 10K tokens again
```

With prefix caching:

```text
common prefix
      │
      ▼
compute once
      │
      ├── Request 1
      ├── Request 2
      └── Request 3
```

This can dramatically change performance for workloads with high prefix reuse.

But benchmark carefully.

Current vLLM benchmarking documentation warns that repeated benchmark runs can reuse prefix-cache entries and inflate measured throughput. ([vLLM][4])

---

# 22. Benchmarking with prefix caching can fool you

Suppose you run:

```text
benchmark #1
```

and get:

```text
2,000 tok/s
```

Run again:

```text
benchmark #2
```

and get:

```text
2,700 tok/s
```

You might think:

> Something improved!

Maybe not.

You may simply have:

```text
prefix cache HIT
```

instead of:

```text
prefix cache MISS
```

Therefore benchmarking requires control over:

```text
cache state
dataset
seed
prompt distribution
input length
output length
concurrency
arrival pattern
warmup
```

# 23. Benchmarking is an experiment, not a command

This is one of the most important lessons.

Bad benchmark:

Good benchmark:

```text
   ↓

   ↓

```

# 26. Compute-bound vs memory-bound

This is where your CUDA knowledge becomes useful.

Imagine:

```text
Tensor Core activity = very high
DRAM activity = moderate
```

Likely:

```text
compute-bound
```

Another workload:

```text
Tensor Core activity = moderate
DRAM activity = extremely high
```

Could indicate:

```text
memory-bandwidth-bound
```

Another:

```text
GPU utilization = 40%
CPU = 100%
```

Potentially:

```text
CPU/request pipeline bottleneck
```

Another:

```text
GPU = 90%
NCCL = high
```

Potentially:

```text
communication-bound
```

Another:

```text
GPU = 90%
KV = 99%
preemptions = high
queue = high
```

Potentially:

```text
memory-capacity / scheduling-bound
```

Same GPU utilization.

Completely different problems.

# 27. Tensor Parallelism performance trap

Suppose a model requires:

```text
TP=4
```

You think:

> TP=8 must be faster.

Not necessarily.

Consider:

```text
TP=4

GPU0 ─────┐
GPU1 ─────┤
GPU2 ─────┤
GPU3 ─────┘
```

versus:

```text
TP=8

GPU0 ─────┐
GPU1 ─────┤
GPU2 ─────┤
GPU3 ─────┤
GPU4 ─────┤
GPU5 ─────┤
GPU6 ─────┤
GPU7 ─────┘
```

More GPUs means:

```text
more compute capacity
```

but potentially:

```text
more synchronization
more NCCL traffic
more coordination
```

Therefore:

```text
TP4 > TP8
```

is entirely possible for a particular workload.

You must benchmark.

# 28. Think in terms of tokens per dollar

This is where performance engineering becomes **architecture**.

Suppose:

```text
GPU A:
$5/hour
1,000 output tok/s

GPU B:
$8/hour
1,500 output tok/s
```

Calculate:

```text
A:
1000 / 5 = 200 tok/s/$

B:
1500 / 8 = 187.5 tok/s/$
```

GPU A is economically better.

But now suppose:

```text
GPU A:
P95 TTFT = 2 sec

GPU B:
P95 TTFT = 700 ms
```

and customer requires:

```text
P95 TTFT < 1 sec
```

GPU A is no longer viable.

Therefore:

> **Cost optimization happens inside the SLO boundary.**

Not before it.

# 29. Speculative decoding

Now we enter an advanced optimization.

Normally:

```text
Large model
    ↓
token
    ↓
token
    ↓
token
```

Suppose we use:

```text
Small draft model
       ↓
generates several candidate tokens
       ↓
Large target model
       ↓
verifies candidates
```

Conceptually:

```text
             ┌──────────────┐
             │ Draft Model  │
             └──────┬───────┘
                    │
             candidate tokens
                    │
                    ▼
             ┌──────────────┐
             │ Target Model │
             └──────┬───────┘
                    │
                 verify
                    │
                    ▼
                 output
```

If many draft tokens are accepted:

```text
effective decoding steps ↓
      ↓
generation speed ↑
```

But there is overhead.

So speculative decoding works best when:

```text
draft model is cheap
+
draft predictions are good
+
target model is expensive
```

---

# 30. Speculative decoding is not magic

Imagine:

```text
draft proposes 8 tokens
```

But target accepts:

```text
1
```

Then the draft model did a lot of unnecessary work.

So you care about:

```text
acceptance rate
draft cost
verification cost
target cost
```

You can think of it as:

```text
benefit ≈ fewer expensive target decoding steps

cost ≈ draft generation + verification overhead
```

The actual gain depends heavily on workload/model pair.

# 31. Quantization

Now consider:

```text
70B BF16
```

Approximate weight storage:

```text
70B × 2 bytes
≈ 140GB
```

FP8:

```text
70B × 1 byte
≈ 70GB
```

INT4:

```text
70B × ~0.5 byte
≈ 35GB
```

This can radically change:

```text
GPU count
KV capacity
memory pressure
cost
```

But quantization isn't simply:

```text
lower precision = faster
```

You must evaluate:

```text
accuracy
quality
kernel support
memory
compute
latency
throughput
```

# 32. Weight memory versus KV memory

Very important.

Suppose:

```text
70B FP8
≈ 70GB weights
```

On:

```text
H100 80GB
```

You might think:

```text
80 - 70 = 10GB KV
```

and call it done.

But real runtime needs additional memory.

And if the model consumes:

```text
~70GB weights
+ runtime/workspace
+ CUDA graph memory
+ other allocations
```

your KV budget may become very small.

So quantization can help not only by fitting the model.

It can also:

```text
reduce weight memory
      ↓
free GPU memory
      ↓
increase KV capacity
      ↓
increase concurrency
```

That is a major serving benefit.

# 33. The optimization hierarchy

When tuning vLLM, I recommend thinking in this order:

```text
                    ┌──────────────────────┐
                    │ Workload correctness │
                    └──────────┬───────────┘
                               ↓
                    ┌──────────────────────┐
                    │ Baseline benchmark   │
                    └──────────┬───────────┘
                               ↓
                    ┌──────────────────────┐
                    │ Identify bottleneck  │
                    └──────────┬───────────┘
                               ↓
              ┌────────────────┼────────────────┐
              ↓                ↓                ↓
          Memory            Compute          Scheduler
              │                │                │
              ↓                ↓                ↓
          KV cache          kernels         batching
          quantization      CUDA graph      chunk prefill
          TP               precision       max tokens
              │                │                │
              └────────────────┼────────────────┘
                               ↓
                    ┌──────────────────────┐
                    │ Benchmark again      │
                    └──────────┬───────────┘
                               ↓
                    ┌──────────────────────┐
                    │ SLO + cost decision  │
                    └──────────────────────┘
```

# 34. The one-variable-at-a-time rule

Suppose baseline:

```text
max_num_seqs = 32
max_num_batched_tokens = 8192
TP = 4
prefix caching = ON
CUDA graphs = ON
```

Then don't change:

```text
TP → 8
AND
max_num_seqs → 64
AND
quantization
AND
chunked prefill
```

at once.

You'll have no idea what helped.

Instead:

### Experiment 1

```text
baseline
```

### Experiment 2

```text
max_num_batched_tokens:
8192 → 16384
```

Measure.

### Experiment 3

Return to baseline and test:

```text
8192 → 4096
```

### Experiment 4

Test:

```text
TP4 → TP8
```

# 39. The production operating point

Suppose your benchmark produces:

| Concurrency | Output tok/s | P95 TTFT |
| ----------: | -----------: | -------: |
|           4 |          300 |    150ms |
|           8 |          550 |    190ms |
|          16 |          900 |    280ms |
|          32 |        1,250 |    450ms |
|          64 |        1,300 |     1.2s |
|         128 |        1,280 |     4.8s |

Customer SLO:

```text
P95 TTFT < 1 second
```

Then:

```text
64 ❌
128 ❌
```

Even though:

```text
64 = highest throughput
```

Your operating region may be:

```text
32
```

Then perhaps deploy enough replicas so normal traffic stays around:

```text
20–30 concurrency / replica
```

rather than:

```text
60–70
```

That gives you:

```text
headroom
+
burst capacity
+
failure tolerance
```

# 40. Capacity planning starts here

Suppose peak workload is:

```text
10,000 output tok/s
```

One GPU safely produces:

```text
1,250 output tok/s
```

at your SLO boundary.

Naive calculation:

```text
10,000 / 1,250
= 8 GPUs
```

But production isn't:

```text
8 GPUs
```

You need:

```text
HA
headroom
failure tolerance
deployment capacity
traffic imbalance
autoscaling delay
```

Maybe:

```text
10 GPUs
```

or:

```text
12 GPUs
```

depending on the architecture.

This is why:

> **Benchmark throughput ≠ production capacity.**

---

# 41. Your next-level metric: useful capacity

Don't ask:

> How many tokens can this GPU generate?

Ask:

> **How many tokens can this GPU generate while meeting my SLO?**

That is:

```text
SLO-constrained sustainable throughput
```

For example:

```text
Maximum raw throughput:
1,500 tok/s

But at 1,500:
P95 TTFT = 2.5 sec ❌

At 1,200:
P95 TTFT = 700ms ✅
```

Your real capacity is:

```text
1,200 tok/s
```

not:

```text
1,500
```

This concept will become extremely important when we reach **autoscaling and capacity planning**.

A strong AIRE answer:

> I would first determine whether the latency is in admission/queueing, prefill, or decode.
