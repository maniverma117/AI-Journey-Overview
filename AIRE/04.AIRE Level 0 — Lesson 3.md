# GPU Memory & KV Cache: How to Size LLM Infrastructure

This is a **very important lesson**.

After this lesson, you should be able to look at:

```text
70B model
BF16
128K context
H100 80GB
500 concurrent users
```

and immediately start thinking:

> "I need to calculate weight memory, KV-cache requirements, concurrency, batching, and GPU topology before I can recommend anything."

That's the mindset we're building.

---

# 1. The biggest misconception about GPU memory

A beginner often thinks:

```text
70B model
×
2 bytes
=
140GB

Therefore:
2 × H100 80GB
```

That is only the **first calculation**.

Real inference looks more like:

```text
GPU Memory
│
├── Model weights
│
├── KV Cache
│
├── Activations
│
├── CUDA graphs
│
├── Workspace
│
├── NCCL buffers
│
└── Runtime overhead
```

Therefore:

```text
GPU requirement
≠
model weight size
```

This distinction is extremely important.

---

# 2. Start with model weights

The easiest part is:

```text
Model parameters × bytes/parameter
```

Typical approximations:

| Precision | Bytes/parameter |
| --------- | --------------: |
| FP32      |               4 |
| FP16      |               2 |
| BF16      |               2 |
| FP8       |               1 |
| INT8      |              ~1 |
| INT4      |            ~0.5 |

These are useful **back-of-the-envelope** calculations; actual formats and metadata can add overhead.

---

# 3. Example: 7B model

BF16:

```text
7B × 2 bytes
```

≈

```text
14 GB
```

So:

```text
7B BF16
≈ 14 GB weights
```

An 80 GB GPU has plenty of room for weights.

But that does **not** mean:

```text
80GB / 14GB
≈ 5 users
```

That calculation would be meaningless.

Why?

Because of KV cache and concurrency.

# 4. Example: 70B


Can't fit the model weights alone.

You now need:


# 5. Example: FP8

Approximately:

```text
70B × 1 byte
≈ 70GB
```

Now:

```text
70GB weights
```

could potentially fit on an 80GB GPU.

But remember:

```text
70GB
+
KV cache
+
runtime
+
workspace
```

So it may still be impossible or leave very little usable cache.

This is why saying:

> "The 70B model is 70GB in FP8, so it fits on an H100 80GB."

is **not sufficient architecture reasoning**.

# 6. Your first architect rule

Memorize:

> **Model weights determine the baseline VRAM requirement. KV cache determines a large part of the remaining serving capacity.**

---

# 7. What exactly is KV cache storing?

During attention we have:

```text
Q
K
V
```

For previous tokens, the model doesn't want to recompute K and V every time.

So it stores:

```text
K
V
```

in the KV cache.

Conceptually:

```text
Tokens

1   2   3   4   5
│   │   │   │   │
▼   ▼   ▼   ▼   ▼

K1 K2 K3 K4 K5
V1 V2 V3 V4 V5

        │
        ▼

     KV CACHE
```

During decode:

```text
New token
    │
    ▼
New Q
    │
    +
existing K/V
    │
    ▼
Attention
```

This is why KV cache dramatically improves decoding efficiency.

---

# 8. What determines KV-cache size?

This is where things become interesting.

KV cache depends on several model/workload characteristics:

```text
KV Cache
│
├── number of layers
├── number of KV heads
├── head dimension
├── sequence length
├── batch/concurrency
└── KV-cache datatype
```

So parameter count alone is insufficient.

---

# 9. The basic KV-cache formula

For a simplified decoder-only Transformer:

```text
KV cache per token
≈

2
×
number of layers
×
number of KV heads
×
head dimension
×
bytes per KV element
```

Why `2`?

Because we store:

```text
K + V
```

Then:

```text
KV cache
≈

tokens
×
layers
×
KV heads
×
head dimension
×
2
×
bytes
```

This is an extremely useful approximation.

---

# 10. Let's calculate one

Suppose a model has:

```text
Layers = 80

KV heads = 8

Head dimension = 128

BF16 = 2 bytes
```

For one token:

```text
2 × 80 × 8 × 128 × 2
```

Let's calculate:

```text
2 × 80 = 160

160 × 8 = 1280

1280 × 128 = 163,840

163,840 × 2
=
327,680 bytes
```

Approximately:

```text
320 KB per token
```

for KV cache.

---

# 11. Now 1,000 tokens

```text
327,680 × 1,000
```

≈

```text
327 MB
```

One sequence:

```text
1K tokens
≈ 327 MB KV
```

Again, illustrative model dimensions.

---

# 12. Now 10K tokens

```text
327 KB × 10,000
```

≈

```text
3.27 GB
```

So one sequence could consume:

```text
~3.27GB KV cache
```

---

# 13. Now 100K tokens

```text
327 KB × 100,000
```

≈

```text
32.7 GB
```

One request.

Now you can see why long-context inference becomes difficult.

Imagine:

```text
100K context
×
10 concurrent requests
```

Approximately:

```text
327 GB KV cache
```

That's enormous.

---

# 14. Important caveat

Don't take that formula and assume every modern model behaves exactly like this.

Why?

Because architectures differ.

Especially:

```text
MHA
GQA
MQA
```

can have very different KV-head counts.

Also:

```text
FP16/BF16
FP8 KV cache
```

changes memory requirements.

And inference engines may have additional allocation behavior.

The formula is a **capacity-estimation tool**, not an exact vLLM allocator model.

---

# 15. Now you understand why GQA matters

Suppose:

```text
Query heads = 64
```

Traditional MHA might have:

```text
KV heads = 64
```

GQA might have:

```text
KV heads = 8
```

That's an:

```text
8× reduction
```

in the KV-head component of the cache.

So:

```text
MHA

64 KV heads
```

versus:

```text
GQA

8 KV heads
```

can dramatically change serving capacity.

This is why **model architecture matters to your infrastructure design**.

---

# 16. Interview question

> Why can two models with the same parameter count have very different inference memory requirements?

Answer:

> Parameter count primarily determines model weight memory. Inference memory also depends on architecture and workload characteristics such as layer count, KV-head count, head dimension, context length, concurrency, precision and KV-cache datatype. Models using GQA or MQA can require substantially less KV memory than comparable MHA architectures.

That's a strong senior answer.

---

# 17. Context length is not concurrency

This is another common mistake.

Suppose:

```text
Model supports 128K context.
```

It does **not** mean:

```text
128K × every request
```

It means the model/runtime can support sequences up to that maximum under the relevant configuration.

Actual request:

```text
Request A → 2K
Request B → 5K
Request C → 80K
Request D → 12K
```

KV usage depends on actual active sequences.

---

# 18. Why concurrency matters

Suppose:

```text
One request
=
2GB KV
```

Then:

```text
10 concurrent requests
≈ 20GB KV
```

and:

```text
30 concurrent requests
≈ 60GB KV
```

So:

```text
concurrency ↑
       ↓
active KV cache ↑
       ↓
GPU memory pressure ↑
```

Eventually:

```text
OOM
```

or the inference engine cannot admit more sequences.


# 28. Why NVLink matters

Imagine:

```text
GPU 0
 │
 │ huge amount of tensor data
 │
 ▼
GPU 1
```

If communication is slow:

```text
GPU 0 waits
GPU 1 waits
```

Your expensive GPUs aren't being efficiently used.

With high-bandwidth GPU interconnects:

```text
GPU 0 ⇄ GPU 1
```

communication can be much faster.

NVIDIA's NVLink/NVSwitch architecture is designed specifically for high-bandwidth GPU-to-GPU communication in multi-GPU systems. [NVIDIA NVLink](https://www.nvidia.com/en-us/data-center/nvlink/?utm_source=chatgpt.com)

# 29. This creates another architecture decision

Suppose the model requires:

```text
4 GPUs
```

You have two possibilities conceptually:

```text
Option A

4 GPUs
in one tightly coupled instance
```

versus:

```text
Option B

4 separate EC2 instances
```

For tightly coupled tensor-parallel inference, Option A may be dramatically easier/better because GPU-to-GPU communication is much faster than ordinary network communication.

This is why:

> **"We need 4 GPUs"**

is incomplete.

You also need to ask:

> **"Do those GPUs need to communicate heavily?"**

# 30. Data parallelism vs tensor parallelism

This distinction will become critical.

### Data parallelism

Each GPU has the model:

```text id="p4jv6b"
          Router
       /     |     \
      ↓      ↓      ↓
    GPU1   GPU2   GPU3
   Model   Model   Model
```

Requests are distributed across replicas.

Great for scaling independent requests.

---

### Tensor parallelism

One model is distributed:

```text id="yq2f0f"
          Model
            │
      ┌─────┼─────┐
      ↓     ↓     ↓
    GPU1  GPU2  GPU3
```

The GPUs cooperate on each inference.

This requires fast inter-GPU communication.

---

# 31. Interview question

> You have 8 GPUs. Should you use tensor parallelism?

Answer:

> Not automatically. If the model fits on one GPU, data parallelism may be preferable for serving independent requests because each GPU can host a complete replica. Tensor parallelism is useful when the model doesn't fit on one GPU or when its performance characteristics justify splitting computation. The choice also depends on interconnect bandwidth, latency requirements and workload concurrency.

That's the answer I want you to develop.

# 34. Why continuous batching matters again

Suppose:

```text
GPU has active requests:
A
B
C
```

A finishes.

Instead of leaving the slot idle:

```text
A → finished
B → running
C → running
D → waiting
```

the scheduler can bring D into execution.

Conceptually:

```text
A █████████
B █████████████
C ███████
D       ████████
E          ███████
```

This keeps the GPU busy.

This is the operational significance of continuous batching.
