# Lab 1O — Production AI Inference Observability

We are now going to build the **observability system for the entire inference platform**, not just put a Grafana dashboard on vLLM.

The target is:

```text
                    USER
                     │
                     ▼
                AI Gateway
                     │
                     ▼
                  llm-d
                     │
              ┌──────┴──────┐
              ▼             ▼
           Prefill        Decode
              │             │
              └─────┬───────┘
                    │
                   vLLM
                    │
                   GPU
                    │
             NIXL / EFA
```

And observability needs to follow the same path:

```text
User request
    │
    ▼
Gateway metrics
    │
    ▼
EPP metrics
    │
    ▼
vLLM metrics
    │
    ▼
GPU/DCGM metrics
    │
    ▼
NIXL/EFA/NCCL metrics
    │
    ▼
Kubernetes / EC2
```

Current llm-d v0.9 documentation provides Prometheus/Grafana integration, EPP metrics, vLLM metrics, dashboards and optional OpenTelemetry tracing. ([Llm-D][1])

---

# 1. Why normal Kubernetes monitoring is insufficient

In normal applications you might monitor:

```text
CPU
Memory
HTTP latency
HTTP errors
Request rate
```

For an LLM, that isn't enough.

Imagine:

```text
CPU = 35%
GPU = 65%
Memory = 60%
HTTP 200 = 99.9%
```

Everything looks healthy.

But users report:

```text
"First token takes 5 seconds."
```

Why?

Possibilities:

```text
Gateway
   ↓
EPP routing delay
   ↓
queue
   ↓
prefill
   ↓
KV transfer
   ↓
decode startup
```

Or:

```text
GPU isn't saturated
BUT
KV cache is 95%
```

Or:

```text
GPU utilization = 60%
BUT
NCCL communication is slow
```

Or:

```text
vLLM healthy
BUT
EFA/NIXL is failing
```

Therefore:

> **AI observability must understand the inference lifecycle.**

```text
┌─────────────────────────────────────┐
│ 1. User / API                       │

├─────────────────────────────────────┤
│ 2. AI Gateway                       │

├─────────────────────────────────────┤
│ 4. vLLM                             │
│ TTFT, TPOT, queue, KV, tokens      │
├─────────────────────────────────────┤
│ 5. GPU / CUDA                       │

├─────────────────────────────────────┤
│ 6. Network / NIXL / NCCL / EFA      │

├─────────────────────────────────────┤
│ 7. Kubernetes / EC2                 │
│ nodes, pods, scheduling, failures   │
└─────────────────────────────────────┘
```

This becomes your **incident drill-down hierarchy**.

# 3. The most important LLM metrics

There are four metrics you should immediately think about whenever somebody says:

> "The LLM is slow."

### TTFT

**Time To First Token**

```text
request
   │
   ├── queue
   ├── prefill
   ├── scheduling
   └── other overhead
   │
   ▼
first token
```

---

### TPOT / ITL

**Time Per Output Token / Inter-Token Latency**

```text
token1 ──50ms── token2 ──50ms── token3
```

Users experience this as:

> "How fast does the response stream?"

---

### E2E latency

```text
request
   │
   ▼
first token
   │
   ▼
last token
```

---

### Token throughput

```text
input tokens/sec
output tokens/sec
```

These are critical for capacity planning.

# 4. vLLM already exposes the metrics we need

Current vLLM exposes Prometheus metrics from:

```text
/metrics
```

including TTFT, inter-token latency, E2E latency, queue time, prefill time, decode time, running/waiting requests, KV usage, token counts and preemption information. ([vLLM][2])

For example:

```bash
curl http://localhost:8000/metrics
```

You will see metrics such as:

```text
vllm:time_to_first_token_seconds
vllm:inter_token_latency_seconds
vllm:e2e_request_latency_seconds

vllm:request_queue_time_seconds
vllm:request_prefill_time_seconds
vllm:request_decode_time_seconds

vllm:num_requests_running
vllm:num_requests_waiting

vllm:kv_cache_usage_perc

vllm:prompt_tokens
vllm:generation_tokens

vllm:num_preemptions
```

The exact metric inventory evolves with vLLM versions, so always inspect the `/metrics` endpoint of the deployed version rather than assuming an older metric name. ([vLLM][2])

# 5. Understand the metric types

Prometheus has several important types.

## Counter

Example:

```text
vllm:prompt_tokens
```

It increases:

```text
100
200
300
400
```

It doesn't normally decrease except when the process restarts.

Calculate rates using:

```promql
rate(vllm:prompt_tokens[5m])
```

---

# 6. Gauge

Example:

```text
vllm:num_requests_running
```

Can go:

```text
5
10
7
15
2
```

Use it for current state.

---

# 7. Histogram

Very important for latency.

Example:

```text
vllm:time_to_first_token_seconds
```

You don't want:

```text
average TTFT = 500ms
```

only.

You care about:

```text
P50
P90
P95
P99
```

because users experience the tail.

---

# 8. Why average latency is dangerous

Suppose 100 requests:

```text
99 requests = 100ms
1 request = 20 seconds
```

Average:

```text
299ms
```

Sounds okay.

But:

```text
P99 ≈ 20 seconds
```

For an interactive production system, that's terrible.

Therefore your AI SLO should usually be based on a percentile.

Example:

```text
P95 TTFT < 1 second
P95 TPOT < 50ms
```

---

# 9. PromQL for TTFT

Suppose you want P95 TTFT.

Conceptually:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(vllm:time_to_first_token_seconds_bucket[5m])
  )
)
```

This means:

```text
histogram
   ↓
rate over 5 minutes
   ↓
combine buckets
   ↓
calculate 95th percentile
```

---

# 10. P99 TTFT

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(vllm:time_to_first_token_seconds_bucket[5m])
  )
)
```

This is the metric I'd put prominently on the production dashboard.

# 11. TPOT / ITL

Current vLLM exposes:

```text
vllm:inter_token_latency_seconds
```

and:

```text
vllm:request_time_per_output_token_seconds
```

The former measures inter-token latency, while the latter is request-level time-per-output-token information. ([vLLM][2])

Conceptually:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(vllm:inter_token_latency_seconds_bucket[5m])
  )
)
```

# 12. Queue time is extremely important

Consider:

```text
TTFT = 4 sec
```

Don't immediately blame GPU compute.

Break it down:

```text
TTFT
 │
 ├── queue time
 ├── prefill time
 ├── KV/cache effects
 ├── scheduling
 └── other inference overhead
```

vLLM exposes:

```text
vllm:request_queue_time_seconds
```

and:

```text
vllm:request_prefill_time_seconds
```

which let you investigate this decomposition. ([vLLM][2])

# 14. Running vs waiting requests

Two metrics:

```text
vllm:num_requests_running
vllm:num_requests_waiting
```

Imagine:

```text
running = 8
waiting = 0
```

Healthy.

Then:

```text
running = 8
waiting = 50
```

Now we have a problem.

The GPU may be perfectly healthy.

But the **serving capacity is saturated**.

Current llm-d documentation specifically highlights `num_requests_waiting` as a primary saturation/autoscaling signal. ([Llm-D][1])

# 15. KV cache utilization

Current vLLM exposes:

```text
vllm:kv_cache_usage_perc
```

It represents the fraction of KV cache in use. ([vLLM][2])

Think:

```text
20% → lots of capacity
50% → healthy
75% → monitor
90% → danger
95% → severe pressure
```

These aren't universal alert thresholds—you derive them from your workload and SLO.

But conceptually:

```text
KV ↑
  ↓
available concurrency ↓
  ↓
queue ↑
  ↓
TTFT ↑
```

---

# 16. Preemption

Current vLLM exposes:

```text
vllm:num_preemptions
```

and per-request preemption metrics. ([vLLM][2])

A rising preemption rate can indicate:

```text
KV pressure
+
insufficient memory
+
aggressive batching
```

So:

```text
KV high
+
preemptions increasing
+
waiting increasing
```

is a much stronger signal than:

```text
GPU utilization = 90%
```

---

# 17. Prefix cache

Current vLLM exposes:

```text
vllm:prefix_cache_hits
vllm:prefix_cache_queries
```

and token-related cache metrics. ([vLLM][2])

You can derive:

```text
prefix hit rate
=
hits / queries
```

Conceptually:

```promql
rate(vllm:prefix_cache_hits[5m])
/
rate(vllm:prefix_cache_queries[5m])
```

But always verify the exact semantics of the deployed version before turning this into an SLO.

---

# 18. Why prefix-cache observability matters

Suppose yesterday:

```text
prefix hit rate = 80%
```

Today:

```text
prefix hit rate = 10%
```

and:

```text
TTFT ↑
input compute ↑
GPU load ↑
```

Nothing is "wrong" with the GPU.

The workload/cache locality changed.

This is exactly why an AIRE needs inference-specific metrics.

---

# 19. Token throughput

Current vLLM exposes counters such as:

```text
vllm:prompt_tokens
vllm:generation_tokens
```

These let you derive:

```text
input tokens/sec
output tokens/sec
```

For example:

```promql
rate(vllm:prompt_tokens[5m])
```

and:

```promql
rate(vllm:generation_tokens[5m])
```

Now you can say:

> "This replica currently processes 45K input tokens/sec and 12K output tokens/sec."

That's much more useful for capacity planning than:

> "GPU is 82% utilized."

# 21. Critical correlation

Never look at GPU metrics alone.

Imagine:

```text
GPU utilization = 98%
```

Could mean:

### Case A

```text
Excellent batching
high throughput
SLO healthy
```

### Case B

```text
Long prefill
decode starving
TTFT bad
```

### Case C

```text
NCCL communication
```

### Case D

```text
CPU/kernel overhead
```

Therefore:

```text
GPU metric
    +
vLLM metric
    +
SLO
```

is the correct unit of analysis.

# 26. Distributed tracing

Metrics tell you:

> **What is happening?**

Logs tell you:

> **What did the components say?**

Traces tell you:

> **Where did this particular request spend its time?**

Example:

```text
Request ID: abc123

Gateway
  20ms
    │
    ▼
EPP
  12ms
    │
    ▼
Prefill
  420ms
    │
    ▼
NIXL
  80ms
    │
    ▼
Decode
  1.2s
```

Now the diagnosis is almost immediate.

llm-d's current observability setup supports OpenTelemetry tracing and documents tracing across the inference stack. ([Llm-D][3])

---

# 27. Logs are not metrics

Bad:

```text
INFO request tenant=abc latency=523ms
INFO request tenant=abc latency=612ms
INFO request tenant=abc latency=421ms
```

Millions of logs.

Instead:

```text
metric:
  request latency histogram

log:
  only useful request-specific context
```

Use logs for:

```text
errors
state transitions
routing decisions
failures
model load
NIXL failures
GPU errors
rollouts
```

Use metrics for:

```text
rates
latencies
counts
saturation
capacity
```

Use traces for:

```text
individual request path
```

---

# 28. Cardinality — very important

Don't create Prometheus labels like:

```text
user_id
request_id
prompt
conversation_id
```

for every request.

Example:

```text
vllm_latency{
  request_id="abc123"
}
```

Then:

```text
1 million requests
=
1 million time series
```

Prometheus becomes unhappy.

Better:

```text
model
tenant_tier
region
pool
endpoint
```

and keep:

```text
request_id
conversation_id
```

in logs/traces.

---

# 29. PII problem

Never put:

```text
prompt
user message
API key
JWT
tool arguments
customer data
```

into normal telemetry.

Especially not:

```text
Prometheus labels
```

You can accidentally turn your observability system into a data-exfiltration system.

Instead:

```text
request_id
trace_id
tenant_hash/id
model
status
token counts
latency
```

with carefully controlled access.

# 31. Production alerting

Don't alert:

```text
GPU > 80%
```

by itself.

Instead:

### Alert 1 — TTFT SLO

```text
P95 TTFT > SLO
for 5 minutes
```

### Alert 2 — Queue saturation

```text
waiting requests > threshold
AND
increasing
```

### Alert 3 — KV pressure

```text
KV > threshold
AND
preemptions increasing
```

### Alert 4 — Error rate

```text
5xx/error rate > threshold
```

### Alert 5 — EPP failure

```text
routing errors increasing
```

### Alert 6 — GPU failure

```text
XID/ECC/hardware error
```

### Alert 7 — P/D transfer

```text
KV transfer latency > SLO
OR
transfer failures increasing
```

Current llm-d also provides Prometheus alerting rules for EPP via `PrometheusRule`. ([Llm-D][4])

# 32. The most important alerting principle

Don't alert on symptoms only.

Example:

```text
TTFT high
```

is a symptom.

Correlate:

```text
TTFT ↑
queue ↑
KV ↑
```

This indicates:

```text
capacity pressure
```

But:

```text
TTFT ↑
queue normal
KV normal
EPP latency ↑
```

suggests:

```text
routing layer
```

And:

```text
TTFT ↑
queue normal
prefill ↑
GPU compute ↑
```

suggests:

```text
prefill workload / compute saturation
```

And:

```text
TTFT ↑
KV transfer ↑
```

suggests:

```text
P/D network path
```

# 33. The AIRE diagnostic matrix

| Symptoms                  | Likely area                       |
| ------------------------- | --------------------------------- |
| TTFT ↑ + queue ↑          | Capacity/scheduling               |
| TTFT ↑ + EPP ↑            | Routing                           |
| TTFT ↑ + prefill ↑        | Prefill compute                   |
| TPOT ↑ + decode queue ↑   | Decode saturation                 |
| KV ↑ + preemption ↑       | KV pressure                       |
| GPU HBM ↑ + KV ↑          | Memory capacity                   |
| GPU 100% + TTFT healthy   | Potentially healthy               |
| GPU 60% + TTFT bad        | Investigate queue/network/routing |
| NIXL latency ↑            | P/D transfer                      |
| NCCL latency ↑            | Multi-GPU communication           |
| EPP errors ↑              | Routing/backend health            |
| HTTP 5xx ↑ + vLLM healthy | Gateway/network/control plane     |
| Prefix hits ↓ + prefill ↑ | Cache locality change             |
| Waiting requests ↑        | Serving saturation                |

This table is worth memorizing.

# 34. Complete incident example

Customer reports:

> "Responses became slow at 10:30."

You open Grafana.

```text
P95 TTFT
10:25 → 700ms
10:30 → 3.2s
```

First question:

```text
What changed?
```

Then:

```text
waiting requests
10:25 → 2
10:30 → 40
```

Then:

```text
KV
10:25 → 60%
10:30 → 94%
```

Then:

```text
preemptions
10:25 → 0
10:30 → increasing
```

GPU:

```text
HBM → 95%
SM → 70%
```

Diagnosis:

> **KV capacity pressure caused scheduling/preemption pressure, which increased queueing and therefore TTFT.**

Not:

> "GPU CPU is high."
