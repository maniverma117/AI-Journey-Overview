We’re now moving from **“How do I run LLM infrastructure?”** to **“How do I economically operate LLM infrastructure?”**

# Lesson 22 — AI Inference FinOps & Cost Engineering

This is a **very important AIRE / AI Solution Architect skill**.

A customer will rarely ask:

> “Can you deploy vLLM?”

They will ask:

> “Can you serve 10 million requests/month with this model, meet P95 latency, maintain HA, and keep the bill below ₹X?”

That is where FinOps becomes part of inference engineering.

---

# 1. The fundamental shift

For normal applications, we often think:

```text
EC2 cost
+
EBS
+
Load Balancer
+
Database
=
Application cost
```

For LLM inference, that's incomplete.

We need to think:

```text
                    LLM COST
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
   GPU compute      Memory/KV       Networking
       │               │                │
       ▼               ▼                ▼
   H100/H200       HBM capacity      EFA/NIC
   P5/P5e          KV cache           transfer
       │
       ▼
   vLLM efficiency
       │
 ┌─────┼─────────────┐
 ▼     ▼             ▼
batching  parallelism  quantization
 ▼        ▼             ▼
throughput  GPU count   memory
       │
       ▼
  $ / useful token
       │
       ▼
  $ / successful request
```

The goal isn't:

> **Minimize GPU count.**

The goal is:

> **Minimize cost while satisfying the customer's SLO.**

That distinction is critical.

---

# 2. The most important FinOps equation

Suppose:

```text
GPU hourly cost = $5/hour
GPU sustainable output throughput = 1,000 tokens/sec
```

Then:

```text
tokens/hour
=
1,000 × 3,600

= 3,600,000 tokens/hour
```

Therefore:

```text
cost / 1M output tokens
=
$5 / 3.6
=
$1.39
```

So:

```text
$ / 1M tokens
```

is much more useful than:

```text
$ / GPU-hour
```

because customers consume **tokens**, not GPUs.

---

# 3. But there's a trap

You cannot simply say:

> H100 = $5/hour
> Therefore H100 is expensive.

You need:

```text
GPU price
       ↓
effective throughput
       ↓
SLO-constrained throughput
       ↓
useful tokens
       ↓
cost/token
```

Imagine:

### GPU A

```text
$5/hour
1,000 tok/s
```

### GPU B

```text
$7/hour
1,800 tok/s
```

GPU B is more expensive per hour.

But:

```text
GPU A:
$5 / 3.6M
= $1.39 / 1M tokens

GPU B:
$7 / 6.48M
= $1.08 / 1M tokens
```

So the **more expensive GPU is actually cheaper per token**.

This is one of the most important concepts in AI FinOps.

---

# 4. Never use theoretical GPU throughput

This is another major AIRE principle.

NVIDIA may advertise enormous Tensor Core throughput.

But your application might achieve:

```text
GPU theoretical:
X TFLOPS

Actual inference:
much lower
```

because of:

* memory bandwidth
* KV cache
* batching
* context length
* output length
* scheduler
* CPU tokenization
* communication
* TP overhead
* CUDA kernels
* model architecture
* prefix caching
* request distribution

Therefore:

```text
THEORETICAL GPU PERFORMANCE
              ≠
PRODUCTION INFERENCE CAPACITY
```

You benchmark the actual workload.

Current vLLM provides `vllm bench` commands for latency, serving, throughput, startup and parameter sweeps. ([vLLM][1])

# 7. Biggest cost lever: model selection

Suppose a customer says:

> “We need GPT-style reasoning.”

Don't immediately deploy:

```text
70B model
```

Ask:

> Does every request actually require 70B?

Maybe:

```text
              Incoming requests
                     │
                     ▼
                Classifier
               /    |     \
              /     |      \
             ▼      ▼       ▼
          Small    Medium   Large
          model    model    model
            │        │        │
            └────────┼────────┘
                     ▼
                  Response
```

Example:

```text
70% simple requests → 8B
25% medium          → 32B
5% difficult        → 70B
```

This can massively reduce GPU consumption.

This is called:

> **Model routing / model cascade**

---

# 8. Example model-routing economics

Suppose:

```text
10 million requests/month
```

Without routing:

```text
10M → 70B model
```

With routing:

```text
7M → 8B
2.5M → 32B
0.5M → 70B
```

Even if the 70B model is excellent, using it for:

> “What is the order status?”

is economically irrational.

This is where an AI architect thinks beyond Kubernetes.

# 10. Cost lever #3 — Tensor Parallelism

Suppose:

```text
TP = 8
```

and you have:

```text
8 × H100
```

One replica consumes:

```text
8 GPUs
```

Now imagine your benchmark shows:

```text
TP8:
10,000 tok/s
```

but:

```text
TP4:
8,500 tok/s
```

At first glance TP8 looks better.

But compare economics.

### TP8

```text
8 GPUs
10,000 tok/s
```

### TP4

```text
4 GPUs
8,500 tok/s
```

Cost efficiency:

```text
TP8:
10,000 / 8
= 1,250 tok/s/GPU

TP4:
8,500 / 4
= 2,125 tok/s/GPU
```

TP4 may be dramatically more efficient.

And you may also get better failure granularity.

This is why:

> **Highest throughput ≠ lowest cost.**

# 12. Cost lever #4 — Batching

This is huge.

Imagine:

```text
Request 1 → GPU
Request 2 → GPU
Request 3 → GPU
Request 4 → GPU
```

versus:

```text
Request 1 ─┐
Request 2 ─┤
Request 3 ─┼──→ GPU batch
Request 4 ─┘
```

GPU resources can be shared across requests.

That's why:

```text
low concurrency
```

can result in terrible economics.

You might have:

```text
H100
↓
10% useful utilization
↓
$5/hour
```

while paying the full GPU price.

---

# 13. But batching has a tradeoff

More batching:

```text
GPU efficiency ↑
throughput ↑
cost/token ↓
```

but potentially:

```text
queueing ↑
TTFT ↑
latency ↑
```

So:

```text
                Cost
                 ▲
                 │
                 │       efficient
                 │      /
                 │     /
                 │    /
                 │   /
                 └──────────────►
                       latency
```

We want the **Pareto-efficient region**:

```text
maximum useful throughput
while meeting latency SLO
```

Current vLLM benchmarking supports sweep/Pareto analysis specifically for balancing user-level and per-GPU throughput. ([vLLM][2])

# 14. The economics of KV cache

Remember our previous lesson:

```text
KV cache = dynamic GPU memory
```

Suppose:

```text
GPU HBM = 80 GB
```

Weights:

```text
60 GB
```

Runtime:

```text
5 GB
```

Available for KV:

```text
15 GB
```

Now a long-context workload arrives.

KV usage:

```text
15 GB
```

Boom.

You can't accept additional concurrency.

You may have:

```text
GPU utilization = 60%
```

and think:

> “We have plenty of GPU capacity.”

Wrong.

You have:

```text
KV capacity exhausted
```

Therefore:

```text
GPU compute utilization
≠
inference capacity
```

This is why KV-aware scaling and routing matter.

# 15. Prefix caching = FinOps

Suppose 1,000 requests contain:

```text
System prompt:
20,000 tokens

Company documentation:
30,000 tokens

User question:
200 tokens
```

Without prefix caching:

```text
50,200 tokens
× 1,000 requests
```

With effective prefix reuse:

```text
50,000-token prefix
computed once/reused

+
200-token changing portion
```

The exact savings depend on cache behavior and workload, but the principle is enormous:

> **Repeated computation is wasted GPU money.**

This is why llm-d's cache-aware routing isn't just a performance feature.

It can be a:

> **FinOps feature.**

# 16. Cost lever #5 — P/D disaggregation

We previously learned:

```text
Prefill
   ↓
KV
   ↓
Decode
```

Prefill:

```text
compute-heavy
```

Decode:

```text
memory-bandwidth-sensitive
```

If one GPU pool has to handle everything:

```text
P + D
```

you may have resource mismatch.

Instead:

```text
              Router
                │
        ┌───────┴────────┐
        ▼                ▼
    Prefill pool     Decode pool
        │                │
      GPUs             GPUs
```

Now you can scale independently.

For example:

```text
Prefill demand ↑
        ↓
Add prefill GPUs
```

while:

```text
Decode demand stable
        ↓
Don't add decode GPUs
```

That can improve economics.

But P/D introduces:

* KV transfer
* networking
* orchestration
* failure modes
* operational complexity

So:

> Don't use P/D just because it is modern.

Use it when the workload benefits.

### Good Spot workloads


unless you design explicitly for interruption.

# 27. H100 vs H200 — FinOps thinking

AWS currently positions P5 with H100 and P5e/P5en with H200 for large-scale AI/LLM workloads. ([Amazon Web Services, Inc.][5])

H200 gives substantially more HBM capacity than H100.

But the question isn't:

> “Which GPU is faster?”

Ask:

> “Which GPU gives the lowest cost while meeting my SLO?”

Suppose H100 requires:

```text
TP8
```

but H200 allows:

```text
TP4
```

The H200 instance may have a higher hourly price but fewer GPUs per replica and potentially less communication.

Therefore:

```text
H100 × 8
```

could be more expensive than:

```text
H200 × 4
```

depending on actual pricing and measured performance.

AWS also reduced P5/P5en pricing in 2025, including expanded availability in Mumbai, so **current regional pricing must be checked rather than using old blog numbers**. ([Amazon Web Services, Inc.][6])

# 37. One important current vLLM practice

When you benchmark cost efficiency, don't accidentally benchmark a cache-warmed artificial workload and conclude that your GPU is faster than production.

Current vLLM documentation explicitly warns that repeated benchmark requests can reuse prefix cache and inflate measured throughput. ([vLLM][4])

So your benchmark methodology should include:

```text
Cold-ish workload
+
realistic workload
+
prefix-reuse workload
+
peak workload
```

Then compare:

```text
TTFT
TPOT
throughput
KV
GPU
cost/token
```

This is exactly the kind of detail that separates **“I deployed vLLM”** from **“I can design an AI inference platform.”**
