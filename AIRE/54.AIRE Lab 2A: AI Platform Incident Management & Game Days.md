# Lab 2A — AI Platform Incident Management & Game Days

Now we move from **designing reliable AI infrastructure** to the skill that separates a platform engineer from a true **AI Reliability Engineer**:

> **When production breaks, can you identify the failure domain quickly, protect the SLO, restore service, and prove why it happened?**

For AI systems, traditional Kubernetes troubleshooting is not enough.

A pod can be healthy while:

* TTFT is terrible
* KV cache is exhausted
* vLLM is preempting requests
* llm-d is routing badly
* NCCL is slow
* EFA is degraded
* one tenant is consuming the GPU fleet
* a model rollout doubled memory usage
* an agent entered a retry loop

So this lab is about **AI-specific incident command**.

---

Traditional SRE:

```text

```

AI SRE:

```text

                            │

                   └────────┬────────┘

```

An incident can originate at **any layer**.

# 2. First Rule: Start With the User

Never begin an incident with:

```bash
kubectl get pods
```

Start with:

```text
What is the user experiencing?
```

Example:

```text
P99 TTFT = 8 seconds
P99 TPOT = 120 ms
HTTP errors = normal
```

This immediately tells you:

```text
Availability looks okay.
Latency is broken.
```

Then investigate latency.

---

For AI add:


# 4. Incident Classification

Use this first-pass matrix:

| Symptom              | First suspect                |
| -------------------- | ---------------------------- |
| HTTP 5xx             | Gateway/app/backend          |
| HTTP 429             | Quota/admission/capacity     |
| TTFT high            | Queue/prefill/KV/capacity    |
| TPOT high            | Decode/GPU/KV contention     |
| E2E high             | TTFT + generation            |
| GPU memory high      | KV/model/runtime             |
| GPU compute high     | Compute saturation           |
| KV near 100%         | Capacity/context/concurrency |
| Queue growing        | Insufficient capacity        |
| Preemptions          | KV/memory pressure           |
| NCCL slow            | Multi-GPU communication      |
| NCCL hang            | GPU/network/topology         |
| NIXL timeout         | P/D transfer/network         |
| EFA errors           | Network                      |
| Pods Pending         | Kubernetes/Karpenter         |
| Node unavailable     | EC2/Karpenter/AZ             |
| One tenant affected  | Tenant policy/routing        |
| All tenants affected | Shared infrastructure        |

This gets you to the right layer quickly.

# 12. Don't Solve KV Problems With Blind GPU Scaling

Suppose:

```text
KV = 99%
```

You add GPUs.

But traffic router sends requests unevenly:

```text
GPU-1 → 99%
GPU-2 → 30%
GPU-3 → 25%
GPU-4 → 20%
```

You haven't solved routing.

Or perhaps the real problem is:

```text
max_num_seqs too high
```

or:

```text
tenant sent huge contexts
```

The right incident response is:

```text
measure → identify bottleneck → mitigate
```

not:

```text
GPU panic button
```

# 25. Circuit Breaker

Three states:

```text
       failures
CLOSED ─────────► OPEN
  ▲                │
  │                │ timeout
  │                ▼
  └────────── HALF-OPEN
```

### CLOSED

Normal traffic.

### OPEN

Stop calling failing dependency.

### HALF-OPEN

Allow limited test traffic.

If successful:

```text
HALF-OPEN → CLOSED
```

If failure:

```text
HALF-OPEN → OPEN
```

This is extremely useful for:

```text
RAG
tools
external APIs
model fallback
```

# 32. Automated Remediation

Some actions can be automated.

Example:

```text
KV > 95%
AND
queue > threshold
AND
TTFT > SLO
```

Could trigger:

```text
scale inference replicas
```

But be careful.

Bad automation:

```text
TTFT ↑
   ↓
scale
   ↓
capacity unavailable
   ↓
more pending pods
   ↓
scale again
   ↓
runaway provisioning
```

Therefore automation requires:

```text
hysteresis
cooldown
limits
```

# 33. Safe Automation

Example:

```yaml id="9g8f5m"
autoscaling:
  min_replicas: 2
  max_replicas: 20

  scale_up:
    threshold: 0.8
    cooldown: 60s

  scale_down:
    threshold: 0.4
    cooldown: 600s
```

And infrastructure:

```text
maximum GPU fleet
maximum cost

```

Always put a ceiling on automation.

# 46. MTTR for AI

Traditional:

```text
MTTR = Mean Time To Recovery
```

For AI break it down:

```text
Detection
   +
Diagnosis
   +
Mitigation
   +
Capacity recovery
   +
Model warmup
   +
Traffic recovery
```

Example:

```text
MTTD = 30 sec
Diagnosis = 2 min
Mitigation = 1 min
GPU provisioning = 4 min
Model load = 3 min
```

Total:

```text
~10.5 min
```

If RTO is:

```text
5 min
```

you have a reliability gap.

# 47. MTTD vs MTTR

Track both.

```text
MTTD
↓
How quickly did we know?

MTTI
↓
How quickly did we identify root cause?

MTTM
↓
How quickly did we mitigate?

MTTR
↓
How quickly did we recover?
```

For AI systems, this decomposition is especially valuable.

| ---------------- | -------------------------------- |
| Queue exploding  | Control admission / scale        |

| TPOT high        | Investigate decode/GPU/NCCL      |

| NIXL failure     | Transfer/fallback/recompute      |

| Pods Pending     | scheduler/Karpenter              |
| AZ failure       | redistribute traffic             |
| Region failure   | global failover                  |
| Prompt injection | isolate tool path                |
| Tool loop        | stop/circuit-break               |
| Cost spike       | token/admission controls         |
