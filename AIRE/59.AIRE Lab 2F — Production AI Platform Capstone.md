# Lab 2F — Production AI Platform Capstone

This is the **full-system design exercise**.

Until now, we learned individual pieces and then learned how to size them. Now we're going to design an enterprise AI platform from **customer requirements all the way to GPU, Kubernetes, security, reliability, observability, DR, and FinOps**.

The important shift is:

> **You are no longer designing a vLLM deployment. You are designing an AI platform.**

---

Imagine you're the lead AI Infrastructure / Reliability Architect.

Your customer is building an enterprise AI platform used by:

* internal employees
* external SaaS customers
* operations teams
* developers
* automated agents

They want one platform supporting multiple AI applications.

# 15. Why Separate Model Pools?

Don't mix everything onto the same GPU fleet.

Imagine:

```text

8B
3B
```

all sharing the same nodes.

Problems:

```text
GPU fragmentation
memory pressure
model loading
noisy neighbors
scaling inefficiency
different GPU requirements
```

Better:

```text
┌─────────────────────────┐
│ 3B GPU Pool             │
│ small/cheap GPUs        │
└─────────────────────────┘

┌─────────────────────────┐
│ 8B GPU Pool             │
│ medium GPUs             │
└─────────────────────────┘

┌─────────────────────────┐
│ 70B GPU Pool            │
│ H100/H200               │
└─────────────────────────┘
```

# 16. Why CPU Is Also Important

A common mistake is thinking:

> "AI platform = GPU everywhere."

No.

Current AWS guidance explicitly treats CPU and GPU inference as complementary. Routing, retrieval, classification, orchestration and guardrails can often run on CPU rather than consuming expensive GPU capacity.

Architecture:

```text
                    CPU
                     │
       ┌─────────────┼─────────────┐
       │             │             │
    Gateway        RAG          Agent
       │             │             │
       │          Vector DB       │
       │             │             │
       └─────────────┼─────────────┘
                     │
                     ▼
                    GPU
                     │
                   LLM
```

This can save substantial money.

# 23. Headroom

Peak:

```text
40 RPS
```

25% headroom:

```text id="h4v3kq"
40 × 1.25
= 50 RPS
```

TP4:

```text
50 / 25
= 2 replicas
```

But N+1:

```text
2 replicas
→ one failure
→ 25 RPS
```

Not enough.

Need:

```text
3 × TP4
```

Capacity:

```text
75 RPS
```

After one failure:

```text
50 RPS
```

Exactly the headroom-adjusted requirement.

GPU:

```text
3 × 4
= 12 GPUs
```

---

# 24. Why Not 2 × TP8?

TP8:

```text
42 RPS
```

Two replicas:

```text
84 RPS
```

After one failure:

```text
42 RPS
```

But required:

```text
50 RPS
```

Therefore it fails the headroom-adjusted N+1 target.

You would need:

```text
3 × TP8
= 24 GPUs
```

unless your HA policy permits a lower post-failure capacity target.

So TP4 may be much more efficient here.

# 32. Why Normal Load Balancing Is Not Enough

Traditional:

```text
round-robin
```

might produce:

```text
Request 1 → A
Request 2 → B
Request 3 → C
```

But LLM servers have state:

```text
KV cache
prefix cache
queue
active sequences
GPU memory
```

Therefore:

```text
Request
   ↓
Which endpoint?
   │
   ├── queue?
   ├── KV?
   ├── prefix?
   ├── latency?
   └── capacity?
```

This is why inference-aware routing exists.

# 33. Prefix Cache

Suppose users repeatedly submit:

```text
System prompt
+
same 30K-document context
+
different question
```

Prefix caching can avoid recomputing common prefixes.

But routing matters.

If request 1 creates cache on:

```text
vLLM-A
```

and request 2 goes to:

```text
vLLM-C
```

you may lose locality.

Therefore:

```text
prefix-aware routing
```

can improve efficiency.

# 54. Model Routing as FinOps

Suppose 60% of requests don't need 70B.

Routing:

```text

10% → 70B
```

```text

```

But quality must be measured.

This creates a multi-objective optimization:

# 61. Spot Strategy


# 67. CTO Question

> "Why does this architecture need 12 GPUs?"

Don't say:

> "Because TP4 requires four GPUs."

Say:

> "Based on the measured workload, one TP4 replica sustains 25 RPS while meeting the latency SLO. Your peak requirement is 40 RPS, and we've included 25% capacity headroom. Three independent TP4 replicas provide 75 RPS total and retain 50 RPS after one replica failure, so the 12-GPU design satisfies both capacity and our stated failure scenario."

That is executive-level technical communication.

---

# 68. Principal Engineer Question

> "Why TP4 rather than TP8?"

Answer:

> "TP8 has better single-replica latency and higher throughput, but the relevant metric is fleet-level SLO-constrained capacity under failure. TP4 allows smaller failure units and, for this workload, three TP4 replicas provide the required capacity after one replica failure with fewer GPUs than the equivalent TP8 design. I'd validate the conclusion against long-context and production-shaped workloads before finalizing it."

---

# 69. Security Architect Question

> "How do you prevent prompt injection from causing AWS changes?"

Answer:

> "The model is not an authorization boundary. The model can produce a proposed tool call, but every tool call passes through a policy-controlled Tool Gateway that validates identity, tenant, resource, action, parameters and risk. AWS access uses least-privilege workload identity, and destructive operations can require human approval. Retrieved documents and tool outputs are treated as untrusted input."

---

# 70. FinOps Question

> "Why is GPU utilization only 55%?"

Answer:

> "I'd first determine whether the platform is intentionally maintaining headroom for the latency and availability SLO. I'd compare useful token throughput, queueing, TTFT, TPOT and failure capacity. If the workload is genuinely underutilizing the fleet, I'd investigate smaller model routing, batching, GPU right-sizing or reducing warm capacity rather than optimizing utilization in isolation."

---

# 71. Reliability Question

> "What happens if an entire AZ disappears?"

Answer:

> "The inference fleet is distributed across AZ failure domains, but each TP group remains internally colocated on the required topology. Routing removes unhealthy endpoints, and the surviving replicas must retain enough SLO-constrained capacity for the stated AZ failure scenario. If that capacity isn't sufficient, the design isn't HA regardless of replica count."

Excellent answer.
