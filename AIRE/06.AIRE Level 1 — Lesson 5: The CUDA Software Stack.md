# AIRE Level 1 — Lesson 5: The CUDA Software Stack

Now we move from **GPU hardware** to the software stack that makes your GPU usable by PyTorch/vLLM.

This lesson is extremely important for production troubleshooting because many “vLLM problems” are actually **driver, CUDA, container, NCCL, or library compatibility problems**.

---

# 2. First principle: CUDA is not just one thing

When someone says:

> “What CUDA version are you using?”

there can actually be several things involved.

For example:

```text
NVIDIA Driver
CUDA Toolkit
CUDA Runtime
PyTorch CUDA build
NCCL version
cuBLAS version
cuDNN version
```

They are related, but they aren't the same component.

# 3. NVIDIA Driver

The **NVIDIA driver** is the critical host-side component that communicates with the physical GPU.

Conceptually:

```text
Linux
  ↓
NVIDIA Driver
  ↓
H100
```

If the driver isn't installed correctly:

```bash
nvidia-smi
```

may fail.

For example:

```text
NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver.
```

At this point:

> Don't troubleshoot vLLM yet.

Your first problem is the GPU/driver layer.

---

# 4. CUDA Toolkit

The CUDA Toolkit is the development ecosystem around CUDA.

It contains tools/libraries used for building CUDA applications.

Conceptually:

```text
CUDA Toolkit
├── nvcc
├── CUDA libraries
├── headers
├── developer tools
└── runtime components
```

You may see:

```bash
nvcc --version
```

and:

```bash
nvidia-smi
```

show apparently different CUDA versions.

This confuses many engineers.

---

# 5. Why `nvidia-smi` CUDA version can confuse you

Run:

```bash
nvidia-smi
```

You might see:

```text
CUDA Version: 12.x
```

This does **not necessarily mean CUDA Toolkit 12.x is installed**.

It indicates the CUDA version supported by the installed driver.

Meanwhile:

```bash
nvcc --version
```

reports the installed CUDA compiler/toolkit version.

So:

```text
nvidia-smi
    ↓
driver-supported CUDA level

nvcc
    ↓
installed CUDA toolkit/compiler
```

That's a very important distinction.

---

# 6. CUDA Runtime

Applications don't necessarily need the entire CUDA Toolkit.

A production container may contain the CUDA runtime libraries needed to execute the application.

Conceptually:

```text
CUDA Toolkit
    ↓
development environment

CUDA Runtime
    ↓
runtime execution
```

This is one reason containers are so useful.

You can have:

```text
Host:
NVIDIA Driver

Container:
specific CUDA userspace
specific PyTorch
specific vLLM
```

rather than installing the entire AI stack directly on the host.

# 10. cuBLAS

Now we reach an important library.

**cuBLAS** = CUDA Basic Linear Algebra Subprograms.

Transformers perform huge amounts of:

```text
matrix multiplication
```

and related linear algebra.

cuBLAS provides highly optimized GPU implementations for these operations.

Simplified:

```text
PyTorch
   ↓
matrix multiplication
   ↓
cuBLAS / optimized kernels
   ↓
Tensor Cores / GPU
```

This is one reason you don't want to implement matrix multiplication yourself.

NVIDIA has spent years optimizing these operations for its GPU architectures.

---

# 11. cuDNN

**cuDNN** is NVIDIA's library for deep-learning primitives.

Historically it has been especially important for operations such as:

```text
convolution
normalization
activation
RNN-related operations
```

For modern Transformer inference, other components and custom kernels can be equally or more important depending on the operation.

The AIRE lesson is:

> cuDNN is part of the optimized deep-learning software stack, but don't assume every Transformer operation goes through cuDNN.

# 12. NCCL

We saw NCCL in Lesson 4.

Now put it into the software stack:

```text
vLLM / PyTorch
       ↓
      NCCL
       ↓
GPU0 ↔ GPU1 ↔ GPU2 ↔ GPU3
```

NCCL handles collective GPU communication.

For example:

```text
AllReduce
AllGather
ReduceScatter
Broadcast
AllToAll
```

This matters tremendously for:

```text
Tensor Parallelism
Pipeline Parallelism
Distributed inference
Distributed training
```

# 16. The classic CUDA mismatch

A common situation:

```text
Host driver
CUDA support = newer

Container
CUDA runtime = older
```

This can often work because NVIDIA maintains backward compatibility relationships between drivers and CUDA runtime versions.

But the reverse situation can cause trouble:

```text
old host driver
+
new CUDA runtime/application
```

The application may require driver capabilities that aren't available.

So always think:

```text
Driver capability
        ≥
requirements of application CUDA stack
```

as a simplified compatibility rule.

For exact compatibility, use NVIDIA's official compatibility matrix rather than guessing.

# 17. What happens when `torch.cuda.is_available()` is false?

Suppose:

```python
import torch

torch.cuda.is_available()
```

returns:

```text
False
```

Don't immediately reinstall PyTorch.

Troubleshoot:

```text
1. Does nvidia-smi work?
2. Does Docker see GPU?
3. Is GPU exposed into container?
4. What PyTorch build is installed?
5. What CUDA runtime does PyTorch expect?
6. Is the driver compatible?
7. Is the correct architecture supported?
```

Then inspect:

```python
print(torch.__version__)
print(torch.version.cuda)
```

This tells you what CUDA version the PyTorch build was compiled against.

# 20. Why CUDA Graphs matter

A normal GPU operation can involve:

```text
CPU
 ↓
launch kernel
 ↓
GPU executes
 ↓
CPU launches next kernel
```

Launching many tiny kernels can create overhead.

CUDA Graphs allow a sequence of operations to be captured and replayed more efficiently in suitable workloads.

Conceptually:

```text
Without graph:

CPU → kernel → CPU → kernel → CPU → kernel

With graph:

CPU → replay graph
          ↓
      kernel
      kernel
      kernel
```

This can reduce CPU launch overhead.

vLLM and other inference systems can exploit CUDA graph techniques for supported execution patterns.

You don't need to implement CUDA Graphs today.

You need to recognize:

> **GPU performance isn't only about raw hardware; kernel-launch and CPU overhead can matter.**

# 21. Why custom kernels matter for LLMs

A Transformer contains many operations:

```text
matmul
attention
softmax
normalization
RoPE
KV-cache operations
sampling
```

A naive implementation could perform many separate operations:

```text
kernel 1
 ↓
kernel 2
 ↓
kernel 3
 ↓
kernel 4
```

Optimized kernels can sometimes:

```text
fuse operations
reduce memory traffic
reduce kernel launches
improve cache locality
use Tensor Cores efficiently
```

This is one reason inference frameworks evolve rapidly.

# 22. FlashAttention intuition

You don't need the implementation details yet.

Understand the goal.

Naive attention can involve large intermediate tensors:

```text
Q × Kᵀ
   ↓
attention matrix
   ↓
softmax
   ↓
× V
```

This creates memory traffic.

Optimized attention implementations aim to reduce unnecessary reads/writes and improve GPU memory behavior.

This is an example of:

> **algorithm + kernel + hardware co-design**

which is becoming increasingly important in AI infrastructure.

# 23. Transformer Engine

NVIDIA's Transformer Engine provides optimized Transformer building blocks and precision support for modern NVIDIA GPUs.

The important AIRE idea:

```text
Transformer
    ↓
precision-aware execution
    ↓
Tensor Cores
    ↓
higher performance
```

Modern NVIDIA architectures increasingly emphasize lower precision such as FP8 and newer low-precision formats.

That means GPU selection and model precision are increasingly coupled.

Official NVIDIA Transformer Engine documentation is the best reference as we get deeper into FP8/FP4 and Blackwell-era inference. [NVIDIA Transformer Engine](https://docs.nvidia.com/deeplearning/transformer-engine/?utm_source=chatgpt.com)

# 26. Interview questions

### Q1. `nvidia-smi` shows CUDA 12.x but `nvcc` shows CUDA 11.x. Is that automatically a problem?

**No.**

They represent different things.

```text
nvidia-smi
→ driver-supported CUDA capability

nvcc
→ installed toolkit
```

You need to evaluate the actual application's compatibility.

---

### Q2. Why can Docker access a GPU when the container doesn't have the NVIDIA driver installed?

Because the container can use the host's NVIDIA driver interface through the NVIDIA container runtime.

The container generally carries the required user-space CUDA libraries while the host supplies the kernel-mode driver.

---

### Q3. `nvidia-smi` works but PyTorch says CUDA unavailable. What do you check?

```text
PyTorch build
CUDA runtime
driver compatibility
GPU visibility
container runtime
architecture support
environment
```

---

### Q4. Why is NCCL important for tensor parallelism?

Because tensor-parallel workers must exchange intermediate results across GPUs. NCCL provides optimized collective communication for those operations.

---

### Q5. Why isn't installing CUDA enough?

Because the stack also needs:

```text
driver
CUDA runtime
PyTorch
NCCL/cuBLAS/etc.
vLLM
compatible GPU architecture
```
