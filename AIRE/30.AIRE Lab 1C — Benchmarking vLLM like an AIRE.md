# Lab 1C — Benchmark vLLM Like an AIRE

Now we stop asking:

> "Does vLLM work?"

and start asking:

> **"How much workload can this GPU serve while meeting my SLO?"**

This is one of the most important labs in the entire AIRE journey.

---

# 2. First define an SLO

Don't benchmark without defining what "good" means.

For our lab, let's choose something simple:

```text
P95 TTFT  < 1 second
P95 TPOT  < 100 ms
Error rate < 1%
```

These are **lab targets**, not universal production recommendations.

Our capacity is:

> Maximum sustainable workload while all these conditions remain true.

That distinction is critical.

---

# 3. Understand the four measurements

### TTFT

Time to first token:

```text
request
   │
   ├──── queue ────┐
   │               │
   │           prefill
   │               │
   └───────────────┴──→ first token
```

---

### TPOT / ITL

Time between generated tokens.

If:

```text
token 1 → 40ms → token 2 → 42ms → token 3
```

then generation feels relatively smooth.

---

### Throughput

How many tokens the system produces per second.

For example:

```text
12,000 output tokens/sec
```

is system throughput.

It does **not** mean each user receives:

```text
12,000 tokens/sec
```

---

### Queue time

Requests waiting before inference begins.

This becomes extremely important near saturation.

---

# 4. Baseline with ONE request

Before concurrent load, establish a baseline.

Run:

```bash
curl -s http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<MODEL>",
    "messages": [
      {
        "role": "user",
        "content": "Explain Kubernetes scheduling."
      }
    ],
    "max_tokens": 200
  }'
```

Do this several times.

Don't use the first request as your benchmark.

Why?

```text
first request
   ↓
possible warmup
possible cache initialization
possible CUDA graph initialization
possible memory allocation
```

So:

```text
cold request ≠ steady-state request
```

# 10. The most important graph

Plot:

```text
Throughput
   │
   │                  ________
   │              ___/
   │          ___/
   │       __/
   │    __/
   │___/
   └──────────────────────────→ Load
```

Initially:

```text
load ↑
throughput ↑
```

Then eventually:

```text
load ↑
throughput ≈ flat
```

while latency explodes:

```text
TTFT
 │
 │                         /
 │                      _/
 │                   __/
 │               ___/
 │______________/____________
                 Load →
```

That intersection is the **knee**.

---

# 11. Why does the knee happen?

Remember our earlier vLLM architecture:

```text
requests
   ↓
scheduler
   ↓
continuous batching
   ↓
prefill/decode
   ↓
KV cache
   ↓
GPU
```

At low load:

```text
GPU has spare capacity
```

As load increases:

```text
batch size increases
GPU utilization increases
throughput increases
```

Eventually:

```text
GPU compute saturated
        OR
HBM bandwidth saturated
        OR
KV cache constrained
        OR
scheduler constrained
        OR
CPU/network constrained
```

Then new requests wait.

So:

```text
waiting requests ↑
       ↓
queue time ↑
       ↓
TTFT ↑
       ↓
SLO violation
```

---

# 12. This is why GPU utilization alone is dangerous

Imagine:

### Test A

```text
GPU utilization: 95%
P95 TTFT: 700ms
Output throughput: 10k tok/s
```

Good.

### Test B

```text
GPU utilization: 98%
P95 TTFT: 4.5 sec
Output throughput: 10.2k tok/s
```

Bad.

The GPU is "more utilized", but the service is worse.

Therefore:

```text
GPU utilization
       +
KV utilization
       +
queue
       +
TTFT
       +
TPOT
       +
throughput
```

must be analyzed together.

While running load:

```bash

  | grep -i kv_cache
```

Conceptually you'll observe:

```text

    ↓

```

As KV approaches its limit:

```text

KV 70%

```

you should start becoming concerned.

At very high KV pressure, vLLM may need to preempt/recompute work depending on configuration and version.

Look for:

```bash

  | grep -i preempt
```

# 14. Important experiment: short vs long prompts

Now keep concurrency fixed.

Test:

```text
10 concurrent
```

with:

### Experiment A

```text
input = 512
output = 128
```

### Experiment B

```text
input = 8,000
output = 128
```

### Experiment C

```text
input = 32,000
output = 128
```

What should happen?

Longer input means:

```text
more tokens
   ↓
more prefill work
   ↓
more compute
   ↓
higher TTFT
```

And potentially:

```text
more KV
   ↓
less concurrency capacity
```

This is why:

> **"500 users" is almost meaningless without token distribution.**

---

# 15. Second important experiment: output length

Keep:

```text
input = 512
```

Test:

```text
output = 50
output = 200
output = 1,000
output = 4,000
```

Longer output means the request remains active longer.

Therefore:

```text
output length ↑
      ↓
request lifetime ↑
      ↓
KV lifetime ↑
      ↓
active sequences ↑
      ↓
concurrency pressure ↑
```

This is one of the reasons agentic workloads can become surprisingly expensive.

---

# 16. Third experiment: repeated prompts

Now test the same long prompt repeatedly.

If automatic prefix caching is enabled and applicable:

```text
Request 1

system prompt
+
large common context
+
question A
```

then:

```text
Request 2

same system prompt
+
same large context
+
question B
```

may benefit from cached prefix computation.

Conceptually:

```text
Without prefix caching:

request 1 → compute prefix
request 2 → compute prefix again

With prefix caching:

request 1 → compute prefix → cache
request 2 → reuse prefix
```

This can substantially change benchmark results.

Therefore:

> **Always know whether your benchmark is exercising the prefix cache.**

Otherwise you may think you discovered a faster GPU when you actually discovered cache reuse.

vLLM's current Automatic Prefix Caching documentation explains this behavior. [vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching.html?utm_source=chatgpt.com)

# 17. Your first AIRE capacity calculation

Suppose our benchmark gives:

```text
One replica:

Input throughput = 20,000 tok/s
Output throughput = 5,000 tok/s

P95 TTFT < 1 sec
P95 TPOT < 100 ms
```

Customer workload:

```text
Input = 80,000 tok/s
Output = 20,000 tok/s
```

A simplistic calculation:

```text
80,000 / 20,000 = 4 replicas
```

and:

```text
20,000 / 5,000 = 4 replicas
```

So:

```text
4 replicas
```

But **don't stop there**.

Production needs:

```text
headroom
+
failure capacity
+
autoscaling delay
+
traffic imbalance
```

Suppose we want 25% headroom:

```text
4 × 1.25 = 5 replicas
```

If we also require one replica failure without violating capacity:

```text
5 replicas
```

might be insufficient depending on the failure model.

If each replica uses:

```text
1 GPU
```

then:

```text
5 replicas = 5 GPUs
```

But if each replica is:

```text
TP = 4
```

then:

```text
5 replicas × 4 GPUs
= 20 GPUs
```

This is why **parallelism architecture changes the economics dramatically**.

---

# 18. The correct production statement

Don't tell a customer:

> "You have 500 users, so you need 8 H100s."

Instead:

> "Based on the measured workload distribution of X input tokens/sec and Y output tokens/sec, our tested vLLM replica sustains Z tokens/sec while maintaining P95 TTFT below the agreed SLO. We therefore require N serving replicas, plus headroom and failure capacity. Each replica uses M GPUs, resulting in a total GPU requirement of N×M."

That is a **Solution Architect answer**.

# 20. One very important professional habit

Change **one variable at a time**.

Bad experiment:

```text
vLLM version changed
+
model changed
+
FP8 enabled
+
TP changed
+
max_num_seqs changed
```

and then:

> "Performance improved!"

You don't know why.

Good experiment:

```text
Baseline
   ↓
change max_num_seqs
   ↓
benchmark
   ↓
restore
   ↓
change max_num_batched_tokens
   ↓
benchmark
```

This is proper performance engineering.
