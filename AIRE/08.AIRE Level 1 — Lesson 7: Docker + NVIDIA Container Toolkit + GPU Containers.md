# 🚀 AIRE Level 1 — Lesson 7: Docker + NVIDIA Container Toolkit + GPU Containers

Today we'll answer a deceptively simple question:

> **How does a Docker container actually use a physical NVIDIA GPU?**

By the end, this should make sense:

```text
                         EC2
┌───────────────────────────────────────────────┐
│                                               │
│  Linux                                        │
│    │                                          │
│    ├── NVIDIA Driver                          │
│    │                                          │
│    ├── Docker Engine                          │
│    │       │                                  │
│    │       ▼                                  │
│    │   NVIDIA Container Toolkit               │
│    │       │                                  │
│    │       ▼                                  │
│    │   ┌───────────────────────────────┐      │
│    │   │       vLLM Container          │      │
│    │   │                               │      │
│    │   │ PyTorch                       │      │
│    │   │ CUDA userspace libraries     │      │
│    │   │ NCCL                          │      │

│    │   └───────────────┬───────────────┘      │
```

# 1. First: what Docker actually does

You already know Docker from DevOps.

Normally:

```text
Docker
  ↓
Container
  ↓
Application
```

For example:

```text
EC2
 │
 └── Docker
      │
      └── nginx container
```

The container has its own:

```text
filesystem
processes
network namespace
environment
libraries
```

But it doesn't normally own physical hardware.

GPU is different.

We want:

```text
Container
    ↓
physical GPU
```

without installing the entire AI stack directly on the host.

---

# 2. The important separation

There are two worlds.

### Host

```text
Host
├── Linux
├── NVIDIA Driver
├── Docker
└── GPU hardware
```

### Container

```text
Container
├── Python
├── PyTorch
├── CUDA userspace
├── NCCL
└── vLLM
```

This is one of the most useful production concepts to understand.

---

# 3. Why don't we install the NVIDIA driver inside the container?

Because the NVIDIA driver is tightly coupled to the host kernel and physical hardware.

Conceptually:

```text
Physical GPU
      ↑
      │
NVIDIA Driver
      ↑
      │
Host Linux kernel
```

The container isn't supposed to independently manage the physical GPU driver.

Instead:

```text
Host
 └── NVIDIA Driver
       ↑
       │
Container runtime
       ↑
       │
Container
```

The container gets access to the GPU through the host's NVIDIA stack.

---

# 4. NVIDIA Container Toolkit

This is the missing piece.

Without GPU support:

```text
Docker
  ↓
Container
  X
GPU unavailable
```

With NVIDIA Container Toolkit:

```text
Docker
  ↓
NVIDIA Container Toolkit
  ↓
NVIDIA Driver
  ↓
GPU
```

NVIDIA's official documentation describes the Container Toolkit as the mechanism for configuring containers to use NVIDIA GPUs. [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/?utm_source=chatgpt.com)

---

# 5. The magic-looking command

You'll eventually run something like:

```bash
docker run --rm --gpus all nvidia/cuda:<tag> nvidia-smi
```

The important part is:

```text
--gpus all
```

It tells Docker:

> Make the available NVIDIA GPUs accessible to this container.

Conceptually:

```text
Host has:

GPU0
GPU1
GPU2
GPU3

docker --gpus all

       ↓

Container sees:

GPU0
GPU1
GPU2
GPU3
```

You can also restrict access.

For example:

```bash
docker run --rm --gpus '"device=0"' ...
```

Then:

```text
Container
   ↓
GPU0 only
```

This becomes extremely useful later in multi-GPU systems.

# 7. Layer 1 — Host GPU

Run:

```bash
nvidia-smi
```

You should see something like:

```text
GPU  Name        Memory
0    H100        80GB
```

If this doesn't work:

**STOP.**

Don't touch Docker.

Don't touch vLLM.

```text
EC2
GPU
driver

```

# 8. Layer 2 — Docker

Now test:

```bash
docker run --rm --gpus all <CUDA image> nvidia-smi
```

The exact image tag should be chosen from a currently supported NVIDIA CUDA image for your driver/GPU combination.

The expected result is that `nvidia-smi` inside the container can see the same GPU.

Now you've proven:

```text
Host GPU
    ↓
Driver
    ↓
NVIDIA Container Toolkit
    ↓
Docker
    ↓
Container
    ↓
GPU
```

# 9. Why this test is so powerful

Imagine:

```text
Host:

✓ works
```

But:

```text
Container:

nvidia-smi
✗ fails
```

You've immediately narrowed the problem.

It probably isn't:

```text

```

```text

NVIDIA Container Toolkit

driver/runtime integration
```

That's proper troubleshooting.

# 10. Layer 3 — PyTorch

Now run a PyTorch container.

Inside:

```python
import torch

print("PyTorch:", torch.__version__)
print("CUDA:", torch.version.cuda)
print("CUDA available:", torch.cuda.is_available())
print("GPU count:", torch.cuda.device_count())

if torch.cuda.is_available():
    print(torch.cuda.get_device_name(0))
```

Expected:

```text
PyTorch: ...
CUDA: ...
CUDA available: True
GPU count: 1
GPU: NVIDIA H100
```

Now we've proven:

```text
Docker
   ↓
CUDA
   ↓
PyTorch
   ↓
GPU
```

# 11. But there's another important concept: image

A GPU container isn't magically a GPU container because it contains Python.

For example:

```text
ubuntu:24.04
```

doesn't automatically give you:

```text
CUDA
PyTorch
NCCL
```

You need a compatible userspace software stack.

A specialized CUDA/PyTorch/vLLM image makes this much easier.

# 12. Container image anatomy

Think of a vLLM image roughly like:

```text
vLLM image
│
├── Ubuntu/Linux userspace
├── Python
├── PyTorch
├── CUDA userspace libraries
├── NCCL
├── optimized libraries/kernels

```

Then:

```text
Host
│
├── Linux kernel
├── NVIDIA Driver
└── Physical GPU
```

This gives you a reproducible environment.

# 15. GPU image vs model

Very important:

> **The model does not have to be baked into the Docker image.**

You could have:

```text
Image
├── vLLM
├── PyTorch
├── CUDA
└── dependencies
```

and separately:

```text
Model storage
├── config
├── tokenizer
├── weights
└── other artifacts
```

At startup:

```text
Container starts
       ↓
vLLM starts
       ↓
download/load model
       ↓
GPU memory
       ↓
ready
```

This is generally much more flexible than rebuilding a multi-GB image every time model weights change.

# 17. GPU visibility

Inside a container you may see environment configuration such as:

```text
NVIDIA_VISIBLE_DEVICES
```

Conceptually:

```text
NVIDIA_VISIBLE_DEVICES=0
```

means:

```text
container → GPU 0
```

while:

```text
NVIDIA_VISIBLE_DEVICES=0,1
```

means:

```text
container → GPU 0 and GPU 1
```

Modern container tooling handles much of this automatically when using `--gpus`.

# 19. GPU isn't like CPU

With CPU you commonly request:

```yaml
resources:
  requests:
    cpu: "2"
```

For GPUs, Kubernetes typically works with discrete GPU resources such as:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

Conceptually:

```text
Pod
 ↓
GPU resource request
 ↓
Kubernetes scheduler
 ↓
GPU node
 ↓
NVIDIA device plugin
 ↓
GPU
```

We'll build this later.

# 20. Why you shouldn't manually assign GPUs in Kubernetes

Imagine:

```text
Node:
8 GPUs
```

and you manually configure:

```text
Pod A → GPU0
Pod B → GPU1
Pod C → GPU2
```

Now Kubernetes doesn't really understand your resource allocation.

You lose proper scheduling semantics.

Instead:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

lets Kubernetes and the NVIDIA device plugin participate in GPU allocation.

This is the cloud-native approach.

# 27. Production Dockerfile philosophy

A simplified conceptual Dockerfile might look like:

```dockerfile
FROM <compatible-vllm-or-cuda-base-image>

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app/ /app/

CMD ["python", "server.py"]
```

But for production:

```text
Don't casually:
RUN pip install latest
```

Prefer pinned/reproducible versions.

For example:

```text
vLLM version
PyTorch version
Python version
CUDA userspace
application dependencies
```

should be controlled.

# 🎯 Interview Questions

### Q1. Why shouldn't the NVIDIA driver normally be installed inside the container?

Because the driver is tied to the host kernel and physical GPU. Containers use the host's NVIDIA driver through the NVIDIA container runtime.

---

### Q2. What does `--gpus all` do?

It requests GPU access for the container through Docker's NVIDIA GPU integration.

---

### Q3. Why does `nvidia-smi` work on the host but fail inside Docker?

Likely:

```text
NVIDIA Container Toolkit
runtime configuration
GPU exposure
container configuration
```

not necessarily the physical GPU.

---

### Q4. Why use containers for vLLM?

```text
reproducibility
dependency isolation
version control
deployment consistency
CI/CD
rollback
```

---

### Q5. Should model weights be baked into the image?

Not necessarily.

Separating:

```text
serving image
```

from:

```text
model artifact
```

often gives better flexibility for model versioning and image reuse.

---

### Q6. What causes GPU inference cold starts?

Potentially:

```text
EC2 provisioning
image pull
model download
model loading into VRAM
CUDA initialization
vLLM initialization
warmup
```
