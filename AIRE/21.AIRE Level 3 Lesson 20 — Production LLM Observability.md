# 5. The first metric: TTFT

You've already learned this.

## Time To First Token

```text
Request sent
    │
    │
    ├──── queue
    │
    ├──── prefill
    │
    ├──── KV transfer if applicable
    │
    ▼
First token
```

So:

```text
TTFT =
request → first token
```

vLLM exposes:

```text
vllm:time_to_first_token_seconds
```

as a histogram. ([vLLM][2])

---

# 6. Why TTFT is so important

Suppose customer says:

> "ChatGPT-like response feels slow."

The user primarily experiences:

```text
How long until something appears?
```

That's TTFT.

Example:

```text
TTFT = 200 ms
```

feels very different from:

```text
TTFT = 5 sec
```

even if both eventually produce the same answer.

---

# 7. But TTFT alone isn't enough

Suppose:

```text
TTFT = 300 ms
```

Great.

But after the first token:

```text
Token 1
   │
 2 sec
   │
Token 2
   │
 2 sec
   │
Token 3
```

The model feels terrible.

So we need:

# ITL

**Inter-Token Latency**

```text
Token 1 ──100ms── Token 2 ──100ms── Token 3
```

vLLM exposes:

```text
vllm:inter_token_latency_seconds
```

as a histogram. ([vLLM][3])

---

# 8. ITL vs TPOT

These terms are often confused.

### ITL

Measures gaps between streamed outputs.

```text
token1 → token2
token2 → token3
token3 → token4
```

### TPOT

Time per output token for a request, generally excluding the first token.

Current vLLM benchmarking documentation defines TPOT as:

```text
(end-to-end latency - TTFT)
--------------------------------
(output tokens - 1)
```

while ITL is measured between consecutive streamed outputs. ([vLLM][4])

Normally they are similar.

But with speculative decoding they can differ.

That's an important interview point.

# 10. Queue time — one of the most important metrics

vLLM exposes:

```text
vllm:request_queue_time_seconds
```

for time spent waiting before processing. ([vLLM][2])

Imagine:

```text

```

You investigate:

```text

Prefill = 350 ms
```

The GPU isn't necessarily the problem.

Your actual problem is:

```text
capacity / scheduling
```

Potential fixes:

```text

increase capacity
improve routing
reduce admission pressure
tune batching
```

# 11. This creates our first diagnostic equation

Conceptually:

```text

```

For a normal non-P/D deployment:

```text
TTFT ≈ Queue + Prefill + overhead
```

For P/D:

```text
TTFT ≈ Queue + Prefill + KV transfer + overhead
```

Now observability becomes **causal**, not just descriptive.

# 16. KV saturation scenario

Imagine:



So:


# 38. Cardinality — extremely important

Here's something you'll appreciate from Prometheus.

Don't create labels like:

```text
request_id
user_id
prompt
conversation_id
```

on every metric.

Why?

Because:

```text
millions of users
×
millions of requests
```

creates enormous time-series cardinality.

Bad:

```text
vllm_ttft{request_id="123456789"}
```

Good:

```text
vllm_ttft{
  model="70b",
  deployment="prod",
  gpu_type="h100"
}
```

Use traces/logs for high-cardinality request identity.

Use metrics for aggregated dimensions.

🔥 This is a **very important production observability principle**.

# 65. Don't put everything into Prometheus

This is a common mistake.

Don't try to make Prometheus your:

```text
request database
```

For example:

```text
prompt text
request_id
conversation_id
user_id
full model response
```

should not become massive metric labels.

Instead:

```text
Prometheus
→ aggregate metrics

Loki
→ structured event logs

Tempo
→ request traces

Object storage / analytics
→ long-term detailed request analytics
```

# 68. The golden debugging table

| Symptom                   | First place to look      |
| ------------------------- | ------------------------ |
| TTFT ↑                    | Queue / prefill / KV     |
| TPOT ↑                    | Decode / HBM bandwidth   |
| Queue ↑                   | Capacity / scheduling    |
| KV ↑                      | Memory/concurrency       |
| GPU util low + queue high | KV/capacity/routing      |
| GPU util high + TTFT high | Compute/batching         |
| DRAM high + Tensor low    | Memory bandwidth         |
| NVLink high               | TP/communication         |
| NIXL latency high         | KV transfer/network      |
| EFA errors                | Network/RDMA             |
| Preemptions ↑             | Memory pressure          |
| E2E high but TTFT normal  | Long generation          |
| One replica hot           | Routing imbalance        |
| All replicas hot          | Fleet capacity           |
| New pods slow             | Cold start/model loading |
