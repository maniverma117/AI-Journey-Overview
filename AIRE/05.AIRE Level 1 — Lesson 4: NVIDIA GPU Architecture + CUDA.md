# AIRE Level 1 — Lesson 4: NVIDIA GPU Architecture + CUDA

Your target after this lesson is to look at an EC2 GPU instance or `nvidia-smi` output and understand **where inference performance is actually coming from**.

The mental model is:

```text
Application / vLLM
       ↓
PyTorch / CUDA libraries
       ↓
CUDA runtime
       ↓
NVIDIA Driver
       ↓
GPU
 ┌────────────────────────────┐
 │ Streaming Multiprocessors  │
 │   ├─ CUDA Cores            │
 │   └─ Tensor Cores          │
 │                            │
 │ L1 / Shared Memory         │
 │ L2 Cache                   │
 │ HBM                        │
 │                            │
 │ NVLink / PCIe              │
 └────────────────────────────┘
```

CUDA is NVIDIA's parallel-computing platform and programming model. Frameworks such as PyTorch and serving engines such as vLLM ultimately use CUDA kernels to execute work on NVIDIA GPUs. ([NVIDIA Docs][1])

---

## 1. Start with the most important distinction: VRAM ≠ GPU performance

Suppose a customer says:

> “H100 has 80 GB memory. My model is 70 GB. So one H100 should be perfect.”

From Lesson 3, you already know why this is incomplete.

The model needs:

```text
GPU VRAM
=
Model weights
+ KV cache
+ CUDA/runtime memory
+ temporary tensors/workspaces
+ fragmentation/headroom
```

But today we add something else:

```text
Model fits in VRAM
        ≠
Model runs fast
```

For inference, you care about at least:

```text
1. VRAM capacity
2. HBM bandwidth
3. Tensor Core compute
4. GPU architecture
5. inter-GPU bandwidth
6. CPU → GPU pipeline
7. software/kernel efficiency
```

This distinction is fundamental for an AIRE.

---

# 2. Anatomy of an NVIDIA GPU

Think of a GPU as a very large parallel-processing machine.

Conceptually:

```text
GPU
│
├── HBM / GPU memory
│
├── L2 cache
│
├── many Streaming Multiprocessors (SMs)
│      │
│      ├── CUDA cores
│      ├── Tensor cores
│      ├── registers
│      ├── shared memory / L1
│      └── warp schedulers
│
├── copy engines
│
├── PCIe
│
└── NVLink
```

For AIRE work, the four pieces you should remember first are:

```text
SM
Tensor Core
HBM
NVLink
```

---

# 3. What is an SM?

**SM = Streaming Multiprocessor.**

You can loosely think of an SM as one of the GPU's main execution engines.

A GPU contains many SMs.

Applications launch a CUDA **kernel**, and huge numbers of GPU threads execute across these SMs.

Conceptually:

```text
CUDA Kernel
      ↓
Grid
      ↓
Blocks
      ↓
Threads
      ↓
SMs
      ↓
CUDA cores / Tensor cores
```

You don't need to write CUDA kernels to be an AIRE.

You need to understand that:

> **GPU utilization usually tells us something about how busy these execution resources are — not whether they're doing useful work efficiently.**

That's an important distinction.

---

# 4. CUDA kernel

When PyTorch performs something like:

```python
output = torch.matmul(A, B)
```

you aren't normally implementing GPU instructions yourself.

The stack looks more like:

```text
PyTorch / vLLM
      ↓
CUDA libraries / custom kernels
      ↓
CUDA runtime
      ↓
kernel launch
      ↓
GPU SMs
```

A kernel could perform things such as:

```text
matrix multiplication
attention
normalization
softmax
KV-cache operations
sampling
memory copies
```

vLLM performance therefore depends partly on how efficiently its kernels use the hardware.

This is why:

```text
same GPU
+ same model
+ different serving engines
```

can produce very different throughput.

---

# 5. CUDA Cores vs Tensor Cores

This comes up constantly in interviews.

## CUDA cores

CUDA cores are general arithmetic execution units.

They're useful for many kinds of numerical operations.

Think:

```text
general GPU arithmetic
```

## Tensor Cores

Tensor Cores are specialized hardware designed to accelerate matrix-oriented operations.

Transformers contain enormous amounts of matrix multiplication:

```text
Q = XWq
K = XWk
V = XWv

Attention output
MLP projections
output projection
```

Therefore Tensor Cores are extremely important for LLM performance.

Simple mental model:

```text
CUDA Core
   ↓
general numerical computation

Tensor Core
   ↓
high-throughput matrix computation
   ↓
Transformers love this
```

Modern NVIDIA Tensor Cores support lower-precision formats that can greatly increase AI throughput.

For example, NVIDIA currently lists H100 SXM peak Tensor Core performance far above its regular FP32 throughput. ([NVIDIA][2])

---

# 6. Why BF16 / FP16 / FP8 matter beyond memory

Earlier we discussed:

```text
BF16 = ~2 bytes/parameter
FP8  = ~1 byte/parameter
INT4 = ~0.5 byte/parameter
```

That affects VRAM.

But precision can also affect **compute throughput**.

For supported operations:

```text
lower precision
      ↓
less memory moved
      +
more Tensor Core throughput
      ↓
potentially more tokens/sec
```

So quantization may give you two benefits:

```text
smaller model memory
+
higher serving performance
```

But never assume:

```text
FP8 = automatically 2× faster than BF16
```

because bottlenecks may be elsewhere.

---

# 7. HBM: one of the most important AIRE concepts

HBM = **High Bandwidth Memory**.

This is the GPU memory where things such as these reside:

```text
model weights
KV cache
activations
temporary buffers
```

The critical word is:

> **Bandwidth**

not simply capacity.

You may have:

```text
80 GB VRAM
```

but you also care about:

```text
how many TB/s the GPU can read/write
```

For example, NVIDIA currently specifies H100 SXM with:

```text
GPU memory:        80 GB
memory bandwidth:  3.35 TB/s
```

([NVIDIA][2])

These are two completely different characteristics.

---

# 8. Capacity vs bandwidth

Imagine two imaginary GPUs.

```text
GPU A
VRAM = 96 GB
Bandwidth = 1 TB/s

GPU B
VRAM = 80 GB
Bandwidth = 3 TB/s
```

GPU A can hold more.

GPU B can move data much faster.

Which is better?

You cannot answer without the workload.

That is exactly how an architect should think.

---

# 9. Why LLM decoding is frequently memory-bandwidth sensitive

Remember autoregressive decoding:

```text
Token 1
 ↓
Token 2
 ↓
Token 3
 ↓
Token 4
```

Each decoding iteration executes the model again to produce the next token.

Large amounts of model data have to be accessed repeatedly.

Therefore decode workloads can become highly sensitive to memory bandwidth.

Simplified:

```text
Prefill:
large matrix operations
→ often easier to exploit massive parallel compute

Decode:
small amount of new work per request per step
+ repeated access to weights/KV
→ commonly memory-bandwidth sensitive
```

This is one reason prefill and decode have quite different performance characteristics.

---

# 10. Arithmetic intensity

Here's a useful advanced concept.

```text
Arithmetic intensity
=
amount of computation
---------------------
amount of memory traffic
```

If you're doing lots of computation for every byte loaded:

```text
compute-bound
```

If you're mostly waiting for memory:

```text
memory-bound
```

LLM workloads can move between these states depending on:

```text
batch size
prompt length
decode phase
model
precision
parallelism
kernel implementation
```

This will become very useful later when optimizing vLLM.

---

# 11. Why batching helps GPU utilization

Suppose one user generates a token.

The GPU may not have enough useful parallel work.

```text
Request A
   ↓
tiny-ish decode workload
```

Now suppose vLLM combines:

```text
A
B
C
D
E
F
G
H
```

into a continuous batch.

Now large matrix operations contain more parallel work.

```text
more batching
      ↓
better Tensor Core utilization
      ↓
more total tokens/sec
```

This is why one GPU might produce:

```text
single user:
60 tok/s
```

but with many users:

```text
aggregate:
1000+ tok/s
```

depending heavily on model and workload.

And this brings us back to:

> **User token speed and aggregate throughput are different metrics.**

---

# 12. GPU memory hierarchy

A simplified hierarchy:

```text
Fastest / smallest

Registers
   ↓
Shared memory / L1
   ↓
L2 cache
   ↓
HBM
   ↓
Host RAM
   ↓
Storage

Slowest / largest
```

Data locality matters tremendously.

If frequently accessed information remains in cache:

```text
fast
```

If kernels repeatedly fetch data from HBM:

```text
slower
```

If you must move data over PCIe:

```text
much worse
```

And if you're continuously loading from disk:

```text
disaster for latency
```

This gives you another useful principle:

> **Model serving is partly a data-movement optimization problem.**

---

# 13. PCIe

GPU and CPU communicate through PCIe in many systems.

Conceptually:

```text
CPU RAM
   ↕
PCIe
   ↕
GPU VRAM
```

For normal serving you don't want your hot-path model weights constantly moving:

```text
CPU → GPU → CPU → GPU
```

You typically want:

```text
weights resident on GPU
KV cache resident on GPU
compute executed on GPU
```

CPU offloading can allow a larger model to run, but it often introduces performance tradeoffs because data must cross a much slower link than HBM.

---

# 14. NVLink

Now imagine multiple GPUs.

```text
GPU0           GPU1
  │              │
  └──── NVLink ──┘
```

NVLink provides high-bandwidth GPU-to-GPU connectivity.

For H100 SXM, NVIDIA specifies up to **900 GB/s NVLink interconnect bandwidth**. ([NVIDIA][2])

Compare the conceptual hierarchy:

```text
HBM local GPU:
extremely fast

NVLink:
very fast GPU ↔ GPU

PCIe:
slower

network between machines:
usually much more expensive again
```

This becomes critical for tensor parallelism.

---

# 15. Why Tensor Parallelism needs fast interconnect

Suppose:

```text
70B model
TP = 4
```

The model is split across:

```text
GPU0
GPU1
GPU2
GPU3
```

Each GPU computes only part of the operation.

But the GPUs frequently need to exchange intermediate results.

So the flow becomes roughly:

```text
GPU0 ─┐
GPU1 ─┼─ collective communication
GPU2 ─┤
GPU3 ─┘
```

This communication happens many times during inference.

Therefore:

```text
TP performance
=
compute
+
GPU communication
```

Not just compute.

---

# 16. NCCL

This is where **NCCL** enters.

NCCL = NVIDIA Collective Communications Library.

It provides optimized multi-GPU communication operations.

Examples include:

```text
AllReduce
AllGather
ReduceScatter
Broadcast
AllToAll
```

NVIDIA's current NCCL docs describe NCCL as a topology-aware library for high-performance collective communication across GPUs, including PCIe, NVLink and network-based interconnects. ([NVIDIA Docs][3])

You don't need to implement NCCL.

As AIRE, you need to recognize:

```text
bad NCCL performance
      ↓
bad tensor-parallel performance
      ↓
low tokens/sec
even when GPUs look busy
```

---

# 17. The AllReduce concept

Imagine four GPUs each calculate part of a result.

```text
GPU0 → A
GPU1 → B
GPU2 → C
GPU3 → D
```

AllReduce can combine these and give the result back to every GPU:

```text
A+B+C+D
    ↓
GPU0
GPU1
GPU2
GPU3
```

NCCL defines AllReduce exactly in this style: values are reduced across ranks and the resulting data is made available on every rank. ([NVIDIA Docs][4])

Large amounts of synchronization here are one reason:

```text
TP=8
```

is not automatically better than:

```text
TP=4
```

---

# 18. An important architecture rule

Suppose your model fits on:

```text
2 GPUs
```

Don't automatically do:

```text
TP = 8
```

just because your node has eight GPUs.

Why?

```text
TP 2
→ less communication

TP 8
→ more communication
→ more synchronization
→ possibly worse efficiency
```

Sometimes the better design could be:

```text
8 GPU node

Replica 1: TP=2
Replica 2: TP=2
Replica 3: TP=2
Replica 4: TP=2
```

rather than:

```text
Replica 1: TP=8
```

Now you're thinking like an inference architect.

# 20. H100 vs H200: what should an architect ask?

Do not start with:

> “Which GPU is faster?”

Ask:

```text
Does the model fit?
What precision?
How much KV cache?
What context?
How much concurrency?
What batch size?
What is TTFT SLO?
What is TPOT SLO?
What throughput is needed?
Are we compute-bound or memory-bound?
What does each GPU cost?
```

Then compare GPUs.

If one GPU has significantly more HBM capacity, that may allow:

```text
larger KV cache
more concurrent sequences
longer context
lower tensor parallelism
```

and eliminating an extra GPU can sometimes matter more than raw FLOPS.


# Interview section

## Q1. What is the difference between CUDA cores and Tensor Cores?

Strong answer:

> CUDA cores handle general GPU arithmetic, while Tensor Cores are specialized for high-throughput matrix operations using formats such as FP16/BF16/FP8 depending on architecture. Transformer inference contains extensive matrix multiplication, so Tensor Core utilization strongly influences LLM performance.

---

## Q2. What is an SM?

> A Streaming Multiprocessor is a primary execution unit within an NVIDIA GPU. CUDA kernels schedule blocks of GPU threads onto SMs, which contain execution resources including CUDA cores and Tensor Cores.

You don't need to explain transistor architecture.

---

## Q3. Why does HBM bandwidth matter for LLMs?

> Model weights and KV-cache data reside in GPU memory. During inference, especially autoregressive decoding, large amounts of data have to be accessed repeatedly. High HBM bandwidth can therefore materially affect token-generation throughput.

Excellent.

---

## Q4. GPU utilization is 100% but tokens/sec is poor. What do you do?

Do **not** say:

> Add GPUs.

Say:

> I would correlate GPU utilization with Tensor Core activity, DRAM utilization, batch size, queue depth, TTFT, TPOT, KV-cache utilization, CPU utilization, request token lengths, and inter-GPU communication. The workload could be memory-bound, poorly batched, communication-bound, throttled, or executing inefficient kernels rather than simply lacking GPUs.

That's an AIRE answer.

---

## Q5. Why does NVLink matter?

> With tensor parallelism, GPUs repeatedly exchange intermediate tensors. NVLink provides high-bandwidth GPU-to-GPU communication, reducing communication overhead compared with slower interconnect paths.

---

## Q6. Why can TP=8 be slower than TP=4?

Because you reduce compute per GPU but increase:

```text
communication
synchronization
collective overhead
```

At some point communication outweighs the extra parallelism.

---

## Q7. Why can GPU memory be 95% while GPU utilization is 20%?

Because:

```text
VRAM usage = allocated/resident data
GPU utilization = execution activity
```

A loaded model can occupy almost all memory while serving almost no traffic.

---

## Q8. How would you choose H100 vs H200 or another newer GPU?

Don't answer purely with specs.

Answer:

> First establish model memory, precision, KV-cache requirement, input/output distributions, concurrency, TTFT/TPOT SLO, throughput target and parallelism. Then benchmark candidate GPUs and compare sustainable throughput, latency and cost per token. More VRAM can also reduce required tensor parallelism and improve concurrency.

Excellent Solution Architect answer.
