# Lab 1E — Failure Engineering for vLLM

Now we move into the **Reliability** part of AI Reliability Engineering.

So far:

```text
Lab 1A → GPU works
Lab 1B → vLLM works
Lab 1C → capacity measured
Lab 1D → performance tuned
```

Now:

```text
Lab 1E → deliberately break it
```

The goal is not merely to make vLLM work.

The goal is to answer:

> **"What happens when something goes wrong, and how long until the service recovers?"**

---

# 1. Production mindset

A weak architecture says:

```text
vLLM pod crashed
      ↓
Kubernetes restarted it
      ↓
Problem solved
```

An AIRE asks:

```text
Why did it crash?
How many requests failed?
How many requests timed out?
Did traffic go somewhere else?
How long until another replica was ready?
Was the GPU healthy?
Did the model have to reload?
Did KV state disappear?
Did TTFT SLO break?
Did error budget burn?
```

That's the difference.

---

We'll eventually test:

```text
                    AI Service

        │              │              │

                       ▼

                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Traffic        Readiness        SLO
      routing        recovery         impact
```

# **Pod failure**

# 4. Why a Deployment matters

Our architecture is currently:

```text
Service
   │
   ▼
Deployment
   │
   ▼
vLLM Pod
```

The Deployment controller maintains:

```yaml
replicas: 1
```

Therefore:

```text
Pod dies
   ↓
Deployment notices
   ↓
creates replacement Pod
```

But there is an important catch.

The replacement pod has to:

```text
schedule
   ↓
start container
   ↓
load model
   ↓
allocate GPU
   ↓
initialize KV cache
   ↓
warm up
   ↓
become Ready
```

For a large model, that can take a meaningful amount of time.


then:

```text
vllm-def       Running
```

and eventually:

```text
vllm-def       1/1 Running
```

# 6. Measure recovery time

This is our first real reliability metric.

Define:

```text
T0 = failure
```

For example:

```text
11:20:00
```

Then:

```text
T1 = service Ready
```

Suppose:

```text
11:20:48
```

Then:

```text
Recovery Time
= T1 - T0
= 48 seconds
```

Now you have an actual measurement.

Not:

> "Kubernetes restarts it quickly."

But:

> "Our current single-GPU vLLM configuration has a measured recovery time of 48 seconds."

---

# 7. Why recovery can be slow

For a GPU model server:

```text
Pod deletion
     ↓
new Pod scheduling
     ↓
GPU allocation
     ↓
container image
     ↓
model availability
     ↓
model loading
     ↓
GPU memory allocation
     ↓
KV cache initialization
     ↓
CUDA warmup
     ↓
readiness
```

The model loading phase can dominate.

For example:

```text
Node scheduling      5 sec
Image startup        3 sec
Model loading       25 sec
CUDA/warmup          8 sec
----------------------------
Total               ~41 sec
```

This is why **AI cold start is fundamentally different from a typical stateless HTTP service**.

---

# 8. Now ask: what happened to traffic?

With one replica:

```text
Client
  ↓
Service
  ↓
vLLM
```

When the only pod disappears:

```text
Client
  ↓
Service
  ↓
NO READY ENDPOINT
```

During that interval, requests may:

* fail
* timeout
* retry
* wait at an upstream gateway

This is why:

```text
Deployment replicas = 1
```

is **not highly available**.

# 9. Move to two replicas

Change:

```yaml
spec:
  replicas: 2
```

Apply:

```bash
kubectl apply -f vllm.yaml
```

Check:

```bash
kubectl get pods -o wide
```

You should now have:

```text
vllm-abc   1/1 Running
vllm-def   1/1 Running
```

But there's a problem.

If each vLLM replica requests:

```yaml
nvidia.com/gpu: 1
```

then we need:

```text
2 replicas
×
1 GPU
=
2 GPUs
```

This is the first place where **HA directly affects GPU cost**.

---

# 10. Test failure with two replicas

Now delete one:

```bash
kubectl delete pod <one-vllm-pod>
```

Immediately:

```bash
kubectl get pods -o wide
```

You should see something like:

```text
vllm-A   Terminating
vllm-B   Running
vllm-C   ContainerCreating
```

The critical point:

```text
Service
  │
  ├── vllm-B ✓
  │
  └── vllm-A ✗
```

There is still a healthy serving replica.

Therefore the service can potentially continue serving while Kubernetes replaces the failed pod.

That's real redundancy.

---

# 11. But don't call this HA yet

Two replicas on the same node:

```text
Node A
 ├── vLLM-1
 └── vLLM-2
```

looks redundant.

But:

```text
Node A dies
```

and both disappear.

So:

```text
2 replicas ≠ node-level HA
```

We need:

```text
Node A
  └── vLLM-1

Node B
  └── vLLM-2
```

And ideally:

```text
AZ-A
  └── GPU node

AZ-B
  └── GPU node
```

This is **failure-domain thinking**.

---

# 12. Pod anti-affinity

We can tell Kubernetes:

> Don't place all vLLM replicas together.

Example:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - key: app
              operator: In
              values:
                - vllm
        topologyKey: kubernetes.io/hostname
```

Meaning:

```text
vLLM-1 → Node A
vLLM-2 → Node B
```

rather than:

```text
Node A
 ├── vLLM-1
 └── vLLM-2
```

---

# 13. Spread across AZs

For production, we can use topology-aware scheduling.

Conceptually:

```text
AZ-A                 AZ-B
 │                    │
GPU Node A           GPU Node B
 │                    │
vLLM-1               vLLM-2
```

Now:

```text
Node A failure
       ↓
vLLM-1 lost
       ↓
vLLM-2 remains
```

and:

```text
AZ-A failure
       ↓
vLLM-2 in AZ-B remains
```

This is much stronger.

# 14. Failure injection #2 — readiness

Now we need to understand one of the most important Kubernetes concepts for AI serving:

```text
Liveness
vs
Readiness
```

### Liveness

Answers:

> "Is this process alive?"

### Readiness

Answers:

> "Should this pod receive traffic?"

Those are **not the same question**.

---

# 15. Why generic HTTP health checks can be dangerous

Imagine vLLM starts:

```text
process alive
HTTP server listening
model loading...
```

If your readiness probe only checks:

```text
GET /
```

it might say:

```text
READY ✓
```

while the model isn't actually ready.

Traffic arrives:

```text
request
 ↓
vLLM
 ↓
model still loading
```

Bad.

Therefore our readiness design must reflect **serving readiness**, not just process existence.

---

# 16. Model-serving lifecycle

Think:

```text
                   Pod
                    │
                    ▼
              Container starts
                    │
                    ▼
                CUDA ready
                    │
                    ▼
               Model loaded
                    │
                    ▼
              KV initialized
                    │
                    ▼
                 Warmup
                    │
                    ▼
                  READY
```

Only at the end:

```text
Service → Pod
```

should traffic be enabled.

# 19. Failure injection #5 — node failure

This is where things become much more interesting.

Imagine:

```text
AZ-A

GPU Node A
   │
   └── vLLM-1
```

and:

```text
AZ-B

GPU Node B
   │
   └── vLLM-2
```

Now:

```text
GPU Node A
     X
```

What should happen?

```text
vLLM-1
   ↓
lost

vLLM-2
   ↓
continues serving

Kubernetes
   ↓
replacement pod requested

Karpenter
   ↓
GPU capacity provisioned if necessary

New GPU node
   ↓
new vLLM
   ↓
model loading
   ↓
Ready
```

That entire chain contributes to your recovery time.

---

# 20. The four different recovery times

This is a powerful mental model.

### RTO

Recovery Time Objective:

> Maximum acceptable recovery time.

### Actual recovery time

What your system actually achieved.

### Pod recovery

```text
Pod failure → Pod Running
```

### Serving recovery

```text
Failure → model loaded → Ready → traffic served
```

These aren't necessarily equal.

For AI:

```text
Pod recovery = 15 sec
```

could coexist with:

```text
Inference recovery = 60 sec
```

because the model still needs to load.

---

# 21. Graceful shutdown

Now let's consider the opposite direction.

Suppose Kubernetes wants to terminate the pod.

We don't want:

```text
SIGTERM
   ↓
process immediately dies
   ↓
requests interrupted
```

Instead:

```text
SIGTERM
   ↓
stop accepting new traffic
   ↓
remove readiness
   ↓
drain existing requests
   ↓
finish inference
   ↓
terminate
```

This becomes especially important with:

* rolling deployments
* Karpenter consolidation
* node replacement
* autoscaling
* model upgrades

---

# 22. `terminationGracePeriodSeconds`

For example:

```yaml
spec:
  terminationGracePeriodSeconds: 120
```

The exact value must come from your workload's longest expected request/drain time.

Don't blindly choose:

```text
300
```

or:

```text
30
```

Ask:

```text
What is P99 generation duration?
What is the longest allowed request?
How quickly can we drain?
What is our SLO?
```

---

# 23. PodDisruptionBudget

Suppose:

```text
replicas = 3
```

and you're doing maintenance.

You don't want Kubernetes voluntarily disrupting all three.

A PDB can express availability expectations.

For example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: vllm-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: vllm
```

Conceptually:

```text
3 replicas

Allowed:

✓ 3 running
✓ 2 running

Avoid:

✗ 1 running
✗ 0 running
```

A PDB is **not** protection from every failure. It primarily governs voluntary disruptions.

# 24. Failure-domain design

Now combine everything:

```text
                 Service
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       vLLM-1               vLLM-2
          │                   │
       GPU Node A           GPU Node B
          │                   │
        AZ-A                AZ-B
```

With:

```text
Pod anti-affinity
+
topology spread
+
PDB
+
readiness
+
graceful shutdown
```

we've built a much more resilient serving layer.

---

# 25. But there is still a major problem

Suppose the customer requires:

```text
99.99% availability
```

and our recovery takes:

```text
2 minutes
```

A single failure can consume a large amount of our error budget.

For 30 days:

```text
99.99%
```

allows approximately:

```text
4.32 minutes
```

of total unavailability.

So:

```text
one 2-minute outage
```

consumes almost half the monthly availability budget.

That changes how we design the system.

# 26. Reliability isn't just "restart faster"

We can improve reliability at multiple layers:

```text
                   Reliability
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
   Prevention       Redundancy       Recovery
       │               │                │
   good config      replicas          restart
   safe rollout     multi-node        replace
   capacity         multi-AZ          reload
   health checks    routing           failover
```

And for AI:

```text
Model reliability
+
GPU reliability
+
Kubernetes reliability
+
network reliability
+
routing reliability
+
dependency reliability
```

# 29. The big lesson

A normal web application might have:

```text

+
database
```

An LLM inference platform has:

```text
             AI Inference Reliability

                    Model
                      │
                      ▼
                    vLLM
                      │
                      ▼
                 KV / Scheduler
                      │
                      ▼
                CUDA / PyTorch
                      │
                      ▼
                     GPU
                      │
                      ▼
                 GPU Node
                      │
                      ▼
                 Kubernetes
                      │
                      ▼
                Karpenter
                      │
                      ▼
                    EC2
```

A failure anywhere can affect inference.

That's why AIRE is a specialized reliability discipline.
