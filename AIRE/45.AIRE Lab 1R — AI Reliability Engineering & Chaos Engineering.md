# Lab 1R — AI Reliability Engineering & Chaos Engineering

Now we move into one of the most important parts of becoming an **AI Reliability Engineer**:

> **Don't just design the happy path. Prove what happens when every important dependency fails.**

For a normal web application:

```text
request
  ↓
application
  ↓
database
```

For our AI platform:

```text
                         Request
                            │
                            ▼
                         Gateway
                            │
                            ▼
                          llm-d
                            │
                ┌───────────┴───────────┐
                ▼                       ▼
             Prefill                 Decode
                │                       │
                └───────────┬───────────┘
                            │
                           vLLM
                            │
                           GPU
                            │
                    ┌───────┴───────┐
                    ▼               ▼
                  NIXL            EFA
                    │               │
                    └───────┬───────┘
                            │
                         Kubernetes
                            │
                         EC2/AZ
```

Every layer can fail.

# 1. Reliability starts with failure domains

Before running chaos experiments, identify your failure domains:

```text
Application
    │
    ├── request
    ├── vLLM process
    └── model

Pod
    │
    └── vLLM pod

GPU
    │
    └── H100/H200

Node
    │
    └── EC2

Replica
    │
    └── TP group

AZ
    │
    └── multiple nodes

Region
    │
    └── entire platform
```

The key question is:

> **What is the smallest failure that causes the service to lose capacity?**

For TP8:

```text
8 GPUs
   │
   └── one logical replica
```

Potentially:

```text
1 GPU failure
     ↓
TP group failure
     ↓
8-GPU replica unavailable
```

That's a huge failure domain.

---

# 2. Reliability is about capacity after failure

Suppose:

```text
Normal:
4 replicas × 4 GPUs
=
16 GPUs
```

Peak demand requires:

```text
12 GPUs
```

So you have:

```text
4 GPUs headroom
```

One replica fails:

```text
16 → 12 GPUs
```

You can still meet demand.

That's:

> **N+1 capacity.**

---

# 3. N+1

If:

```text
N = capacity required for workload
```

then:

```text
N+1
```

means you can lose one failure unit and still operate.

But the failure unit matters.

For:

```text
TP4
```

N+1 means:

```text
one 4-GPU replica
```

For:

```text
TP8
```

N+1 means:

```text
one 8-GPU replica
```

So:

```text
TP8
```

can require much more spare capacity for the same availability objective.

---

# 4. Availability vs redundancy

Two replicas:

```text
id="h2r8sm"
Replica A
Replica B
```

is not automatically HA.

What if both are:

```text
same node
```

?

Then:

```text
node failure
 ↓
A + B gone
```

What if both are:

```text
same AZ
```

?

Then:

```text
AZ failure
 ↓
A + B gone
```

Therefore:

> **Redundancy is only useful if replicas are separated across the failure domain you care about.**

---

# 5. Topology

For a production deployment:

```text
                    Model replicas
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
           AZ-a                    AZ-b
             │                       │
       ┌─────┴─────┐           ┌─────┴─────┐
       ▼           ▼           ▼           ▼
    Replica A   Replica B   Replica C   Replica D
```

But there is an important conflict with distributed inference.

A TP group wants:

```text
tight GPU connectivity
```

while HA wants:

```text
failure-domain separation
```

You should not spread one tightly coupled TP group across AZs merely for theoretical HA.

Instead:

```text
TP group
  ↓
same tightly connected topology

replica groups
  ↓
different nodes/AZs
```

This is a recurring architectural tradeoff.

# 9. RTO

**Recovery Time Objective**

Means:

> How long can the service take to recover?

Example:

```text
failure:
10:00:00

service recovered:
10:02:30
```

RTO:

```text
2m30s
```

But don't confuse:

```text
pod recreated
```

with:

```text
service recovered
```

The pod might be:

```text
Running
```

while:

```text
model loading
```

and therefore not actually serving.

# 10. Readiness is your reliability boundary

For vLLM:

```text
process started
    ↓
CUDA initialized
    ↓
model loaded
    ↓
weights loaded into HBM
    ↓
KV configured
    ↓
warmup
    ↓
API responding
    ↓
READY
```

Only after the final stage should traffic be routed.

Otherwise:

```text
EPP
 ↓
new pod
 ↓
model loading
 ↓
requests fail
```

---

# 11. Liveness vs readiness

### Liveness

> “Is the process alive?”

### Readiness

> “Can this instance safely receive production traffic?”

These are not the same.

Example:

```text
vLLM process:
alive = yes

model:
loading

readiness:
false
```

Correct.

# 12. Graceful shutdown

Now the opposite experiment.

Suppose:

```bash
kubectl delete pod <pod>
```

The pod disappears immediately.

Bad for streaming:

```text
client
  ↓
stream
  ↓
pod killed
  X
```

Better:

```text
SIGTERM
   ↓
stop accepting new requests
   ↓
finish/drain active requests where practical
   ↓
release resources
   ↓
terminate
```

You therefore need:

```yaml
terminationGracePeriodSeconds: 120
```

The exact value should come from your measured request duration distribution, not an arbitrary number.

---

# 13. PDB

A PodDisruptionBudget protects against too many **voluntary disruptions** happening simultaneously.

Conceptually:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: vllm
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: vllm
```

If you have:

```text
4 replicas
```

this means:

```text
at least 3
```

should remain available during supported voluntary disruption scenarios.

But:

> **PDB does not protect you from every failure.**

For example:

```text
node crash
AZ failure
GPU hardware failure
```

can bypass the protection that a voluntary-disruption mechanism provides.

---

# 14. PDB + topology

PDB alone:

```text
4 replicas
minAvailable = 3
```

doesn't guarantee:

```text
3 different nodes
3 different AZs
```

You need:

```text
PDB
+
topology spread
+
anti-affinity
```

---

# 15. Topology spread

Conceptually:

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: vllm
```

This encourages an even distribution across zones.

But for GPU workloads, topology constraints must be combined carefully with:

```text
GPU availability
TP requirements
node types
Karpenter
```

Otherwise you can create an impossible scheduling requirement.


# 23. EPP failure is different from vLLM failure

If:

```text
vLLM-1 fails
```

EPP can potentially route:

```text
vLLM-2
vLLM-3
vLLM-4
```

But if:

```text
EPP itself fails
```

the intelligence responsible for endpoint selection is affected.

Therefore EPP is a **control-plane dependency for inference routing**.

# 24. Failure #6 — NIXL failure

Our P/D architecture:

```text
Prefill
   │
   ▼
NIXL
   │
   ▼
EFA
   │
   ▼
Decode
```

Break the transfer path.

Possible outcomes:

### Fail closed

```text
request
 ↓
P/D transfer fails
 ↓
request fails/retries
```

### Recompute

```text
KV transfer fails
 ↓
decode recomputes
```

### Fallback to integrated serving

Potentially:

```text
P/D unavailable
 ↓
integrated vLLM pool
```

The right choice depends on your architecture and SLO.

Current llm-d disaggregation operations documentation explicitly discusses failure handling policies where KV transfer can fail and the system can either fail or recompute depending on configuration/workload. ([llm-d.ai](https://llm-d.ai/docs/operations/disaggregation?utm_source=chatgpt.com))

# 25. P/D failure is not necessarily a service failure

This is subtle.

Suppose:

```text
P/D:
NIXL transfer failed
```

But you can recompute:

```text

```

Then:

```text
availability = preserved
latency = degraded
```

So your SLO model should distinguish:

```text
hard failure
vs
performance degradation
```

This is exactly why AI SLOs should include latency.

# 31. Retry budget

A production gateway should constrain retries.

For example:

```text

```

and use:


Don't blindly retry every:


The retry behavior should depend on the failure.

# 32. 429 is sometimes healthy

This is a very important mindset.

Suppose capacity is exhausted.

You return:

```http
429 Too Many Requests
```

That may actually be the **correct reliability behavior**.

Compare:

### Option A

```text
accept everything
 ↓
queue explodes
 ↓
all users get 30-second latency
 ↓
timeouts
 ↓
retry storm
 ↓
outage
```

### Option B

```text
capacity exhausted
 ↓
reject excess low-priority traffic
 ↓
premium users remain healthy
```

Option B is often better.

> **Controlled rejection can be a reliability feature.**

# 35. Active-active vs active-passive

### Active-active

```text
Region A → 50%
Region B → 50%
```

Both serve traffic.

Advantages:

```text
capacity already warm
fast failover
```

Disadvantages:

```text
double operational complexity
data/model consistency
higher baseline cost
```

---

### Active-passive

```text
Region A → 100%
Region B → standby
```

Cheaper.

But failover requires:

```text
capacity activation
model loading
traffic shift
```

Potentially much higher RTO.

---

# 36. Model DR is different from database DR

For an AI inference service:

```text
Model
```

is often immutable.

You don't necessarily need:

```text
RPO = 0
```

for model weights.

You need:

```text
correct model artifact
available
quickly loadable
verified
```

But:

```text
conversation state
agent state
RAG data
tenant metadata
```

may have completely different RPO/RTO requirements.

So separate:

```text
model DR
data DR
application-state DR
KV cache DR
```

---

# 37. KV cache is generally disposable state

This is another important insight.

If:

```text
GPU dies
```

you usually lose:

```text
KV cache
```

But you can generally recompute it.

Therefore:

```text
KV cache
=
performance state
```

rather than:

```text
authoritative business state
```

This simplifies disaster recovery.

But P/D architectures can make KV transfer operationally important for latency, so losing KV can still cause significant performance degradation.
