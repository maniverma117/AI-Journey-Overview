Now we're connecting the three things we've learned:

```text

     +

     ↓

```

The architecture we're building is:

```text
                       Client
                          │
                          ▼
                    vLLM Service
                          │
                  ┌───────┴────────┐
                  │                │
               vLLM-1           vLLM-2
                  │                │
                  └───────┬────────┘
                          │

                          │
                          ▼
                    KEDA / HPA
                          │

                          │
                          ▼
```

This is **two-level autoscaling**.

---

# 1. The most important concept

KEDA/HPA and Karpenter solve **different problems**.

### HPA/KEDA

Answers:

> **"How many inference replicas do I need?"**

### Karpenter

Answers:

> **"Where do I get the compute capacity for those replicas?"**

So:

```text
Traffic spike
     ↓
Need more vLLM replicas
     ↓
HPA/KEDA
     ↓
Pod created
     ↓
No GPU available
     ↓
Pod Pending
     ↓
Karpenter
     ↓
GPU node created
     ↓
Pod schedules
```

Do not confuse these layers.

---

# 2. Why normal HPA is insufficient

Traditional application:

```text
CPU ↑
  ↓
HPA
  ↓
replicas ↑
```

LLM inference:

```text
GPU utilization ↑
```

doesn't necessarily tell us whether users are suffering.

You might have:

```text
GPU = 95%
TTFT = 300ms
```

which may be healthy.

Or:

```text
GPU = 80%
queue = 100
TTFT = 8s
```

which is unhealthy.

AWS's current EKS inference guidance explicitly recommends combining inference signals such as queue depth, latency/TTFT, and KV utilization rather than relying on GPU utilization alone.

# 5. Scaling from capacity

Suppose traffic becomes:

```text
15,000 output tok/s
```

and:

```text
1 replica = 5,000 tok/s
```

Then:

```text
15,000 / 5,000
= 3 replicas
```

So the theoretical requirement is:

```text
3 replicas
```

But production needs headroom.

If we want 25% headroom:

```text
3 × 1.25
= 3.75
```

Round up:

```text
4 replicas
```

This is far better than:

> "Scale when GPU hits 70%."

# 7. Understand what KEDA actually does

KEDA is not itself your inference scheduler.

Conceptually:

```text id="zq3ycc"
vLLM metric
      ↓
KEDA
      ↓
HPA
      ↓
Deployment replicas
```

So:

```text
KEDA → HPA → vLLM Deployment
```

KEDA translates external/event-driven metrics into Kubernetes autoscaling behavior.

# 8. Start with a simple metric

For our first experiment, let's use **waiting requests**.

Conceptually:

```text id="a6w1am"
waiting requests > threshold
       ↓
scale out
```

For example:

```text
target = 5 waiting requests per replica
```

If:

```text
waiting = 20
```

then approximately:

```text
20 / 5 = 4 replicas
```

This isn't a universal formula; we're using it to understand the mechanics.

Don't simply query:


Instead, think about:

```promql

```

or:

```promql

```

or:

```promql

  ...
```

for latency.

Eventually a sophisticated production system might combine:

```text

+

+

+

```

into a scaling policy.

# 11. Simple KEDA object

Once Prometheus is available, the conceptual KEDA object looks like:

```yaml id="x4a1vb"
apiVersion: keda.sh/v1alpha1
kind: ScaledObject

metadata:
  name: vllm-scaler

spec:
  scaleTargetRef:
    name: vllm

  minReplicaCount: 1
  maxReplicaCount: 5

  triggers:
    - type: prometheus

      metadata:
        serverAddress: http://prometheus.monitoring.svc:9090

        query: |
          <YOUR_VLLM_WAITING_REQUEST_QUERY>

        threshold: "5"
```

**Do not paste this unchanged into your cluster yet.**

The Prometheus service name and actual vLLM metric must match your environment.

First discover:

```bash id="xbyy4t"
kubectl get svc -A | grep -i prometheus
```

and:

```bash id="9z7o0k"
curl -s http://localhost:8000/metrics | grep -i waiting
```

# 12. Why `minReplicaCount` matters

Suppose:

```yaml id="8cgjj7"
minReplicaCount: 1
```

Then quiet traffic:

```text
1 GPU
```

Peak traffic:

```text
1 → 2 → 3 → 4 → 5 GPUs
```

If:

```yaml id="d74k3p"
minReplicaCount: 0
```

you potentially get:

```text
quiet period
   ↓
zero replicas
   ↓
zero GPU capacity
```

This saves money.

But the next request has to trigger:

```text
scale
 ↓
GPU node
 ↓
image
 ↓
model
 ↓
warmup
 ↓
ready
```

which can cause a large cold-start latency.

For interactive LLMs, scale-to-zero is therefore a **cost vs latency** decision.

---

# 13. Warm capacity

A better strategy may be:

```text
minimum = 1
```

or:

```text
minimum = 2
```

So:

```text
traffic low

GPU-1 ✓ warm
GPU-2 ✓ warm

traffic spikes

GPU-3 → provision
GPU-4 → provision
```

The warm replicas absorb the initial spike while Karpenter catches up.

# 14. Now introduce Karpenter

HPA/KEDA may decide:

```text
replicas = 4
```

but suppose we only have:

```text
GPU node A
└── vLLM-1
```

Then:

```text
vLLM-2 → Pending
vLLM-3 → Pending
vLLM-4 → Pending
```

Karpenter sees unschedulable pods.

Then:

```text id="f1v8mt"
Pending Pods
     ↓
Karpenter
     ↓
NodeClaim
     ↓
EC2 GPU instance
     ↓
Node joins EKS
     ↓
GPU discovered
     ↓
Pods schedule
```

This is the second half of autoscaling.

# 15. Karpenter NodePool for GPU

Conceptually:

```yaml id="qj53jz"
apiVersion: karpenter.sh/v1
kind: NodePool

metadata:
  name: gpu

spec:
  template:
    spec:
      requirements:

        - key: karpenter.k8s.aws/instance-gpu-name
          operator: In
          values:
            - h100

        - key: kubernetes.io/os
          operator: In
          values:
            - linux

      taints:
        - key: nvidia.com/gpu
          effect: NoSchedule
```

The exact requirements should match the instance types and labels available in your cluster.

Karpenter's current NodePool API is documented here. [Karpenter NodePools](https://karpenter.sh/docs/concepts/nodepools/?utm_source=chatgpt.com)

---

# 16. Don't forget the toleration

If the GPU NodePool has:

```text id="fdj0n4"
nvidia.com/gpu:NoSchedule
```

your vLLM pod needs:

```yaml id="tddkqg"
tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule
```

Otherwise:

```text
Karpenter creates GPU node
       ↓
vLLM pod still can't schedule
       ↓
Pending
```

That's a very realistic failure.

# 18. Measure scale-up latency

This is one of your most important AIRE metrics.

Define:

```text
T0 = traffic spike
T1 = KEDA/HPA decides to scale
T2 = pod becomes Pending
T3 = Karpenter creates node
T4 = node Ready
T5 = GPU available
T6 = container starts
T7 = model loaded
T8 = vLLM Ready
T9 = traffic successfully served
```

Your real scale-up latency is:

```text
T9 - T0
```

Not:

```text
HPA decision time
```

That's a huge distinction.

---

# 19. Example

Suppose:

```text id="1b8xg3"
Traffic spike       = 10:00:00
HPA scale decision   = 10:00:15
Karpenter node       = 10:00:35
Node Ready           = 10:00:50
Pod starts           = 10:00:55
Model loaded         = 10:01:30
Ready                = 10:01:35
```

Then:

```text id="9kqv1n"
scale-up latency
= 95 seconds
```

If your traffic spike lasts only:

```text
60 seconds
```

autoscaling won't save you.

You needed:

```text
warm capacity
```

or:

```text
predictive scaling
```

or:

```text
faster model startup
```

---

# 20. This is where capacity planning meets autoscaling

Suppose:

```text id="z4h9e8"
baseline = 2 GPUs
peak = 8 GPUs
scale-up time = 90 sec
```

If traffic can increase 5× in:

```text
20 seconds
```

then reactive autoscaling is too slow.

Your architecture might need:

```text id="svk9d4"
2 warm GPUs
+
2 warm buffer GPUs
+
Karpenter reactive capacity
```

Now:

```text
traffic spike
   ↓
buffer absorbs immediately
   ↓
Karpenter provisions additional GPUs
   ↓
system catches up
```

This is **headroom engineering**.

---

# 21. Scale-down is equally important

Suppose we reached:

```text id="1vqvzs"
8 GPUs
```

then traffic falls.

We don't want:

```text id="0klv7v"
8 expensive GPUs
running forever
```

So:

```text
traffic ↓
    ↓
HPA replicas ↓
    ↓
pods terminate
    ↓
GPU nodes become underutilized
    ↓
Karpenter consolidation
    ↓
nodes removed
```

Karpenter's current disruption/consolidation mechanisms include configurable consolidation behavior and disruption budgets. [Karpenter disruption documentation](https://karpenter.sh/docs/concepts/disruption/?utm_source=chatgpt.com)

---

# 22. But scale-down can hurt LLMs

Suppose a GPU is:

```text
95% idle
```

Karpenter thinks:

> "Remove it."

But that GPU contains:

```text
model weights
+
warm KV/cache state
```

Removing it means:

```text
model unloaded
```

Next spike:

```text
new GPU
 ↓
model download/load
 ↓
warmup
```

So aggressive consolidation can cause:

```text
cost ↓
but
cold starts ↑
```

Again:

> **Optimization requires an SLO.**

---

# 23. Protect important GPU pods

You may use mechanisms such as:

```text
PodDisruptionBudget
```

and Karpenter disruption controls such as:

```text
karpenter.sh/do-not-disrupt
```

where appropriate.

But don't simply mark every GPU workload:

```text
do-not-disrupt = true
```

because then you can destroy your ability to consolidate unused capacity.

The question is:

> Which capacity is worth keeping warm?

# 25. One critical problem: oscillation

Suppose:

```text
queue > 5
```

causes scale-up.

Then:

```text
queue < 5
```

causes scale-down.

Traffic fluctuates:

```text
5.1
4.9
5.2
4.8
5.1
```

You can get:

```text
scale up
scale down
scale up
scale down
```

This is **flapping**.

Use:

```text
cooldown
+
stabilization
+
hysteresis
+
appropriate scale-down delay
```

Kubernetes HPA supports configurable scale-up/scale-down behavior and stabilization windows. [Kubernetes HPA documentation](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/?utm_source=chatgpt.com)

---

# 26. Example hysteresis

Instead of:

```text
scale up at 5
scale down at 5
```

use:

```text
scale up:
queue > 10

scale down:
queue < 2
```

Now the system has a deadband:

```text
queue
 │
10 ───────── scale up
 │
 │
 │      stable
 │
2  ───────── scale down
```

This reduces oscillation.

# 27. One more important issue: multi-GPU vLLM

Suppose your model uses:

```text
TP = 4
```

and each replica requires:

```text
4 GPUs
```

Now:

```text
HPA replicas = 1
```

means:

```text
4 GPUs
```

and:

```text
HPA replicas = 2
```

means:

```text
8 GPUs
```

You cannot think:

```text
"Scale from 1 GPU to 2 GPUs."
```

The unit of scaling is:

```text
TP replica
```

So:

```text
1 replica = TP group = 4 GPUs
```

This is extremely important for capacity planning.
