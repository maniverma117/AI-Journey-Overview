# Lab 1X — Advanced AI Gateway, Quotas & Traffic Engineering

This lab is about the **front door of the AI platform**.

We already know how to run:

```text
vLLM
llm-d
GPU
Karpenter
NIXL
EFA
```

But none of that matters if the platform accepts unlimited traffic.

A production AI platform must control:

```text
who can call
what they can call
how much they can consume
how fast they can consume it
what happens during overload
what happens during failure
```

---

# 2. Why normal HTTP rate limiting isn't enough

Traditional API:

```text
100 requests/sec
```

can be reasonable.

But LLM requests might be:

```text
Request A = 100 tokens
Request B = 100,000 tokens
```

Both are:

```text
1 request
```

yet their resource consumption is dramatically different.

Therefore:

> **LLM traffic must often be controlled by tokens as well as requests.**

---

# 3. Four dimensions of AI traffic control

Think:

```text
                  TRAFFIC CONTROL
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
     Request            Token           Concurrency
      rate               rate
       │                 │                 │
       └─────────────────┼─────────────────┘
                         ▼
                      Priority
```

For example:

```text
Tenant A:
20 RPS
100K input tok/s
20K output tok/s
50 concurrent
```

That's much more meaningful than simply:

```text
20 RPS
```

---

# 4. Request rate limiting

The simplest:

```text
Tenant A
 ↓
100 requests/min
```

If request 101 arrives:

```text
429 Too Many Requests
```

Useful for:

```text
abuse prevention
basic quotas
API protection
```

But insufficient for AI capacity management.

---

# 5. Token rate limiting

Instead:

```text
Tenant A
 ↓
100,000 input tokens/sec
 ↓
20,000 output tokens/sec
```

This aligns more closely with:

```text
GPU compute
KV
memory
cost
```

---

# 6. Why input and output should be separated

Input tokens primarily drive:

```text
Prefill
```

Output tokens primarily drive:

```text
Decode
```

And we already know:

```text
Prefill ≠ Decode
```

So potentially:

```text
Input token budget
→ protect prefill capacity

Output token budget
→ protect decode capacity
```

This becomes particularly powerful with P/D.

---

# 7. Token bucket

A common rate-limiting algorithm is the **token bucket**.

Imagine:

```text
Bucket
capacity = 100 tokens

refill = 10 tokens/sec
```

Request costs:

```text
20 tokens
```

Bucket:

```text
100 → 80
```

Another:

```text
30
```

becomes:

```text
80 → 50
```

When empty:

```text
request
 ↓
wait or reject
```

---

# 8. Why token bucket works well for AI

LLM traffic is bursty.

Suppose:

```text
normal = 10 RPS
burst = 30 RPS
```

You don't necessarily want to reject every burst.

Token bucket allows:

```text
steady refill
+
controlled burst
```

while preventing unlimited traffic.

---

# 9. But what should one token mean?

This is subtle.

A request with:

```text
10 input tokens
```

should not necessarily cost exactly:

```text
10 quota units
```

while output:

```text
10 tokens
```

may consume different GPU resources.

You can define weighted units:

```text
cost units
=
input tokens × input weight
+
output tokens × output weight
```

For example:

```text
1 input token = 1 unit
1 output token = 2 units
```

This is only an example.

The weights should come from benchmarked resource consumption.

---

# 10. Predictive admission control

Suppose a request arrives:

```text
input = 50K tokens
max_output = 8K
```

Before accepting it, estimate:

```text
expected resource demand
```

Then ask:

```text
Can the platform safely admit this request?
```

This is better than:

```text
accept everything
 ↓
discover overload later
```

# 12. Concurrency limiting

Suppose:

```text
Tenant A
max concurrent = 100
```

Current:

```text
99
```

New request:

```text
100 → accepted
```

Next:

```text
101 → queue/reject
```

This protects:

```text
GPU

scheduler
```

from uncontrolled active sequences.

---

# 13. Why concurrency is especially dangerous for LLMs

Suppose each request consumes:

```text
1GB KV
```

and you allow:

```text
100 concurrent
```

Potentially:

```text
100GB KV
```

Now:

```text
200 concurrent
```

could require:

```text
200GB
```

This can turn into:

```text
KV pressure
 ↓
preemption
 ↓
queue
 ↓
latency
 ↓
OOM
```

So concurrency limits are also memory protection.

---

# 14. Per-model concurrency

Don't necessarily use:

```text
global concurrency = 1000
```

Instead:

```text
Model A:
100

Model B:
500

Model C:
1000
```

because models have different:

```text
GPU requirements
KV footprint
latency
```

---

# 15. Per-tenant + per-model limits

Even better:

```text
Tenant A
 ├── Model A → 50 concurrent
 ├── Model B → 100 concurrent
 └── Model C → 200 concurrent
```

This prevents one tenant from exhausting a specific model fleet.

# 16. Priority

Imagine:

```text
P0 = critical customer
P1 = standard customer
P2 = internal
P3 = batch
```

Under normal conditions:

```text
all accepted
```

Under overload:

```text
P0
 ↓
P1
 ↓
P2
 ↓
P3
```

This is admission control based on business priority.

---

# 17. Weighted fairness

Pure priority can starve lower classes.

Suppose:

```text
P0 = 100% traffic
```

Then:

```text
P3
```

may never execute.

Instead you can define:

```text
P0 → 60%
P1 → 25%
P2 → 10%
P3 → 5%
```

during contention.

This gives:

> **Weighted fairness.**

# 18. Queue architecture

A simple architecture:

```text
                  Gateway
                     │
           ┌─────────┼─────────┐
           ▼         ▼         ▼
         P0 Queue  P1 Queue  P2 Queue

                     ▼

```

Now the platform controls who gets GPU time.

---

# 19. Queue is not free

A common mistake:

> "If the GPU is full, just queue everything."

No.

Queue growth causes:

```text
queue
 ↓
TTFT
 ↓
user timeout
 ↓
client retry
 ↓
more traffic
 ↓
larger queue
```

Potentially creating a positive feedback loop.

---

# 20. Queue limits

Instead:

```text
max queue = 1000
```

Once reached:

```text
new request
 ↓
429 / overload
```

This is:

> **Load shedding.**

---

# 21. Load shedding

Under severe overload:

```text
normal:
accept

moderate:
queue

high:
reject low priority

critical:
protect P0 only
```

Example:

```text
P0 → accept
P1 → queue
P2 → reject
P3 → reject
```

This keeps the platform alive.

# 23. Circuit breaker

Suppose:

```text
Model A
```

is failing.

Without a circuit breaker:

```text
request
 ↓
Model A
 ↓
failure
 ↓
retry
 ↓
Model A
 ↓
failure
```

Thousands of times.

Instead:

```text
Model A
 ↓
failure threshold reached
 ↓
OPEN
 ↓
stop sending traffic
```

Then periodically:

```text
half-open
 ↓
test
 ↓
healthy?
```

If healthy:

```text
CLOSED
```

# 25. Retry policy

Retries are dangerous in AI.

Suppose:

```text
1 request
```

fails.

Client retries:

```text
2 requests
```

Then gateway:

```text
retry
```

Now:

```text
4
```

Then:

```text
8
```

You can create:

> **Retry amplification.**

---

# 26. Retry budget

Define:

```text
retry budget
```

For example:

```text
at most 5% additional traffic
```

from retries.

Or:

```text
one retry
```

for specific failure classes.

Never:

```text
retry forever
```

---

# 27. Retry only appropriate failures

Good retry candidates may include transient infrastructure errors:

```text
connection reset
temporary unavailable
```

Bad retry candidates:

```text
invalid request
authorization failure
quota exceeded
context too large
policy violation
```

Retrying those only creates noise.

# 28. Streaming cancellation

This is often overlooked.

User starts:

```text
large generation
```

then closes the browser.

If the platform doesn't cancel the inference:

```text

       │
       ▼
vLLM continues generating
       │
       ▼
GPU consumed
       │
       ▼
tokens discarded
```

That's wasted:

```text
GPU
KV
cost
```

So:

> **Client disconnect → propagate cancellation whenever possible.**

---

# 29. Cancellation is a FinOps feature

Suppose:

```text

```

cancel after:

```text

```

instead of generating:

```text

```

That's a huge savings.

Therefore:

```text

```

belongs in:

```text

```

# 30. Deadline propagation

Client:

```text
timeout = 5 seconds
```

The backend should understand that deadline.

Don't allow:

```text
Gateway timeout = 5s
vLLM continues = 60s
```

because the user has already abandoned the request.

Better:

```text
Client deadline
 ↓
Gateway
 ↓
router
 ↓
model server
```

Each layer respects the remaining budget.

---

# 31. Timeout budget

Suppose:

```text
total deadline = 2s
```

You might conceptually allocate:

```text
Gateway = 50ms
Routing = 20ms
Queue = 300ms
Prefill = 700ms
KV transfer = 100ms
Decode startup = 100ms
remaining = buffer
```

If queue already consumes:

```text
1.8s
```

don't send the request to a model that will definitely miss the deadline.

This is:

> **Deadline-aware admission.**

# 57. AIRE interview question

### "Why not simply increase Karpenter capacity when traffic spikes?"

Excellent answer:

> "Because GPU provisioning has significant startup latency, while LLM traffic can spike much faster. Also, accepting unlimited work while waiting for GPUs causes queue growth, KV pressure and latency collapse. We need admission control, bounded queues, load shedding and warm capacity in addition to autoscaling."

---

# 58. Another interview question

### "Why are token quotas better than request quotas?"

Answer:

> "LLM requests have highly variable computational and memory cost. One request could contain 100 tokens while another contains 100,000. Token-based quotas correlate more closely with GPU compute, prefill work, KV consumption and cost."

---

# 59. Another

### "What happens if clients retry every 500ms?"

Answer:

> "We can create retry amplification and overload the already-degraded backend. I would use bounded retry budgets, exponential backoff with jitter, Retry-After, server-side load shedding and circuit breakers, and avoid retrying deterministic failures such as authorization, quota or invalid-request errors."

---

# 60. Another

### "Why should the gateway know about tokens?"

Answer:

> "Because token volume is a better approximation of inference resource consumption than request count. Token-aware admission lets us protect prefill and decode capacity, enforce fair tenant usage and improve cost attribution."
