# Level 2 — Lesson 11 Multi-GPU Inference: TP vs PP vs DP vs EP — Extreme Deep Dive

This is a **major milestone**.

Up to now, we have mostly thought:

```text
Request
   ↓
vLLM
   ↓
ONE GPU
   ↓
Response
```

Production AI infrastructure quickly becomes:

```text
                    ┌──────────────┐
                    │   Requests   │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │    Router    │
                    └──────┬───────┘
                           ↓
                 ┌─────────┴─────────┐
                 ↓                   ↓
             GPU group A         GPU group B
                 │                   │
             ┌───┴───┐           ┌───┴───┐
             │ GPU   │           │ GPU   │
             │ GPU   │           │ GPU   │
             │ GPU   │           │ GPU   │
             │ GPU   │           │ GPU   │
             └───────┘           └───────┘
```

And inside each model replica, the model itself may be distributed across GPUs.

This lesson is about **how and why**.

---

# 1. The four major parallelism strategies

For inference, remember these four:

```text
TP = Tensor Parallelism
PP = Pipeline Parallelism
DP = Data Parallelism
EP = Expert Parallelism
```

Their basic purpose:

| Strategy | What gets split?                   | Main purpose                     |
| -------- | ---------------------------------- | -------------------------------- |
| TP       | Model tensors/layers' computations | Make one model use multiple GPUs |
| PP       | Transformer layers                 | Spread model across stages       |
| DP       | Model replicas / requests          | Increase serving throughput      |
| EP       | MoE experts                        | Distribute experts across GPUs   |

The critical distinction:

> **TP/PP help one model execution span GPUs. DP creates independent serving capacity. EP is specialized for MoE models.**

Current vLLM supports TP and PP for distributed inference/serving, and its current configuration also supports DP, EP and newer context-parallel mechanisms. ([vLLM][1])

---

# 2. First principle: parallelism solves different problems

Suppose you have:

```text
70B model
```

and:

```text
1 × H100 80GB
```

The model may not fit.

You could use:

```text
TP=2
```

Now:

```text
GPU 0 → part of model
GPU 1 → part of model
```

This solves:

> **model memory capacity**

But suppose the model already fits on one GPU.

Now customer says:

```text
1000 concurrent users
```

You don't necessarily want:

```text
TP=8
```

You may want:

```text
8 independent replicas
```

That's DP-style scaling.

So:

```text
Model doesn't fit
        ↓
TP / PP

Model fits but throughput insufficient
        ↓
DP / replicas
```

This distinction will save you from many bad architecture decisions.

# 3. Tensor Parallelism — the deepest concept first

Let's start with a Transformer layer.

Simplified:

```text
X
│
├── Q projection
├── K projection
├── V projection
│
▼
Attention
│
▼
Output projection
│
▼
MLP
│
▼
Next layer
```

A huge amount of this computation is matrix multiplication.

For example:

```text
Y = XW
```

Suppose:

```text
W = huge matrix
```

Instead of storing the entire matrix on one GPU:

```text
             W
┌──────────────────────────────┐
│                              │
│         Entire matrix        │
│                              │
└──────────────────────────────┘
             │
             ▼
          GPU 0
```

we partition it:

```text
                    W
       ┌────────────┬────────────┐
       │            │            │
       ▼            ▼            ▼
     W0             W1           W2
     GPU0           GPU1         GPU2
```

Each GPU performs part of the computation.

That's the fundamental idea behind TP.

---

# 4. Why TP requires communication

Here's the part people often miss.

Suppose:

```text
GPU0 computes part A
GPU1 computes part B
GPU2 computes part C
GPU3 computes part D
```

Eventually the model needs the combined result.

Therefore:

```text
GPU0 ─────┐
GPU1 ─────┤
GPU2 ─────┼──► communication ──► combined result
GPU3 ─────┘
```

This is where **NCCL** becomes critical.

NCCL is NVIDIA's topology-aware collective communication library for multi-GPU communication. It provides operations including AllReduce, AllGather, ReduceScatter and AlltoAll. ([NVIDIA Docs][2])

---

# 5. AllReduce

Let's make this concrete.

Suppose:

```text
GPU0 = [1, 2]
GPU1 = [3, 4]
GPU2 = [5, 6]
GPU3 = [7, 8]
```

AllReduce SUM gives every GPU:

```text
[16, 20]
```

because:

```text
1 + 3 + 5 + 7 = 16
2 + 4 + 6 + 8 = 20
```

So:

```text
GPU0 ─┐
GPU1 ─┤
GPU2 ─┼──► SUM ──► [16,20]
GPU3 ─┘

then every GPU receives [16,20]
```

That's exactly what NCCL AllReduce means: reduce values across ranks and make the result available on every rank. ([NVIDIA Docs][3])

---

# 6. AllGather

Suppose:

```text
GPU0 = A
GPU1 = B
GPU2 = C
GPU3 = D
```

AllGather produces:

```text
[A,B,C,D]
```

on every GPU.

Conceptually:

```text
GPU0 ── A ─────┐
GPU1 ── B ─────┤
GPU2 ── C ─────┼──► everyone gets [A,B,C,D]
GPU3 ── D ─────┘
```

NCCL defines AllGather as gathering data from all ranks and distributing the concatenated result to every rank. ([NVIDIA Docs][3])

---

# 7. ReduceScatter

Now reverse the idea.

Suppose:

```text
GPU0 = [A1,A2]
GPU1 = [B1,B2]
GPU2 = [C1,C2]
GPU3 = [D1,D2]
```

ReduceScatter might produce:

```text
GPU0 → A1+B1+C1+D1
GPU1 → A2+B2+C2+D2
```

So instead of everyone getting everything:

```text
reduce
+
scatter
```

NCCL provides ReduceScatter directly. ([NVIDIA Docs][3])

# 9. Why NVLink matters

Imagine TP=8.

If GPUs communicate through a high-bandwidth GPU interconnect:

```text
GPU0 ⇄ GPU1
GPU1 ⇄ GPU2
GPU2 ⇄ GPU3
...
```

communication can be much faster than sending traffic through slower host/network paths.

This is why an 8-GPU server with strong GPU-to-GPU connectivity can be dramatically more suitable for TP than eight GPUs spread arbitrarily across machines.

The architecture matters.

Consider:

### Architecture A

```text
1 node

GPU0
GPU1
GPU2
GPU3
GPU4
GPU5
GPU6
GPU7
```

with high-speed GPU interconnect.

Very attractive for:

```text
TP=8
```

---

### Architecture B

```text
Node A:
GPU0 GPU1 GPU2 GPU3

        network

Node B:
GPU4 GPU5 GPU6 GPU7
```

Now some TP communication crosses the network.

You potentially have:

```text

   ↓
```

# 11. This gives us a major rule

> **Keep tightly communicating TP groups within the strongest available GPU interconnect domain whenever possible.**

That is why vLLM's current multi-node guidance commonly uses:

```text
TP = GPUs per node
PP = number of nodes
```

For example:

```text
2 nodes
8 GPUs/node
```

can be:

```text
TP=8
PP=2
```

rather than:

```text
TP=16
PP=1
```

because the latter makes the TP group span nodes. vLLM documents this as a common multi-node configuration. ([vLLM][1])

# 12. Pipeline Parallelism

Now we approach the model differently.

Suppose:

```text
80 Transformer layers
```

Instead of splitting individual matrix operations across GPUs, split layers:

```text
GPU0:
Layer 1–20

GPU1:
Layer 21–40

GPU2:
Layer 41–60

GPU3:
Layer 61–80
```

That's:

```text
PP=4
```

Conceptually:

```text
Input
  │
  ▼
┌────────────┐
│ GPU0       │
│ Layers 1-20│
└─────┬──────┘
      │ activations
      ▼
┌─────────────┐
│ GPU1        │
│ Layers21-40 │
└─────┬───────┘
      │
      ▼
┌─────────────┐
│ GPU2        │
│ Layers41-60 │
└─────┬───────┘
      │
      ▼
┌─────────────┐
│ GPU3        │
│ Layers61-80 │
└─────────────┘
      │
      ▼
    Output
```

Current vLLM describes PP as distributing model layers across GPUs and allows PP and TP to be combined. ([vLLM][1])

---

# 13. TP vs PP

This is one of your interview questions.

### Tensor Parallelism

Splits:

```text
individual layer computation
```

across GPUs.

Communication:

```text
frequent
```

---

### Pipeline Parallelism

Splits:

```text
layers
```

across stages.

Communication:

```text
activation transfer between stages
```

So:

```text
TP:
Layer
 ├── GPU0
 ├── GPU1
 ├── GPU2
 └── GPU3

PP:
GPU0 → Layers 1-20
GPU1 → Layers 21-40
GPU2 → Layers 41-60
GPU3 → Layers 61-80
```

---

# 14. Pipeline bubbles

PP introduces an important problem:

> **pipeline bubbles**

Imagine:

```text
Time →

GPU0: █████████████
GPU1:     █████████
GPU2:         ███████
GPU3:             █████
```

At the beginning:

```text
GPU0 is working
GPU1 waiting
GPU2 waiting
GPU3 waiting
```

That's wasted capacity.

At the end:

```text
GPU0 finished
GPU1 finished
GPU2 finishing
GPU3 still working
```

Again, some GPUs are idle.

This is called a **pipeline bubble**.

# 15. Why microbatching helps

Instead of:

```text
Request
   ↓
Stage 0
   ↓
Stage 1
   ↓
Stage 2
   ↓
Stage 3
```

you can process multiple microbatches:

```text
Microbatch A
Microbatch B
Microbatch C
Microbatch D
```

so:

```text
Time →
GPU0: A B C D
GPU1:   A B C D
GPU2:     A B C D
GPU3:       A B C D
```

Now the pipeline is more continuously occupied.

This is one reason PP becomes more useful for high-throughput workloads.

# 16. Why PP can be useful across nodes

Suppose:

```text
Node A
8 GPUs

Node B
8 GPUs
```

You have:

```text
16 GPUs
```

You could technically:

```text
TP=16
```

but then TP communication can span the network.

Alternative:

```text
TP=8
PP=2
```

means:

```text
Node A
TP group of 8
      ↓
activation transfer
      ↓
Node B
TP group of 8
```

Now the high-frequency TP communication remains inside each node.

That is often a much more attractive topology.

# 17. Data Parallelism

Now completely change the mental model.

Instead of:

```text
one model
spread across GPUs
```

we have:

```text
Replica A → GPUs 0-3
Replica B → GPUs 4-7
```

Each replica has the model.

```text
             Router
             /    \
            /      \
           ▼        ▼
      Replica A   Replica B
       TP=4        TP=4
      GPU0-3      GPU4-7
```

Requests can be distributed independently.

That's DP.

Current vLLM describes data parallel deployment as replicating model weights across separate GPU groups to process independent batches. ([vLLM][4])

---

# 18. Why DP is so powerful for serving

Suppose:

```text
One TP=4 replica:
1,000 tok/s
```

You have 8 GPUs.

Option A:

```text
TP=8
```

Maybe:

```text
1,600 tok/s
```

Option B:

```text
2 × TP=4
```

Maybe:

```text
2 × 1,000
= 2,000 tok/s
```

Now DP wins.

Why?

Because you're reducing:

```text
cross-GPU synchronization
```

and increasing:

```text
independent request processing
```

This is why:

> **The fastest way to use more GPUs is not necessarily to make one model replica bigger.**

---

# 19. DP is not free either

Each replica needs:

```text
model weights
+
KV cache
+
runtime memory
```

So:

```text
1 × TP8
```

may use:

```text
one model copy
```

while:

```text
2 × TP4
```

uses:

```text
two model copies
```

Memory cost changes.

Therefore:

```text
TP vs DP
```

is a resource allocation problem.

---

# 20. The fundamental TP vs DP tradeoff

Think:

```text
             Need more model capacity?
                      │
                     YES
                      │
                      ▼
                     TP/PP
```

versus:

```text
             Model already fits?
                      │
                     YES
                      │
                      ▼
             Need more throughput?
                      │
                     YES
                      │
                      ▼
                     DP
```

But production architecture is more nuanced.

You often combine them:

```text
DP × TP
```

# 21. Example: DP=4, TP=2

You have:

```text
8 GPUs
```

Configure:

```text
DP=4
TP=2
```

Conceptually:

```text
Replica 1:
GPU0 GPU1

Replica 2:
GPU2 GPU3

Replica 3:
GPU4 GPU5

Replica 4:
GPU6 GPU7
```

Each replica has:

```text
TP=2
```

and four independent request-processing groups.

Current vLLM supports configurations such as:

```bash
vllm serve MODEL \
  --data-parallel-size 4 \
  --tensor-parallel-size 2
```

which requires 8 GPUs. ([vLLM][4])

# 22. The subtle KV-cache consequence

This is extremely important.

Suppose:

```text
DP=4
```

You have:

```text
Replica A KV cache
Replica B KV cache
Replica C KV cache
Replica D KV cache
```

They are independent.

That means if:

```text
Request 1
```

gets routed to A:

```text
prefix cache = HIT
```

but the same request later gets routed to B:

```text
prefix cache = MISS
```

Potentially.

Current vLLM documentation explicitly notes that each DP engine has an independent KV cache and that intelligent routing can improve prefix-cache benefits. ([vLLM][4])

This is the beginning of:

# **cache-aware routing**

which we'll later encounter in llm-d.

---

# 23. Why a simple round-robin load balancer isn't always optimal

Imagine:

```text
Replica A:
KV = 90%
Queue = 30

Replica B:
KV = 30%
Queue = 2
```

A basic load balancer:

```text
request
   ↓
round robin
   ↓
A
```

is stupid from an inference perspective.

A smarter router considers:

```text
queue
+
KV availability
+
prefix cache
+
request length
+
model replica state
```

and chooses:

```text
B
```

This is one of the major differences between:

```text
ordinary web load balancing
```

and:

```text
LLM inference routing
```

# 24. Expert Parallelism

Now we enter MoE.

Consider a Mixture-of-Experts model.

Instead of:

```text
one giant MLP
```

you might have:

```text
Expert 1
Expert 2
Expert 3
...
Expert 64
```

A router selects a small subset:

```text
token
 ↓
router
 ↓
Expert 7
Expert 23
```

So although the model may contain enormous total parameters, each token only activates a subset.

---

# 25. EP distributes experts

Imagine:

```text
GPU0:
Expert 0-7

GPU1:
Expert 8-15

GPU2:
Expert 16-23

GPU3:
Expert 24-31
...
```

Now token routing becomes:

```text
Token
  │
  ▼
Router
  │
  ├────► GPU0 expert
  ├────► GPU3 expert
  └────► GPU7 expert
```

This requires communication.

And this is where:

```text
AllToAll
```

becomes especially interesting.

NCCL's AlltoAll exchanges different data between every rank, with each rank sending data to and receiving data from every other rank. ([NVIDIA Docs][3])

---

# 26. Why MoE can be communication-heavy

Suppose:

```text
8 GPUs
```

and tokens route to different experts.

You might have:

```text
GPU0
 ├─ token → GPU3
 ├─ token → GPU5
 ├─ token → GPU7

GPU1
 ├─ token → GPU2
 ├─ token → GPU4
 ...
```

Now the network is busy moving token activations around.

So MoE performance depends on:

```text
expert computation
+
routing
+
AllToAll
+
GPU topology
```

This is one reason high-end AI systems care enormously about interconnect topology.

---

# 27. Current vLLM MoE architecture

Current vLLM supports data parallelism for both dense and MoE models, and for MoE workloads it can combine data parallelism with TP or expert parallelism. Its documentation describes `DP × TP` grouping and the `--enable-expert-parallel` option. ([vLLM][4])

This means modern inference architectures aren't always:

```text
TP OR DP
```

They can become:

```text
DP × TP × EP
```

and newer vLLM configurations also expose additional parallelism dimensions.

Very important.

If:


```text

=
```



# 33. Example architecture decision

Suppose:

```text
70B FP8
```

and benchmark results:

| Architecture | GPUs |    Output tok/s | P95 TTFT |
| ------------ | ---: | --------------: | -------: |
| TP1          |    1 |     Doesn't fit |        — |
| TP2          |    2 |             800 |    500ms |
| TP4          |    4 |           1,350 |    600ms |
| TP8          |    8 |           1,700 |    900ms |
| 2×TP4        |    8 | 2,400 aggregate |    700ms |

Customer SLO:

```text
P95 TTFT < 1 sec
```

Which architecture is better?

Probably:

```text
2 × TP4
```

because:

```text
aggregate throughput ↑
latency acceptable
```

even though a single TP8 replica has more raw model-parallel compute.

# 34. The hidden benefit of DP

Two replicas give you:

```text
failure isolation
```

If:

```text
Replica A dies
```

you still have:

```text
Replica B
```

Whereas a single TP8 replica has:

```text
one distributed failure domain
```

If one GPU fails:

```text
entire replica
```

may be unavailable.

This matters for:

```text
availability
fault isolation
rolling deployments
capacity
```

---

# 35. But DP has a cost

Two replicas means:

```text
2 × model weights
```

So if:

```text
model = 70GB
```

roughly:

```text
TP8:
one logical model distributed across 8 GPUs

2×TP4:
two model copies
```

You spend more memory on replicated weights.

Therefore the decision is:

```text
memory efficiency
       vs
throughput
       vs
latency
       vs
availability
```

That's an architecture decision.

# 36. Multi-node vLLM

Current vLLM supports multi-node deployment and documents both Ray and multiprocessing execution paths. For multi-node deployments, the environments should be consistent across nodes; vLLM recommends containerized environments to reduce host heterogeneity. ([vLLM][1])

Typical architecture:

```text
             Load Balancer
                    │
             vLLM endpoint
                    │
              Ray / workers
          ┌─────────┴─────────┐
          ▼                   ▼
       Node 0              Node 1
      8 × H100             8 × H100
       TP=8                 TP=8
          │                   │
          └─────────PP────────┘
```

For:

```text
16 GPUs
```

you might use:

```text
TP=8
PP=2
```

```text
        /      \             │
      YES       NO            │
       │         │            │
```

```text
TP4
GPU communication suddenly slows
```

Symptoms:

```text
GPU utilization weird
NCCL latency ↑
TTFT ↑
TPOT ↑
```

You shouldn't immediately blame vLLM.

Investigate:

```text
NVLink
PCIe
NIC
NCCL
topology
driver
GPU health
```

---

### Scenario C

```text
TP4 works
TP8 is slower
```

Possible reasons:

```text
more NCCL communication
worse topology
smaller per-GPU workload
synchronization overhead
```

---

### Scenario D

```text
TP4 = 1,300 tok/s
2×TP2 = 1,700 tok/s
```

Possible explanation:

```text
TP4 has more synchronization
2 independent replicas have better request-level parallelism
```

# 45. The most important lesson of today

If you remember only one thing:

> **More GPUs is not an architecture.**

The architecture is:

```text
MODEL
  ↓
MEMORY
  ↓
PARALLELISM
  ↓
TOPOLOGY
  ↓
COMMUNICATION
  ↓
SCHEDULING
  ↓
ROUTING
  ↓
CAPACITY
  ↓
SLO
  ↓
COST
  ↓
RELIABILITY
```

And the four core questions are:

```text
1. Does the model fit?
2. How fast can one replica serve?
3. How many independent replicas do I need?
4. How do I keep latency and availability within SLO under failure and burst traffic?
```

That is **AI infrastructure architecture**.
