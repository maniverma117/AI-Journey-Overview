---

# 1. First principle: Kubernetes does NOT run the model as one magical 16-GPU object

This is a very common misunderstanding.

You might imagine:

```text
Kubernetes Pod
   │
   ├── GPU0
   ├── GPU1
   ├── ...
   └── GPU15
```

across two nodes.

But a normal Kubernetes pod cannot span nodes.

A Pod belongs to **one node**.

So if we have:

```text
Node A
8 GPUs
```

and:

```text
Node B
8 GPUs
```

we need multiple processes/pods that collectively form one distributed workload.

Conceptually:

```text
              Distributed vLLM
                     │
          ┌──────────┴──────────┐
          │                     │
       Worker A              Worker B
          │                     │
       Node A                 Node B
          │                     │
       GPU × 8                GPU × 8
          │                     │
          └────── NCCL/EFA ────┘
```

The distributed framework coordinates them.

Kubernetes provides:

```text
placement
resources
networking
lifecycle
```

The distributed runtime provides:

```text
ranks
process groups
GPU communication
model partitioning
execution
```

This distinction is fundamental.

Think:

```text
Kubernetes

├── How many GPUs?

├── Which nodes?
├── Which topology?
├── Networking
├── Secrets/config

├── Health
```

But Kubernetes doesn't understand:

```text

AllReduce

```

That's vLLM/PyTorch/NCCL territory.

# 3. Distributed runtime responsibilities

The distributed runtime needs to establish:

```text
WORLD_SIZE
RANK
MASTER_ADDR
MASTER_PORT
```

Conceptually:

```text
WORLD_SIZE = 16

Node A:
  rank 0
  rank 1
  ...
  rank 7

Node B:
  rank 8
  rank 9
  ...
  rank 15
```

The exact process/rank arrangement depends on the launcher and vLLM configuration.

The important idea is:

> Every distributed process must agree on the same world.

---

# 4. What is a rank?

A **rank** is an identity for a process participating in distributed computation.

Imagine:

```text
WORLD_SIZE=4
```

Then:

```text
rank 0
rank 1
rank 2
rank 3
```

Every process knows:

```text
I am rank X
There are Y total participants
```

For example:

```text
Node A

GPU0 → rank 0
GPU1 → rank 1
GPU2 → rank 2
GPU3 → rank 3
```

and:

```text
Node B

GPU0 → rank 4
GPU1 → rank 5
GPU2 → rank 6
GPU3 → rank 7
```

for an 8-process distributed job.

---

# 5. Master address

The workers need a rendezvous point.

Conceptually:

```text
Node A
  │
  ├── master process
  │
  └── MASTER_ADDR
           │
           ▼
        Node B
```

For Kubernetes, this typically means providing a stable network identity such as:

```text
Service DNS
```

rather than relying on an ephemeral Pod IP.

For example:

```text
vllm-head.default.svc.cluster.local
```

could resolve to the coordinating endpoint.

---

# 6. Why Kubernetes Service matters

Pod IPs can change.

Suppose:

```text
vllm-head
Pod IP = 10.42.2.17
```

Pod dies:

```text
❌
```

New pod:

```text
10.42.7.31
```

If workers are hardcoded to:

```text
10.42.2.17
```

they're broken.

A Service gives you a stable DNS identity:

```text
vllm-head
    │
    ▼
Service
    │
    ▼
current Pod
```

This is standard Kubernetes service discovery, but becomes particularly important for distributed workloads.

# 7. Head/worker architecture

For learning, a useful conceptual model is:

```text
                  Service
                     │
                     ▼
                 Head Pod
                     │
          ┌──────────┴──────────┐
          │                     │
       Worker 1              Worker 2
          │                     │
        Node A                Node B
```

But don't confuse this with:

> "head = model server and worker = just GPU."

The exact process architecture depends on the distributed execution framework and vLLM deployment method.

The head is primarily about **coordination/control**, while workers execute distributed computation.

---

# 8. vLLM distributed execution

vLLM supports distributed execution using multiple GPUs and multiple nodes. Its current documentation describes tensor parallelism, pipeline parallelism and combinations of these for multi-node deployments.

For example:

```text
TP=8
PP=2
```

means:

```text
8-way tensor parallelism
×
2 pipeline stages
=
16 GPUs
```

So:

```text
8 × 2 = 16
```

---

# 9. Recommended topology

Suppose your hardware is:

```text
Node A
8 × H100

Node B
8 × H100
```

A sensible architecture to evaluate is:

```text
TP=8
PP=2
```

because:

```text
Node A
GPU0-7
  ↓
TP communication stays local

        ↓

Node B
GPU0-7
  ↓
TP communication stays local
```

The pipeline-stage communication crosses nodes.

This can be preferable to:

```text
TP=16
```

where tensor-parallel communication itself spans nodes.

But:

> **This is a benchmark hypothesis, not a universal rule.**

# 11. Why taints are useful

You don't want:

```text
frontend pod
backend pod
logging pod
random cronjob
```

accidentally consuming an expensive H100 node.

So:

```text
H100 nodes
   │
   └── taint
```

and only LLM workloads have:

```yaml
tolerations:
- key: accelerator
  operator: Equal
  value: h100
  effect: NoSchedule
```

Conceptually:

```text
Normal pod
    ↓
❌ H100

LLM pod
    ↓
✓ H100
```

# 12. GPU request

A GPU worker needs a GPU resource request.

For example:

```yaml
resources:
  requests:
    nvidia.com/gpu: 8
  limits:
    nvidia.com/gpu: 8
```

This means:

> "This Pod needs eight GPUs on one node."

Therefore the node must have at least:

```text
8 available GPUs
```

This is why:

```text
8 × H100/node
```

is particularly convenient for:

```text
TP=8
```

---

# 13. Very important: don't confuse replicas with workers

Suppose:

```yaml
replicas: 2
```

That does **not necessarily mean**:

```text
2 independent LLM replicas
```

If your distributed workload is modeled as a multi-pod distributed job, those pods may be workers belonging to **one distributed replica**.

This is why distributed inference deployment semantics must be understood before blindly putting a Deployment around it.

You need to distinguish:

```text
inference replicas
```

from:

```text
distributed worker processes
```

This distinction becomes critical for autoscaling.

### Architecture A

```text
2 independent replicas

Replica A
 ├── Node A
 └── 8 GPUs

Replica B
 ├── Node B
 └── 8 GPUs
```

Maybe:

```text
TP8 × 2 replicas
```

### Architecture B


# 15. Architecture A

Traffic can be:

```text
              Router
             /      \
            /        \
      Replica A    Replica B
```

If Node A fails:

```text
Replica A ❌
Replica B ✓
```

You retain capacity.

---

# 16. Architecture B

Traffic goes to:

```text
           Router
              │
       distributed replica
          /         \
      Node A       Node B
```

Node A fails:

```text
distributed replica ❌
```

The entire model serving unit may disappear.

This is a much larger failure domain.

---

# 17. This affects SLO design

Suppose your target is:

```text
99.99%
```

You cannot simply say:

> "Kubernetes restarts the Pod."

Because distributed model startup might involve:

```text
Pod scheduling
 ↓
GPU allocation
 ↓
container startup
 ↓
distributed rendezvous
 ↓
model loading
 ↓
CUDA initialization
 ↓
NCCL initialization
 ↓
weights
 ↓
KV cache
 ↓
warmup
 ↓
readiness
```

That can take a significant amount of time.

Therefore:

```text
Kubernetes restart
```

isn't equivalent to:

```text
service recovered
```




# 19. Why readiness protects the router

Suppose Node A is loading:

```text
70B model
```

and takes:

```text

```

If your Service/router immediately sends traffic:

```text

   ↓

   ↓

```

Bad.

Instead:

```text

   ↓
model loads
   ↓

   ↓

   ↓

```


```text

```

You have:



```text
H100

```

If Karpenter provisions:

```text

```

it doesn't solve the problem.


# 21. Example NodePool concept

A simplified conceptual NodePool:

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: h100-llm
spec:
  template:
    metadata:
      labels:
        accelerator: h100
        workload: llm
        network: efa

    spec:
      requirements:
      - key: kubernetes.io/arch
        operator: In
        values:
        - amd64

      - key: node.kubernetes.io/instance-type
        operator: In
        values:
        - p5.48xlarge

      taints:
      - key: accelerator
        value: h100
        effect: NoSchedule
```

The exact NodePool should be adapted to your EKS/Karpenter version and environment.

The architectural principle matters more:

```text
Pod requirements
        ↓
NodePool constraints
        ↓
EC2 instance
```

must agree.

# 31. One important AWS architectural rule

For tightly coupled distributed GPU workloads:

> **Prefer keeping the participating nodes in the same Availability Zone when the deployment requires low-latency/high-bandwidth communication.**

Why?

Because your traffic is:

```text
GPU
 ↓
EFA
 ↓
network
 ↓
GPU
```

You don't want to introduce unnecessary cross-AZ network characteristics into the critical path.

This also means your capacity planning must account for:

```text
GPU capacity per AZ
```

not merely:

```text
GPU capacity in region
```

# 32. AZ failure versus node failure

This is where Solution Architecture gets interesting.

### Node failure

```text
Node A ❌
Node B ✓
```

Potentially recoverable by another node.

### AZ failure

```text
AZ-A ❌
```

and your distributed group was:

```text
Node A + Node B
```

both inside AZ-A.

Now:

```text
entire distributed replica ❌
```

You need another replica in:

```text
AZ-B
```

But you generally **do not want to spread one tightly coupled TP group across AZs just to get HA**.

Instead:

```text
              Router
             /      \
            /        \
       Replica A    Replica B
         AZ-A         AZ-B
```

Each replica has its own tightly connected GPU topology.

This is the proper separation of:

```text
performance domain
```

and:

```text
failure domain
```

---

Think:

```text
Within replica
    ↓

    ↓

```

So:

```text

```

is primarily about:

```text
model execution
```


# 39. The interview question you should master

### "How would you deploy a 200B model across 16 H100 GPUs on EKS?"

A strong answer:

> "First I'd establish the model's weight and KV-cache memory requirements and benchmark whether TP8 on a single 8-GPU node is sufficient. If the model requires multiple nodes, I'd evaluate TP8×PP2 against TP16 based on communication overhead and scaling efficiency. I'd use dedicated EFA-enabled GPU NodePools, topology-aware placement, pinned GPU/CUDA/NCCL/vLLM images, and validate EFA/NCCL independently before introducing vLLM. I'd treat each distributed model group as a large failure domain and deploy independent replicas across AZs for HA rather than spreading a tightly coupled TP group across AZs. KEDA/HPA would scale complete inference replicas, while Karpenter provisions the required GPU nodes. Finally I'd benchmark TTFT, TPOT, throughput, NCCL bandwidth, KV capacity and recovery time against the customer's SLO."

That is now a **Solution Architect-level answer**, not simply a Kubernetes answer.
