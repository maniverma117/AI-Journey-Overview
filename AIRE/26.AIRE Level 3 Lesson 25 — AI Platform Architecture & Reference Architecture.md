# 11. Why llm-d matters

Suppose:

```text

KV = 90%

vLLM B:
KV = 40%

vLLM C:
KV = 65%
```

A normal round-robin router:

```text

```

doesn't understand inference state.

An inference-aware router can consider:

```text
KV
queue
prefix cache
active requests
latency
token load
```

and choose a better endpoint.

That's the fundamental reason for llm-d.

Current llm-d architecture defines the Router, InferencePool and model-server layers, with the Endpoint Picker responsible for inference-aware scheduling.

# 24. Multi-AZ vs multi-GPU topology

You can't arbitrarily spread a TP group across AZs.

For example:

```text

GPU1 → AZ-A
GPU2 → AZ-B
GPU3 → AZ-C
GPU4 → AZ-A
```

could be disastrous because communication crosses network boundaries.

Therefore:

> **Failure-domain placement and GPU communication topology must be designed together.**

A TP group should generally remain within an appropriate tightly connected failure domain.

# 47. RTO vs RPO

You should know these.

### RTO

```text
Recovery Time Objective
```

How quickly must the system recover?

Example:

```text
RTO = 5 minutes
```

### RPO

```text
Recovery Point Objective
```

How much data can we lose?

Example:

```text
RPO = 1 minute
```

For model artifacts:

```text
RPO ≈ near-zero
```

is often practical with versioned immutable artifacts.

For runtime KV cache:

```text
RPO
```

is different because KV can generally be recomputed.

is not necessarily a disaster if:

```text

```


# 49. P/D architecture

```text

            │             │
```

```text

```

```text

```

This gives independent scaling.

But only introduce it if the measured workload justifies the complexity.

# 52. Now let's attack the architecture 🔥

A good architect doesn't just design the happy path.

They ask:

> **What happens when things fail?**

---

## Failure 1 — GPU dies

```text
GPU failure
    ↓
vLLM replica unhealthy
    ↓
Readiness fails
    ↓
llm-d stops routing
    ↓
Kubernetes replaces pod
    ↓
Karpenter provides capacity if needed
    ↓
model loads
    ↓
warmup
    ↓
ready
```

---

# 53. Failure 2 — Entire node dies

```text
Node failure
    ↓
TP replica lost
    ↓
Pod unavailable
    ↓
llm-d reroutes
    ↓
Kubernetes schedules replacement
    ↓
Karpenter provisions GPU node
```

But:

```text
Does remaining capacity satisfy SLO?
```

That is the key question.

---

# 54. Failure 3 — AZ fails

```text
AZ-A failure
      ↓
multiple replicas lost
      ↓
traffic redirected
      ↓
AZ-B/AZ-C absorb traffic
```

But only if:

```text
surviving capacity >= required capacity
```

Otherwise:

```text
HA architecture exists
but SLO still fails
```

This is a common architecture mistake.

---

# 55. Failure 4 — Model rollout goes bad

```text
v2
 ↓
canary
 ↓
TTFT ↑
 ↓
SLO violation
 ↓
automatic rollback
 ↓
v1
```

No human should need to SSH into the GPU node.

---

# 56. Failure 5 — Karpenter can't provision

Suppose:

```text
H100 capacity unavailable
```

Then:

```text
Pending pod
   ↓
Karpenter
   ↓
no suitable capacity
```

Now you need architectural alternatives:

```text
H200
different AZ
different instance type
existing warm capacity
smaller model
degraded mode
queue
```

This is where customer requirements and infrastructure choices meet.

---

# 57. Failure 6 — KV cache exhaustion

```text
KV = 100%
      ↓
requests wait
      ↓
TTFT increases
      ↓
SLO breach
```

Potential responses:

```text
scale replica
reduce max context
improve prefix caching
change batching
increase GPU memory
KV offload
```

But each has different tradeoffs.

---

# 58. Failure 7 — RAG database unavailable

Don't let:

```text
Vector DB failure
```

turn into:

```text
entire platform failure
```

Depending on business requirements:

```text
RAG unavailable
      ↓
fallback:
LLM without retrieval
```

or:

```text
return controlled error
```

This is an application-level resilience decision.

---

# 59. Failure 8 — Tool API unavailable

Suppose:

```text
CRM API
```

is down.

The agent shouldn't repeatedly retry forever.

Use:

```text
timeout
retry budget
circuit breaker
fallback
```

and perhaps:

```text
"Unable to access CRM currently"
```

rather than hallucinating a successful action.

---

# 60. Failure 9 — malicious prompt

```text

       ↓

       ↓
Tool Gateway
       ↓

       ↓
DENY
       ↓

       ↓

```

The model may be compromised.

The platform remains safe.

That's the architecture we want.

# 61. Failure 10 — compromised tenant

Suppose Tenant A's API key is stolen.

Our architecture should allow:

```text

      ↓
block identity
      ↓

      ↓
stop tool access
      ↓

```

The blast radius should be limited.

That's:

> **Blast-radius engineering.**

# 62. Blast radius

This is an important SRE concept.

Bad:

```text
one IAM role
   ↓
everything
```

Bad:

```text
one namespace
   ↓
all tenants
```

Bad:

```text
one API key
   ↓
all tools
```

Better:

```text
Tenant
 │
 ├── identity
 ├── quotas
 ├── data access
 ├── tools
 └── audit
```

with bounded permissions.
