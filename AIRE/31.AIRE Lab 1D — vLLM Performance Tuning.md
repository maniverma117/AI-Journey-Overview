# Lab 1D — vLLM Performance Tuning

Now we're going to do what an **AI Reliability Engineer** actually does after getting vLLM running:

> **Find the configuration that maximizes useful throughput without violating latency, memory, or reliability SLOs.**

Don't change everything at once. We'll run controlled experiments.

---

## 1. Our optimization model

Think of vLLM as having three competing objectives:

```text
                         PERFORMANCE
                              │
             ┌────────────────┼────────────────┐
             │                │                │
             ▼                ▼                ▼
        Throughput         Latency          Memory
        tokens/sec         TTFT/TPOT        KV/HBM
             │                │                │
             └────────────────┼────────────────┘
                              ▼
                         SLO boundary
                              │
                              ▼
                     Best configuration
```

A configuration that produces:

```text
20k tok/s
```

isn't necessarily better than one producing:

```text
18k tok/s
```

if the first one gives:

```text
P95 TTFT = 4 sec
```

while the second gives:

```text
P95 TTFT = 700 ms
```

Your objective is:

> **Maximum sustainable throughput subject to the SLO constraints.**

# 4. `max_num_seqs`

This controls the maximum number of sequences that can be processed concurrently by the scheduler.

Think:

```text
max_num_seqs = 8

                 vLLM
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
     req1       req2       req3
       ...
                 req8
```

You aren't saying:

> "Only eight requests per second."

You're saying roughly:

> "At most eight active sequences can participate concurrently."

---

## 5. Why increasing it can help

Suppose:

```text
max_num_seqs = 4
```

and your GPU isn't busy enough.

Increase:

```text
4 → 8 → 16 → 32
```

Potentially:

```text
batching ↑
GPU utilization ↑
throughput ↑
```

But eventually:

```text
concurrency ↑
       ↓
KV memory ↑
       ↓
scheduler pressure ↑
       ↓
latency ↑
```

So bigger isn't automatically better.

# 7. `max_num_batched_tokens`

This parameter is even more interesting.

It controls how many tokens can be processed in a scheduler iteration/batch budget.

Conceptually:

```text
request 1 → 2,000 tokens
request 2 → 1,000 tokens
request 3 → 500 tokens
```

Total:

```text
3,500 tokens
```

The scheduler has a token budget controlling how much work can enter an iteration.

---

# 8. Why this matters for prefill

Imagine:

```text
Request A
100,000 input tokens
```

and:

```text
Request B
20 output tokens
```

If the scheduler allows too much prefill work at once:

```text
A ███████████████████████████████
B █
```

the huge prompt can dominate GPU execution.

The user for B might experience:

```text
TTFT ↑
ITL ↑
```

This is the **prefill interference** problem.

---

# 9. Chunked prefill

Instead of:

```text
100K-token prefill
████████████████████████████
```

we can conceptually process:

```text
chunk 1
████

chunk 2
████

chunk 3
████

...
```

while allowing decode work to continue receiving scheduler attention.

Conceptually:

```text
Without chunking:

PREFILL █████████████████████
DECODE                     ██


With chunking:

PREFILL ███   ███   ███   ███
DECODE     ██    ██    ██    ██
```

This can improve responsiveness for mixed workloads.

Current vLLM versions use chunked prefill in relevant configurations and expose scheduling controls around batched tokens. [vLLM optimization documentation](https://docs.vllm.ai/en/stable/configuration/optimization.html?utm_source=chatgpt.com)

---

# 10. The tradeoff

Smaller token budget:

```text
max_num_batched_tokens ↓
        ↓
less prefill interference
        ↓
decode gets more opportunities
        ↓
ITL/TPOT may improve
```

But:

```text
prefill gets fragmented
        ↓
possible throughput reduction
        ↓
TTFT may increase
```

Larger token budget:

```text
max_num_batched_tokens ↑
        ↓
more work per iteration
        ↓
prefill throughput ↑
```

but potentially:

```text
decode interference ↑
        ↓
ITL ↑
```

So again:

```text
there is no magic number
```

# 13. KV cache tuning

Remember our memory model:

```text
GPU memory
│
├── Model weights
├── KV cache
├── CUDA/runtime
├── workspace
└── other allocations
```

vLLM needs enough KV capacity to keep active sequences alive.

If KV is too small:

```text
requests
   ↓
KV pressure
   ↓
preemption/recompute
   ↓
performance degradation
```

Watch:

```bash
curl -s http://localhost:8000/metrics \
  | grep -i kv_cache
```

And:

```bash
curl -s http://localhost:8000/metrics \
  | grep -i preempt
```

---

# 14. A common mistake

Suppose:

```text
GPU memory = 90%
```

You think:

> "Excellent! We're using the GPU efficiently."

Not necessarily.

Suppose:

```text
KV = 97%
waiting requests = 100
P95 TTFT = 8 seconds
```

Then your GPU is **memory saturated and operationally unhealthy**.

You need headroom.

# 15. CUDA graphs

Now another optimization layer.

Normally CUDA work involves kernel launches:

```text
CPU
 ↓
launch kernel A
 ↓
launch kernel B
 ↓
launch kernel C
```

Launch overhead can matter when workloads involve many repeated GPU operations.

CUDA Graphs allow CUDA work to be captured and replayed more efficiently:

```text
capture execution
       ↓
GPU graph
       ↓
replay
```

Potential benefit:

```text
CPU launch overhead ↓
GPU execution efficiency ↑
```

But there is a cost:

```text
memory consumption
+
graph capture complexity
+
shape/configuration constraints
```

So don't blindly enable/disable things.

vLLM's current optimization documentation discusses CUDA graph behavior and memory considerations. [vLLM optimization documentation](https://docs.vllm.ai/en/stable/configuration/optimization.html?utm_source=chatgpt.com)

---

# 16. When would you use eager mode?

You may encounter:

```text
--enforce-eager
```

This forces eager execution rather than using CUDA graphs.

It can be useful for:

```text
debugging
compatibility
memory troubleshooting
```

but it can reduce performance.

So if somebody says:

> "Let's just use `--enforce-eager` because it fixes the problem."

Your response should be:

> "What problem are we solving, and what performance regression did the change introduce?"

That's AIRE thinking.

# 17. Prefix caching

Now let's make the workload realistic.

Imagine every request contains:

```text
System prompt
+
Company policy
+
100-page documentation
+
User question
```

The first request has to process:

```text
████████████████████████████████
```

If subsequent requests share the same prefix, prefix caching can reuse previously computed KV state.

Conceptually:

```text
Request 1:

COMMON PREFIX ███████████████
QUESTION A                  ██


Request 2:

COMMON PREFIX ███████████████  ← cached
QUESTION B                  ██  ← compute
```

This can dramatically change TTFT/prefill behavior.

---

# 18. But there's a benchmark trap

Suppose you benchmark:

```text
same prompt
100 times
```

and prefix caching is active.

You may conclude:

> "My GPU can process this workload extremely fast."

But you may actually be measuring:

```text
cache hit performance
```

rather than:

```text
real-world unique prompt performance
```

Therefore benchmark both:

```text
cache cold
```

and:

```text
cache warm
```

when prefix reuse is part of your actual workload.

# 20. The tuning loop

Your entire performance engineering process should look like:

```text
             Establish baseline
                    │
                    ▼
                Hypothesis
                    │
                    ▼
             Change ONE thing
                    │
                    ▼
                Benchmark
                    │
                    ▼
                Observe SLO
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Better              Worse
          │                   │
          ▼                   ▼
       Keep                Revert
          │
          ▼
      Next variable
```

Never:

```text
change 10 flags
      ↓
run benchmark
      ↓
"it's faster"
```

# 21. Build your first Pareto table

Suppose your experiments produce:

| Config | Output tok/s | P95 TTFT | P95 TPOT |  KV |
| ------ | -----------: | -------: | -------: | --: |
| A      |        8,000 |    500ms |     55ms | 70% |
| B      |       10,000 |    650ms |     60ms | 78% |
| C      |       12,000 |     1.8s |     80ms | 90% |
| D      |       13,000 |     4.5s |    120ms | 97% |

If our SLO is:

```text
P95 TTFT < 1s
P95 TPOT < 100ms
```

then:

```text
C → invalid
D → invalid
```

Even though they have higher throughput.

Our candidate set becomes:

```text
A
B
```

Then we choose based on:

```text
cost
headroom
failure tolerance
expected traffic
```

This is a **Pareto/SLO optimization problem**.

# 22. Now think like a customer architect

Customer says:

> "We want maximum tokens per second."

Don't immediately tune throughput.

Ask:

```text
What is your TTFT SLO?
What is your TPOT/ITL SLO?
What is your peak concurrency?
What is the input token distribution?
What is the output token distribution?
How much prefix reuse?
What percentage of requests are long-context?
What is the availability target?
What is the GPU budget?
```

Because:

```text
Maximum throughput
```

and:

```text
Maximum useful throughput
```

are different things.

---

# 23. Our tuning hierarchy

When a benchmark is poor, investigate in this order:

```text
1. Is the model configured correctly?
             ↓
2. Does it fit comfortably?
             ↓
3. Is KV capacity sufficient?
             ↓
4. Is scheduler batching effective?
             ↓
5. Is prefill interfering with decode?
             ↓
6. Is GPU compute saturated?
             ↓
7. Is HBM bandwidth saturated?
             ↓
8. Is CPU/tokenization limiting?
             ↓
9. Is NCCL communication limiting?
             ↓
10. Is network limiting?
```

Don't jump to:

> "Buy a bigger GPU."

# 24. AIRE troubleshooting scenario

Imagine Grafana shows:

```text
GPU utilization      = 92%
HBM utilization      = 96%
KV cache             = 94%
Waiting requests     = 70
P95 TTFT             = 4.2s
P95 TPOT             = 35ms
```

What does this tell you?

The decode speed itself is actually decent:

```text
TPOT = 35ms
```

But:

```text
KV + HBM + waiting + TTFT
```

are concerning.

Likely:

```text
memory/capacity pressure
        ↓
active requests constrained
        ↓
queue grows
        ↓
TTFT explodes
```

Potential actions:

```text
reduce concurrency
tune scheduler
increase GPU memory
reduce context
use KV optimization
add replica
change model/precision
```

Not necessarily:

```text
"GPU compute is too slow."
```


```text

```

This is why **one metric never tells the whole story**.
