# 2. Why doesn't the LLM understand text directly?

A model doesn't receive:

```text
Hello, how are you?
```

as normal English.

It receives **numbers**.

The conversion is performed by a **tokenizer**.

Hugging Face describes the tokenizer as the component responsible for preparing model inputs; it converts text into model-compatible inputs such as token IDs. ([Hugging Face][1])

Conceptually:

```text
"Hello, how are you?"

       │
       ▼

Tokenizer

       │
       ▼

["Hello", ",", " how", " are", " you", "?"]

       │
       ▼

[9707, 11, 1268, 527, 499, 30]
```

Those IDs are an illustration; different models use different tokenizers and vocabularies.

That difference matters operationally.

---

# 3. What exactly is a token?

A token is **not necessarily a word**.

It could be:

```text
word
part of a word
punctuation
space + word
special symbol
```

For example:

```text
"Kubernetes"
```

might become:

```text
["Kuber", "netes"]
```

while another model tokenizer might encode it as a single token.

Therefore:

```text
characters != words != tokens
```

This distinction is extremely important for AI infrastructure.

---

Because almost every important production property is related to token counts.

Consider:

```text

Input: 100 tokens
Output: 100 tokens
```

versus:

```text

Input: 100,000 tokens
Output: 4,000 tokens
```

Those requests are radically different workloads.

The second request affects:

```text

KV cache

throughput

cost
```

So when a customer says:

> We have 1,000 users.

That is not enough information.

As an architect, eventually you should ask:

```text

Average output tokens?

```

This is our first important architectural lesson:

> **User count alone is almost useless for sizing LLM infrastructure.**

# 7. Model size and GPU VRAM

This is one of the first calculations you need to memorize.

Suppose you have:

```text
70 billion parameters
```

Using BF16 or FP16:

```text
~2 bytes / parameter
```

Then approximate weight memory:

```text
70 billion × 2 bytes

= 140 billion bytes

≈ 140 GB
```

So approximately:

```text
70B model BF16
≈ 140 GB just for model weights
```

And that's **before** accounting for:

```text
KV cache
CUDA context
activations
workspace
CUDA graphs
runtime buffers
```

Therefore:

```text
H100 80 GB

cannot hold

~140 GB BF16 model weights

on one GPU
```

This immediately creates an architecture decision.

# 9. Why GPUs?

Transformers perform enormous numbers of matrix operations.

Simplifying heavily:

```text
Input Matrix
      ×
Weight Matrix
      =
Output Matrix
```

For example:

```text
[ huge matrix ]

       ×

[ huge matrix ]

       =

[ huge matrix ]
```

GPUs are extremely effective at massively parallel numeric operations.

NVIDIA's Tensor Cores are specifically designed to accelerate tensor/matrix operations used heavily by AI workloads. Modern Transformer Engine support also exploits lower-precision formats such as FP8 to increase throughput and reduce memory consumption. ([NVIDIA Docs][2])

# 13. What are Tensor Cores?

NVIDIA GPUs have different kinds of execution units.

Simplifying:

```text
GPU
│
├── CUDA Cores
│
└── Tensor Cores
```

Tensor Cores are highly optimized for matrix operations common in AI.

This becomes important when choosing precision.

For example:

```text
FP32

vs

FP16 / BF16

vs

FP8
```

Newer hardware can perform certain low-precision operations at much higher throughput.

NVIDIA currently documents FP8 acceleration on Hopper, Ada, and Blackwell-class GPUs via Transformer Engine; Blackwell also supports newer low-precision formats. ([NVIDIA Docs][2])

# 14. Why lower precision?

Imagine every parameter requires:

```text
FP32 = 4 bytes
BF16 = 2 bytes
FP8  = 1 byte
```

Very approximately.

For a 70B model:

```text
FP32

70B × 4
≈ 280 GB
```

BF16:

```text
70B × 2
≈ 140 GB
```

FP8:

```text
70B × 1
≈ 70 GB
```

This is why precision can dramatically affect:

```text
VRAM requirements
memory bandwidth
throughput
GPU count
cost
```

There are accuracy and implementation considerations, so don't simply assume:

```text
lower precision = always better
```

We'll study quantization separately.

# 18. Now the important part: LLM inference has two phases

This is perhaps the most important concept in today's lesson.

LLM generation has:

```text
1. PREFILL

2. DECODE
```

Understand these deeply.

# 19. Prefill

Suppose the prompt is:

```text
10,000 tokens
```

During prefill:

```text
10,000 input tokens
        │
        ▼
   Transformer
        │
        ▼
calculate attention
        │
        ▼
build KV cache
        │
        ▼
first output token
```

So:

```text
Prompt
   ↓
PREFILL
   ↓
First token
```

The user-visible metric strongly associated with this stage is:

# TTFT

```text
Time To First Token
```

User submits:

```text

```

```text

```

```text

```


Already you can see why AI architecture is not just DevOps.

# 22. Decode phase

Once the first token has been generated:

```text

   ↓
Token 2
   ↓
Token 3
   ↓
Token 4
   ↓
...
```

This is called **autoregressive decoding**.

The model generates approximately one next token at a time.

# 23. Why does it generate one token at a time?

Suppose output is:

```text
Kubernetes automatically scales workloads...
```

The generation conceptually looks like:

```text
Prompt
 ↓
"Kubernetes"

Prompt + Kubernetes
 ↓
"automatically"

Prompt + Kubernetes automatically
 ↓
"scales"
```

and so forth.

But recomputing the whole past repeatedly would be extremely expensive.

This is where KV cache matters.

---

# 24. KV Cache

During attention, the model computes Keys and Values.

Instead of recomputing historical K/V tensors for every generated token, it stores them.

Conceptually:

```text
Previous tokens

1  2  3  4  5  6

↓  ↓  ↓  ↓  ↓  ↓

K/V K/V K/V K/V K/V K/V

        │
        ▼

      KV CACHE
```

Then when token 7 is generated:

```text
new query

      +

existing KV cache

      ↓

attention
```

This makes decoding far more practical.

---

# 25. Where is KV cache stored?

Usually in GPU memory for high-performance inference.

Therefore GPU VRAM contains more than model weights.

Conceptually:

```text
GPU 80 GB
┌──────────────────────────────┐
│                              │
│ Model weights                │
│ ███████████████████████      │
│                              │
│ KV Cache                     │
│ █████████████                │
│                              │
│ CUDA graphs/workspace/etc.   │
│ █████                        │
│                              │
└──────────────────────────────┘
```

This will become crucial when configuring vLLM.

Current vLLM exposes explicit controls for KV-cache sizing, KV-cache datatype, weight offloading, and the percentage of GPU memory the model executor can consume. ([vLLM][3])

# 28. Why vLLM exists

A naive serving implementation might waste significant GPU memory and schedule requests inefficiently.

vLLM provides an inference engine designed specifically to achieve high throughput and efficient memory use.

We'll later study:

```text

Continuous batching
Chunked prefill
Prefix caching
Speculative decoding
Tensor parallelism
Data parallelism
KV cache management
```

vLLM's current optimization documentation explicitly describes chunked prefill as a mechanism for combining compute-heavy prefill work with memory-heavy decode work, improving GPU utilization and latency behavior. ([vLLM][4])

That sentence introduces another important distinction.

# 29. Prefill vs Decode have different hardware behavior

Simplifying:

```text
PREFILL

often more compute-bound
```

while:

```text
DECODE

often more memory-bandwidth-bound
```

Why?

During decode, the GPU repeatedly needs to access:

```text
model weights
KV cache
```

while generating relatively little new computation per output token compared with prefill.

This becomes critically important for GPU selection and distributed inference.

# 30. Memory bandwidth

Imagine:

```text
GPU compute engine
       ▲
       │
       │ data
       │
       ▼
      HBM
```

Even if your Tensor Cores are extremely fast, if weights/data can't reach them fast enough:

```text
Tensor Cores wait
```

That's a memory-bandwidth bottleneck.

So choosing GPU based only on:

```text
TFLOPS
```

is a mistake.

You also care about:

```text
VRAM capacity
HBM bandwidth
Tensor Core throughput
precision support
inter-GPU bandwidth
network
```

# 31. Why HBM matters

GPU memory is commonly high-bandwidth memory designed for extremely high throughput.

Think:

```text
CPU RAM

large-ish
moderate bandwidth
```

versus:

```text
GPU HBM

limited/expensive
extremely high bandwidth
```

LLM inference constantly moves enormous quantities of model data.

That makes memory bandwidth a critical performance factor.

# 44. What happens under concurrency?

Imagine:

```text
Request A
Request B
Request C
Request D
Request E
```

Traditional naive serving could process them inefficiently.

vLLM uses scheduling and batching mechanisms so work from multiple requests can execute together.

Conceptually:

```text
GPU batch

A A A A
B B B
C C C C
D D
E
```

Requests can dynamically enter/leave execution.

That's **continuous batching**, which we'll dedicate an entire lesson to.

# 45. Why batching improves GPU usage

GPUs love large parallel workloads.

Imagine executing:

```text
one tiny matrix operation
```

repeatedly.

The GPU might not be efficiently utilized.

Instead:

```text
many requests
        ↓
batch operations
        ↓
larger matrix work
        ↓
better hardware utilization
```

But there's a tradeoff.

More batching can improve:

```text
throughput
```

while hurting:

```text
latency
```

So our goal is not:

```text
maximum throughput
```

It is:

```text
maximum throughput

subject to

latency SLO
```

That is a very important AIRE principle.

# 46. Chunked prefill

Suppose one request arrives with:

```text
100,000 input tokens
```

while 20 users are decoding.

A huge prefill can interfere with decoding.

vLLM's chunked-prefill mechanism divides large prefills into smaller chunks and schedules decode work preferentially. Current vLLM documentation says this helps balance compute-bound prefill and memory-bound decode workloads and can improve both utilization and latency characteristics. ([vLLM][4])

Conceptually:

```text
Bad:

[PREFILL PREFILL PREFILL PREFILL PREFILL]

decode waits
```

Better:

```text
[PREFILL][decode][decode][PREFILL][decode]
```

Simplified, but correct mental model.

# 47. This leads to something very advanced

Once you understand:

```text
Prefill
=
different workload
```

and:

```text
Decode
=
different workload
```

you might eventually ask:

> Why run both on the same GPU pool?

Exactly.

Advanced distributed systems can do:

```text
                 Request
                    │
                    ▼
                Router
                    │
          ┌─────────┴─────────┐
          │                   │
      Prefill GPUs         Decode GPUs
          │                   │
          └──── KV transfer ──►
```

vLLM currently documents disaggregated prefilling as an experimental feature specifically intended to allow TTFT and inter-token latency to be tuned independently. ([vLLM][6])

Later, **llm-d** becomes especially relevant here.
