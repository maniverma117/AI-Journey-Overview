# Lab 1L — Prefill/Decode Disaggregation (P/D)

This is a major milestone.

Until now, we've mostly treated an LLM replica like this:

```text
Request
   │
   ▼
┌──────────────────────────────┐
│            vLLM              │
│                              │
│  Prefill → KV → Decode       │
│                              │
└──────────────┬───────────────┘
               │
              GPU
```

Now we're going to split those two workloads:

```text
                         Request
                            │
                            ▼
                         Router
                            │
              ┌─────────────┴─────────────┐
              │                           │
              ▼                           ▼
        PREFILL POOL                DECODE POOL
        ┌───────────┐               ┌───────────┐
        │ GPU GPU   │               │ GPU GPU   │
        │ GPU GPU   │               │ GPU GPU   │
        └─────┬─────┘               └─────┬─────┘
              │                           │
              │       KV CACHE             │
              └──────────┬────────────────┘
                         │
                    NIXL / RDMA
                         │
                        EFA
```

This is called **Prefill/Decode Disaggregation**, or **P/D disaggregation**.

Current llm-d documentation describes the basic motivation exactly this way: prefill tends to be compute-bound, decode tends to be memory-bandwidth-bound, and separating them can reduce interference and allow independent scaling/tuning.

---

# 1. First: understand why prefill and decode behave differently

Remember the request lifecycle:

```text
Input tokens
     │
     ▼
  PREFILL
     │
     ▼
  KV CACHE
     │
     ▼
  DECODE
     │
     ▼
Output tokens
```

Suppose:

```text
Input = 20,000 tokens
Output = 500 tokens
```

The model must process the 20K input tokens during prefill.

Then it generates the 500 output tokens sequentially.

So:

```text
20,000 input tokens
       ↓
   PREFILL

500 output tokens
       ↓
   DECODE
```

They stress the GPU differently.

---

# 2. Prefill

Prefill processes many input tokens.

Conceptually:

```text
20K tokens
   │
   ▼
large matrix operations
   │
   ▼
Tensor Cores
   │
   ▼
GPU compute
```

This tends to be more **compute-intensive**.

Think:

```text
PREFILL
   ↓
high FLOPs
   ↓
Tensor Core utilization
   ↓
compute-bound tendency
```

This is why a long prompt can produce a large burst of computation.

---

# 3. Decode

Now suppose the model needs to generate:

```text
500 output tokens
```

Generation is autoregressive:

```text
token 1
   ↓
token 2
   ↓
token 3
   ↓
...
token 500
```

Each step uses the accumulated KV cache.

The workload can become much more sensitive to:

```text
HBM bandwidth
KV cache movement
memory latency
batching
```

So:

```text
DECODE
   ↓
memory movement
   ↓
HBM bandwidth
   ↓
memory-bound tendency
```

This is simplified—the exact bottleneck depends on model, batch size, sequence lengths, hardware and configuration—but it's a very useful AIRE mental model.

---

# 4. The interference problem

Now imagine one GPU serving:

```text
Request A
20K-token prompt
```

and simultaneously:

```text
Request B
decode token #200
```

You have:

```text
Long PREFILL
       +
DECODE
```

The prefill computation can consume substantial GPU resources.

That can interfere with decode.

Result:

```text
Request B
  ↓
decode delayed
  ↓
ITL/TPOT increases
```

And this matters because interactive users care strongly about:

```text
"How quickly do I get the next token?"
```

not merely:

```text
"How many total tokens did the GPU produce?"
```

---

# 5. Example

Imagine:

```text
User A:
50K input tokens

User B:
already generating
```

Without careful scheduling:

```text
50K PREFILL
████████████████████████

DECODE
       waiting...
       waiting...
       waiting...
```

User B experiences:

```text
ITL ↑
TPOT ↓
```

even though:

```text
GPU utilization = 99%
```

This is another reason:

> **99% GPU utilization can still mean poor user experience.**

---

# 6. P/D disaggregation changes the architecture

Instead of:

```text
                      vLLM
                       │
              ┌────────┴────────┐
              │                 │
           Prefill           Decode
              │                 │
              └────── GPU ─────┘
```

we create:

```text
                    Router
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        Prefill Pool         Decode Pool
             │                   │
          GPU GPUs             GPU GPUs
             │                   │
             └────── KV ────────┘
```

Now:

```text
Prefill capacity
```

and:

```text
Decode capacity
```

can be tuned separately.

---

# 7. This is similar to microservices—but don't oversimplify it

You might think:

> "Prefill is just one microservice and decode is another."

Not quite.

The two stages are tightly coupled through:

```text
KV cache
```

The decode stage cannot simply start from scratch.

It needs the KV generated by prefill.

So:

```text
PREFILL
   │
   │ produces KV
   ▼
KV transfer
   │
   ▼
DECODE
   │
   ▼
tokens
```

That KV transfer is now a critical part of your inference path.

---

# 8. KV becomes a network object

This is a huge conceptual shift.

Earlier we thought:

```text
KV cache
   ↓
GPU memory
```

Now:

```text
Prefill GPU
    │
    │ KV
    ▼
Network
    │
    ▼
Decode GPU
```

Therefore:

> **KV cache is no longer only a memory-management problem. It becomes a data-movement problem.**

This connects directly to our previous Lab 1I/1J topics:

```text
GPU
 ↓
PCIe
 ↓
NIC
 ↓
EFA
 ↓
RDMA
 ↓
NIC
 ↓
GPU
```

---

# 9. Why NIXL matters

This is where **NIXL** becomes important.

We previously said:

```text
NCCL
=
collective GPU communication
```

while:

```text
NIXL
=
inference-oriented data movement
```

For P/D, we care about:

```text
Prefill GPU
     │
     │ KV blocks
     ▼
Decode GPU
```

NIXL is designed for this type of high-performance inference data movement.

vLLM provides a NIXL connector for KV-cache transfer, and current llm-d P/D documentation uses NIXL-based mechanisms for efficient KV movement.

# 11. Why RDMA matters even more now

Suppose:

```text
KV size = 10 GB
```

You need to transfer:

```text
10 GB
```

from prefill to decode.

If effective bandwidth is:

```text
100 GB/s
```

ideal transfer time:

```text
10 / 100
= 0.1 sec
```

If effective bandwidth becomes:

```text
20 GB/s
```

then:

```text
10 / 20
= 0.5 sec
```

That's a huge difference.

And real systems also have:

```text
synchronization
software overhead
PCIe
memory registration
network congestion
transfer scheduling
```

So the actual latency can be higher.

---

# 12. P/D does NOT automatically make everything faster

This is extremely important.

You may think:

```text
P/D
 ↓
more GPUs
 ↓
faster
```

Not necessarily.

You have introduced:

```text
KV transfer
```

into the critical path.

So:

```text
P/D benefit
=
reduced P/D interference
+
independent scaling
+
better resource utilization

minus

KV transfer overhead
+
orchestration overhead
+
network dependency
```

llm-d's current documentation explicitly notes that disaggregation can improve latency isolation and independent tuning, but it does **not inherently guarantee higher overall throughput**.

---

# 13. When P/D makes sense

Strong candidates:

```text
Long prompts
+
interactive generation
+
high concurrency
+
strong TTFT/ITL SLOs
```

For example:

```text
Input:
50K tokens

Output:
2K tokens
```

This can create significant prefill pressure.

Separating:

```text
Prefill
```

from:

```text
Decode
```

can prevent long prompts from disturbing active generations.

---

# 14. When P/D may not be worth it

Suppose:

```text
Input = 100 tokens
Output = 50 tokens
```

and:

```text
low concurrency
```

Then:

```text
P/D infrastructure
+
NIXL
+
EFA
+
KV transfer
+
additional orchestration
```

might add complexity without providing meaningful benefit.

This is why architecture must follow workload characteristics.

# 15. Independent scaling

This is one of the biggest benefits.

Suppose:

```text
Prefill demand = 800 units
Decode demand  = 200 units
```

Without P/D:

```text
combined serving pool
```

You must provision a mixed capacity.

With P/D:

```text

████████████
████████████
████████████

Decode pool
████
████
```

You can independently scale:

```text
Prefill:
10 GPUs

Decode:
4 GPUs
```

This is a major FinOps opportunity.

# 24. KV transfer is not always mandatory

Important distinction.

There are two broad scenarios:

### P/D

```text
Prefill
  ↓
KV transfer
  ↓
Decode
```

The decode stage needs the generated KV.

### Prefix cache sharing

```text
Worker A
  ↓
KV cached
  ↓
Worker B can potentially reuse
```

This is more of an optimization.

If sharing fails:

```text
recompute
```

may be possible.

For P/D, however, transfer is part of the execution path.

Therefore:

```text
P/D transfer failure
```

can be much more serious.

---

# 25. Failure model

Suppose:

```text
Prefill P1
     │
     │ KV
     ▼
Decode D1
```

P1 dies before KV transfer completes.

What happens?

You need a policy.

Potentially:

```text
Request
  ↓
P1 ❌
  ↓
retry/recompute on P2
  ↓
KV
  ↓
D1
```

This increases:

```text
TTFT
```

---

# 26. Decode failure

Suppose:

```text
P1 ✓
D1 ❌
```

The KV might still exist at P1.

Can we simply send it to D2?

Potentially, if:

```text
KV state is accessible
+
compatible
+
transfer path healthy
```

Then:

```text
P1
 │
 │ KV
 ▼
D2
```

This is one reason KV lifecycle and compatibility are so important.

llm-d's current operational documentation discusses fault tolerance, KV block leases and recomputation/transfer behavior for disaggregated serving.

---

# 27. KV compatibility

You cannot blindly transfer arbitrary KV between workers.

Both sides need compatible assumptions about things such as:

```text
model architecture
layers
KV heads
head dimension
dtype
KV cache format
attention backend
cache configuration
vLLM compatibility
connector compatibility
```

Otherwise:

```text
KV from P1
       ↓
D1
       ↓
❌ incompatible
```

Therefore P/D pools should generally be treated as a compatible serving fleet.

```text

=

+

+
KV transfer
+

```

P/D tries to improve:

```text

```

but adds:

```text

```

So:

```text

=
prefill queue
+

+
KV transfer
+

```

If:

```text

```

is very fast:

```text

```

If:

```text
KV transfer
```

is slow:

```text

```

This is the critical tradeoff.

# 41. The five schedulers problem

We've now reached a very interesting point.

Our system has multiple decision makers:

```text
1. AI Gateway
   └── auth / quota / policy

2. llm-d
   └── inference routing

3. vLLM
   └── token scheduling

4. Kubernetes
   └── pod/GPU placement

5. Karpenter
   └── node provisioning
```

And now:

```text
6. P/D orchestration
   └── prefill/decode coordination
```

If these systems make conflicting decisions, you can create feedback loops.

Example:

```text
llm-d sends traffic to P1
        ↓
P1 queue increases
        ↓
KEDA scales P
        ↓
new P2 starts
        ↓
router doesn't know P2 is useful yet
        ↓
P1 remains overloaded
```

This is why **observability and control-plane coordination** become increasingly important.

# 42. P/D is not just a performance feature

This is perhaps the most important takeaway.

P/D affects:

```text
Performance
+
Capacity
+
Autoscaling
+
Networking
+
Routing
+
Reliability
+
FinOps
+
Deployment
+
Observability
```

So when a customer asks:

> "Should we enable P/D?"

the answer is not:

> "Yes, it improves performance."

> "We need to characterize the prefill/decode workload ratio, latency SLOs, concurrency, KV sizes, network topology and transfer cost. Then benchmark integrated versus disaggregated serving under the target workload."

# 45. Interview checkpoint

### Question

**"Why would you use prefill/decode disaggregation?"**

Strong answer:

> "Prefill and decode have different resource characteristics. Prefill tends to be compute-intensive while decode is often memory-bandwidth-sensitive. In a combined serving instance, long prefills can interfere with active decode requests and increase ITL or TPOT. Disaggregation allows independent scaling and resource tuning of the two stages. However, it introduces KV-cache transfer into the critical path, so the benefit depends on KV size, transfer bandwidth, networking, workload shape and latency SLOs. I would benchmark P/D against integrated serving rather than assume it is faster."

That's a strong production answer.
